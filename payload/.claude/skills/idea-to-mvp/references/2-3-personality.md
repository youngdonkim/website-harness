이 문서는 2단계의 마지막 하위 단계다. 2단계는 `2-0-dev-setup.md`(개발환경 준비) → `2-1-mockup.md`(기능·화면 목록과 주요 화면) → `2-2-mockup-design-upgrade.md`(전문가 수준 디자인 개선) → 이 문서 순서로 간다. 2-2를 마친 화면은 깔끔하다 — 위계가 서고, 간격·글자 단계가 맞고, 강조색이 주 버튼 하나에만 있다. 그런데 실수 없이 정돈된 만큼 「어느 서비스인지」가 화면에서 잘 안 보이고, 최소 기능과 심플한 디자인에서 멈춘다. 이 하위 단계는 **2-2까지의 결과를 바닥으로 두고, 그 위에 이 서비스만의 얼굴을 더한다 — 얼마나 깊이 바꿀지가 다른 세 판으로.** 2-2의 바닥(강조색 세 자리·글자 단계·간격 단계·접근성 바닥선)은 어느 판에서도 뒤집지 않는다(§1.3). 「화면 구조는 그대로」는 대담판에만 걸린다 — 혁신판은 핵심 행동 화면의 조작과 배치를, 파격판은 화면 구조와 은유까지 바꿀 수 있다(§1.4).

**들어오는 때** — 2-2가 끝나 `feature-list.md` 머리에 `디자인 개선 확인 끝:` 줄이 생긴 뒤다(`2-2-mockup-design-upgrade.md` §2.9). 2-2를 건너뛰었으면 브리프 「12」의 `건너뜀` 한 줄이 곧 통과다. 깨진 화면 위에 개성을 얹으면 개성까지 다시 고쳐야 한다. 사용자가 2-3을 콕 집어 부르면 이 확인 줄이 없어도 들어온다(§2.1 1번). 3단계 이후를 이미 지난 프로젝트에서 하는 갈래는 §2.12다.

**기본은 진행이고, 건너뛸 수 있다** — 건너뛰어도 2-2까지의 깔끔한 화면이 그대로 바닥이라, 2-2처럼 「건너뛰지 않는 것이 기본」이라고 압박하지 않는다. 입구 안내에서 「건너뛰면 지금 화면 그대로 갑니다」를 한 번 말한다(§2.1).

## 1. 이 하위 단계가 하는 일

이 하위 단계의 목표는 **대표 화면에서 바꾸는 층이 다른 세 판을 비교안으로 만들어 사람이 고르게 하고, 고른 것을 브리프와 토큰·부품에 적어 나머지 화면과 3단계가 따르게 하는 것**이다. 산출물은 넷이다.

- **브리프 「13. 개성」과 「4」「8」의 해당 행** — 값(브랜드 면 색·제목 서체·로고·사진 톤)은 「4」에, 대표 움직임과 조작에 붙는 움직임은 「8」에, 고른 판·개성을 어디에 어떻게 쓰는지·조작 방식·은유는 「13」에 적는다 (§4.1). 2-2가 「4」(값)와 「12」(쓰는 규칙)를 나눈 것과 같은 방식이다.
- **바뀐 토큰·부품** — 2층 `brand-surface`·`brand-surface-foreground`, 제목 서체 중간 변수 `brand-font`(클래스 `font-brand`가 가리킨다), 1층 사진 톤 변수, 로고 부품과 파비콘, 브랜드 색 면을 그리는 전용 부품, 질감 클래스. 혁신판이면 조작 부품과 `lib/motion.ts`, 파격판이면 은유 부품(`src/components/{수단}/`)과 `lib/{수단}.ts`. 프로젝트 `AGENTS.md` 연결 정보의 `BRAND_PARTS:` 줄과 `font-brand`를 붙이는 글자 이름, 무거운 라이브러리를 들였으면 `HEAVY_LIBS:`·`HEAVY_PARTS:` 줄 (§2.9).
- **본 화면 자리로 옮긴 고른 판** — 그 판의 대상 화면(§1.1 표). 나머지 화면은 2-2 규칙대로 조용히 둔다.
- **(파격판을 고르면) 화면 목록 일부** — 은유가 바꾸는 화면을 `feature-list.md` 화면 목록에 반영하고 머리에 `은유 반영:` 줄 (§2.7).

**이 단계에서 지키는 원칙 둘**

- **본 화면·본 토큰은 고르기 전까지 에이전트가 건드리지 않는다 — 비교안 폴더와 판 CSS 파일에서만.** 여러 판이 함께 쓰는 파일은 판을 띄우기 전에 한 번 손본다 — 공유 파일 준비 에이전트가 하고, 패키지 설치만 메인이 한다(§2.5 표). 이 문서에서 「메인이 미리 손본다」·「메인이 판을 띄우기 전에」는 이 준비까지 가리킨다. 새 토큰 이름도 판 CSS 파일 안의 범위 클래스에서만 값을 주고, 본 `:root`에는 고른 뒤(§2.9) 넣는다.
- **다시 만드는 범위는 판이 정한다** — 대담판은 화면을 다시 만들지 않는다(배치 그대로, 고른 것은 토큰과 부품에 담는다). 혁신판·파격판이 바꿀 수 있는 범위는 §1.4 표다. 어느 판이든 대상 화면이 아닌 화면은 손대지 않는다.

**점검 항목의 정본은 design-system 스킬 `references/visual-polish.md`의 「I 개성」 묶음이다.** 브랜드 색·강조색의 원칙은 design-system `SKILL.md` 「브랜드 색은 어디에 쓰나」·「강조색은 어디에 쓰나」, 디자인 시스템 페이지 「브랜드」 영역의 모양은 `bootstrap-project.md` §6.1이 정본이다. **메인이 이 셋을 읽고, 그 판에 닿는 것만 지시서에 걸러 넣는다** — 화면을 만드는 에이전트에게 읽으라고 시키지 않는다 (AGENTS.md 위임 절).

### 1.1 세 판의 정의

세 판은 **바꾸는 층**이 다르다. 뒤 판은 앞 판의 층을 모두 품는다.

| | 대담판 | 혁신판 | 파격판 |
|---|---|---|---|
| 바꾸는 층 | ① 겉모습 | ① + ② 조작 방식 | ① + ② + ③ 은유 |
| 한 줄 뜻 | 같은 화면을 더 과감하게 꾸민다 | 핵심 행동을 하는 방법을 바꾼다 | 화면 자체가 무엇을 닮았는지를 바꾼다 |
| 바꾸는 것 | 색·글꼴·질감·여러 겹 면·움직임 여럿·감탄 포인트 하나(§1.2) | 위 + 핵심 행동을 하는 방법과 그 화면의 배치. 갈래는 브리프 「6. 주 사용 맥락」에 맞춰 — 폰 위주면 손동작(길게 누르기·끌어 놓기·밀기)·말로 입력, 컴퓨터 위주면 단축키 명령창·한 번에 여럿 고르기·여럿이 동시에 편집 | 위 + 화면 구조·은유. 은유를 만드는 수단은 여러 갈래 — 3D 장면·지도 위에 펼치기·대화로 주고받기·카드 더미 넘기기·게임판·카메라로 비추기 등. 3D는 그중 하나 |
| 대상 화면 | 대표 화면(첫 화면) + 핵심 행동 화면이 2단계에 있으면 그 화면 | 핵심 행동이 일어나는 화면 | 첫 화면. 그 안에서 핵심 행동 흐름까지 이어져도 된다 |
| 새 기능 | 안 만든다 | 안 만든다. 떠오르면 「새 기능 후보」로 보고만. 새 정책·제약(고를 수 있는 날짜 범위·시간 간격 등)도 만들지 않는다 — 본 화면이 쓰는 선택지 그대로, 좁혀야 하면 「정책 후보」로 보고만 | 놀이 요소 1~2개까지 만들어 보여도 된다. 「새 기능 후보」로 표시 |
| 데이터 | 지금 저장·조회 코드(데이터를 읽고 쓰는 함수 모음) 그대로 | 그대로. 저장하는 때도 바꾸지 않는다 | 그대로 |
| 기술 | CSS 움직임만 (사용자 확정 2026-10-21) | `motion`. 손동작 갈래를 고를 때만 `@use-gesture/react` | 위 + 고른 수단에 필요한 라이브러리만 (예: 3D면 `three`·`@react-three/fiber`·`@react-three/drei`, 지도면 지도 라이브러리) |
| 고르면 늘어나는 일 | 거의 없음 | 3단계 상태 화면(조작이 중간에 끊겼을 때 등) 몇 개 | 화면 목록 일부를 다시 열고, 3단계가 늘어난다 (§2.7·§3.1) |

- **「핵심 행동」은 어디서 읽나** — `intent.md` 「5. 유저 플로우」 표의 「핵심 행동」 열에서 사용자가 이 서비스를 쓰는 이유가 되는 행동 하나를 먼저 고르고, 그 행동이 어느 화면에서 일어나는지는 `feature-list.md` 화면 목록의 「주 행동」 칸으로 찾는다.
- **대상 화면이 갈릴 때 고르는 법** — 「첫 화면」이 로그인 전후로 갈리면(처음 온 사람의 소개 화면과 로그인 뒤 홈) 핵심 행동 흐름이 시작되는 쪽을 고른다. 핵심 행동이 여러 화면에 걸치면 화면 목록 「주 행동」 칸이 핵심 행동을 가리키는 첫 화면을 고른다. 첫 화면의 「주 행동」이 `없음`이면(둘러보기만 하는 첫 화면) 혁신판의 대상은 흐름 순서로 「주 행동」 칸이 처음 차는 화면이다. 고른 화면과 이유를 §2.3 메시지에 한 줄로 알린다.
- **겉모습은 대담판이 정하고 뒤 두 판이 이어받는다** — 그림 소재·로고·브랜드 색·제목 서체·사진 톤은 대담판의 ① 겉모습 안에 들어간다. 혁신판·파격판은 대담판의 겉모습을 자기 폴더로 복사해 쓰고 자기 층만 바꾼다(§2.5).
- **파격판은 브리프 「5. UI 패턴 지정」의 사용자 확정 모양도 깰 수 있다** — 비교안이고 고르는 것은 사람이라서다. 깼으면 판 고르기(§2.7)에서 「확정하셨던 {모양}을 바꾸는 판입니다」라고 알린다. **첫 화면이 이미 은유 수단인 서비스**(첫 화면이 지도·대화방·카드 더미 등)면 파격판은 그 수단을 다시 쓰지 않고 다른 수단·다른 은유를 고른다 — 같은 수단에 은유 이름만 바꾸면 대담판과 차이가 작다.
- **판 이름은 코드에서 `bold`·`innov`·`leap`이다** — 비교안 주소 `/dev/drafts/{화면}-{판}`, 판 폴더 `drafts/_{판}/`, 범위 클래스 `draft-{화면}-{판}`, 판 CSS 파일 `src/styles/drafts/{화면}-{판}.css`, 1층 새 이름 접두 `--{판}-…`. 판 CSS 파일과 범위 클래스는 화면마다 하나다 — 대담판이 두 화면을 맡으면 `{화면1}-bold.css`·`{화면2}-bold.css` 둘이다.

**브랜드 색 단계 고르기** — 같은 계열이든 두 번째 색이든, 램프에서 단계를 고를 때 셋을 본다. 메인이 2층 `:root`를 보고 지시서에 「바탕 색」과 「피할 단계」를 적어 넘긴다.

1. **면과 바탕의 대비 1.2:1 이상** — 바탕은 2층 `--background`다. 이보다 낮으면 면이 바탕에 묻혀 띠가 안 보인다. 디자인 시스템 페이지 「브랜드」 영역이 「바탕과 면」 대비를 계산값으로 보인다(§2.4).
2. **바탕이 흰색이 아니면 옅은 끝 단계를 먼저 의심한다** — 미색·옅은 회색·옅은 색조처럼 바탕이 옅은 색이면, 램프의 가장 옅은 단계(50 등)는 바탕과 거의 같은 색이다. 옅은 쪽에서 고를 때 한두 단계 진한 쪽부터 보고, 그래도 1번을 못 넘으면 진한 끝(900~950)으로 간다.
3. **2층에 이미 다른 이름으로 이어진 단계는 피한다** — 특히 「지금 선택된 것」·누르기 전 강조(hover)·`accent`·`muted`·`secondary`처럼 상태나 다른 면을 나타내는 바탕. 같은 값이면 브랜드 색 면이 「선택된 칸」처럼 읽힌다.

면 위 글자 4.5:1과 면 위 주 버튼 3:1은 그대로다(§1.3 1번). **진한 면을 고르면 주 버튼은 면 밖이 기본이다** — 면 위에는 테두리 버튼만 둔다. (실측 2026-10-21 한잔여권 시험: 옅은 바탕 프로젝트에서 「아주 옅은 50~100 단계」 기본값대로 고르니 50 단계는 바탕과 1.02:1, 100 단계는 선택된 칸 바탕과 같은 값이었다. 같은 날 시험에서 진한 면 위에 강조색 주 버튼을 두니 2.6:1로 3:1에 못 미쳤다.)

**제목 서체가 이미 있을 때** — 1단계 브리프 「4」의 「서체 — 제목」이 이미 채워져 2-0이 그 서체를 깔아 둔 프로젝트다. 메인이 §2.1에서 2층·3층 파일을 보고 아래 셋을 처리한다.

1. **지금 서체가 바닥이다** — 대담판은 방향에 맞으면 지금 제목 서체를 그대로 두고, 바꾸면 디자인 시스템 페이지 「브랜드」 영역에 지금 서체와 새 후보 하나를 나란히 보인다. 사람이 「그대로 둘지, 바꿀지」를 견준다.
2. **이어진 모양을 맞춘다(메인이 판을 띄우기 전에)** — `@theme inline`의 `--font-brand`(또는 shadcn 복사본이 쓰는 `--font-heading` 같은 제목 서체 이름)가 서체 변수를 바로 가리키면, 비교안이 덮어써도 클래스에 닿지 않는다 — `@theme inline`은 값을 클래스에 그대로 적어 넣는다. 그래서 2층 `:root`에 지금과 값이 같은 `--brand-font`를 두고, 그 줄들이 `var(--brand-font)`를 가리키게 바꾼다 — `--font-brand`와 `--font-heading`이 둘 다 있으면 **둘 다** 중간 변수에 잇는다. 한쪽만 이으면 다른 쪽을 쓰는 글자(상단 메뉴 로고·카드 제목 등)가 비교안에서는 안 바뀌어, 사람이 본 비교안과 고른 뒤 화면이 달라진다. 이어 둔 쪽을 쓰는 본 부품(상단 메뉴 등)은 고르면 함께 바뀌니 판 고르기 때 알린다(§2.7 「판마다 고르면 늘어나는 일」). 계산값은 그대로라 본 화면은 바뀌지 않는다. 여러 판이 함께 쓰는 줄이라 메인이 미리 바꾸고(§2.5 표), 판 에이전트의 「건드린 본 파일」에는 들지 않는다(2-2 §2.4의 중간 변수와 같은 방식). (실사고 2026-10-21 한잔여권 시험: 범위 클래스로 `--font-brand`만 덮어써 서체가 안 바뀌었고, 에이전트가 중간 변수를 즉석으로 만들었다.)
3. **전역 제목 규칙이 있으면 그 범위가 기본이다** — 3층(`3-components.css`)이나 진입 CSS에 제목 태그(`h1`~`h6`)마다 `font-brand`를 거는 규칙이 있으면, 「제목 서체를 쓰는 글자」는 이미 그 규칙의 태그 범위로 정해져 있다. 「큰 제목에만」으로 저절로 좁히지 않는다 — 사람이 1단계·2-2에서 그 범위로 화면을 보고 넘어왔다. 범위를 좁혀 보고 싶으면 대담판 범위 클래스 안에서만 좁힌 쪽(예: 작은 제목은 본문 서체)을 덮어 보이고, 고르면 §2.9에서 3층 규칙을 고친다. 브리프 「13」 「제목 서체를 쓰는 글자」와 연결 정보에는 글자 이름 대신 「제목 태그 `h1`~`h3`(3층 전역 규칙)」처럼 규칙 범위로 적는다.

**움직임과 3단계 모션의 몫** — 2-3은 대표 움직임 여럿을 어디서·무엇이·어떤 순서로(말로) 정하고, 비교안에서는 2-0이 자리만 잡아 둔 모션 토큰 이름(`duration-*`·`ease-*`)으로 만든다. 3단계 §2.4가 기본 세트 넷과 길이·곡선 값(1층)을 정하고, 「8」의 「대표 움직임」 행이 이미 `사용자 확정`이면 다시 묻지 않고 길이·곡선 값만 전체와 맞춘다. `motion` 라이브러리는 판마다 다르다.

- **대담판** — CSS만. `motion`을 깔지 않는다. 대담판을 고른 뒤 더 큰 움직임이 필요하면 3단계 모션 절이 들일지 정한다.
- **혁신판·파격판** — 메인이 컨셉 고르기 뒤 `motion`을 깐다(§2.5 표). 고르면 3단계는 「들일지」를 묻지 않는다. 고르지 않으면 3단계에서 지운다.
- **탄성 곡선이 2층에 없을 때** — 2층 `ease-*`에 탄성 곡선 이름이 없거나 프로젝트 `AGENTS.md`가 그런 곡선을 막는 옛 프로젝트면, 비교안은 판 CSS 파일 안에 판 접두 이름(1층 `--bold-…` 값 + `--ease-bold-spring` 같은 이름)으로 두고 보고한다. 고르면 전체 적용에서 2층 `ease-*`에 이름 하나를 더하고, 프로젝트 `AGENTS.md`의 움직임 규칙 줄(예: 「spring 없음」)을 고친다(§2.9 대담판 ⑤).

### 1.3 바닥 금지 — 어떤 판에서도 그대로

지시서마다 이 목록 전부를 걸러 넣는다. 판이 바뀌어도 풀리지 않는다.

1. **대비** — 글자 4.5:1, 면 위 주 버튼과 면 3:1(WCAG 1.4.11 — 글자가 아닌 요소의 대비 기준), 포커스 표시 그대로(브리프 「9」). **질감·그라데이션 면은 가장 나쁜 자리로 잰다.** 진한 면을 고르면 **주 버튼은 면 밖이 기본**이다 — 면 위에는 테두리 버튼만. 면 위 회색 글자(`muted-foreground`)가 4.5:1을 못 넘으면 2층 이름을 범위 안에서 덮어쓰지 않는다 — 면 전용 짝 이름(비교안에서는 판 접두, 고른 뒤 2층 `brand-surface-muted-foreground`)을 두거나 면을 옅게 한다.
2. **신호 색 혼동 금지** — 강조색(`primary`)은 주 행동 하나·지금 선택된 것·포커스 표시 세 자리에만. **바뀐 조작과 은유 안에도 같다** — 주 행동을 전용 조작 대상(끌어 놓는 카드·명령창의 실행 줄·여럿 고르기 막대의 실행 단추 등)이 맡으면 그 대상이 강조색 자리이고 대체 경로 버튼은 테두리 버튼. 은유 안(3D 장면·게임판·지도 등)의 「지금 선택된 것·오늘」에는 강조색을 쓸 수 있고, 장식에는 쓰지 않는다. 브랜드 색을 버튼·칩·태그·아이콘·제목 글자에 쓰지 않고, 브랜드 색 면이 버튼처럼 보이는 크기·모서리를 갖지 않게 한다.
3. **글자·간격 단계 유지** — 브리프 「12」의 단계 그대로. 제목 서체는 글꼴만 바꾸고 크기 단계는 그대로. 단 대표 장면 한 곳에 「전시용 제목」 한 단계를 더할 수 있다.
4. **동작 줄이기 예외 없음** — 모든 움직임과 은유의 연출(3D 회전·카드 넘김·지도 날아가기 등)이 꺼진다. 정지 화면 + 대체 경로로.
5. **기술 바닥** — 바뀐 조작과 은유에는 같은 일을 하는 평범한 길(버튼·목록)을 같은 화면에 둔다. 키보드로도 된다. 폰 폭(390)에서 터치로 된다. 고른 수단이 안 되는 환경이면 대체 화면(예: WebGL 없음 → 2D 화면, 카메라·마이크 권한 거부 → 직접 입력, 지도 못 불러옴 → 목록). 무거운 라이브러리를 받는 동안 로딩 뼈대. 제목 서체는 굵기 하나, 한글 조각 로딩.
6. **참고 베끼기 금지** — 트렌드 사례·참고 사이트의 로고·그림·사진·문구를 가져오지 않는다. 로고를 남의 로고와 닮게 그리지 않는다. 기법만 배운다.
7. **실물 속이기 금지** — 사용자의 실제 기록처럼 보이는 자리에 생성 이미지를 쓰지 않는다. 사진 톤은 밝기·채도·따뜻함만 조금, 색상(hue) 돌리기 없음. 외부 이미지 생성 도구·API, 외부 3D 모델은 부르지 않는다. 3D를 쓰면 코드로 만든 단순한 모형과 이미 받은 견본 사진만.
8. **데이터 구조 그대로** — 저장·조회 코드와 예시 데이터를 그대로 읽는다. 저장 구조·저장하는 때를 바꾸지 않는다.
9. **사람 몫 유지** — AI가 판을 대신 고르지 않고, 자기 점검으로 「확인 완료」「잘 나왔다」라고 하지 않는다.

**이번 범위 밖** — 마스코트·일러스트 생성(바깥 이미지 생성 도구·API가 필요하다), 사진 파일 자체의 색 보정, 다크 모드. 브리프 「4」 「마스코트」 행은 `추후 결정`으로 둔다.

### 1.4 판에 따라 풀리는 제한

2-2까지의 제한 가운데 판에 따라 풀리는 것이다. 지시서에는 그 판의 열만 넣는다.

| 2-2까지의 제한 | 대담판 | 혁신판 | 파격판 |
|---|---|---|---|
| 그림 소재 하나 | 주 소재 하나 + 보조 하나 | 대담판과 같음 | 대담판과 같음 |
| 소재는 대표 장면에서만 크게 | 대표 장면 밖에도 소재 **모양**은 되풀이할 수 있다(크기·자리·개수 규칙 안에서). 면·움직임은 대표 장면에만 | 같음 | 같음 |
| 브랜드 색 면 화면당 하나 | 대표 장면에서는 여러 겹 면. 그 밖 화면은 하나 | 같음 | 같음 |
| 면은 단색 | 질감·그라데이션 허용. 브리프 「7. 피할 것」(보라→파랑 그라데이션·유리 반사 남발 등)은 그대로 | 같음 | 같음 |
| 대표 장면 크기 | 첫눈에 보이는 면적의 절반까지 | 같음 | 화면 전체가 장면일 수 있다 |
| 대표 움직임 하나 | 대표 장면마다 2~3개, 탄성 곡선, 감탄 포인트 하나(핵심 행동에 붙는 연출). CSS로 | 같음 + 바뀐 조작에 붙는 움직임 | 같음 + 은유의 움직임 |
| 일러스트 금지 | SVG로 직접 그리는 분위기 그림 허용 | 같음 | 같음 + 고른 수단의 그림(3D면 코드로 만든 단순 모형) |

| 기능 자리 그대로 | 기능(누르는 것)은 모두 자리가 있어야 한다. 대표 장면이 같은 **정보**를 크게 보이면 원래 자리의 그 정보 줄은 줄이거나 뺄 수 있다 — 보고에 「줄인 자리」로 | 같은 기능을 다른 방식으로는 허용. 기능이 빠지면 안 된다 | 기능은 은유 안의 다른 모양으로 있어도 된다. 빠지는 기능은 보고 |
| 새 기능 금지 | 그대로 | 그대로(후보로 보고만) | 놀이 요소 1~2개 만들어 보이기 허용, 「새 기능 후보」로 표시 |
| 추가 라이브러리 금지 | 그대로 — CSS 움직임만 (사용자 확정 2026-10-21) | `motion` 허용. `@use-gesture/react`는 손동작 갈래를 고를 때만 | `motion` + 고른 수단에 필요한 라이브러리만(3D·지도 등). 같은 원칙(§1.5) |

### 1.5 기술 허용과 무거운 라이브러리

**고정 스택과의 관계** — 2-0의 고정 스택(모든 프로젝트가 반드시 쓰는 조합)은 그대로다. 새 패키지는 「고정 스택 밖은 필요할 때만」(`2-0-dev-setup.md` §2.2) 규칙 안의 추가다. 메인이 컨셉 고르기 뒤 고른 수단이 쓰는 패키지만 판을 고정해 깔고, `mvp/adr.md`에 「2-3 비교안용, 고르지 않으면 3단계에서 지움」으로 한 줄 적는다.

**무거운 라이브러리에 같은 원칙 넷** — 3D·지도처럼 받는 양이 큰 라이브러리는 어느 수단이든 아래를 지킨다.

1. 비교안 주소에서만, 동적 import(그 화면에 들어갈 때만 내려받기)로 부른다. 다른 화면 번들에 섞이지 않게 하려는 것이다.
2. 판을 고정해 깔고 `adr.md`에 한 줄 적는다.
3. 숫자 값은 수단마다 한 파일(`lib/{수단}.ts`)에 모은다.
4. 색은 2층 이름으로만 읽는다.

**디자인 규칙 검사(`design-check.sh`)와 비교안 폴더** — 비교안 폴더도 검사한다(3단계 §2.5 「비교안 폴더는 반드시 넣는다」). 걸린 줄은 지우는 게 아니라 **판 보고에 목록으로** 받는다(§4.3 보고 ⑬). 15번(브랜드 색 면 자리)은 개발용 묶음 `(dev)`를 뺀다.

**16번 「무거운 라이브러리 자리」** — 연결 정보에 두 줄을 둔다. `HEAVY_LIBS:`(이 프로젝트가 들인 무거운 라이브러리 이름, 공백으로 나눔 — 예: `three @react-three/fiber maplibre-gl`)와 `HEAVY_PARTS:`(그것을 불러도 되는 부품 파일 목록). 16번은 `HEAVY_LIBS:`의 이름을 불러오는 파일이 `HEAVY_PARTS:` 밖에 있으면 찍는다. 15번과 같은 세 갈래다 — 아직 안 들임 → 해당 없음 / 들였는데 목록 줄 없음 / 목록 밖 파일. `(dev)`는 뺀다. 문장 규칙만으로는 무거운 라이브러리가 다른 화면으로 퍼지는 것을 못 막는다. 2-1에서 이미 들인 견본 지도 라이브러리도 이 목록에 든다 — 그런 라이브러리가 있는데 두 줄이 없으면 판을 띄우기 전 공유 파일 준비에서 넣는다(§2.5 표 「연결 정보 `HEAVY_LIBS:`·`HEAVY_PARTS:`」 행). (2026-10-22 시험: 견본 지도가 이미 있는 프로젝트에서 어느 단계도 두 줄을 넣지 않아 16번이 「줄 없음」으로 남았다.)

**은유 수단의 원시 값을 어느 층에 둘까** — 조명 세기·카메라 각도, 지도의 처음 확대 단계, 게임판의 칸 수 같은 숫자는 둘 자리가 따로 없으면 비교안 코드 곳곳에 흩어진다(2026-10-21 시험에서 3D 숫자가 그랬다).

| 값 | 자리 | 이유 |
|---|---|---|
| 수단의 숫자(3D면 조명·카메라·비율, 지도면 처음 확대 단계, 게임판이면 칸 수) | 수단마다 한 파일 `lib/{수단}.ts`(예: `lib/scene.ts`·`lib/board.ts`) | 이런 라이브러리는 값을 CSS 변수가 아니라 JS 숫자로 받는다. `motion`의 `lib/motion.ts`와 같은 방식이다 |
| 수단 안의 색(3D 재질·지도 표시·게임판 칸) | 2층 새 이름 `--{수단}-{역할}`(예: `--scene-surface`·`--board-cell`). 화면은 `getComputedStyle`로 2층 이름만 읽는다 | 색의 정본은 계속 1·2층 CSS다. naming-taxonomy의 「color/domain — 기능 전용 팔레트」 문법 그대로 |
| 색 글자를 라이브러리가 읽는 꼴로 바꾸는 도우미 | 같은 `lib/{수단}.ts` | 그 안의 `rgb(` 같은 글자가 검사 1번 오탐이 되지 않게 제품 코드 폴더 밖에 둔다 |
| 1층 램프를 바로 읽기 | 금지 | 1층 램프를 바로 읽으면 검사 2번에 걸린다(2026-10-21 시험) — 2층 이름을 거친다 |
| 수단 안 좌표(SVG·겹친 글의 자리)를 CSS 변수로 넘기기 | 허용 — `style={{ "--x": … }}`처럼 CSS 변수만 넘기는 `style`. 값은 `lib/{수단}.ts`(비교안에서는 `_leap/{수단}.ts`)에서 읽는다 | 좌표는 칸마다 달라 클래스로 둘 수 없다. 색·간격처럼 토큰이 있는 값을 `style`로 넣는 것은 그대로 금지 |

비교안 단계에서는 숫자를 판 폴더 안 한 파일(`_leap/{수단}.ts`)에, 색 이름을 판 CSS 파일의 범위 클래스 안에 두고, 고른 뒤 전체 적용에서 `lib/{수단}.ts`와 2층으로 옮긴다. 검사 1번은 `(dev)` 비교안 폴더의 판 폴더(`_bold/`·`_innov/`·`_leap/`) 안 `.ts` 파일(`{수단}.ts`·`motion.ts`)을 보지 않는다 — 제품 코드 폴더 밖 `lib/`로 옮길 값 파일이라서다(2026-10-22 시험: `_leap/{수단}.ts`의 색 변환 도우미 `rgb(`가 1번에 걸렸다). 은유 안의 강조색은 §1.3 2번이고, 대비는 가장 나쁜 자리(3D면 조명이 가장 어두운 자리)로 잰다.

**손동작 영역과 스크롤** — 혁신판에서 손동작 갈래나 끌어 놓기를 고른 경우다. 폰에서 손동작 영역이 화면 대부분을 덮으면 페이지를 스크롤할 수 없게 된다(2026-10-21 시험).

1. 가로로 미는 손동작이면 세로 스크롤은 막지 않는다(`touch-action: pan-y`).
2. 세로 스크롤까지 막는 손동작 영역은 폰 화면 높이의 절반 이하.
3. 절반을 넘어야 하면, 손동작 영역 밖에 스크롤할 수 있는 여백이나 손잡이를 남기고 보고한다.
4. 컴퓨터 위주 서비스의 끌어 놓기(마우스로 카드·쪽지를 끌어 옮기기)는 폰에서 손잡이를 잡거나 길게 눌러야 끌기가 시작되게 한다 — 끌 수 있는 것 위를 손가락이 스쳐도 페이지 스크롤이 막히지 않는다.

1. **안 맞는 판을 입구에서 뺀다** (§2.1) — 파격판 하나를 빼면 약 27만 토큰·21분이 준다.
2. **대담판 먼저, 나머지는 동시에** (§2.5) — 벽시계 시간이 줄고, 뒤 두 판이 겉모습을 다시 정하지 않는다.
3. **자기 점검 회차에 상한** — 대담 3·혁신 4·파격 5회. 고치지 않는 확인 촬영 1회는 따로. 스크린샷은 절반 크기로 찍는다(그림을 읽는 토큰이 준다). 같은 오류로 2회 막히면 멈춘다(§2.6).
4. **트렌드 조사는 sonnet, 페이지 12개 안팎에서 멈춤** — 결과 표 5~8줄. Aside로 화면을 찍으면(§2.2) 그림을 읽는 토큰이 늘어나니 스크린샷은 절반 크기로, 움직임 연속 컷은 기법 후보로 남은 사례에만 찍는다(아직 실측 없음).
5. **발상은 메인이 직접** — 웹 조회가 없고 메인이 이미 자료를 안다.
6. **판마다 대상 화면을 하나로**(+빈 상태) — 대담판만 핵심 행동 화면을 하나 더 할 수 있다.
7. **빌드는 메인이 마지막에 한 번** — 에이전트마다 빌드하지 않는다.
8. **대화 비우기** — SKILL.md §3.2 요금제 한도 목록이 2-3을 「컨셉 고르기까지」·「끝까지」 둘로 나눈다. 컨셉 고르기 뒤에 비울 거면, 메인이 고른 컨셉 세 줄을 브리프 「13」 표 아래 `고른 컨셉(만드는 중):` 줄에 임시로 적고 비운다(§2.3).

## 2. 진행 절차

### 2.1 들어오기 — 안내·판 빼기·건너뛰기

1. **들어오는 줄을 확인한다** — `feature-list.md` 머리에 `디자인 개선 확인 끝:` 줄이 있거나 브리프 「12」가 `건너뜀`인지 본다. 판별(SKILL.md §1.2)로 들어왔는데 둘 다 아니면 2-2로 돌아간다(SKILL.md §1.2 5번). **사용자가 2-3을 콕 집어 불렀으면 이 확인보다 사용자 지시가 먼저다** — 확인 줄이 없어도 들어오고, 무엇을 건너뛰었는지만 한 줄로 알린다(예: 「디자인 개선 확인 기록이 없는 프로젝트라, 그 확인은 건너뛰고 지금 화면 위에 개성을 입힙니다」). 옛 템플릿 프로젝트(브리프에 「13」 절도, 그 확인 줄도 없음)가 대개 이 경우다. 브리프 「12」가 `추후 결정`이면 화면 규칙이 아직 없다는 뜻이라, 들어오되 그 사실을 같은 한 줄에 붙인다 — 2-2로 끌고 가지 않는다.
2. **브리프에 「13. 개성」 절이 없거나 옛 모양이면 먼저 맞춘다** — 옛 템플릿으로 만든 프로젝트를 사용자가 콕 집어 2-3으로 불렀을 때다. `1-design-brief-template.md`의 「13」 표를 그대로 넣고, 「4」의 빠진 것도 같은 때 템플릿 자리 그대로 더한다 — 「우리가 쓰는 값」 표의 「색 — 브랜드 면」 행(색 행들 끝, 「서체 — 제목」 행 앞), 「이미지·영상 계획」 표 바로 아래(그 아래 안내 글머리보다 앞)의 「사진 톤:」 줄. 「13」이 있어도 「고른 판」 행이 없는 옛 모양(판이 둘이던 때의 행 여섯)이고 아직 `추후 결정`이면 새 표로 바꾼다. `feature-list.md` 머리에 `화면 대조 끝:` 줄이 있거나 3단계 화면이 이미 있으면 §2.12도 함께 따른다.
3. **이어 가는 자리인지 본다** — 브리프 「13」 표 아래에 `고른 컨셉(만드는 중):` 줄이 있으면 컨셉 고르기 뒤에 대화를 비웠다가 돌아온 것이다. 컨셉을 다시 고르지 않고 그 줄의 컨셉으로 §2.4부터 잇는다. 비교안 폴더에 판 폴더(`drafts/_{판}/`)가 이미 있으면 `git status`와 그 폴더를 보고 남은 판만 만든다. 브리프 「13」에 「고른 판」이 파격판으로 적혔는데 `feature-list.md` 머리에 `은유 반영:` 줄이 없으면 §2.7 「파격판을 고르면」부터 잇는다.
4. **안내를 한 번 낸다** — 아래 넷을 한 메시지로. 답이 없거나 「좋아요」면 세 판 모두로 진행한다 — 이 자리는 묻는 자리가 아니라 알리는 자리다.
   1. **세 판을 이 서비스의 말로 알린다** — 이 서비스의 대상 화면과 핵심 행동 이름으로 한 줄씩. 예: 「대담판은 {첫 화면}을 더 과감하게 꾸민 판, 혁신판은 {핵심 행동}을 하는 방법 자체를 바꾼 판, 파격판은 {첫 화면}을 아예 다른 물건처럼 바꾼 판입니다.」 어떤 조작·물건으로 바꿀지는 아직 말하지 않는다 — 컨셉은 §2.3에서 후보로 낸다. 입구에서 구체적인 조작·은유를 예로 들면 그것이 첫 후보로 굳는다.
   2. **비용을 알린다** — 세 판 모두면 40분~1시간(대담판이 두 화면이면 더), 고른 뒤 파격판이면 3단계 일이 늘어난다는 것(§1.6).
   3. **안 맞는 판을 뺄지 한 번 묻는다** — 메인이 브리프 「10. 가치 우선순위」와 서비스 성격을 보고, 맞지 않아 보이는 판이 있으면 이유와 함께 「빼는 것을 권합니다」라고 붙인다(예: 「신뢰」가 맨 앞인 송금 서비스의 파격판). 「10」이 비었으면(`추후 결정`) 「1」의 관점과 「7. 피할 것」으로 보고, 거기서도 근거가 없으면 권하지 않는다. 고르는 것은 사용자다. 답이 없으면 세 판 모두 만든다. 3단계를 이미 지난 프로젝트면 기본은 대담판·혁신판 둘이다(§2.12).
   4. **건너뛸 수 있다고 한 번 말한다.**

안내 골자 — 말투는 `AGENTS.md` 응답 톤에 맞춰 풀어서 전달:

> 화면이 깔끔해졌으니, 이제 이 서비스만의 얼굴을 입혀 보겠습니다. 얼마나 깊이 바꿀지가 다른 세 가지 판을 만들어 지금 화면과 나란히 보여 드립니다. 대담판은 {이 서비스에 빗댄 한 줄}, 혁신판은 {한 줄}, 파격판은 {한 줄}입니다. 먼저 요즘 비슷한 서비스들이 쓰는 표현을 찾아보고, 판마다 방향 후보를 글로 보여 드릴 테니 하나씩 골라 주세요. 세 판을 다 만들면 40분에서 1시간쯤 걸립니다. {맞지 않아 보이는 판이 있으면: 이 서비스는 {이유}라 {판}은 빼는 것을 권합니다.} 빼고 싶은 판이 있으면 말씀해 주세요. 이 단계는 건너뛰셔도 됩니다 — 그러면 지금의 깔끔한 화면 그대로 다음으로 갑니다.

**건너뛰는 길** — 사용자가 건너뛰겠다고 하면 더 설득하지 않는다. 메인이 브리프 「13. 개성」을 표 대신 `건너뜀 — {사유} (YYYY-MM-DD)` 한 줄로 바꾸고 §3 완료 체크리스트로 바로 간다. 이 한 줄이 있어야 SKILL.md §1.2 판별이 다음에 2-3으로 되돌아오지 않는다. 건너뛰면 3단계는 브랜드 색 면·대표 장면 줄과 검사 ① 15번을 해당 없음으로 넘긴다.

### 2.2 트렌드 조사

대담판에 쓸 표현 기법을 **실제로 조회한 사례**로 모은다. 미리 외운 유행 목록으로 채우지 않는다.

- **누가** — 서브 에이전트 하나(sonnet). 메인이 §2.3 발상을 하는 동안 백그라운드로 돈다. 지시서는 §4.2.
- **무엇을** — 같은 성격의 서비스에서 최근 사례가 쓰는 기법 5~8개. 후보마다 아래 여섯 항목.

| 기법(쉬운 말) | 어떤 모습인가 한 줄 | 본 사례(이름과 주소) | 확인 방법 | 본 날짜 | 이 서비스에 맞나 한 줄 |
|---|---|---|---|---|---|

- **도구 — Aside가 있으면 화면을 찍어 본다** — 웹 조회 도구는 페이지의 글만 가져와 색·서체·움직임을 볼 수 없다(2026-10-21 시험 두 곳에서 사례 전부가 「글로만 확인」이었다). 메인이 `command -v aside`로 보고, Aside(사용자의 실제 브라우저를 AI가 조종하는 도구)가 있으면 지시서에 Aside 갈래를 넣는다 — `aside repl`로 공개 사례 페이지를 열어 `page.screenshot()`으로 화면을 찍고, 움직임은 짧은 간격으로 몇 장 연속 찍는다(0·0.3·0.6·1초). 움직임 컷은 페이지를 연 직후부터(로딩이 끝나기를 기다리지 않고), 또는 스크롤·마우스 올림을 한 직후부터 찍는다 — 다 멈춘 뒤에 찍으면 네 장이 같은 그림이다(2026-10-22 시험: 열고 2.5초 기다린 뒤 찍어 「움직임 컷으로 확인」이 0줄이었다). Aside가 없으면 지금처럼 글 도구로 조회하고, 사례마다 주소를 남겨 사람이 §2.3에서 직접 열어 보고 거르게 한다. 사용자가 스크린샷·화면 녹화를 주면 그것으로 반영한다.
- **「확인 방법」은 셋 중 하나로 적는다** — 「화면으로 확인(스크린샷 경로)」 / 「움직임 컷으로 확인(스크린샷 경로)」 / 「글로만 확인」(앱스토어 소개글 등). 글로만 확인한 사례는 색·움직임의 실제 모습을 못 본 것이다. 「본 날짜」는 페이지에 날짜가 있으면 적고, 없으면 「날짜 모름」.
- **근거는 실제로 연 주소뿐이다** — 열지 않은 사례를 기억으로 채우지 않는다. 트렌드는 판정이 아니라 후보라, 사람이 §2.3에서 거른다.
- **조회 규칙** — 같은 실패 2회면 멈추고 보고, 401·403·404는 재시도 금지, 로그인·봇 차단·캡차가 뜨면 우회하지 않고 그 사이트는 건너뛴다. 로그인이 필요한 사이트는 열지 않는다. 조회는 페이지 12개 안팎에서 멈춘다.
- **Aside를 쓸 때 더 지키는 것** — Aside는 사용자가 로그인해 둔 실제 브라우저라 아래를 지시서에 넣는다. ① 쓰기 전에 `aside guide repl`을 읽는다. ② 읽고 찍기만 한다 — 사용자 계정으로 어떤 행동(좋아요·팔로우·댓글·다운로드·가입·동의 버튼)도 하지 않는다. ③ 찍은 그림은 프로젝트 `.draft-checks/trend/`(git에 올리지 않음)에 둔다 — 메인이 띄우기 전에 `.gitignore`에 `.draft-checks/` 줄이 있는지 보고 없으면 더한다(§2.5 표 마지막 행을 이때 당겨 한다). Aside REPL의 파일 쓰기는 Aside 세션 폴더(`~/.aside/u/0/sessions/*/`) 안에만 되어 프로젝트 절대 경로로는 저장되지 않는다 — 세션 폴더에 찍은 뒤 셸에서 프로젝트 `.draft-checks/trend/`로 옮기고, 세션 폴더의 원본은 지운다(2026-10-22 시험: 상대 경로로 저장해 세션 폴더에 생겼고, 옮긴 뒤에도 원본이 남았다). ④ 메인이 지시서를 쓰기 전에 Aside가 어느 프로필로 뜨는지 본다(`aside host profiles`, 명령이 다르면 `aside --help`로 확인) — 프로젝트 `AGENTS.md` 「소유와 계정」 표의 「브라우저 작업 프로필」과 다르거나 표가 비었거나 `(확인 필요)`면, 로그인하지 않은 공개 페이지만 연다는 문장을 지시서에 한 번 더 적는다(2026-10-22 시험: 표가 `(확인 필요)`였고 에이전트는 어느 프로필로 떴는지 몰랐다).
- **가져오지 않는 것** — 사례의 로고·그림·사진·문구. 기법만 배운다. 찍은 스크린샷도 기법을 보는 자료일 뿐, 화면에 넣지 않는다.
- **메인이 고른다(후보)** — 결과 중 맞는 것 2~4개를 대담판 후보로 표시하고, §2.3 메시지에 함께 낸다. 「글로만 확인」 사례는 주소를 함께 내 사람이 열어 볼 수 있게 한다.

### 2.3 발상과 컨셉 고르기 (사용자 몫)

**발상은 메인이 직접 한다** — 브리프 「1」(브랜드 인상·관점), `intent.md` 「3. 원하는 것」, 화면 목록의 핵심 행동을 메인이 이미 알고 있고, 웹 조회가 필요 없는 일이라 위임하면 같은 자료를 두 번 읽게 된다.

혁신판·파격판 컨셉 후보를 **각 3개** 낸다. 후보마다 여섯 항목.

| 이름 | 다른 분야에서 가져온 것 | 쓰는 수단 | 핵심 행동이 어떻게 바뀌나 | 브리프 「1」과 맞나 | 만들기 어려움(하·중·상) |
|---|---|---|---|---|---|

- **다른 분야에서 가져온다** — 게임·실물 물건·놀이·다른 장르의 앱. 혁신은 대개 다른 분야에서 온다 — 사람 고르기를 손가락으로 밀어 넘기는 카드 더미로 바꾼 데이팅 앱, 내 공간을 방 하나 꾸미기로 바꾼 미니홈피, 메뉴 찾기를 단축키 명령창으로 바꾼 업무 도구들이 그 예다. 같은 장르 앱의 평균을 따르지 않는다. 트렌드 조사 결과는 참고만 한다.
- **이 문서와 `visual-polish.md`의 예시를 후보로 그대로 쓰지 않는다** — 예시(그림 소재·다른 분야·수단·은유의 예)는 모양을 보이는 것이지 고를 목록이 아니다. 떠오른 후보가 문서 예시와 같은 소재·물건이면 버리고 이 서비스의 「1」·「6」·`intent.md` 「3. 원하는 것」에서 다시 짓는다. (2026-10-22 시험: 그림 소재 예시가 시험 서비스와 거의 같은 유형의 것이라 메인이 일부러 피했는데, 문서를 읽지 않은 판 에이전트가 같은 소재를 그렸다 — 그 유형에서 가장 먼저 떠오르는 소재가 예시에 들어 있었다. 다른 시험에서는 「다른 분야」 예가 그대로 첫 후보로 떠올랐다.)
- **서비스 유형과 조작·은유를 짝짓지 않는다** — 「이 유형이면 이 은유」 식의 짝은 정답지처럼 쓰여 첫 후보가 그대로 그 짝이 된다(2026-10-21 시험). 후보는 브리프 「6. 주 사용 맥락」·`intent.md` 「3. 원하는 것」과 다른 분야에서 가져온 것으로 짓는다.
- **「쓰는 수단」** — 혁신판은 핵심 행동을 하는 방법의 갈래(손동작·단축키 명령창·말로 입력·여럿이 동시에 편집·한 번에 여럿 고르기 등), 파격판은 은유를 만드는 수단(3D 장면·지도 위에 펼치기·대화로 주고받기·카드 더미 넘기기·게임판·카메라로 비추기 등). 세 후보가 한 수단에 몰리지 않게 섞는다. 첫 화면이 이미 어떤 수단(지도 등)이면 파격판 후보에서 그 수단은 뺀다(§1.1). 브리프 「5. UI 패턴 지정」의 사용자 확정 모양을 깨는 후보는 그 사실을 「브리프 「1」과 맞나」 항목에 한 줄로 적는다.
- **혁신판 세 후보 중 둘은 브리프 「6. 주 사용 맥락」에 맞는 갈래, 하나는 맥락 밖 갈래** — 폰 위주면 둘은 손동작·말로 입력 쪽, 컴퓨터 위주면 둘은 단축키·여럿 고르기·동시 편집 쪽이다. 맥락에 맞는 쪽이 대부분 이기지만, 하나는 뜻밖의 후보를 두어 발상이 좁아지지 않게 한다.
- **권한이 필요한 수단도 후보로 낸다** — 카메라로 비추기·말로 입력처럼 권한이 필요한 수단은 권한 거부 때의 대체 경로가 반드시 있다는 조건으로 낸다(§1.3 5번).
- **한 메시지로 낸다** — ① 대담판: 방향 한 문장 초안(주 소재가 드러나게) + 쓸 기법 2~4개(트렌드 표에서) ② 혁신판 후보 셋 ③ 파격판 후보 셋 ④ 「판마다 하나씩 골라 주세요. 섞거나 바꿔 말씀하셔도 됩니다」. 입구에서 뺀 판은 내지 않는다.
- **사용자가 「알아서」라고 하면** — 메인이 판마다 하나를 이유와 함께 권하고, 「이대로 만들까요?」 한 번 확인 뒤 진행한다. 고르지 않은 후보는 보고에 남긴다.
- **고른 컨셉은 아직 브리프에 확정으로 적지 않는다** — 판 고르기(§2.7) 뒤에 적는다(§2.8). 메인은 고른 컨셉 세 줄을 판 지시서에 그대로 옮긴다. 대화를 비울 거면 브리프 「13」 표 아래에 `고른 컨셉(만드는 중): 대담 「…」 · 혁신 「…」 · 파격 「…」 (YYYY-MM-DD)` 한 줄을 임시로 적고 비운다 — 판을 고르면 이 줄을 지운다.
- **고른 뒤 메인이 패키지를 깐다** — 고른 수단이 쓰는 패키지만 한 번에(§2.5 표 「`package.json`·잠금 파일」 행).

### 2.4 디자인 시스템 페이지에 값 먼저

**비교안 화면을 만들기 전에 값부터 올린다** — 2-2 §2.3과 같은 이유다. 바뀌는 것은 **판마다 자기 영역을 따로 갖는다**는 것이다 — 세 에이전트가 같은 페이지 파일을 고치면 서로 덮어쓴다.

- **메인이 판을 띄우기 전에 자리를 만든다** — 디자인 시스템 페이지(`/dev/design-system`) 「브랜드」 영역(`bootstrap-project.md` §6.1 「브랜드」 행)에 판마다 자리 하나씩(`<BrandPanel edition="bold" />`처럼 판 이름으로 부르는 부품 셋)을 두고, 그 부품 파일은 각 판 폴더 안의 빈 껍데기(`drafts/_bold/brand-panel.tsx`·`_innov/`·`_leap/`)로 미리 만든다. 입구에서 뺀 판의 자리는 만들지 않는다.
- **「브랜드」 영역이 아예 없는 옛 페이지면 틀에서 옮긴다** — 틀이 바뀌기 전에 만든 디자인 시스템 페이지에는 그 영역이 없다. 메인이 틀 `.claude/templates/mockup-canvas/app/(dev)/dev/design-system/page.tsx.template`의 브랜드 구역(코드 주석 `── 브랜드` 이하 — 판 자리 목록·판 자리 부품·영역 부품)을 옮기고 페이지에 영역 부품을 단다. 로고·면 대비 같은 「지금 값」 목록은 고른 뒤 생기니 빈 채로 둔다.
- **각 판 에이전트는 자기 껍데기 파일만 채운다.**
  - 대담판 — 브랜드 색 면·질감 견본과 대비(바탕과 면 1.2:1 이상, 면 위 글자, 면 위 주 버튼 — 질감 면은 가장 나쁜 자리 견본으로), 제목 서체 견본(그 서체를 붙일 글자 이름마다)과 전시용 제목, 로고 세 안 × 세 크기(상단 메뉴 크기 · 파비콘 크기 16·32px · 큰 크기), 같은 견본 사진 한 장의 원본·보정, 움직임 설명(어디서·무엇이·순서 — 글로).
  - 혁신판 — 대담판 겉모습을 이어받았다는 표시 + 조작 설명(무엇을·어떻게 하면 무엇이 일어나나)과 대체 경로 목록.
  - 파격판 — 위 + 고른 수단이 쓰는 색 견본(2층 이름별)과 수단의 숫자 값 목록(예: 3D면 조명·카메라, 지도면 처음 확대 단계 — 계산값으로).
- **값은 코드에 적지 않고 계산값으로 보인다** — 설명 글에 px·hex 숫자를 쓰지 않는다.

**새 토큰 이름은 판 CSS 파일 안에서만 값을 준다** — 판마다 `src/styles/drafts/{화면}-{판}.css`를 두고, 그 안의 범위 클래스(`draft-{화면}-{판}`)에서 `--brand-surface`·`--brand-surface-foreground`·`--brand-font`·사진 톤 변수에 값을 준다. **범위 클래스는 `--font-brand`가 아니라 `--brand-font`를 덮어쓴다** — `@theme inline`은 `--font-brand`의 값을 클래스에 그대로 적어 넣어서, 범위 클래스가 `--font-brand`를 덮어써도 클래스에 닿지 않는다. 모든 판이 쓰는 이름 줄(`--color-brand-surface: var(--brand-surface);`·`--font-brand: var(--brand-font);` 같은 것)은 메인이 2층 `@theme inline`에 미리 더한다. 판만의 새 이름(전시용 제목 등)은 판 CSS 파일 안의 `@theme inline`에 판 접두로 둔다. 두 번째 색 램프처럼 1층 값이 새로 필요하면 판 CSS 파일 안에 **판 접두를 붙인 새 이름**(`--bold-cover-900`)으로 둔다 — 1층 파일의 지금 값을 바꾸지 않는다. 고른 뒤 전체 적용에서 접두를 떼고 1층으로 옮긴다. **새 서체를 비교안에서만 `next/font`로 실으면** 그 서체의 변수 클래스(`next/font`가 주는 `variable` 클래스)를 범위 클래스와 같은 요소에 붙인다 — 그 서체 변수는 클래스를 붙인 요소에서만 풀려서, `<html>`에 없으면 범위 클래스의 `--brand-font`가 빈 값을 가리킨다.

브리프 「4」의 기존 값(색 다섯·본문 서체·둥글기)과 「9」, 「12」의 규칙은 비교안이 바꾸지 않는다 — 바꿔야 할 것 같으면 바꾸지 말고 보고하게 한다. 전시용 제목 한 단계만 예외다(§1.3 3번).

### 2.5 세 판 만들기

**만드는 순서 — 대담판 먼저, 그다음 혁신판·파격판 동시에.** 지시서는 §4.3 템플릿으로 판마다 쓴다.

| 순서 | 판 | 위임 단위 | 모델 | 시험 실측(2026-10-21) |
|---|---|---|---|---|
| 1 | 대담판 | 에이전트 하나 — 자기 「브랜드」 영역 + 대상 화면(+빈 상태) + 자기 점검 | opus | 제작 약 12분, 22만 토큰 |
| 2 | 혁신판 | 에이전트 하나 — 대담판 겉모습을 복사해 이어받고 조작만 바꿈 + 자기 점검 | opus | 약 8분, 17만 토큰 |
| 2 | 파격판 | 에이전트 하나 — 대담판 겉모습을 복사해 이어받고 은유를 바꿈 + 자기 점검 | opus | 약 21분, 27만 토큰 |

- **왜 대담판이 먼저인가** — 혁신판·파격판은 ①을 품는다. 대담판이 겉모습을 정해 두면 뒤 둘은 겉모습을 다시 정하지 않고 복사해 쓴다 — 시험에서 혁신판이 8분으로 끝난 까닭이다. 셋을 한꺼번에 띄우면 벽시계 시간은 줄지만 판마다 겉모습이 제각각이 되어, 사용자가 「조작이 좋은지」와 「색이 좋은지」를 섞어 보게 된다.
- **사용자가 대담판을 뺐으면** — 혁신판·파격판이 각자 ①을 정한다(동시에).
- **혁신판·파격판을 띄운 뒤 메인은 턴을 끝낸다** — 대기 고리(sleep)로 기다리지 않는다. 에이전트가 끝나면 알림이 와서 이어진다.
- **판 에이전트가 20분 넘게 파일 변화가 없으면 프로세스를 본다** — 다른 판의 알림으로 깨어났을 때나 사용자가 진행을 물을 때, 남은 판의 폴더와 `.draft-checks/{판}/`의 수정 시각을 본다. 20분 넘게 그대로면 `ps`로 그 판의 점검 스크립트·헤드리스 브라우저(화면 없이 도는 브라우저)가 멈춰 있는지 보고, 멈췄으면 끄고 그 에이전트에 SendMessage로 「점검을 멈추고 보고를 마무리하라」고 한다. (실사고 2026-10-21 시험: 판 에이전트가 점검 스크립트를 백그라운드로 돌리고 끝나기를 기다리는 셸 고리를 짰는데, 그 고리가 자기 명령 줄과도 맞아 30분 동안 끝나지 않았다 — §2.6.)

**공유 파일 충돌을 피하는 법** — 두 에이전트가 같은 파일을 동시에 고치면 한쪽이 고친 줄을 다른 쪽이 덮는다(실사고 — 3단계 세 묶음의 공통 부품 중복, 2-1 두 묶음의 저장·조회 코드 동시 수정). 그래서 **공유 파일은 판을 띄우기 전에 한 번 손보고, 에이전트는 판 이름이 붙은 자기 파일만 쓴다.**

**공유 파일 준비는 서브 에이전트 하나(sonnet)에 맡긴다** — 아래 표의 「띄우기 전에 하는 일」은 옛 프로젝트일수록 커서(사진 찍기 스크립트 교체·`shell__bleed`·「브랜드」 영역 옮기기·셸 갈래 조사 등 여덟 가지 안팎) 메인이 직접 하면 「코딩은 위임」과 부딪힌다. 메인이 직접 하는 것은 패키지 설치(「`package.json`·잠금 파일」 행과 Playwright 설치)·개발 서버 띄우기·`.gitignore` 한 줄뿐이다. 순서는 ① 메인이 컨셉 고르기 뒤 패키지를 깔고 개발 서버를 확인한다 → ② 준비 에이전트가 표의 나머지 행을 하고, 메인이 2층에서 뽑을 「바탕 색」·「피할 단계」(§1.2)와 셸 갈래 조사 결과를 보고에 담는다 → ③ 메인이 그 보고로 판 지시서를 쓴다. 준비 지시서에는 표의 해당 행, 「판 폴더 안은 빈 껍데기만 만든다」, 재위임 금지, 「`git checkout`·`git restore` 금지」, 「명령을 백그라운드로 돌리지 마라」를 넣는다. 준비 에이전트가 고친 본 파일은 판 에이전트의 「건드린 본 파일」 수에 들지 않는다 — 메인이 준비 보고로 그 목록을 따로 안다. (2026-10-22 시험: 3단계를 지난 프로젝트에서 준비가 여덟 가지라 sonnet 하나에 맡겼고 약 3분에 끝났다.)

| 공유 파일 | 메인이 띄우기 전에 하는 일 | 에이전트는 |
|---|---|---|
| 2층 CSS 맨 끝 「비교안」 블록 | `2-semantic.css` 맨 끝 「비교안」 주석 아래에 판 CSS 파일마다 `@import` 줄을 더하고, 빈 판 CSS 파일 `src/styles/drafts/{화면}-{판}.css`를 만든다 — 화면마다 하나라, 대담판이 두 화면이면 대담판 파일은 둘이다 | 그 판의 범위 클래스·1층 새 이름·`@theme inline` 새 이름 줄을 모두 자기 판 CSS 파일 안에 둔다. 판 CSS 파일은 2층에 `@import`로 붙어 있어 문법이 틀리면 개발 서버의 모든 화면이 깨진다 — 고친 뒤 바로 한 화면을 열어 확인한다 |
| `@theme inline` 이름 줄 | 모든 판이 쓰는 이름(`brand-surface`·`brand-surface-foreground`·`brand-font`)을 2층에 미리 더한다. 제목 서체가 이미 있으면 §1.2 「제목 서체가 이미 있을 때」 2번의 중간 변수도 이때 | 판만의 새 이름은 판 CSS 파일 안의 `@theme inline`에 판 접두로 |
| 클래스 합치기 함수 `cn()` 설정 | 손대지 않는다 | 판만의 새 글자 이름을 쓰는 요소는 `cn()`을 거치지 않게 둔다. 등록은 전체 적용 때 세 곳(1층 값·2층 이름 줄·`cn()`)을 한 번에 |
| 목업 캔버스 목록 파일 손 부분(`screens.ts`의 `SCREEN_OVERRIDES`) | 세 판 주소를 `drafts`에 미리 더한다(`states: ["empty"]` — 화면 목록 상태 표에서 그 화면의 빈 상태가 「해당없음」이면 `states`를 비우고, 그 판 지시서에 「빈 상태 비교안은 만들지 마라」를 적는다) — 대담판은 첫 화면과 핵심 행동 화면 ID, 혁신판은 핵심 행동 화면 ID, 파격판은 첫 화면 ID 아래. 2-2의 고르지 않은 판 줄은 그대로 둔다 | 고치지 않는다 |
| 디자인 시스템 페이지 | §2.4대로 판별 자리와 빈 껍데기를 만든다. 「브랜드」 영역이 아예 없는 옛 페이지면 틀의 브랜드 구역부터 옮긴다(§2.4) | 자기 껍데기 파일만 채운다 |
| 비교안의 셸 갈래 | 대상 화면의 셸 갈래(상단 메뉴 없는 집중 화면 등)가 비교안 묶음의 셸과 다르면, 비교안이 대상 화면과 같은 셸 갈래로 뜨게 미리 맞춘다 — 셸을 흉내 낸 틀을 따로 짓지 않는다(2-2 §2.4). 비교안 묶음이 셸을 씌우지 않는 틀이면 판 폴더 안 `layout.tsx`가 그 셸 갈래를 씌우라고 지시서에 적는다. 묶음이 이미 한 갈래를 씌우면 갈래별 비교안 묶음(예: `drafts/(focus)/` 라우트 그룹과 그 `layout.tsx` — 라우트 그룹 이름은 주소에 안 나타나 주소는 그대로)을 만들고 판 폴더 자리를 지시서에 적는다. 대상 화면들의 셸 갈래가 여럿이면 갈래마다 | 지시서가 적은 자리에 만든다. 본 화면과 셸이 다르게 뜨면 보고에 적는다 |
| 3층 `shell__bleed` | 3층에 없는 옛 셸이면 셸 틀 `.claude/templates/app-shell/README.md` 「옛 셸에서 화면 폭 전체 면 쓰기」대로 미리 더한다(3층 한 줄 + 본문 영역 가로 넘침 자르기 + 부품 목록 색인). 더할 수 없으면 지시서에 「본문 폭 전체로 두고 보고」를 적는다 | 붙여 쓰기만 한다 — 3층과 셸은 본 파일이다 |
| 사진 찍기 스크립트 `scripts/canvas-shots.mjs` | 프로젝트에 펼쳐 둔 스크립트가 옛 판이면(`grep -c view-ready scripts/canvas-shots.mjs`가 0) 틀 `.claude/templates/mockup-canvas/scripts/canvas-shots.mjs.template`로 바꾼다 — 하네스 동기화는 틀만 바꾸고 펼쳐 둔 파일은 그대로 둔다. 옛 판은 늦게 그려지는 화면을 기다리지 않는다(§2.11) | 고치지 않는다 |

| 판끼리 같이 쓰는 부품 | — | 판마다 폴더 `drafts/_bold/`·`_innov/`·`_leap/`. 혁신·파격판은 `_bold/`에서 필요한 것을 **자기 폴더로 복사**해 쓴다 — 고르지 않은 대담판을 지워도 남은 판이 깨지지 않게 |
| 빌드 결과물 `.next` | 다 끝난 뒤 메인이 한 번 빌드한다. 실서비스 빌드 서버(`next start`)가 떠 있으면 빌드 전에 사람에게 그 서버를 꺼도 되는지 묻고 기다린다 — 복사본에서 빌드하지 않는다(`2-1-mockup.md` §2.6.3 3번) | 빌드하지 않는다(타입 검사·린트까지) |
| 개발 서버 | 개발 서버 하나를 확인하거나 띄워 주소를 지시서에 적는다(떠 있는 서버가 `next start`면 쓰지 않고 새 개발 서버) | 그 서버를 쓰고, 끄지 않는다. 자기가 띄운 프로세스만 끈다 |
| 자기 점검 기록 자리 | 프로젝트 `.gitignore`에 `.draft-checks/` 줄이 있는지 보고, 없으면 더한다 | `.draft-checks/{판}/`에만 쓴다 |

**`@import`가 듣는지 먼저 본다** — (2026-10-21 Tailwind v4 컴파일러로 시험: 파일 맨 끝 `@import`와 그 안 `@theme inline` 이름이 클래스로 생겼다. 판·버전이 다른 프로젝트를 위해 확인은 남긴다.) 메인이 위 준비를 마치면 타입 검사 전에 빌드를 한 번 돌려, 판 CSS 파일 안 `@theme inline`의 이름이 클래스로 생기는지(빌드된 CSS에 그 이름이 있는지) 본다. 실서비스 빌드 서버(`next start`)가 떠 있으면 이 빌드 전에 사람에게 그 서버를 꺼도 되는지 묻고 기다린다(위 표 「빌드 결과물」 행). 생기지 않으면 판 CSS 파일 방식을 쓰지 않는다 — `2-semantic.css` 맨 끝 「비교안」 주석 아래에 메인이 판별 블록을 미리 만들어 두고, 판 에이전트를 동시에 띄우지 않고 차례로 돌린다.

**만들 때의 세부**

- **출발점은 지금 본 화면이다** — 대담판은 2-2를 거친 본 화면 코드를 자기 비교안 폴더(`drafts/{화면}-bold/`)로 복사해 그 위에 개성을 더한다. 혁신판·파격판은 대담판 비교안을 자기 폴더로 복사해 시작한다(대담판을 뺐으면 본 화면에서).
- **브랜드 색 면은 전용 부품으로 만든다** — 판 폴더 안에 전용 부품(예: `HeroBand`·`EmptyState`)을 두고 `bg-brand-surface`는 그 부품 안에서만 쓴다. 화면 코드에 `bg-brand-surface`를 흩지 않는다 — 고른 뒤 그 부품이 본 부품이 되고, 3단계 검사 ① 15번이 부품 밖 사용을 잡는다. 대표 장면의 여러 겹 면도 겹마다 전용 부품이다.
- **화면 폭 전체 띠는 셸 본문 틀 밖으로 편다** — 셸의 본문 틀은 최대 폭(`max-w-content`)과 좌우 여백 안에 있어, 그냥 두면 띠가 넓은 화면에서는 본문 폭에서 멈추고 폰에서는 양옆이 빈다. 띠 부품의 맨 바깥 요소에 셸 클래스 `shell__bleed`(본문 틀 밖으로 셸 본문 영역 끝까지 펴는 3층 클래스 — 셸 틀 `.claude/templates/app-shell/README.md`)를 붙인다. 띠는 화면 맨 위 첫 요소로 두고, 화면이 따로 둔 컨테이너 쿼리 상자(`@container`) 안에 넣지 않는다 — 그 안에서는 폭을 그 상자 기준으로 재서 덜 펴진다. 3층에 그 클래스가 없는 옛 셸이면 메인이 판을 띄우기 전에 더해 둔다(위 표 「3층 `shell__bleed`」 행) — 3층과 셸은 본 파일이라 판 에이전트가 더하지 않는다. 메인도 더할 수 없었으면 「본문 폭 전체」로 두고 보고에 적는다.
- **로고** — 세 안 모두 리액트 부품(`fill="currentColor"`)으로 판 폴더에 둔다. 파비콘 파일은 고른 뒤 만든다(§2.9).
- **사진 톤** — 사진 톤 클래스는 판 CSS 파일의 범위 클래스 아래에서만 듣게 둔다. 본 `3-components.css`의 본 규칙은 고치지 않는다.
- **움직임** — 대담판은 모션 토큰 이름(`duration-*`·`ease-*`)으로만, CSS로. 동작 줄이기 설정이면 꺼진다(전역 규칙이 이미 있다 — `bootstrap-project.md` §1.4). 옛 전역 규칙이 지연(`animation-delay`·`transition-delay`)을 0으로 두지 않으면 차례 움직임의 지연이 남아 동작 줄이기에서도 요소가 늦게 나타난다 — 판 CSS의 범위 안에서 지연도 0으로 막는다. 혁신판·파격판의 `motion` 숫자는 판 폴더 안 한 파일(`_innov/motion.ts` 등)에 모으고, 비교안 맨 바깥에 `motion`의 동작 줄이기 설정(`MotionConfig reducedMotion="user"`)을 둔다.
- **무거운 라이브러리** — 비교안 주소에서만 동적 import로 부르고, 받는 동안 로딩 뼈대를 보인다(§1.5). 은유 부품이 첫 그림을 다 그리면 `data-view-ready="1"`을 낸다 — 목업 캔버스 사진 찍기가 이것을 기다린다(§2.11).
- **데이터는 본 화면과 같은 저장·조회 코드를 거친다** — 2-2 §2.4와 같다.

**지시서에 꼭 넣을 것** — 이번 규칙은 자동으로 들어오지 않는 자료(이 문서·design-system 새 절·`visual-polish.md` I 묶음)에만 있으니 메인이 걸러 넣는다 (실사고: 스킬에만 있던 규칙을 에이전트가 몰라 어겼다).

- `2-1-mockup.md` §2.6.3의 「화면 작업 지시서에 꼭 넣을 문장」 전부(2층 이름 클래스만 · 목록 파일과 `?state=` · 브라우저 자동화로 확인 완료 결론 금지 · 떠 있는 서버가 개발 서버인지 확인하고 쓰기, 네가 띄운 프로세스만 끈다 · 강조색 주 버튼 하나 · 재위임 금지). **단 두 문장은 비교안에 맞게 바꿔 넣는다** — 둘 다 본 파일을 고치라는 말이라 아래 「건드린 본 파일 0개」와 부딪힌다.
  - 「대응 없는 요소는 전용 부품으로 만들어 부품 목록에 등록하라」 → 「대응 없는 요소는 판 폴더 안 전용 부품으로 만든다. 부품 목록(`docs/components.md`)은 고치지 말고, 등록할 줄을 보고에만 적어라.」
  - 「필요한 주소가 없으면 주소 모음 파일에 더하고 보고하라」 → 「필요한 주소가 주소 모음 파일에 없으면 고치지 말고 멈추고 보고하라.」
- 파일 보호 두 줄(`AGENTS.md` 위임 절) — 「`git checkout`·`git restore`로 파일을 되돌리지 마라 — 다른 판 에이전트가 고친 변경까지 지워진다.」「작업 중간에 자동 임시 저장 커밋이 생길 수 있다 — 정상이니 되돌리지 마라.」 혁신판·파격판은 같은 작업 폴더에서 동시에 돈다.
- 비교안 폴더 규칙 — 「네 판 폴더(`drafts/_{판}/`·`drafts/{화면}-{판}/`)와 네 판 CSS 파일(`src/styles/drafts/{화면}-{판}.css`)과 네 「브랜드」 껍데기 파일만 고쳐라. 다른 판 폴더는 읽기만 하라. 1·2층 토큰 파일과 본 부품, 본 화면, 목업 캔버스 목록 파일은 고치지 마라. 패키지를 깔지 마라. 빌드(`next build`)를 돌리지 마라. 보고에 네가 건드린 본 파일 수(0이어야 한다)를 적어라.」 메인이 미리 손본 공유 파일은 이 수에 들지 않는다 — 메인이 그 목록을 따로 안다.
- 그 판의 허용 범위(§1.4 표의 그 판 열)와 바닥 금지 전부(§1.3).
- **「이렇게 밀어라」 문장** — 「하지 마라」만 주면 에이전트는 가장 안전한 쪽(조용한 화면)으로 모인다. 그래서 함께 넣는다: 「방향 한 문장을 먼저 정하고 모든 선택을 거기에 맞춘다. 서체·배치·색·움직임 중 한두 축을 과감하게 민다. 대표 장면 안에서 격자를 깨는 요소 한두 개를 의도적으로 둔다.」
- 강조색 원칙 문장(2-2 §2.4와 같음, 바뀐 조작·은유 안에도 같다 — §1.3 2번)과 브랜드 색 자리 목록·대비 3:1/4.5:1·바탕과 면 1.2:1·진한 면이면 주 버튼은 면 밖(design-system `SKILL.md` 「브랜드 색은 어디에 쓰나」), 그리고 메인이 2층에서 뽑은 「바탕 색」과 「피할 단계」(§1.2 「브랜드 색 단계 고르기」).
- 판 CSS 문법 확인 — 「판 CSS 파일은 2층에 `@import`로 붙어 있어 문법이 하나라도 틀리면 개발 서버의 모든 화면(본 화면 포함)이 깨진다. 판 CSS를 고친 뒤 바로 한 화면을 열어 확인하라.」 (실사고 2026-10-21 시험: 닫는 괄호 하나가 더 들어가 모든 화면이 몇 초 동안 500 오류를 냈다.)
- 셸 갈래 — 위 표 「비교안의 셸 갈래」 행에서 정한 자리와 「셸을 흉내 낸 틀을 짓지 마라. 본 화면과 셸이 다르게 뜨면 보고에 적어라」.
- 바깥 파일 — 「바깥 사이트에서 파일을 받지 마라.」 대담판(과 글자 로고를 다시 만드는 판)만 예외 한 줄 — 「글자 로고를 패스로 바꿀 때 그 서체 파일(무료 서체 사이트에서 그 글자만)을 받아도 된다. 받은 파일은 커밋하지 않는다. 못 받으면 `<text>`로 두고 보고하라.」
- (혁신판·파격판) 「동시에 도는 다른 판 폴더에서 나온 린트 오류는 고치지 말고 보고만 하라.」
- 고른 컨셉 세 줄과 그 판의 컨셉(대담판은 방향 한 문장과 쓸 기법).
- 개발 서버 주소와 자기 점검 절 문장(§2.6).
- **화면 속 자리를 예로 들 때는 예시 데이터에 맞춘다** — 「오늘」이 아니라 「예시 데이터의 가장 최근 기록」처럼 쓴다. 예시 데이터에 오늘 기록이 없으면 「오늘 자리」 예시는 화면에서 찾을 수 없다(2026-10-21 시험).
- 보고 항목(§4.3 done-when) — 특히 판마다 브리프 「13」 표 초안, 자기 점검 회차표, 새 기능 후보, (파격판) 바뀌는 화면과 늘어나는 일.

### 2.6 자기 점검

각 판 에이전트가 다 만든 뒤 자기 판을 브라우저 자동화로 열어 찍고, 눌러 보고, 고친다. 만드는 손이 눈을 감고 있으면 조작·은유처럼 직접 해 봐야 아는 것을 못 고친다. 판정·판 고르기는 그대로 사람 몫이다. 이 예외는 `AGENTS.md` 「검증」 절의 「예외 — 2-3 비교안 자기 점검」 줄이 연다.

- **누가** — 2-3에서 비교안을 만드는 서브 에이전트만. 메인과 전체 적용 에이전트는 하지 않는다. 다른 단계로 넓히지 않는다.
- **무엇을** — 자기 판을 열어 스크린샷을 찍고, 고른 조작대로 직접 해 보며 고친다(누르기·길게 누르기·끌기, 단축키 입력, 여럿 고르기 등). 묶음은 넷: ① 데스크톱 폭 ② 폰 폭(실제 터치 이벤트) ③ 동작 줄이기 켬 ④ 키보드만. 혁신판·파격판은 ⑤ 고른 수단이 안 될 때(WebGL 끔·카메라나 마이크 권한 거부·지도 못 불러옴 등)의 대체 화면을 더한다.
- **도구** — 프로젝트에 이미 깔린 Playwright(목업 캔버스 그림 찍기용)를 쓴다. 새로 깔지 않는다. 3D는 크로미움을 `--use-angle=swiftshader`로, 카메라·마이크는 가짜 장치(`--use-fake-device-for-media-stream`)로 띄운다. 서버는 지시서에 적힌 개발 서버를 쓴다 — 로컬 개발 서버 밖의 사이트는 열지 않는다.
- **시간 상한과 대기 고리 금지** — 점검 스크립트는 앞에서(foreground) 돌리고, 한 번에 5분을 넘기면 끊는다. 끝나기를 기다리는 셸 고리(`sleep`·`pgrep` 고리)를 짜지 않는다. `AGENTS.md`의 대기 고리 금지는 메인에게 하는 말이라 서브 에이전트 지시서에는 들어가지 않으니 이 문장을 지시서에 넣는다. (실사고 2026-10-21 시험: 판 에이전트가 점검 스크립트를 백그라운드로 돌리고 `pgrep -f`로 끝나기를 기다리는 고리를 짰다. 스크립트는 첫 장에서 오류로 이미 끝났는데, 그 고리가 자기 명령 줄과도 맞아 30분 동안 끝나지 않았다. 회차 상한은 고리가 끝나지 않으면 쓸모가 없다.)
- **회차 상한** — 대담판 3, 혁신판 4, 파격판 5회. 회차는 「찍고 → 고친」 한 번이다. 고친 뒤 고치지 않고 찍기만 하는 확인 촬영 1회는 세지 않는다. 같은 오류로 2회 막히면 멈추고 보고한다. 스크린샷은 절반 크기로 찍는다.
- **기록 자리** — 스크린샷과 점검 스크립트는 프로젝트 `.draft-checks/{판}/`(git에 올리지 않음). 이름은 `{판}-{회차}-{묶음}.png`. 사람이 나중에 같은 자리를 비교해 볼 수 있다.
- **보고에 쓰는 것** — 회차마다 「보인 것」과 「고친 것」 표. 「확인 완료」「잘 나왔다」「문제없다」 같은 결론은 쓰지 않는다.
- **메인이 하지 않는 것** — 메인은 스크린샷을 열어 판의 좋고 나쁨을 판단하지 않는다. 사용자에게 폴더 위치와 회차표만 전한다.

**지시서에 넣을 문장**

> 「자기 점검 — 다 만든 뒤, 이미 떠 있는 개발 서버 `{주소}`에서 네 판을 Playwright로 열어 찍고 눌러 보며 고쳐도 된다. 묶음은 데스크톱 폭·폰 폭(터치)·동작 줄이기·키보드{혁신·파격판이면: ·고른 수단이 안 될 때의 대체 화면}. 회차는 최대 {N}회(고치지 않는 확인 촬영 1회는 따로), 같은 오류로 2회 막히면 멈추고 보고하라. 점검 스크립트는 앞에서(foreground) 돌리고 한 번에 5분을 넘기면 끊어라. 끝나기를 기다리는 셸 고리(`sleep`·`pgrep` 고리)를 짜지 마라. 스크린샷은 `.draft-checks/{판}/`에 둔다. 이것은 만드는 손의 점검이다 — 보고에 「확인 완료」「잘 나왔다」 같은 결론을 쓰지 말고, 회차마다 보인 것과 고친 것만 표로 적어라. 위 「브라우저 자동화로 확인 완료 결론 금지」 문장은 이 결론 금지로 지킨다.」

### 2.7 사용자 선택 (사용자 몫)

메인은 판 보고를 모두 받으면 화면 밖 검사를 돌린다 — 빌드 한 번 → 린트 → 타입 검사, 본 코드가 비교안 폴더를 불러오는 곳 0건(`2-2-mockup-design-upgrade.md` §2.4의 grep), 무거운 라이브러리(3D·지도 등)를 부르는 파일이 그 비교안 폴더 안뿐인지. 떠 있는 서버가 `next start`(실서비스 빌드 서버)면 그 서버를 쓰지 않고, 빌드 전에 사람에게 그 서버를 꺼도 되는지 묻고 기다린다(`2-1-mockup.md` §2.6.5 3번). 복사본에서 빌드하지 않는다(`2-1-mockup.md` §2.6.3 3번). 그다음 비교안이 붙은 화면의 캔버스 사진을 찍고(§2.11) 아래를 한 메시지로 낸다.

- **볼 주소** — 목업 캔버스(`/dev/canvas`)와 디자인 시스템 페이지(`/dev/design-system`). 개발 서버가 떠 있지 않으면 띄워 주소를 알린다.
- **판마다 요약** — 방향 한 문장, 무엇이 바뀌었나(사용자 말로), 바닥 처리(대체 경로·동작 줄이기·폰 터치·키보드·고른 수단이 안 될 때의 대체 화면).
- **자기 점검 요약** — 「보조 AI가 판마다 몇 번 열어 보고 무엇을 고쳤는지」와 스크린샷 폴더 위치. 「잘 나왔다」는 말은 하지 않는다.
- **판마다 고르면 늘어나는 일** — 대담판 「거의 없음」, 혁신판 「3단계에서 상태 화면 몇 개」, 파격판은 판 보고 ⑫를 사용자 말로(바뀌는 화면 이름과 늘어나는 일). 3단계를 지난 프로젝트에서 대담판이 제목 서체나 로고를 바꿨으면, 대담판(과 그 겉모습을 이어받은 판) 줄에 「고르시면 이미 있는 화면 전부의 제목 서체·상단 메뉴 로고가 함께 바뀝니다」를 붙인다(§2.12 3번). **고르기 전에 이 비용을 보여 주는 것이 핵심이다.**
- **새 기능 후보** — 판 보고 ⑪을 사용자 말로, 「채택하려면 기능 목록에 더해야 합니다」 한 줄.
- **임시로 정한 것·줄인 자리** — 에이전트가 브리프에 없는 값을 임시로 고른 것, 대표 장면 때문에 줄이거나 뺀 정보 줄.
- **섞기** — 「겉모습(색·서체·로고·질감)은 판끼리 섞으셔도 됩니다. 조작 방식과 은유는 한 판의 것을 고릅니다.」 조작·은유를 섞으면 사실상 새 판이라 다시 만들어야 한다. 로고는 세 안 중 따로 골라도 된다.
- **사람이 봐 주실 것** — 판마다 강조색 주 버튼(또는 주 행동을 맡은 조작 대상)이 먼저 눈에 들어오는지, 브랜드 색 면이 버튼처럼 보이지 않는지, 바뀐 조작 방법이 실제로 해 보면 어떻게 느껴지는지(폰 위주 서비스면 폰으로). AI는 화면을 못 보니 이것은 사람이 본다.

받은 수정은 2-2 §2.6과 같은 차례로 고친다(`2-1-mockup.md` §2.7 「코멘트 반영」·「고치는 손」). 고르기 전이라 고칠 곳도 그 판의 폴더와 판 CSS 파일 안이다. 바뀐 결정은 그 자리에서 브리프에 적는다.

AI는 어느 판이 낫다고 대신 판정하지 않는다. 추천을 물으면 브리프 「1」의 브랜드 인상과 「10. 가치 우선순위」에 비춰 근거를 대고 하나를 권하되, 고르는 것은 사용자다.

**혁신판을 고르면** — 화면 목록은 그대로이고, 그 화면 행의 「주 행동」 칸만 「명령창에 한 줄 쓰기(전용 부품)」·「사진 여러 장 한 번에 고르기(전용 부품)」처럼 조작 부품을 가리키게 고친다.

**파격판을 고르면 — 2-1 화면 목록으로 일부 되돌아가기** — `화면 대조 끝:` 전에만 한다(그 뒤 프로젝트는 §2.12).

1. 메인이 판 보고 ⑫의 「바뀌는 화면」을 `feature-list.md` 6절 화면 목록의 행과 맞대 「바뀌는 화면 표」(화면 ID · 지금 · 은유를 따르면 · 만드는 때)를 만든다.
2. 사용자에게 그 표를 보이고, 합치거나 빼는 화면·메뉴 구조(8절) 변경을 정한다. 새 기능 후보를 채택하면 1~2절 기능 목록·범위 결정에 더한다.
3. 메인이 6~10절을 고친다. 2단계에 이미 만든 화면이 바뀌면 그 행의 「만드는 때」를 `3단계 — 은유 따라 다시`로 바꾼다(2-3 전체 적용은 고른 판의 대상 화면만 옮긴다).
4. 머리에 한 줄을 더한다: `은유 반영: YYYY-MM-DD — 파격판 「{컨셉}」, 바꾼 화면 {화면 ID 목록}`. `확정:` 줄은 지우지 않는다. 이 줄이 「2-1을 다시 열었다가 닫았다」는 표시라, 대화를 비웠다가 돌아와도 이어 갈 자리를 안다.
5. 그다음 §2.8 브리프 기록으로 간다.

### 2.8 브리프에 기록

사용자가 고르면 메인이 직접 기록한다 — 브리프는 메인만 쓴다 (SKILL.md §3). **값은 §2.7 보고 요약에서 옮기지 않는다** — 에이전트가 고른 판 코드에서 뽑아 보고에 낸 「13」 표 초안(§4.3 done-when ⑦)과 고른 판 코드(판 CSS 파일·전용 부품)에서 옮긴다. 메인은 브랜드 색 값과 서체 이름 몇 개를 고른 판 코드와 표본 대조한다 (2-2 §2.7과 같은 이유 — 보고 요약으로 적었다가 전체 적용이 사람이 고른 것과 달라진 실사고가 있다).

1. **「13. 개성」** — 표를 항목마다 `사용자 확정`과 확정일로 채운다. 「고른 판」에 고른 판과 섞은 내용(예: 「혁신판 — 겉모습은 대담판 그대로」). 조작 방식·은유·대체 경로·쓰는 수단과 들인 기술은 혁신판·파격판만, 아니면 「바꾸지 않음」. 대표 장면 2가 아직 없는 화면이면 「3단계에서 만들 때」를 붙인다. 「4」의 값을 다시 적지 않고 「「4」의 브랜드 면 색」처럼 가리킨다 (§4.1). 표 아래 `고른 컨셉(만드는 중):` 줄이 있으면 지운다.
2. **「4. 확정 브랜드 자산」** — 「색 — 브랜드 면」 행(hex, 강조색과 같은 계열인지, 바탕과 면·면 위 글자·면 위 주 버튼 대비 — 질감 면이면 가장 나쁜 자리 값), 「서체 — 제목」 행(이름·무료 여부·받은 굵기 하나), 「로고」 행(고른 안과 한 줄 설명 — 파일 위치는 적지 않는다), 이미지·영상 계획 표 아래 「사진 톤:」 줄. 「마스코트」 행은 `추후 결정`으로 둔다.
3. **「8. 모션·인터랙션 방향」** — 고른 대표 움직임을 움직임마다 「대표 움직임: <어디서>」 행으로 말로(어디서·무엇이·순서), 혁신판·파격판이면 「조작에 붙는 움직임」 행도. `사용자 확정`과 확정일. 사용자가 고른 것이라 바로 `사용자 확정`이다. ms 값은 적지 않는다.
4. **고르지 않은 판은 그대로 둔다** — 3단계 `화면 대조 끝:` 때 2-2의 고르지 않은 판과 함께 지운다(§4.5). 그 시점이 이미 지난 프로젝트면 §2.12 1번대로 고른 직후에 지운다.

### 2.9 전체에 적용하기

다 고른 뒤 한 번 한다. **고른 값을 토큰·부품에 넣고, 고른 판 화면을 본 화면 자리로 옮긴다.** 대상 화면이 아닌 화면은 손대지 않는다 — 로고가 상단 메뉴에 들어가고 제목 서체가 정한 글자 이름에 붙으면서 저절로 따라온다. 지시서는 §4.4.

**공통 앞부분(모든 판)**

1. **판 CSS 파일 값 → 1·2층 토큰** — 고른 판 CSS 파일의 `--brand-surface`·`--brand-surface-foreground`·`--brand-font` 값을 2층 `:root`로, 사진 톤 보정 값을 1층 변수로 옮긴다. 판 접두가 붙은 1층 새 이름(두 번째 색 램프 등)은 접두를 떼고 1층으로 옮긴다. 옮긴 뒤 고른 판의 범위 클래스와 판 CSS 파일, 그 `@import` 줄을 지운다. 프로젝트 `AGENTS.md` 연결 정보에 그 범위 클래스 이름이 적혀 있으면(세 층 파일 설명 줄 등) 그 이름도 함께 지운다 — 남으면 뒤 에이전트가 없는 클래스를 찾는다. 고르지 않은 판의 CSS 파일과 `@import` 줄은 3단계까지 남긴다(뒤 단계를 이미 지났으면 §2.12 1번).
2. **제목 서체 로딩** — design-system `font-loading.md` §4대로(구글 폰트는 `next/font/google`, 라틴 조각 미리 받기 끄기 · npm 폰트는 조각화 CSS). 굵기 하나만 받는다. 고르지 않은 판의 서체 로딩은 그 판 폴더 안에만 둔다.
3. **로고 부품과 파비콘** — 고른 로고 부품을 본 부품 자리(`src/components/`)로 옮기고 상단 메뉴·첫 탭 앱바의 로고 자리에 넣는다. 파비콘은 CSS 변수를 못 써 색 값이 파일 안에 들어가므로 `public/brand/`에 두고 메타데이터로 잇는다 — `src/app/` 안에 두면 검사 ① 1번이 잡는다. 16px에서 뭉개지는 안이면 단순판을 파비콘으로 쓴다.
4. **브랜드 색 면 전용 부품 → 본 부품** — 판 폴더의 전용 부품(띠·여러 겹 면·빈 상태 그림 등)을 `src/components/`로 옮긴다. 3단계가 쓸 자리(완료 화면 위쪽 면 등)의 부품은 지금 만들지 않는다 — 3단계가 그 화면을 만들 때 만든다.
5. **사진 톤 클래스** — 3층 `3-components.css`에 사진 톤 클래스 하나를 두고 견본 사진 자리(목록 그림·대표 이미지)에 붙인다. 부품 목록(`docs/components.md`)에 그 클래스를 등록한다(검사 ① 4번).
6. **고른 판 화면 → 본 화면 자리** — 대상 화면 코드를 본 화면 파일 자리로 옮긴다. 판 폴더의 부품 대신 본 부품을 부르게 하고 범위 클래스를 떼어 낸다. 목업 캔버스 목록 파일에서 고른 판을 `drafts`에서 뺀다.
7. **연결 정보** — 프로젝트 `AGENTS.md` 「디자인 시스템 연결 정보」의 「적용 규칙 요약」에 적는다: `BRAND_PARTS:` 줄(브랜드 색 면을 쓸 수 있는 전용 부품 파일 경로, 공백으로 나눔 — 검사 ① 15번이 읽는다)과 `font-brand`를 붙이는 글자 이름(브리프 「13」 「제목 서체를 쓰는 글자」 그대로 — 전역 제목 규칙이면 그 태그 범위). 연결 정보 어디에도 비교안 범위 클래스 이름(`draft-…`)은 적지 않는다 — 비교안이 지워지면 낡은 안내가 된다. 이미 적혀 있으면 지금 남아 있는 비교안 것만 남긴다.
8. **디자인 시스템 페이지** — 「브랜드」 영역이 「지금 값」 하나로 돌아간다. 고르지 않은 판의 자리와 껍데기는 그 비교안과 함께 3단계에서 지운다.

**판별로 더하는 일**

| 판 | 더하는 일 |
|---|---|
| 대담판 | ① 판 CSS 파일의 값을 1·2층으로 옮기고 판 접두를 뗀다(공통 1번) ② 면 여러 겹을 그리는 부품들을 `src/components/`로, 모두 `BRAND_PARTS:`에 ③ 질감 클래스를 3층에 두고 부품 목록에 등록 ④ 전시용 제목을 판 접두 이름(`--text-bold-display` 등)에서 `--text-display`로 바꿔 세 곳(1층 값·2층 이름 줄·`cn()`)에 등록 ⑤ 움직임 여럿을 모션 토큰 이름으로 — 비교안이 판 접두 탄성 곡선(`--ease-bold-spring` 등)을 썼으면 2층 `ease-*`에 이름 하나를 더해 옮기고, 프로젝트 `AGENTS.md`의 움직임 규칙 줄(예: 「spring 없음」)을 고친다 |
| 혁신판 | 대담판 ①~⑤ + ⑥ 조작 부품(예: 끌어 놓아 일정 옮기기·명령창·여럿 고르기 막대)을 `src/components/`로 — 대체 경로 버튼과 키보드 처리를 같은 부품 안에 ⑦ `motion` 숫자는 `lib/motion.ts` 한 파일로, 앱 맨 바깥에 동작 줄이기 전역 설정(`MotionConfig reducedMotion="user"`) ⑧ 화면 목록 「주 행동」 칸이 그 조작 부품을 가리키는지 확인 |
| 파격판 | 대담판 ①~⑤ + 혁신판 ⑥·⑦ + ⑨ 은유 부품을 `src/components/{수단}/`(예: `scene/`·`board/`)로. 무거운 라이브러리를 쓰면 동적 import·로딩 뼈대·고른 수단이 안 될 때의 대체 화면·목록 보기 대체 경로를 함께 ⑩ 수단의 숫자 값은 `lib/{수단}.ts` 한 파일로, 색은 2층 이름 `--{수단}-{역할}`로 (§1.5) ⑪ 무거운 라이브러리를 들였으면 연결 정보에 `HEAVY_LIBS:`·`HEAVY_PARTS:` 두 줄(검사 ① 16번이 읽는다) |

**위임** — 서브 에이전트 하나. 대담판·혁신판은 sonnet(정해진 것을 옮기는 일), 파격판은 opus(수단의 값 자리를 새로 정하고 구조가 바뀌는 일). 메인은 위 순서, 고른 것(섞었으면 섞은 내용), 브리프 「13」·「4」·「8」의 해당 행을 따르라는 줄을 지시서에 넣는다. 지시서에는 `2-1-mockup.md` §2.6.3의 「화면 작업 지시서에 꼭 넣을 문장」 전부와 이 몫의 한 문장을 넣는다:

- 2-3 몫 한 문장: 「고른 값을 1·2층 토큰과 본 부품에 넣고 고른 판 화면을 본 화면 자리로 옮겨라. 대상 화면 말고 다른 화면은 손대지 마라. `bg-brand-surface`는 `BRAND_PARTS:`에 적은 부품 안에서만 쓴다{파격판이면: , 무거운 라이브러리는 `HEAVY_PARTS:`에 적은 부품 안에서만 부른다}. 보고에 바꾼 토큰·부품 목록, `BRAND_PARTS:` 줄{파격판이면: 과 `HEAVY_LIBS:`·`HEAVY_PARTS:` 줄}, 본 코드와 연결 정보에 남은 고른 판 범위 클래스 이름 수(0이어야 한다)를 담아라.」

**고르지 않은 판** — 3단계 `화면 대조 끝:` 때 지운다. 지우는 목록은 §4.5다 — 판 폴더(`_bold/` 등)와 비교안 화면, 판 CSS 파일과 그 `@import` 줄, 「브랜드」 껍데기와 자리, 목업 캔버스 목록 파일의 그 주소, 고르지 않은 판만 쓰던 패키지(`npm uninstall`과 `adr.md` 한 줄), 연결 정보에 적힌 그 범위 클래스 이름.

### 2.10 확인

- **화면 밖 검사** — 메인이 빌드·린트·타입 검사를 돌리고, 배포 전 디자인 규칙 검사를 프로젝트 최상위에서 `bash .claude/scripts/design-check.sh --only 1,2,7,10,12,15,16`으로 미리 한 번 돌린다.
  - 1·2·7·15번은 0건이어야 한다. 15번이 「해당 없음」이면 `BRAND_PARTS:` 줄을 빠뜨린 것이다 — 이 자리에서는 브랜드 색을 들였으니 해당 없음이 나오면 안 된다.
  - 10번(동작 줄이기 전역 규칙) — 혁신·파격판은 `motion` 전역 설정까지 눈으로 본다.
  - 12번은 주 버튼이 1개가 아닌 화면이 모두 화면 목록 「주 행동」 칸으로 설명되어야 한다(브랜드 색 면은 `primary`가 아니라 세지 않는다). 주 버튼이 0개인 화면이 조작 부품 화면이면 「주 행동」 칸이 그 부품을 가리키는지 본다.
  - 16번(무거운 라이브러리 자리) — 0건. 무거운 라이브러리를 들이지 않았으면 「해당 없음」이 맞다.
  - 본 코드가 비교안 폴더를 불러오는 곳 0건과 본 화면에 남은 범위 클래스 0건도 확인한다. 비교안을 옮겼으면 타입 검사 전에 빌드를 먼저 다시 돌린다(2-2 §2.8과 같은 이유).
- **화면 문구 검토 한 번** — 2-3은 문구를 새로 정하지 않지만, 띠·빈 상태 그림·조작 안내·은유 화면에 붙은 글이 있으면 메인이 바뀐 화면 코드 경로를 `ux-writing-reviewer` 에이전트에 넘긴다. 기준은 브리프 「2. 보이스 앤 톤」이다.
- **목업 캔버스 사진을 다시 찍는다** — 전체(§2.11).
- **사람이 목업 캔버스에서 본다** — 목업 캔버스 주소를 주고, 대상 화면과 로고가 들어간 상단 메뉴, 사진 톤이 씌워진 목록을 봐 달라고 한다. 「화면마다 강조색 주 버튼(또는 주 행동을 맡은 조작 대상)이 하나씩 보이는지, 브랜드 색 면이 버튼처럼 보이지 않는지」, 혁신·파격판이면 「바뀐 조작을 직접 해 보기」, 무거운 라이브러리를 들였으면 「그 화면이 처음 뜨는 속도는 실서비스 빌드로 봐야 정확하다(개발 서버는 느리다)」를 붙인다. AI가 열어 본 것으로 확인 완료라 하지 않는다.

코드 정리는 여기서 하지 않는다 — 3단계 끝에 한 번이다(SKILL.md 「2·3단계는 한 브랜치로 간다」).

### 2.11 목업 캔버스 사진 다시 찍기

목업 캔버스는 멀리서 볼 때 미리 찍어 둔 그림(`npm run canvas:shots`)을 보여 준다. 토큰을 바꿔 화면이 달라졌는데 다시 찍지 않으면 캔버스에 옛 그림이 남는다. 2-3에서는 두 자리에서 찍는다(2-2의 두 자리는 2-2 문서에 있다).

| 자리 | 찍는 범위 |
|---|---|
| 세 판 완성 뒤(§2.7 사용자 선택 전) | 비교안이 붙은 화면 ID만 |
| 전체 적용 뒤(§2.10 사람 확인 전) | 전체 — 토큰이 바뀌어 모든 화면이 달라졌다 |

- **늦게 그려지는 화면은 다 그린 뒤 찍는다** — 은유 부품(3D 장면·게임판 등)은 첫 그림을 그리면 `data-view-ready="1"`을 내고, 그림 찍기 스크립트가 그것을 기다린다(지도 화면의 `data-map-ready="1"`과 같은 방식). 3D를 쓰면 스크립트가 크로미움을 `--use-angle=swiftshader`로 띄운다.
- **찍은 때를 보인다** — 캔버스의 멀리서 보기 카드 귀퉁이에 「찍은 때」가 작게 보인다. 그림이 화면 파일보다 오래돼도 사람이 알아볼 수 있다.

### 2.12 뒤 단계를 이미 지난 프로젝트에서 할 때

`feature-list.md` 머리에 `화면 대조 끝:` 줄이 있거나 그 뒤 단계까지 간 프로젝트에서 사용자가 2-3을 부른 경우다. 옛 템플릿 프로젝트에 개성을 나중에 들이는 때가 대개 이렇다. 절차는 §2.1~§2.10 그대로이고, 다섯이 다르다.

1. **고르지 않은 판은 고른 직후에 지운다** — 기본 절차는 3단계 `화면 대조 끝:` 때 지우지만(§4.5), 그 자리는 이미 지났다. 그래서 §2.9 전체 적용을 마치면 같은 위임 안에서 고르지 않은 판의 것을 모두 지운다 — §4.5 「3단계 `화면 대조 끝:`까지 남는 것」 목록 전부(비교안 화면·판 폴더·판 CSS 파일과 `@import` 줄·「브랜드」 껍데기와 자리·목업 캔버스 목록 파일의 그 주소·그 판만 쓰던 패키지·연결 정보에 적힌 그 범위 클래스 이름). 차례와 확인은 `3-frontend-build.md` §2.3.2 2번과 같다(본 코드가 비교안 폴더를 불러오는 곳 0건 확인 → 지움 → 빌드 → 타입 검사). 2-2의 고르지 않은 판이 아직 남아 있으면 그것도 이때 같이 지운다.
2. **대표 장면 2가 이미 있으면 그 화면도 다듬는다** — 핵심 행동 화면이나 완료 화면처럼 「13」의 대표 장면 2 자리가 이미 코드에 있으면 「3단계에서 만들 때」를 붙이지 않는다. 대담판이 그 화면도 대상으로 만든다. 그 자리의 브랜드 색 면 전용 부품은 §2.9에서 본 부품으로 옮기고 `BRAND_PARTS:`에 더한다.
3. **이미 있는 나머지 화면은 토큰·부품으로만 따라오게 둔다** — 로고(상단 메뉴), 제목 서체(정한 글자 이름이나 전역 제목 규칙), 사진 톤 클래스(견본 사진 자리)는 이미 있는 화면에 저절로 들어간다. 그 밖에 화면마다 소재·브랜드 색을 더하지 않는다 — 대표 장면이 아닌 화면은 2-2 규칙대로 조용히 둔다. 빈 상태 그림처럼 자리 목록에 넣은 자리가 이미 여러 화면에 있으면, 그 자리 부품 하나를 고치고 화면들이 그 부품을 부르게만 한다. 화면을 다시 만들지 않는다. 손댄 화면 목록을 보고에 받는다. 이렇게 저절로 따라오는 만큼, 대담판이 제목 서체나 로고를 바꾸면 이미 있는 화면 전부가 바뀐다 — 판 고르기 때 알린다(§2.7 「판마다 고르면 늘어나는 일」).
4. **기본은 대담판·혁신판만 낸다** — `화면 대조 끝:` 뒤의 `feature-list.md`는 갱신하지 않는 기록이라, 파격판의 「화면 목록 다시 열기」(§2.7)를 할 자리가 없다. 사용자가 파격판을 콕 집어 원하면 낸다 — 그 판을 고르면 은유가 바꾸는 화면을 같은 전체 적용 위임 안에서 다시 만들고(opus), 화면 목록은 고치지 않고 브리프 「13」 「은유」 행에 「바꾼 화면」을 적는다. `은유 반영:` 줄은 적지 않는다.
5. **공유 파일 준비에서 옛 것을 먼저 맞춘다** — 이런 프로젝트는 2-3 문서가 「이미 있다」고 보는 것이 옛 모양인 경우가 많다. §2.5 공유 파일 표의 세 행을 판을 띄우기 전에 본다 — 디자인 시스템 페이지 「브랜드」 영역(없으면 틀에서 옮김, §2.4), 3층 `shell__bleed`(옛 셸이면 메인이 더함), 사진 찍기 스크립트(옛 판이면 틀로 바꿈). 비교안의 셸 갈래도 같은 표대로 맞춘다.

확인은 §2.10 그대로이고, 3단계 배포 전 검사를 이미 돌린 프로젝트라 `design-check.sh` 검사 전체를 한 번 다시 돌린다. 이미 배포한 프로젝트면 사람이 목업 캔버스에서 본 뒤에 다시 배포한다.

### 4.2 트렌드 조사 지시서 템플릿

메인이 채워 sonnet 서브 에이전트 지시서 본문으로 넘긴다 — 지시 파일을 따로 두지 않는다. `{ }`는 프로젝트마다 바뀌는 자리다.

```markdown
# 표현 기법 트렌드 조사 — {프로젝트}

<direction>
{서비스 한 줄 — 예: 동네 이웃끼리 중고 물건을 사고파는 앱}의 첫 화면을 더 과감하게 꾸미려 한다. 같은 성격의 서비스({비슷한 유형 — 예: 중고 거래·동네 커뮤니티 앱})가 최근 쓰는 **표현 기법** 5~8개를 실제로 연 사례로 모아라. 미리 아는 유행 목록으로 채우지 말고, 연 페이지에서 본 것만 적는다.

결과는 아래 표 하나로 낸다. 후보마다 한 줄.

| 기법(쉬운 말) | 어떤 모습인가 한 줄 | 본 사례(이름과 주소) | 확인 방법 | 본 날짜 | 이 서비스에 맞나 한 줄 |
|---|---|---|---|---|---|

- 「확인 방법」은 「화면으로 확인(스크린샷 경로)」 / 「움직임 컷으로 확인(스크린샷 경로)」 / 「글로만 확인」(앱스토어 소개글 등) 중 하나.
- 「본 날짜」는 페이지에 날짜가 있으면 그 날짜, 없으면 「날짜 모름」.
- 기법은 쉬운 말로 쓴다(예: 「굵은 제목 + 비대칭 배치」, 「카드 위 부드러운 빛 번짐」).

{Aside가 있으면:
```

### 4.3 판 지시서 템플릿

대담판 기본형에, 혁신판·파격판은 아래 「더하는 블록」을 붙인다. 메인이 채워 판마다 opus 서브 에이전트 지시서 본문으로 넘긴다. 「개성 항목」은 메인이 `visual-polish.md` I 묶음의 지시 문장을 이 화면의 말로 바꿔 넣는다 — 아래 줄들은 모양을 보이는 예다. 「브랜드」 영역의 모양은 메인이 `bootstrap-project.md` §6.1·§6.3에서 걸러 넣는다.

### 4.5 비교안 폴더에 남는 것

고른 뒤 무엇이 본 코드로 가고 무엇이 3단계까지 남는지다. 2-2 §4.3과 같은 방식이다.

- **본 코드로 가는 것** — 고른 판의 대상 화면 코드(본 화면 자리로), 고른 판 CSS 파일의 값(1·2층 토큰으로 옮기고 그 파일과 `@import` 줄은 지움), 고른 로고 부품과 브랜드 색 면 전용 부품(본 부품으로), 사진 톤·질감 클래스(3층), 파비콘(`public/brand/`), 혁신판이면 조작 부품과 `lib/motion.ts`, 파격판이면 은유 부품과 `lib/{수단}.ts`.
- **디자인 시스템 페이지** — 「브랜드」 영역이 「지금 값」 하나로 돌아간다.
- **3단계 `화면 대조 끝:`까지 남는 것** — 고르지 않은 판의 비교안 화면과 판 폴더(`drafts/_{판}/`·`drafts/{화면}-{판}/`), 그 판 CSS 파일과 `2-semantic.css`의 그 `@import` 줄, 디자인 시스템 페이지의 그 판 자리와 「브랜드」 껍데기, 목업 캔버스 목록 파일의 그 비교안 주소, 고르지 않은 판만 쓰던 패키지(`npm uninstall`과 `adr.md` 한 줄). 3단계에서 `화면 대조 끝:`을 적을 때 2-2의 고르지 않은 판과 함께 모두 지운다(`3-frontend-build.md` §2.3.2). 연결 정보에 그 범위 클래스 이름이 적혀 있으면 그것도 지운다. git에는 남는다. 그 시점을 이미 지난 프로젝트면 고른 직후에 지운다(§2.12 1번). 자기 점검 기록 `.draft-checks/`는 git에 없으니 사람이 판을 고른 뒤 지워도 된다.
- **3단계 대조의 기준은 목업 캔버스 목록 파일과 화면 목록 「주소」 칸** — 비교안 주소(`/dev/drafts/…`)는 3단계 대조에 들지 않는다.

## 5. 사용자 응대 톤

- **톤**: SKILL.md §1.3 따름 — `AGENTS.md` 응답 톤(~입니다 체)·친근·짧게.
- **개성은 이 서비스의 말로 보여 준다** — 「대담판」·「그림 소재」 같은 이름만 늘어놓지 말고, 「동네를 걷는 서비스라 점선 발자국을 첫 화면 띠와 로고에 넣어 보겠습니다」처럼 이 서비스와 이어서 말한다. 사용자에게 디자인 지식을 요구하지 않는다.
- **건너뛰기를 막지 않는다** — 「건너뛰면 지금 화면 그대로 갑니다」를 한 번만 말한다. 2-2처럼 출발점 얘기로 다시 붙잡지 않는다.
- **고르는 건 사용자다** — "제가 보기엔 대담판이 낫습니다"로 결정을 대신하지 않는다. 물으면 브랜드 인상에 비춰 근거와 함께 권하되 선택은 맡긴다. AI는 화면을 못 본다고 분명히 말한다. 보조 AI가 스스로 열어 보며 고쳤다는 것은 판정이 아니라 만드는 과정이라고 말한다.
- **고르기 전에 늘어나는 일을 꼭 말한다** — 특히 파격판은 화면 목록 일부를 다시 열고 3단계가 늘어난다는 것.
- **"섞어도 된다"를 꼭 말한다** — 겉모습은 판끼리 섞을 수 있고, 조작 방식과 은유는 한 판의 것을 고른다는 것. 로고는 세 안 중 따로 골라도 된다는 것도 함께.
- **"마스코트도 만들어 주세요"** — 지금은 바깥 이미지 생성 도구가 필요해 범위 밖이라고 짚고, 브리프 「4」 「마스코트」 행에 `추후 결정`으로 남긴다.
- **"더 화려하게"** — 판 고르기로 푼다. 대담판보다 더 바꾸고 싶으면 혁신판·파격판이 그 자리라고 짚는다. 대담판 안에서 더 꾸미고 싶다는 뜻이면 사용자 결정이라 브리프 「13」에 이유와 함께 적고 따른다 — 단 바닥 금지(대비·동작 줄이기·강조색 세 자리 등, §1.3)는 바꾸지 않는다.
- **위임을 알린다** — 트렌드 조사는 sonnet 에이전트 하나, 판마다 opus 에이전트 하나(대담판 먼저, 그다음 둘 동시에), 전체 적용은 대담판·혁신판이면 sonnet, 파격판이면 opus 에이전트 하나에 맡긴다고 짧게 알린다 (`AGENTS.md` 위임 절).
- **목업 캔버스는 사람이 보는 도구다** — 「AI가 열어 봤으니 됐습니다」라고 하지 않는다. AI는 검사 결과와 주소까지 알리고, 보는 것은 사용자 몫이다.
