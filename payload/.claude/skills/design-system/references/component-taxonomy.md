## 1. 역할 분류 — 6가지

모든 컴포넌트는 6가지 역할 중 하나다.

| 역할 | 하는 일 | 범용 예 |
|---|---|---|
| **action** | 사용자가 누르는 것 | button, FAB, link |
| **input** | 값을 받는 것 | text-field, select, checkbox, slider |
| **container** | 내용을 담는 면 | card, sheet, dialog, section, popover |
| **navigation** | 위치·이동을 다루는 것 | app-nav, tabbar, stepper, breadcrumb |
| **feedback** | 상태를 알리는 것 | toast, progress, skeleton, confetti, badge |
| **display** | 정보를 보여주는 것 | list, table, chip, avatar, thumbnail |

회사마다 부르는 이름이 달라도(toast vs snackbar) 역할은 같다 — 분류는 용어 차이에 오염되지 않는 층.

## 2. 어휘 두 갈래 — 범용 vs 전용

- **범용 컴포넌트**: 어느 제품에나 있는 개념 (button, dialog, sheet, badge, input, stepper…).
  **이름은 shadcn 부품 이름을 따른다** — shadcn 이름이 곧 업계 표준명이라 이름만 보고 누구나(사람·AI) 뭔지 안다.
  shadcn에 없는 범용 개념만 업계 표준 영어명으로 짓는다.
- **전용 컴포넌트**: 이 제품에만 있는 고유 개념 — 자유 명명 허용.
  **단, 인벤토리 등록 필수** (§6 색인 한 줄 형식으로).

## 3. 동의어 규칙 — 하나의 개념 = 하나의 이름

인벤토리에 개념별 **정본(canonical) 이름**을 지정하고, 동의어를 함께 기록한다:

```
정본: Dialog   ← 이렇게도 부름: modal, popup, 모달, 팝업  (되돌리기 어려운 확인은 AlertDialog)
정본: Sheet    ← bottom-sheet, side panel, 바텀시트  (끌어올리는 판은 Drawer)
정본: Badge    ← chip, tag, pill, 칩, 태그
정본: Input    ← field, text-field, textbox, 입력창  (여러 줄은 Textarea)
```

요청에 동의어가 등장하면("팝업 띄워줘") 정본으로 번역한 뒤 인벤토리를 찾는다.

## 4. 작성 규약 (cva·토큰 계약)

- **부품은 TSX 파일 하나** — 범용은 `components/ui/`(shadcn 복사본), 전용은 `components/`. 파일 이름 = 인벤토리의 정본 용어
  (개념은 표준어, 인스턴스는 용도 접두어 허용: `ExitDialog`)
- **변형은 cva의 `variant`·`size`로 만든다** — 같은 부품의 다른 모양은 클래스 이름이 아니라 prop이 고른다
  (`<Button variant="secondary" size="sm">`). 새 모양이 필요하면 그 부품의 cva에 variant를 더한다
- **클래스 합치기는 `cn()`** (`lib/utils.ts`) — 부품이 받은 `className`을 자기 클래스 뒤에 합친다. 우리 2층 이름을 알려 준 판이라야
  `text-b1` 같은 글자 이름이 글자색과 겹쳐 지워지지 않는다 — 부품은 합치기 패키지가 아니라 늘 `@/lib/utils`에서 불러온다
  ([bootstrap-project.md](bootstrap-project.md) §1.5)
- **화면은 배치 클래스만 준다** — 화면이 부품에 주는 `className`은 바깥 여백·폭·flex·grid뿐이다. 색·둥글기·글자
  같은 겉모양은 부품 안(cva)이 정한다
- 값은 전부 **semantic 이름 클래스·theme 스케일 클래스** — 이 계약을 지킨 부품만 이식 가능해진다 (§7)
- **BEM(`.블록__요소--변형`)은 `3-components.css`의 전용 클래스에만 남는다** — 안전 영역 덧셈처럼 클래스로 못 푸는
  스타일이 그 자리다 (예: `.shell__bottom`)

### 4.1 모양이 shadcn 기본과 다를 때 — 고치는 차례

1. **2층 값으로 맞춘다** — 색·둥글기·글꼴이 다르면 `--primary`·`--radius`·`--font-sans`를 바꾼다. 대부분 여기서 끝난다.
2. **variant를 더한다** — 같은 부품의 다른 모양이 필요하면 그 부품의 cva에 variant를 추가한다.
3. **부품 파일을 고친다** — 1·2로 안 되면 `components/ui/` 파일을 직접 고치고, AGENTS.md adapter의
   「고친 shadcn 부품 목록」에 파일과 고친 이유를 한 줄 적는다. 다시 받을 땐 `npx shadcn add <이름> --diff`로
   차이를 보고 목록대로 다시 고친다. `--overwrite`는 쓰지 않는다 — 우리 수정이 묻지도 않고 덮인다.
4. **화면에서 겉모양을 덮어쓰지 않는다** — `<Button className="bg-[#..] rounded-[14px]">`처럼 쓰지 않는다.

## 6. 인벤토리(사전) 형식

- **개념 단위로 등록** — 블록 패밀리(예: `calc-*` 14블록)는 1항목으로 묶는다
- **코드가 진실, 사전은 색인** — 컴포넌트 추가 절차의 마지막 단계가 "사전에 한 줄 추가"

**이 원칙을 지키는 방법 — 인벤토리든 함정 절이든, 코드나 그 파일 머리 주석을 보면 알 수 있는 값은 적지 않고 가리키기만 한다:**

- **구분은 둘** — 범용(`components/ui/`)과 전용(`components/`). 등록 단위는 부품 파일이다
- 한 줄 형식: `이름 | 범용/전용 | 한 줄 설명 | 파일 경로`
  variant 목록은 적지 않는다 — 부품 파일의 cva 정의가 정본이다.
  설명은 **한 문장** — 그게 무엇인지만. 왜 만들었는지·어떻게 쓰는지·어떤 값인지는 적지 않는다.
- **자세한 설명의 정본은 그 부품 파일의 머리 주석이다.** 같은 사실을 인벤토리에 다시 쓰지 않는다.
  두 군데 쓰면 반드시 어긋난다 — 실제로 존재하지 않는 필드 설명, 사용처 0인데 "쓴다"고 적힌 항목, 이미 사라진 사용처 참조가 한 프로젝트에서 동시에 나온 적 있다.
- **무엇이 어떻게 바뀌었나는 적지 않는다** — "예전엔 ~였고 지금은 ~로 바꿨다"는 git log 몫이다. (뭘 하면 터지는지의 사고 이력과는 다르다 — 그건 회귀(regression)를 막는 근거라 함정 절에 남긴다.)
- **문서가 이기는 자리는 셋이다** — 인벤토리 항목이 아니라 프로젝트 문서의 별도 "함정" 절에 모은다: ① 여러 파일에 흩어진 걸 모은 집계(예: "폭 분기는 다섯 곳뿐이고 여기 있다"), ② 어느 한 파일에도 안 속하는, 여러 파일에 걸친 절차, ③ 코드에 없는 규칙 — 값의 하한·상한 같은 금지, "팝업이라 부르지 마라" 같은 용어 통제, 위에서 구분한 사고 이력. 항목에 섞으면 길어지고, 길어지면 안 읽힌다.
- **지금 안 쓰는 부품**은 사연 없이 "지금 쓰는 곳 없음" 한 마디로 끝낸다.

```
좋은 예: Dialog | 범용 | 확인·경고용 모달 창 | src/components/ui/dialog.tsx
나쁜 예: Dialog | 범용 | 확인·경고용 모달. z-index는 1300 고정,
         ESC로 닫히고 배경 클릭 시 닫히며 최초 도입은 3월... (2000자 회고록)
```

### 6.1 전체 부품 색인

인벤토리 문서 **맨 끝**에 `## 전체 부품 색인` 구간을 따로 둔다. 사람이 읽는 본문(위 한 줄 형식)과 달리, 이 구간은 **기계가 대조하는
목록**이다 — 부품 파일 경로와 `3-components.css`의 클래스 이름을 **한 줄에 하나씩, 꾸밈 없이** 코드 블록 안에 늘어놓는다.

왜 따로 두나 — 「새로 만든 부품이 인벤토리에 다 올라갔나」를 검사가 줄 전체 일치로 대조한다(idea-to-mvp는 3단계 배포 전 검사의
디자인 규칙 검사). 본문은 부품을 묶어 적거나 설명을 붙이니 그대로 대조하면 빠진 것과 오탐이 섞인다. 경로·이름만 있는 목록이라야
「이 파일이 목록에 있나」가 한 줄로 갈린다.

````markdown
## 전체 부품 색인

_부품 파일이나 `3-components.css` 클래스를 더하거나 지울 때 이 구간을 지우고 다시 만든다. 목록은 `find src/components -name '*.tsx' | sort`와 `grep -hoE '^\.[A-Za-z][A-Za-z0-9_-]*' src/styles/3-components.css | sed 's/^\.//' | sort -u`의 출력이다._

```
src/components/site-header.tsx
src/components/ui/button.tsx
src/components/ui/dialog.tsx
shell__bottom
```
````

- **꾸밈을 붙이지 않는다** — 줄 앞의 `- `, 뒤의 설명, 굵게 표시가 붙으면 줄 전체 일치에서 전부 「없음」으로 나온다.
- **경로는 저장소 최상위 기준**(`src/…`), 클래스는 앞의 `.`을 뗀 이름이다. 변형(cva의 `variant`)은 클래스가 아니라 적지 않는다.
- **언제 다시 만드나** — 부품 파일을 더하거나 지울 때, `3-components.css`에 클래스를 더하거나 지울 때. 손으로 고치지 않고 아래 명령으로
  다시 뽑아 구간을 통째로 바꾼다. 경로는 프로젝트 연결 정보(AGENTS.md)의 부품 폴더·3층 CSS 경로로 바꾼다.

```bash
{ find src/components -name '*.tsx' | sort
  grep -hoE '^\.[A-Za-z][A-Za-z0-9_-]*' src/styles/3-components.css | sed 's/^\.//' | sort -u; }
```

## 7. 이식성 — 다른 프로젝트로 옮기기

| 대상 | 다음 프로젝트에서 |
|---|---|
| 범용 컴포넌트 | **`npx shadcn add`로 다시 받는다** — 2층 이름 계약 덕에 받은 그대로 새 브랜드 색·모양이 적용된다. 이전 프로젝트 adapter의 「고친 shadcn 부품 목록」 중 새 프로젝트에도 필요한 것만 다시 고친다 |
| 전용 컴포넌트 | **새로 조립** (제품 고유 개념이므로) — 단 재료는 shadcn 부품 + semantic 클래스 |
| 인벤토리 | **새로 작성** (받은 범용 부품 등록 + 전용 신규 등록) |
