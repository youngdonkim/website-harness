4단계는 코드만 짜는 단계가 아니다. 클라우드 DB·로그인·배포가 **밖의 계정에 묶이는 순간**이라, 어느 계정으로 무엇을 만들지가 코드보다 먼저 정해져 있어야 한다. 이걸 뒤로 미루면 실제로 이런 일이 난다 — 백엔드를 다 붙인 뒤에 "회사 이메일 계정으로 만들어졌네"를 발견해서 프로젝트를 새로 만들고 키·비밀번호·시크릿·콜백 주소를 전부 다시 잇는다 (실사고 1건: 4단계를 끝낸 뒤 Supabase가 회사 조직에 만들어진 걸 발견 — 프로젝트 재생성·마이그레이션 재푸시·Vercel 환경변수·깃허브 Secret·Auth 설정을 전부 다시 했다).

이 문서는 **사람이 브라우저에서 해야 하는 일**을 모아 둔 자리다. AI는 CLI(터미널 명령)로 할 수 있는 건 하지만, 계정 만들기·로그인·결제 등록·앱 심사는 못 한다. 순서는 이렇다 — **AI가 이 체크리스트를 보여준다 → 사람이 계정·로그인 쪽을 끝낸다 → AI가 CLI 쪽을 잇는다 → 4-1로 간다.**

> ⚠ 여기 적힌 외부 서비스의 화면 위치·명령·요금제 조건은 이 글을 쓴 시점 기준이다. 따라 하기 전에 공식 문서로 지금도 맞는지 확인하고, 달라졌으면 공식 문서를 따르고 이 문서를 고쳐야 한다고 사용자에게 보고한다. 반대로 "계정을 먼저 정한다"·"비밀번호는 보이는 순간 저장한다" 같은 우리 규칙과 실사고 기록은 그대로 지킨다.

## 1. 이 하위 단계가 하는 일

- 4단계가 만들 것들이 묶일 계정을 정하고, 그 계정으로 외부 서비스 로그인·등록을 끝낸다.
- 리드타임(lead time)이 긴 것(소셜 로그인 앱 등록·심사, 결제 대행사 심사, 도메인)을 지금 시작해서 4-2·4-3에서 기다리지 않게 한다.
- 비밀값이 어디 저장돼 있는지 장부로 남긴다 (값 자체는 이 저장소에 안 들어간다).

**여기서 안 하는 것**: 표·정책·코드 — 그건 4-1부터다. 이 문서는 "만들 준비"지 "만들기"가 아니다.

## 2. 0번 — 어느 계정으로 할지부터

체크리스트를 보기 전에 한 줄로 먼저 답한다 — **이 서비스는 누구 소유인가(개인/회사/팀)?** 이 답이 아래 §3의 계정 전부를 정한다.

**프로젝트 `AGENTS.md`에 「소유와 계정」 표가 있으면 소유 답은 이미 받아 둔 것이다** (project-init이 사용자에게 물어 채움). 그 경우 이 절의 확인은 "지금 로그인된 계정이 표의 계정과 일치하는가"의 **대조**로 좁혀진다 — **여기서 `docs/account-check.md`를 읽고** 아래 표의 명령으로 실제 계정을 꺼내 표와 맞춰 본다. 다르면 아래 표 「계정이 다르면」 행대로 맞춘다. 표가 없거나(옛 프로젝트) 항목이 `(확인 필요)`면 아래대로 처음부터 확인하고, 이번에 확정된 계정은 표에 채운다.

| 확인할 것 | 어떻게 |
|---|---|
| 지금 로그인된 계정이 소유자인가 | 각 대시보드의 프로필에서 **이메일**을 본다. 아이디만 보고 판단하지 않는다 — 아이디는 개인 것 같은데 이메일만 회사인 경우가 흔하다 |
| CLI가 어느 계정 토큰인가 | 먼저 `.claude/scripts/with-owner.sh --check`(소유·장부·키 이름·gh 계정 — 키 값은 안 나옴), 그다음 `.claude/scripts/with-owner.sh npx vercel whoami`·`.claude/scripts/with-owner.sh npx supabase orgs list`로 확인한다. 브라우저에 로그인된 계정과 CLI 토큰의 계정이 다른 경우가 있다 |
| 계정이 다르면 | **gh를 포함해 전부** 소유자 계정의 발급 토큰을 이 컴퓨터의 계정 장부(`~/.config/harness/<소유>.env` — 소유는 `.claude/owner`)에 두고 실행기로 CLI에 넘긴다(gh는 `GH_TOKEN`, Vercel은 `VERCEL_TOKEN`, Supabase는 `SUPABASE_ACCESS_TOKEN`). 로그인 갈아타기·활성 계정 전환은 전역이라 소유가 다른 프로젝트를 조용히 망가뜨리고, 토큰이 걸리면 효과도 없다 (`docs/account-check.md`) |
| 서비스 간 연결(연동 로그인·앱 설치·저장소 연결)이면 | **양쪽을 대조한다** — 연결에 붙는 건 상대 서비스(로그인·권한을 빌려주는 쪽)의 지금 세션이다. 상대 쪽 로그인 계정도 표와 맞춘 뒤 연결하고, 끝나면 화면의 연결 계정을 표와 재대조한다 |
| 브라우저 작업 프로필이 정해져 있고 로그인돼 있는가 | 표의 「브라우저 작업 프로필」 항목을 본다. 비어 있으면 사용자에게 묻고 채운다. 그 프로필로 이 소유의 서비스들에 실제로 로그인돼 있어야 한다 — 로그인 폼이 뜨면 아직 준비가 안 된 것이다 |

화면 작업 프로필 규칙은 AGENTS.md 「소유와 계정」 그대로다 — 여기선 §2 표 마지막 행으로 대조만 한다.

**계정에 묶이는 쓰기 작업 직전마다, 같은 걸음에서 활성 계정을 다시 확인한다.** 쓰기 작업은 리소스 생성·환경변수 설정·PR 생성·머지·브라우저 콘솔 작업이다. 작업 시작 때 한 번 확인한 것을 여러 걸음 뒤에 믿지 않는다. [실측] 개인·회사 프로젝트를 오가면 gh의 전역 활성 계정이 앞 명령과 달라진다. 실행기 없이 부르면 다음 호출이 조용히 다른 계정으로 간다 — 그래서 활성 계정에 기대지 않고 장부의 토큰(`GH_TOKEN`)으로 고정한다. 브라우저 에이전트는 마지막 로그인 계정으로 열린다.

**AI는 서비스마다 "회사 계정이냐 개인 계정이냐"를 사용자에게 명시적으로 확인받는다.** 위 명령으로 나온 이메일·조직 이름을 서비스별로 보여주며 "GitHub은 `aaa@company.com` — 회사 계정입니까, 개인 계정입니까?"처럼 하나씩 판정을 받는다. 이메일 도메인만 보고 AI가 회사/개인을 단정하지 않는다 — 회사 도메인을 개인 용도로 쓰는 경우도, 개인 지메일이 회사 계정인 경우도 있어서 판정은 사람 몫이다. (근거: 실사고에서 아이디는 개인 것처럼 보였는데 이메일만 회사 것이었다 — 겉보기 판단이 사고의 시작이었다.)

**AI는 이 답을 받기 전에는 어떤 외부 리소스도 만들지 않는다.** 답이 없으면 물어보고 멈춘다 — 되돌리기 비싼 갈림길이라는 점에서 SKILL.md §1.5 에스컬레이션 기준 (c) "결과를 되돌리기 비싼 갈림길"에 그대로 해당한다.

**잘못된 계정에 이미 생긴 리소스는 — ID·시크릿·주소가 따라가면 옮기고, 아니면 새로 만든다.** 옮긴 뒤엔 옛 계정에 남는 잔여 권한(협력자·로그인 연결·CLI 토큰)을 걷는다. [실측: GitHub 저장소·OAuth 앱은 이전해도 ID·시크릿이 유지돼 설정 변경 0건 / GCP 프로젝트는 이전 비용이 새로 만드는 것보다 커서 새로 만듦 / Vercel은 팀 초대 없이 프로젝트 이전 요청 기능이 있다(쓴 시점 기준) — 초대로 유료 자리를 헛되이 만들 필요가 없다]

**배포·CI가 이미 붙었거나 사용자가 들어온 뒤에 소유를 통째로 옮겨야 하면 `/transfer-ownership` 스킬을 쓴다** — 저장소·DB·호스팅·로그인 앱·AI 키를 정해진 순서로 옮기고 계정 표까지 다시 쓰는 절차다. 여기 4-0 시점처럼 아직 배포 전이면 그 절차는 과하다 — 위 판단대로 그 자리에서 옮기거나 새로 만든다.

## 3. 준비 체크리스트

각 항목에 **[사람]**(계정 만들기·결제·심사·일회용 코드(OTP)·패스키처럼 사람만 되는 일), **[Aside]**(브라우저 에이전트가 대시보드에서 하는 일), **[AI]**(터미널 명령으로 하는 일)를 표시했다. 같은 항목 안에서는 **앞 몫이 끝나야 다음 몫으로 넘어간다.**

- **[Aside] 몫은 대시보드에서만 되는 일이다** — 토큰·키 발급, 조직 초대·수락, 앱 설치·저장소 연결. **로그인·재로그인도 Aside가 한다.** 사람은 OTP·패스키 입력만 맡고, **이메일 인증 코드는 Aside가 메일함에서 읽어 넣는다.**
- **[Aside]가 비밀값을 받는 절차는 넷이다** — 화면에서 읽어 **파일로만 저장**(대화에 값을 남기지 않는다) → 그 값으로 API를 한 번 불러 유효한지 확인 → §4.1 값을 넣는 곳 표대로 제자리에 설치 → 파일 삭제. **저장에 실패했으면 값 모르는 토큰을 살려 두지 않고 즉시 폐기한 뒤 다시 발급한다.**
- **예외 — 자동화를 붙이면 계정이 제재되는 서비스는 [사람]이다.** 카카오(계정·디벨로퍼스 콘솔)가 그렇다: `docs/account-check.md` 「서비스별 함정」의 카카오 항목. AI는 사람이 건네준 키를 설정에 넣는 CLI 작업만 한다.
- **발급 토큰은 계정 단위다** — 소유 계정당 하나를 만들고, 그 소유의 프로젝트들이 **계정 장부 파일 하나를 나눠 쓴다.** 같은 소유 장부에 이미 살아 있는 토큰이 있으면 다시 발급하지 않는다. **이름은 프로젝트가 아니라 용도·기기로 짓는다**(계정 단위 토큰에 프로젝트 이름을 붙이면 그 프로젝트가 끝났을 때 남들이 쓰는 토큰을 지우게 된다). 프로젝트 스코프 토큰은 권한을 일부러 좁힐 때만 따로 만든다.

### 3.1 GitHub

- **[Aside]** 저장소가 소유자 계정·조직 아래에 있는지 확인한다. 아니면 저장소 설정의 Transfer(소유권 이전) 기능으로 지금 옮긴다 — 지금은 싸지만, 배포·CI를 다 붙인 뒤에 옮기면 웹훅·Secret을 전부 다시 연결해야 한다.
- **[AI]** gh CLI 인증(계정 장부의 발급 토큰 `GH_TOKEN`)은 `github-connect` ⑤에서 이미 끝나 있다 — 여기서는 토큰이 살아 있고 표의 계정 것인지 `.claude/scripts/with-owner.sh gh api user --jq .login`으로 확인만 한다. 없거나 죽었으면 `github-connect`를 돌린다(발급 길·권한·파일 규칙은 거기에). **토큰이 걸리면 활성 계정 전환은 효과가 없다** (`docs/account-check.md` gh 항목).
- **[AI]** 깃허브 Secret 3종(`SUPABASE_ACCESS_TOKEN`·`SUPABASE_PROJECT_REF`·`SUPABASE_DB_PASSWORD`)은 Supabase 프로젝트를 만든 뒤 AI가 `.claude/scripts/with-owner.sh gh secret set`으로 넣는다 — 사람이 미리 할 일은 없다. 실제로 넣는 절차는 4-1에서 한다.

### 3.2 Supabase

- **[사람]** 소유자 이메일로 계정·조직을 만든다. 무료 요금제는 활성 프로젝트 개수에 상한이 있으니, 옛 프로젝트가 남아 있으면 정리한다 (멈춘 프로젝트도 상한에 들어가는지는 요금제 문서로 지금 확인한다).
- **[Aside]** CLI 인증은 발급 토큰으로 한다 — 같은 소유 장부에 살아 있는 `SUPABASE_ACCESS_TOKEN`이 없을 때만 계정 화면에서 접근 토큰을 만들어 계정 장부에 `SUPABASE_ACCESS_TOKEN=`으로 둔다(값을 화면에 내지 않는 쓰기 모양은 `github-connect` 「장부에 키 한 줄 쓰기」). 조직 이름은 `SUPABASE_ORG`로 함께 둔다. 소유가 다른 프로젝트가 한 컴퓨터에 있으면 로그인 갈아타기 금지(`docs/account-check.md` 원칙 ②). 지금 어느 계정인지는 CLI 자체의 조직 조회 명령으로 확인한다 — 맥 키체인 조회 명령은 허용 창이 떠서 무한 대기한다(실측 여러 번). 무한 대기 가능성이 있는 명령은 시간 상한을 걸어 부른다.
- **[사람]** 리전(region)을 정한다. 한국 서비스면 서울(`ap-northeast-2`)이 기본이다. 이 리전은 뒤 하위 단계(배포)에서 정할 Vercel 함수 리전과 맞춰야 하므로, 어떤 리전으로 갈지 여기서 미리 정해 둔다.
- **[AI]** 프로젝트를 생성한다: `.claude/scripts/with-owner.sh npx supabase projects create <이름> --org-id <조직> --region <리전> --db-password <생성값>`. **DB 비밀번호는 AI가 만들어서 프로젝트 `.env.cli`(git 미추적, 프로젝트 전용 키 — 실행기가 장부 다음에 읽는다)에 넣고(CLI가 읽는 값이라 `.env.local`이 아니다 — 내려받기가 덮어쓴다), "지금 비밀번호 관리자에 옮겨 두세요"라고 사용자에게 말한다** — 이 비밀번호는 대시보드에서 다시 볼 수 없고 재설정만 된다. 재설정하면 깃허브 Secret(`SUPABASE_DB_PASSWORD`)도 같이 교체해야 한다.
- **[AI]** 생성이 "This operation is currently unavailable" 또는 "Partial System Outage" 문구로 실패하면, 재시도로는 안 풀린다. status.supabase.com에서 장애 여부를 확인하고, 원인이 서비스 장애면 몇 분 간격으로 자동 재시도를 걸어두고 사용자에게도 알린다 (실측 1건: 전 지역 장애로 40분 넘게 막혔다).
- **[AI]** 생성 직후 `link`(로컬을 이 프로젝트에 연결) → `db push`(마이그레이션이 있으면 반영) → `projects api-keys`로 키를 받아 3.3의 Vercel 환경변수로 넘긴다. `db push` 뒤 시드 데이터는 AGENTS.md 「클라우드에 시드 넣기」 절차대로(대시보드 SQL 편집기 — [Aside]). 최신 확인: Supabase CLI에 `db push --include-seed` 같은 시드 옵션이 있으면 그쪽이 더 낫다 — 공식 문서로 확인한다. Auth 사이트 주소와 콜백 허용 목록은 대시보드(Authentication → URL Configuration)나 관리 API(`PATCH /v1/projects/{ref}/config/auth`의 `site_url`·`uri_allow_list`)로 AI가 설정한다. 허용 목록에 실서비스 주소와 미리보기 배포 도메인 패턴(와일드카드)을 둘 다 넣는다. 미리보기 패턴이 없으면 미리보기 배포에서 로그인·OAuth 콜백이 깨진다.

### 3.3 Vercel

- **[Aside]** CLI 인증은 발급 토큰으로 한다 — 위 §3.2와 같은 방식(장부의 `VERCEL_TOKEN`, 팀 slug는 `VERCEL_TEAM`). 3단계 첫 배포 때 이미 장부에 `VERCEL_TOKEN`을 두었으면(`3-frontend-build.md` §2.6) 살아 있는지 확인만 한다. 3단계에서 만든 프로젝트가 소유자 계정·팀 아래인지 CLI 자체 조회 명령으로 확인한다.
- **[사람]** **커밋 작성자의 Git 계정이 소유자의 Vercel 계정에 연결돼 있는지 확인한다** — 배포 플랫폼은 커밋 이메일이 아니라 Git 계정 연결로 사람을 판정한다. 연결이 없으면 유료 팀은 승인 대기, 그 외는 배포 실패다(프리뷰·실서비스 모두). Git 계정 하나는 배포 플랫폼 계정 하나에만 붙는다 — 한쪽에서 끊었으면 소유자 계정에 다시 붙인다. [실사고: 개인 프로젝트에서 연결이 없어 배포가 막혔고, 커밋 작성자 설정을 바꿔도 소용없었다]
- **[Aside]** **깃허브 저장소를 연결한다** — 연결을 누르기 전에 브라우저의 GitHub 로그인 계정도 표와 대조한다(연결은 양쪽 계정을 본다 — §2 표. 실사고: 개인 GitHub 세션이 붙어 회사 저장소가 목록에 안 보였다). 대시보드 → Settings → Git → Connect에서 깃허브 앱 권한을 허용한다. **이걸 안 하면 main에 머지해도 배포가 안 된다** — done-task 스킬의 "머지 = 배포" 전제가 깨지는 것이다 (실측 1건: CLI로만 배포해 온 프로젝트라 이 연결이 없었고, 머지 뒤 3분을 기다려도 새 배포가 안 생겨서 손으로 `vercel deploy --prod`를 돌렸다). `vercel git connect`가 실패하면 원인은 대부분 GitHub 앱의 저장소 접근 목록 누락이다 — 처방은 `3-frontend-build.md` §2.6 첫 배포 체크리스트.
- **[사람]** (Pro 팀이면, 쓴 시점 기준) 비공개 저장소에 커밋한 사람을 팀원으로 **자동 추가하는 옵션이 기본 켜짐이고 자리당 유료**다 — 끄고 수동 승인으로 바꾼다. [실측: 청구서에서 발견]
- **[사람]** (Pro 팀이면, 쓴 시점 기준) **프리뷰 배포에 로그인 보호가 기본**이다 — 지인에게 프리뷰 링크를 보내면 Vercel 로그인으로 튕긴다. 보호를 끄거나 실서비스 주소로 보낸다 (`3-frontend-build.md` §2.7이 이 사실을 참조한다). [실측]
- **[AI]** 환경변수를 `.claude/scripts/with-owner.sh npx vercel env add`로 Production·Preview 둘 다 등록한다. 이름은 코드가 정하고 `.env.example`이 정본이다.
- **[AI]** 함수 리전을 앞서 정한 DB 리전에 맞춰 둔다 — 3단계 첫 배포에서 `vercel.json`에 리전을 이미 적었으면(`3-frontend-build.md` §2.6 「속도 점검」) 그 값이 DB 리전과 같은 곳인지 본다(서울: Supabase `ap-northeast-2` = Vercel `icn1`). 다르거나 안 적었으면 어느 리전으로 맞출지 여기서 정해 프로젝트 `AGENTS.md` 「배포 리전」 줄에 적는다 — 배포 설정에 반영하고 실제 리전을 확인하는 건 뒤 하위 단계(배포, `4-3-backend-deploy.md` §2.6) 몫이다.

### 3.4 소셜 로그인 앱(GitHub·구글·카카오 등)

**Supabase 프로젝트를 만든 뒤에 한다** — 콜백 주소에 프로젝트 참조 아이디(ref)가 들어가서(`https://<ref>.supabase.co/auth/v1/callback`), 나중에 계정을 옮기면 앱을 다시 등록해야 한다. 그래서 위 3.2에서 계정이 확정된 다음에 진행한다.

**소유권 이전이 안 되는 제공사의 앱은 가장 늦게, 소유 계정이 확정된 뒤에 만든다.** 앱을 새로 만들면 제공사가 주는 사용자 아이디가 갈려서 **이미 가입한 사람이 같은 계정으로 못 들어온다** — 되돌릴 수 없는 결정이다. 이전이 되는 제공사(GitHub 등)는 앱을 옮겨도 id·secret이 따라와서 이 문제가 없다. 그러니 **제공사마다 이전 가능 여부부터 확인하고**, 안 되는 쪽(카카오)은 소유가 확정되기 전에 만들지 않는다.

**콘솔에서 무엇을 만들기 전에, 오른쪽 위 프로필 이메일을 「소유와 계정」 표와 먼저 대조한다** — 사람이든 브라우저 에이전트든 같다. 콘솔은 마지막에 쓴 계정으로 열린다 (실사고: 브라우저 에이전트가 개인 계정으로 열린 콘솔에 회사 프로젝트의 GCP 프로젝트를 만들었다). 브라우저 에이전트는 표의 계정을 지정해 연다 (계정 지정·전환 방식은 `docs/account-check.md`).

**제공사를 고르기 전에, 그 제공사가 앱 하나에 콜백 주소를 몇 개까지 허용하는지 확인한다.** 이 수가 만들 앱의 수를 정한다. 어느 제공사가 어느 쪽인지는 공식 문서로 확인한다.

- **콜백 여러 개(구글·카카오 등)** — 앱을 하나 만든다. 그 앱에 실서비스 콜백 `https://<ref>.supabase.co/auth/v1/callback`과 로컬 콜백 `http://localhost:54321/auth/v1/callback`을 둘 다 등록한다.
- **콜백 하나(GitHub 등)** — 앱을 로컬용·실서비스용 둘로 만든다. 로컬용 앱 이름에 `(local)`을 붙인다. [실측 1건: 앱을 하나만 만들면 로컬 로그인과 실서비스 로그인 중 하나가 안 붙는다.]

만든 client id·secret은 §4.1 값을 넣는 곳 표대로 넣는다.

- **[사람]** 카카오 — 브라우저 에이전트를 붙이면 계정이 제재되니 사람이 직접 연다(§3 도입부 예외). developers.kakao.com에서 앱을 만들고 카카오 로그인을 활성화한다. 동의 항목 중 `profile_nickname`·`profile_image`를 켠다(안 켜면 이름·사진이 안 넘어온다). `account_email` 같은 부가 권한은 추가 절차(심사·서류)가 붙을 수 있다 — **필요하면 그 시점의 공식 절차를 확인해 따르고, 확인한 내용을 여기 고쳐 적는다.** 필요 없으면 켜지 않는다. Redirect URI를 등록하고, REST API 키와 Client Secret(보안 탭에서 생성·활성화)을 Supabase의 Providers → Kakao 화면에 넣는다.
- **[Aside]** 구글 — console.cloud.google.com에서 OAuth 동의 화면(외부)을 만들고, OAuth 클라이언트 ID(웹)를 만들어 리디렉션 URI를 등록한다. ID와 Secret을 Supabase의 Providers → Google 화면에 넣는다.
- 참고로 Supabase는 카카오 닉네임과 구글 실명을 같은 `full_name` 항목에 넣는다 — 구글 실명이 그대로 공개 작성자명으로 나갈 수 있다는 뜻이고, 이게 4-2 첫 로그인 때 닉네임을 한 번 확인받는 이유다. 사진은 둘 다 `avatar_url`에 들어간다.
- **[사람]** 로컬 소셜 로그인을 쓰려면 위 방식대로 로컬 콜백을 등록하고, 로컬용 앱 값을 §4.1 값을 넣는 곳 표 로컬 자리에 넣는다 — 없으면 로컬 소셜 로그인 버튼이 동작하지 않는다.
- (로컬 반복 검증용 세션은 4-2 §13)

### 3.6 로컬 도구

- **[사람이 정함]** Docker Desktop을 깔지 정한다. `docker --version`이 되면 이미 있는 것이니 묻지 않고 다음 줄로 간다. 없으면 AI가 무엇에 쓰는지와 크기를 쉬운 말로 알리고 묻는다 — 2단계 도구와 달리 묻는 까닭은 용량이 크고 4단계에서야 쓰는 프로그램이라서다. 묻기 전에 AI가 **그 자리에서** 지금 정보를 확인해 문안에 넣는다 — 설치 방식·약관·무료 조건은 Docker가 새 판을 낼 때마다 바뀔 수 있어, 하네스에 적힌 예나 지난번 기억으로 채우지 않는다: ① 이 컴퓨터에 필요한 최소 메모리(Docker 공식 설치 안내의 시스템 요구 사항) ② 무료로 쓸 수 있는 조직 규모 조건(<https://docs.docker.com/subscription/desktop-license/>) ③ 쓸 설치 도구에 지금 등록된 정보 — 윈도우는 `winget show --id Docker.DockerDesktop -e`로 패키지 id·설치 방식(컴퓨터 전체 설치인지)·딸린 약관(Agreements)과 그 주소, 맥은 `brew info --cask docker-desktop`으로 이름과 설치 방식. 확인이 안 되는 항목은 「확인 못 함」이라고 그대로 알린다. 문안 골자:

  > 4단계에서는 내 컴퓨터 안에 연습용 DB를 띄워 놓고 만듭니다. 그 DB를 돌리는 프로그램이 Docker Desktop(내 컴퓨터 안에 작은 서버 묶음을 띄우는 프로그램)인데, 이 컴퓨터에는 아직 없습니다.
  >
  > - **크기** — 프로그램과 처음 받는 DB 파일을 합쳐 수 GB를 차지하고, 켜 두는 동안 메모리를 씁니다(공식 최소 메모리 [확인한 값]).
  > - **비용** — 개인·작은 회사는 무료이고, [확인한 조건]을 넘는 회사에서 업무로 쓰면 유료입니다.
  > - **약관** — 설치하면 Docker 이용 약관([확인한 약관 주소])에 동의하게 됩니다. [설치 도구가 약관 동의를 따로 묻는다면: 설치 명령이 이 약관에 동의하는 표시를 함께 보냅니다.]
  >
  > 어떻게 할까요?
  >
  > 예시 답변: 「깔아 주세요」(→ 제가 깝니다) / 「제가 직접 깔게요」(→ 공식 설치 파일 주소를 드립니다) / 「회사 규모 조건에 걸려요」(→ 같은 일을 하는 다른 프로그램을 알려 드립니다)

  - **「깔아 주세요」면 AI가 깐다** — ③에서 확인한 패키지 이름으로 설치한다(쓴 시점 예: 맥 Homebrew `brew install --cask docker-desktop`, 윈도우 `winget install -e --id Docker.DockerDesktop` — 이름·옵션은 ③의 확인 결과가 정본). 설치 도구가 약관 동의를 물으면(winget은 딸린 약관이 있으면 묻고, 사람이 없는 셸에서는 동의 옵션 `--accept-package-agreements`를 붙여야 진행된다 — 옵션 이름도 그때 `winget install --help`로 확인), 위 문안에서 그 약관 주소를 보여 준 뒤 받은 「깔아 주세요」가 그 동의다. 문안에 없던 약관이 설치 중에 새로 나오면 설치를 멈추고 그 약관을 보여 다시 묻는다. 맥에 Homebrew가 없거나, 설치 중 관리자 암호를 묻거나(Homebrew가 시스템 폴더에 명령을 연결할 때), 윈도우가 「이 앱이 디바이스를 변경하도록 허용하시겠어요?」 창을 띄우면 — AI는 암호를 넣지 않는다. 맥은 아래 「직접 깔게요」 방법으로 사용자에게 넘기고, 윈도우 창의 「예」는 사용자가 누른다. 같은 실패가 2번 나면 멈추고 무엇이 실패했는지 알린다.
  - **「제가 직접 깔게요」면** — Docker 공식 설치 안내(맥 <https://docs.docker.com/desktop/setup/install/mac-install/>, 윈도우 <https://docs.docker.com/desktop/setup/install/windows-install/>)의 설치 파일 주소를 주고, 「됐어요」를 기다린다.
  - **어느 쪽이든 다 깔린 뒤** — 사용자가 Docker Desktop을 한 번 열어 이용 약관 창의 Accept(동의)를 누른다. 누르기 전에는 Docker가 돌지 않는다. AI는 `docker info`로 돌고 있는지 확인한다 (`4-1-backend-db.md` §3.1).
  - **조직 규모 조건에 걸리면** — `4-1-backend-db.md` §3.1의 대안 중 하나를 같은 방식으로 묻고 깐다.
- **[사람]** Docker 이미지가 잘 받아지는지 `docker pull hello-world`로 확인한다. 회사 네트워크나 VPN이 이미지 저장소(레지스트리)를 막는 경우가 있다 (실측 1건: 못 받아져서 Supabase CLI를 이미 받아 둔 이미지와 맞는 옛 버전으로 고정했다).
- **[AI]** Supabase CLI와 Docker도 Node.js와 같은 방식으로 판을 맞춘다 (`2-0-dev-setup.md` §2.2 「Node.js 버전부터 정한다」) — 고를 판은 공식 문서로 서로 맞는지 확인하고, 고른 판 숫자는 이 문서에 적지 않고 4단계 기록(`mvp/backend-build.md`)과 ADR에 적는다. Supabase CLI는 개발 의존성이라 `package.json`에 정확한 판으로 고정된다.
- **[사람]** 다른 프로젝트의 로컬 Supabase가 같은 포트를 쓰고 있으면 `supabase/config.toml`에서 포트를 옮긴다.
- **[AI]** `gh`·`vercel`·`supabase` 인증이 전부 계정 장부의 발급 토큰이고 표의 계정 것인지 §2 방식대로 다시 확인한다.

### 3.7 도메인(선택)

- **[사람]** 붙일 도메인이 있으면 지금 결정한다 — `NEXT_PUBLIC_SITE_URL`·Supabase의 사이트 주소·콜백 허용 목록·sitemap의 절대 주소, 이렇게 네 군데에 들어가서 나중에 바꾸면 넷을 전부 다시 이어야 한다. 없으면 `*.vercel.app` 주소로 가고, 6단계 전에 다시 결정한다.

> **참고 — 쓴 시점 실측 (§3 전반에 걸린 사실이고 규칙은 아니다. 어긋나면 공식 문서를 따르고 이 줄을 고쳐야 한다고 보고한다.)**
>
> - 팀 범위로 발급한 토큰은 CLI의 **개인 계정 조회 명령이 권한 없음으로 답할 수 있다** — 실패로 보고 재발급하지 말고 조직·프로젝트 조회로 확인한다.
> - 호스팅 CLI의 프로젝트 연결 명령은 **로컬 env 파일에 토큰 줄을 하나 더 쓴다** — 그 파일을 손으로 관리 중이면 연결 뒤 한 번 확인한다.
> - AI 제공사 키는 **워크스페이스 범위로 발급해야** 별도 헤더 없이 쓰이는 경우가 있다.
> - gh는 등록된 계정이 둘이면 **전역 활성 계정이 저절로 바뀌는 일이 있다**(§2 [실측]) — 그래서 활성 계정이 아니라 장부의 토큰(`GH_TOKEN`)으로 고정한다.
>
> 더 긴 목록은 `transfer-ownership` 스킬 §10.

## 4. 비밀값 장부

값 자체는 적지 않고, **어디에 있는지만** 적는다. 아래 표를 채워서 `backend-build.md`의 "배포 정보" 아래에 옮겨 둔다.

정본은 이 서식을 채워 옮긴 `mvp/backend-build.md`이고, 여기 표는 서식이다.

| 비밀값 | 만든 곳 | 저장된 곳 | 다시 볼 수 있나 | 만료일 | 갱신 시 같이 바꿀 곳 |
|---|---|---|---|---|---|
| DB 비밀번호 | AI 생성 | 프로젝트 `.env.cli`(git 미추적, 프로젝트 전용 키) + 비밀번호 관리자(정본) + 깃허브 Secret | 아니오 — 재설정만 가능 | 없음 | `.env.cli` ↔ 깃허브 Secret |
| 접근 토큰 | 계정 화면에서 발급 | 이 컴퓨터의 계정 장부(`~/.config/harness/<소유>.env`) + 깃허브 Secret | 재발급 가능 — 무기한도 장기간 안 쓰면 회수될 수 있음 | (발급 화면에서 확인해 적는다) | 계정 장부 ↔ 깃허브 Secret ↔ 같은 소유 장부를 쓰는 다른 프로젝트의 깃허브 Secret |
| Publishable·Secret 키 | 자동 발급 | Vercel env·`.env.local` | 예 | 없음 | Vercel env(Production·Preview) ↔ `.env.local` |
| 카카오 키 | 카카오 콘솔 | Providers 설정 | 예 | (콘솔에서 확인) | Providers 설정 ↔ (앱이 직접 부르면) 런타임 env |
| 구글 ID·Secret | 구글 콘솔 | Providers 설정 | ID는 예, Secret은 한 번만 | (콘솔에서 확인) | Providers 설정 ↔ (앱이 직접 부르면) 런타임 env |
| AI 제공사 키 | 각 콘솔 | `.env.local` + Vercel | 대부분 한 번만 | (콘솔에서 확인) | `.env.local` ↔ Vercel env |
| 소금값(salt) | AI 생성 | `.env.local` + Vercel | 예 | 없음 | `.env.local` ↔ Vercel env |

**「갱신 시 같이 바꿀 곳」은 짝으로 적는다.** 같은 값이 두 곳 이상에 들어가면 한 곳만 바꿨을 때 나머지가 옛 값으로 남아 **특정 기능만 조용히 실패한다.** 어느 자리에 들어가는지는 §4.1 값을 넣는 곳 표가 정본이고, 장부에는 그 자리를 짧게 적어 둔다.

**폐기 규칙 — 지우기 전에 묻는다.** 토큰·키를 지우기 전에 **같은 계정의 다른 프로젝트가 그 값을 쓰는지 먼저 확인하고 사용자에게 묻는다.** 발급 토큰은 계정당 하나를 여러 프로젝트가 나눠 쓰는 게 기본이라, 이 프로젝트만 보고 지우면 남의 프로젝트가 멈춘다. **프로젝트가 다른 소유로 옮겨 갔다는 이유만으로 옛 계정의 토큰을 폐기하지 않는다** — 그 계정은 그 계정대로 계속 쓰인다.

**규칙: 한 번만 보여주는 값은 보이는 그 순간 비밀번호 관리자에 옮긴다.** "나중에 옮겨야지"가 실사고의 시작이다. **에이전트가 만든 토큰·키도 같다** — 값을 그 자리에서 확보하고, 못 확보했으면 값 모르는 채로 살려 두지 않고 바로 폐기한 뒤 다시 만든다. 다단계 선택(스코프 → 프로젝트 등)은 마지막 단계 값이 화면에 표시된 것을 확인한 뒤에 만든다.

### 4.1 자격 증명 값을 넣는 곳 표 — 같은 값을 어디어디에 넣나

로그인 제공사의 client id·secret 한 벌은 **여러 곳에 같은 값으로** 들어간다. 한 곳만 넣으면 로그인은 된다. 그런데 특정 기능만 조용히 실패한다. 먼저 쓰임 두 가지를 가른다.

1. **로그인** — Supabase가 처리한다. 값은 Supabase에 넣는다. 로컬(도커)과 클라우드는 별개 프로젝트다. 각자 자기 콜백을 문 제공사 앱의 값을 받는다.
   - 로컬 Supabase ← `.env`의 `SUPABASE_AUTH_EXTERNAL_<PROVIDER>_CLIENT_ID`·`_SECRET`. config.toml이 읽는다.
   - 클라우드 Supabase ← 대시보드 Authentication → Providers.
2. **앱이 제공사 API를 직접 부름** — 예: 탈퇴 시 앱 승인 취소. 값은 앱 런타임 env에 넣는다. 이 쓰임이 없으면 이 줄은 건너뛴다.
   - 로컬 앱 ← `.env.local`의 `<PROVIDER>_OAUTH_CLIENT_ID`·`_SECRET`. 이름은 `.env.example`이 정본이다.
   - 실서비스 앱 ← Vercel 환경변수. 같은 이름으로 Production·Preview 둘 다.

콜백 하나짜리 제공사는 로컬 앱과 실서비스 앱이 다르다. **로컬 자리에는 로컬 앱 값을, 실서비스 자리에는 실서비스 앱 값을 넣는다.** 값이 섞이면 짝이 안 맞아 401로 거부된다. 콜백 여러 개짜리는 앱이 하나다. 로컬·실서비스가 같은 값이다.

| 값 | 원천 | 로컬에 넣는 곳 | 실서비스에 넣는 곳 |
|---|---|---|---|
| 로컬 앱 client id·secret | 제공사 콘솔의 로컬용 앱 | 로그인: `.env` `SUPABASE_AUTH_EXTERNAL_<PROVIDER>_*` · (직접호출 시) `.env.local` `<PROVIDER>_OAUTH_*` | — |
| 실서비스 앱 client id·secret | 제공사 콘솔의 실서비스용 앱 | — | 로그인: 클라우드 대시보드 Providers · (직접호출 시) Vercel `<PROVIDER>_OAUTH_*` |

⚠ **secret은 항상 제공사 콘솔의 원본에서 복사한다. Supabase에서 꺼낸 값을 다른 곳에 넣지 않는다.** [실측 1건] Supabase 관리 API로 읽은 provider secret은 원본과 형식이 다른 값이었다. 그 값을 Vercel에 넣자 제공사 인증이 401로 거부됐다. 로그인은 멀쩡했다 — Supabase가 내부의 진짜 값으로 처리해서다. 그래서 원인 찾기가 오래 걸렸다. 한 번만 보이는 secret은 그 순간 비밀번호 관리자에 넣는다. 값을 잃었으면 콘솔에서 새로 발급한다.

⚠ **secret을 새로 발급하면, 위 표에서 그 앱이 들어간 항목을 전부 같이 교체한다.** 한 곳만 바꾸면 나머지가 옛 값으로 남는다. 제공사 대부분은 회전 중에 옛 secret을 잠시 살려 둔다. 공식 문서로 확인한다.

**같은 값이 한 곳에서는 인증되고 다른 곳에서는 401이면, 코드보다 계정·앱·자격 증명 값 연결을 먼저 의심한다.** 값은 그 client id·secret으로 제공사 API를 한 번 호출해 확인한다. 여러 곳에 넣기 전에 원천에서 한 번 검증한다. 그러면 잘못된 값이 퍼지지 않는다.

## 5. AI의 진행 방식

1. 4단계에 들어서면 4-1보다 먼저 §2·§3을 한 화면 체크리스트로 만들어 보여준다 — 코드명이 아니라 그 프로젝트의 말로 풀어서, 배치 질문(SKILL.md §1.4)으로 한 번에 묻는다.
2. 사람이 자기 몫을 끝냈다고 답하면, **AI가 명령으로 실제로 확인한다** — 말만 믿고 넘어가지 않는다.
3. AI 몫(프로젝트 생성·환경변수·Secret·Auth 설정)은 결과가 밖으로 나가는 일이라 **위임하지 않고 메인이 직접 한다** (AGENTS.md의 배포 위임 금지 원칙과 같은 이유다).
4. 리드타임이 긴 것은 시작만 시켜 두고 4-1로 넘어간다 — 완료를 기다리지 않는다.
5. 장애나 권한 부족으로 막히면 막힌 항목만 사용자에게 넘기고, 나머지 로컬 4-1 작업은 계속 진행한다.
