이 단계는 **관문 아님** — 거르기는 마지막 단계(MvpLaunch)의 광고 실측에서 한 번만 한다 (SKILL.md §1.1). 이 단계는 광고 앞에 내놓을 물건의 앞면(화면)을 완성하는 자리다.

**이 단계 이름이 프런트엔드 구현(FrontendBuild)인 이유** — 여기서 하는 일이 딱 그것이다. 2단계 코드에 남은 화면을 더하고, 빠진 화면이 없는지 대조하고, 움직임을 입히고, 배포한다. **새로 짓지 않고 이어서 짓는다** — 2단계에서 만든 리액트 코드가 곧 앱의 화면이고, 이 단계는 그 코드 위에 남은 화면과 상태 화면을 더한다. **이 앱 코드는 버리는 물건이 아니다** — 4단계(BackendBuild)가 같은 코드에 백엔드를 얹어 실서비스로 완성한다. 처음부터 끝까지 앱은 하나다.

**용어 두 개를 섞지 않는다**:

- **목업 캔버스** — 만든 화면들을 실제 주소로 작은 창(iframe)에 띄워 데스크톱 폭과 폰 폭(390)으로 나란히 늘어놓은 개발용 페이지(`/dev/canvas`). 2단계 개발환경 준비가 넣었고, 개발 서버에서만 열린다. 사람이 모든 화면을 한눈에 보는 도구이지 산출물이 아니다.
- **워킹 프로토타입(working prototype)** — 브라우저 로컬스토리지(localStorage)로 데이터가 도는 워킹 앱. 이 단계 끝의 **앱 상태를 가리키는 말**이지 단계 이름이 아니다. 백엔드가 아직 없다는 뜻일 뿐, 이 코드를 나중에 버린다는 뜻이 아니다.

「프로토타입」은 문서에서는 항상 수식어를 달고 쓴다.

## 1. 단계 목표

이 단계의 목표는 **2단계 코드에 남은 화면을 더해 화면 목록을 다 채우고, 움직임을 입혀 배포해 실제로 눌러지는 앱과 공개 링크를 만드는 것**이다. 네 스텝으로 간다:

1. **남은 화면 만들기** (§2.2) — 공통 부품을 먼저 만들고, 화면 목록에서 `만드는 때 = 3단계`인 화면과 상태 표의 `O` 칸 중 아직 없는 상태 화면을 2단계 코드에 더한다. 이미 있는 화면은 다시 만들지 않는다. **프런트엔드 + 로컬스토리지까지** (백엔드 없음).
2. **대조·사람 확인** (§2.3) — 화면 ID마다 주소와 상태 화면이 코드에 있는지 대조하고, `feature-list.md` 머리에 `화면 대조 끝:`을 적고, 고르지 않은 비교안을 지운 뒤 사람이 목업 캔버스와 앱을 본다.
3. **모션 + 배포 전 검사 + 코드 정리** (§2.4·§2.5) — 화면에 움직임을 입히고, 바로 배포하지 않고 배포 전 검사 세 가지(디자인 규칙 검사 · 코드 품질 검사 · 화면 문구 검사)를 통과한 뒤, 지난 정리 뒤 바뀐 코드를 정리한다.
4. **배포** (§2.6) — Vercel로 공개 링크를 만든다. 지인·팀 동료에게 보여줄 때도, 4단계에서 백엔드를 얹을 때도 이 링크를 쓴다.

산출물은 **프로젝트 루트의 앱 코드 + 배포 링크** 둘이다. **앱 코드가 본 산출물이고, 4단계가 그대로 이어받는다** — 백엔드가 없을 뿐 실서비스가 될 코드 그 자체다. 그래서 이 단계는 "나중에 다시 짤 거니까 대충"이 통하지 않는다 (§4 산출물 스펙). 목표를 이뤘는지는 §3 완료 체크리스트로 판정한다.

**입력은 넷이고 맡은 역할이 다르다**:

- **`feature-list.md` 6~10절 — 빠짐 없음 담당.** 어떤 화면을 몇 개 만들지, 빈 상태·오류 같은 상태 화면까지 무엇을 빠뜨리지 않을지가 여기서 나온다. **화면 목록과 상태 표가 곧 빠짐 점검표다** — `MVP 포함 = O` 화면이 전부 「주소」를 갖고, 상태 표의 `O` 칸이 전부 `?state=` 값을 가져야 이 단계 앞부분이 끝난다. 메뉴 구조(8절)가 메뉴 형태의 정본이다.
- **2단계 코드 — 생김새의 본보기이자 이어 지을 바탕.** 2단계가 만들고 2-2가 다듬은 화면, 1·2층 토큰, 셸, 공통 부품, 저장·조회 코드가 이미 있다. 이 단계가 더할 화면은 이 코드를 그대로 쓰고 같은 모양으로 만든다. 2-2 비교안의 빈 상태·로딩 화면이 상태 화면의 본보기다.
- **`design-brief.md` — 말투·고정 문구·화면 규칙의 정본.** 확정 브랜드 자산·보이스 앤 톤·「문자 그대로」 고정 문구·UI 패턴 지정·모션·접근성 바닥선·가치 우선순위·「12. 화면 규칙」이 전부 여기 있다. 참고 자료가 아니라 **지시**다 — §2.2.3 지시 골자가 이 문서를 그렇게 가리킨다.
- **`intent.md` — 화면 순서·원하는 것 자료.** 사람이 어떤 순서로 어떤 화면을 거치는지(「5. 유저 플로우」), 사용자가 이 서비스에서 무엇을 원하고 그래서 어디에 힘을 줄지(「3. 원하는 것」), 함께 정한 화면 모양(「6. 함께 정한 것」)이 여기서 나온다. 플로우 표의 핵심 행동은 그 화면에 **어떤 요소가 있어야 하는지**로 읽을 자료이지 문구·배치의 스펙이 아니다.

하나라도 빠지면 안 된다. 화면 목록만 보면 빠진 화면은 없는데 생김새가 제각각이 되고, 이미 있는 코드만 보면 만들어 둔 화면만 남고 상태 화면이 빠지고, 브리프가 빠지면 문구와 규칙이 흔들리고, `intent.md`가 빠지면 어디에 힘을 줄지가 흐려진다.

**무엇이 정본인가** — 화면 생김새·흐름·상태·화면 문구·디자인 값의 정본은 2단계에서 화면을 만든 순간부터 리액트 코드다. 브리프는 코드에 실을 수 없는 다섯 가지(말투, 「문자 그대로」 고정 문구, 「11. 이 서비스만의 사실」, 왜 그렇게 정했는지, 모션 방향)의 정본으로 끝까지 남는다. `feature-list.md`는 「어떤 화면을 만들어야 하나」 할 일 목록으로, 이 단계의 대조(§2.3)를 마치면 갱신하지 않는 기록이 된다 (SKILL.md §2.2). 그래서 `화면 대조 끝:`을 적기 전까지 이 단계는 `feature-list.md`의 「주소」 칸과 상태 표의 `?state=` 괄호를 채우고, 만들다 발견한 빠진 화면을 근거 한 줄과 함께 더할 수 있다. 화면이 크게 늘거나 흐름이 바뀌면 여기서 더하지 말고 2-1로 돌아가 화면 목록을 다시 연다.

**여기서 안 하는 것 (의도적)**:

- ❌ **개발환경 구성** — 스택 선택·버전 조합·Supabase 자리·Vercel 플러그인·디자인 시스템 첫 세팅·목업 캔버스는 2단계 개발환경 준비(`2-0-dev-setup.md`)가 이미 했다. 스택은 2단계에서 고정됐고 이 단계에서 다시 고르지 않는다 (`2-0-dev-setup.md` §2.1·§2.2).
- ❌ **백엔드** — DB 테이블·RLS·로그인·서버 로직은 전부 4단계(BackendBuild) 몫이다. 이 단계 데이터는 브라우저 로컬스토리지에 담긴다 (왜 이렇게 나누는지는 `2-0-dev-setup.md` §2.3).
- ❌ **퍼널 계측·실결제** — 4단계.
- ❌ **다크모드·다국어·성능 튜닝** — production 영역. (단 반응형은 폰으로 열어볼 수 있어야 하니 챙긴다.)

**작업 모드가 절마다 다르다** (SKILL.md §1.5) — 헷갈리지 않게 미리 정리한다:

| 절 | 모드 | 누가 하나 |
|---|---|---|
| §2.2 남은 화면 만들기 | 초안 모드 | AI가 공통 부품·남은 화면·상태 화면을 끝까지 만들고 화면 밖 검사(빌드·린트·타입)까지 |
| §2.3.1 빠진 화면 대조 | 초안 모드 | 메인이 대조 명령을 돌리고 빠진 것을 채우게 한다 |
| §2.3.3 대조 뒤 화면 보기 | — | **사람 몫.** AI는 화면을 보지 않는다 |
| §2.4 모션 참고 받기 | 인터뷰 모드 | 절 입구에서 사용자에게 한 번 묻는다. 분석·적용은 AI가 초안 모드로 완주 |
| §2.6 배포 후 클릭 확인 | — | **사람 몫.** AI가 자동 도구로 사인오프하지 않는다 |

## 2. 진행 절차

### 2.1 단계 시작 — 이전 정리 내용을 보여주고, 이번 단계가 할 일을 안내한다

이전 단계(Mockup)가 남긴 산출물과 코드를 읽고 짧게 요약해 보여주는 것으로 시작한다:

- **만들 화면 개수** — `feature-list.md` 화면 목록에서 `MVP 포함 = O`인 화면이 몇 개인지(전체 몇 개 중 몇 개인지 같이), 그중 2단계에서 만든 것과 이번에 만들 것(`만드는 때 = 3단계`)이 각각 몇 개인지, 상태 표의 `O` 칸 중 아직 `?state=` 값이 없는 상태 화면이 몇 개인지.
- **빠짐 점검 결과** — 10절의 고아 화면·막다른 골목이 0건인지, 일곱 갈래 점검에서 근거 없는 X가 남아 있는지.
- **화면 규칙** — 브리프 「12. 화면 규칙」이 채워졌는지, 건너뜀 한 줄인지.

빠짐 점검이 비어 있거나 0건이 아닌 항목·근거 없는 X가 보이면 화면부터 만들지 말고 **2-1로 잠깐 돌아가 화면 목록을 먼저 채우자고** 안내한다 (`2-1-mockup.md` §2.5.7). 화면 목록이 곧 만들 화면의 전체 목록이라, 목록에 없는 화면은 코드에도 안 생긴다.

이어서 `mvp/intent.md`의 **서비스 한 줄 정의**와 `mvp/design-brief.md`의 **관점·브랜드 인상 한 줄·확정 브랜드 자산**도 한 줄씩 보여준다 — 이번 화면의 말투와 미감 기준이다.

그다음 **남은 화면을 같은 코드에 더해 화면 목록을 다 채우고, 사람이 본 뒤 배포하는 단계**라는 걸 설명한다.

설명 골자 — 말투는 `AGENTS.md` 응답 톤에 맞춰 풀어서 전달:

> 2단계에서 화면 목록을 다 적었고, 그중 주요 화면은 실제 앱 코드로 만들어 다듬었습니다. 이번에는 남은 화면 — 설정·비밀번호 찾기·삭제 확인 같은 화면과, 데이터가 없을 때·불러오는 중·오류가 났을 때의 화면 — 을 같은 코드에 더하겠습니다. 이미 만든 화면은 그대로 두고, 2단계에서 정한 화면 규칙대로 만듭니다. 다 만들면 화면 목록과 하나하나 맞춰 본 뒤, 모든 화면을 한 페이지에 모아 보는 목업 캔버스 주소를 드리겠습니다. 보시고 괜찮다고 하시면 화면에 움직임을 입히고 배포까지 하겠습니다. 움직임을 입힐 때 어떤 움직임을 닮고 싶은지 한 번 여쭙겠습니다. 데이터는 아직 서버가 아니라 브라우저 안에 저장되는 수준입니다. 진짜 DB(데이터를 모아 두는 저장소)는 나중(4단계)에 붙입니다.

**끝나면 같이 볼 사람이 있는지 미리 한 번 짚어 둔다** — 비의무 (§2.7).

이미 `feature-list.md` 머리에 `화면 대조 끝:`이 있으면(스킬 중간 재실행 등) §2.4부터 이어 가고, §3 체크리스트로 검증해 부족한 부분만 보완하도록 안내한다 — 처음부터 다시 만들지 않는다.

**`이전 결론 → 이번 결론` 섹션은 이 단계엔 없다** (SKILL.md §2.2) — 그 체인은 6단계 `launch-plan.md`에서 처음 시작한다. 진행 중 아이디어·가설이 뒤집히면 그 결과를 코드에 그대로 반영하고, 문장으로 확정하는 건 6단계 최종 확정에서 한다.

### 2.2 남은 화면 만들기 — 2단계 코드에 「만드는 때 = 3단계」 화면과 상태 화면을 더한다

이 절차는 SKILL.md §1.5 **초안 모드** — AI가 문서와 이미 있는 코드를 스펙 삼아 끝까지 만든 뒤 완성본으로 리뷰받는다. 중간에 화면 하나하나 승인받지 않는다.

**범위** — 화면 목록에서 `만드는 때 = 3단계`인 화면, 그리고 상태 표의 `O` 칸 중 아직 `?state=`로 뜨지 않는 상태 화면. 상태 화면은 상태 표의 `O` 옆 한 줄 문구를 그대로 지시로 쓴다. 이미 있는 화면은 다시 만들지 않는다.

**상태 화면은 `?state=`로 뜨게 한다** — 주소 끝에 `?state=empty|loading|error|forbidden`을 붙이면 그 상태가 뜬다. 이 표시는 저장·조회 코드가 개발 서버에서만 상태 표시 읽기 도우미(`src/lib/dev-state.ts`)로 읽어 빈 결과·느린 응답·오류·권한없음을 돌려준다. 화면 코드는 그 결과를 실제 처리 경로대로 그리면 된다 — 화면 안에 상태 흉내를 따로 넣지 않는다. 그래서 상태 화면이 뜨면 실제 빈 결과·오류 처리 경로가 돈다는 뜻이기도 하다.

**만든 화면은 목업 캔버스 목록 파일에 올린다** — 화면마다 `src/app/(dev)/dev/canvas/screens.ts`에 화면 ID·이름·흐름 묶음·주소·띄울 상태를 올린다. 메인은 에이전트 보고의 「화면 ID ↔ 주소」 표로 화면 목록의 「주소」 칸과 상태 표 칸 끝 괄호(`?state=` 값)를 채운다.

만드는 일은 **서브 에이전트에 위임한다** — 화면이 많으면 출력이 크고, 메인이 직접 하면 뒤따르는 대조(§2.3)와 검수에 써야 할 맥락이 그 출력으로 덮인다. 화면이 많으면 §2.2.1대로 공통 부품을 먼저 만든 뒤 묶음으로 나눠 여러 에이전트에 맡긴다.

**모델은 sonnet이다** — 공통 부품·남은 화면·상태 화면 모두. 생김새와 짓는 규칙은 2단계가 이미 정했고(2-1이 처음 만들고 2-2가 다듬은 코드), 이 단계는 정해진 공통 부품과 화면을 따라 만드는 일이라서다. 처음 정하는 일은 opus, 따라 하는 일은 sonnet이 하네스의 기본 원칙이다 (SKILL.md §3.2).

1. **시작 전 확인 (메인)** — `feature-list.md`의 빠짐 점검(10절)이 비어 있거나 X가 근거 없이 남아 있으면 만들지 말고 2-1로 돌아가 채운다 (§2.1).
2. **공통 부품과 주소 (서브 에이전트 하나, sonnet)** — §2.2.1.
3. **남은 화면 (서브 에이전트 sonnet, 묶음이면 여럿)** — 지시서에 `2-1-mockup.md` 「주요 화면 만들기」 절의 **화면 작업 지시서에 꼭 넣을 문장 전부**를 넣고, 3단계 몫 한 문장을 더한다:
   - 3단계 몫 한 문장: 「화면 목록의 `만드는 때 = 3단계` 행과 상태 표의 `O` 칸 중 아직 없는 것만 만들어라. 이미 있는 화면은 고치지 마라. 공통 부품은 `components/common/`의 것을, 화면 주소는 주소 모음 파일의 것을 쓰고, 공통으로 쓸 만한 부품이나 새 주소 모음을 따로 만들지 말고 보고하라.」
4. **화면 밖 검사 (메인)** — 빌드·린트·타입 검사를 돌린다. 화면은 보지 않는다 (`AGENTS.md` 검증 원칙).

**화면 요소 → 부품 대응과 짓는 규칙은 2단계 그대로다** — 버튼·확인 창·입력칸 같은 화면 요소를 어느 shadcn 부품의 어느 variant로 만드는지, 모양이 shadcn 기본과 다를 때 푸는 차례, 처음부터 피할 모양(목록 항목마다 카드·상태색 장식·14px 아래 글자·안내 문구가 이름 노릇)은 `2-1-mockup.md` 「주요 화면 만들기」 절의 「화면 요소 → 부품」 표를 따른다. 이 규칙은 스킬 밖 문서에만 있어 에이전트가 알 길이 없으니, 메인이 표와 프로젝트 `AGENTS.md` 디자인 시스템 연결 정보의 「적용 규칙 요약」을 `<constraints>`에 걸러 넣고 이 꼭 넣을 문장을 더한다:

> 요소마다 「화면 요소 → 부품」 표로 부품·variant를 정하고, 대응 없는 요소는 전용 부품으로 만들어 인벤토리에 등록하며, 보고에 「화면 요소 → 부품」 표를 남겨라.

메인은 diff 검수 때 이 표를 본다 — 표에 없는 요소가 화면에 있거나, 같은 요소가 화면마다 다른 부품으로 만들어졌으면 거기서 잡는다.

**이미지·아이콘 자산** — 브리프 「이미지·영상 계획」 표의 장면은 실물이 있으면 이때 코드에 넣는다(`public/` 등 프로젝트 자산 위치). 브리프는 고치지 않는다 — 이미지가 어디 있는지는 코드가 정본이다. 없으면 장면 설명을 적은 자리 표시를 그대로 두고, 늦어도 6단계 광고 전에 실물로 바꾼다(`1-intent.md` §4.3 「4.」).

#### 2.2.1 공통 부품 먼저

**화면이 많아 여러 에이전트에 묶음으로 나눠 맡길 때는, 나누기 전에 공통 부품과 주소부터 만든다.** 첫 에이전트가 두 가지를 먼저 해 둔 뒤에 묶음 에이전트를 띄운다.

1. **공통 부품** — 아래 「어느 화면 묶음에서나 반드시 나오는 부품」 중 아직 없는 것을 `components/common/`에 만든다: 불러오기 실패 패널(「다시 시도」), 권한없음 패널, 로딩 뼈대(목록·글·입력 화면 모양), 입력 칸 묶음(이름·칸·도움말·오류 문구 + `aria-describedby`), 되돌리기 어려운 확인 창(진행 표시·창 안 오류·「다시 시도」), 본문 폭 틀, 위치 줄(돌아가기 링크), 로그인 필요 행동 막기(로그인·가입 마무리로 보내기)와 데이터 오류 갈래(없음·권한없음·로그인 필요). 2단계에서 이미 만든 부품은 다시 만들지 않고, 2-2 비교안의 빈 상태·로딩 화면을 본보기로 모양을 맞춘다.
2. **주소** — 이번에 더할 화면의 주소를 전부, 2단계가 만든 주소 모음 파일(화면 주소를 한 곳에 모은 상수 파일 — 없으면 이때 하나 만든다)에 먼저 적는다. 묶음마다 주소를 따로 모으면 같은 주소가 여러 파일에 생긴다.

묶음 에이전트에게는 이 부품과 주소를 쓰고, 공통으로 쓸 만한 부품이나 새 주소 모음을 따로 만들지 말고 보고하라고 지시한다. 묶음마다 공통 부품·주소를 따로 만들면 3단계 끝 코드 정리(§2.5 「검사 뒤 — 코드 정리」)가 그것을 합치느라 커진다 — 먼저 한 곳에 모아 두는 것이 정리를 작게 하는 가장 싼 방법이다.

화면이 적어 에이전트 하나가 끝까지 만들면 이 차례를 따로 떼지 않는다 — 같은 에이전트가 공통 부품부터 만들고 화면으로 간다.

#### 2.2.2 입력 — 문서 세 개와 이미 있는 코드

**에이전트가** `mvp/feature-list.md` · `mvp/intent.md` · `mvp/design-brief.md` **셋을 전문 그대로 읽고**, 이미 있는 화면·공통 부품·저장·조회 코드를 읽는다 — 작업의 입력(대상)이라 에이전트가 읽는다. `AGENTS.md`가 메인이 읽으라고 하는 「규칙 자료」와 다르다. 요약해서 넘기지 않는다 — 화면 목록이 길어서 요약하면 잘린 만큼 화면이 빠진다.

#### 2.2.3 지시 골자

화면 에이전트에 넘길 지시 골자 — `AGENTS.md` 태그 규칙대로 `<direction>`·`<constraints>`에 나눠 담는다. 2단계 지시 골자(`2-1-mockup.md` 「주요 화면 만들기」 절)의 문구·데이터·브리프·가독성 줄은 그대로 가져오고, 아래가 이 단계의 몫이다:

> **입력 세 개와 이미 있는 코드의 역할이 다르다.**
>
> - `feature-list.md` 6~10절 — **만들 화면의 전체 목록과 구조(정본).** 6절 화면 목록에서 `만드는 때 = 3단계`인 화면을 **ID 순서대로 하나도 빠짐없이** 만들고, 7절 상태 표에서 `O`인데 `?state=` 값이 안 붙은 상태 화면(빈 상태·로딩·오류·권한없음)도 **각각 `?state=`로 뜨게** 만든다. `O` 옆에 적힌 한 줄이 그 상태 화면에 보여줄 것이다. 반대편 역할(공급자·운영자)의 화면도 같은 기준으로 전부 만든다. 화면 목록에 없는 화면은 만들지 마라. `MVP 포함 = X`인 화면으로 가는 버튼도 만들지 마라 — 눌러도 갈 곳이 없는 죽은 버튼이 된다. 어느 버튼인지는 9절 「미룬 화면을 가리키는 버튼」 표에 있다. **홈 첫 화면은 화면 목록 홈 행에 적힌 결정(유형·최상단 차례·로그인 전후 분리)을 제약으로 따른다** — 유형별 관례보다 이 기록이 우선이다.
> - **이미 있는 코드** — 2단계 화면과 공통 부품이 생김새의 본보기다. 같은 토큰·셸·부품으로, 2-2 비교안의 빈 상태·로딩 화면과 같은 모양으로 상태 화면을 만든다. 데이터는 이미 있는 저장·조회 코드를 거친다. 기존 화면에는 손대지 마라.
> - `design-brief.md` — **시각 디자인과 화면 문구의 정본. 참고 자료가 아니라 지시다.** 특히 「12. 화면 규칙」(글자 단계·간격 단계·격자·색 쓰는 자리·버튼 종류·부품 상태·아이콘·이미지 비율·폰 배치 규칙)을 그대로 따른다. 나머지는 2단계 지시 골자와 같다.
> - `intent.md` — **화면 순서와 사용자가 원하는 것을 읽는 자료.** 플로우 표의 화면 이름과 핵심 행동은 그 화면에 어떤 요소가 있어야 하는지를 보여주는 **단서**이지 문구·배치의 스펙이 아니다.
>
> **메뉴**: `feature-list.md` 8절 「메뉴 구조」가 정본이다 — 거기 적힌 폭·메뉴 그대로만 만들고, 그 절에 없는 메뉴(데스크톱용 헤더 메뉴·사이드바 등)는 새로 지어내지 마라. 그 절에 폭별 메뉴가 안 적혀 있으면 임의로 만들지 말고 먼저 물어봐라.
>
> **폭**: 화면은 처음부터 반응형이다. 화면 전체가 바뀌는 전환(상단 메뉴 ↔ 햄버거 메뉴처럼) 하나만 뷰포트 분기로 만들고, 나머지 부품 크기 대응과 브리프 「12」의 폰 배치 규칙은 컨테이너 쿼리로 만든다 (§2.5 검사 ① 3번).
>
> **보고**: 만든 화면의 화면 ID(상태 화면은 ID와 `?state=` 값)와 주소를 짝지은 표, 「화면 요소 → 부품」 표, 없어서 만들지 못한 부품, 임시로 정한 것, 「사실 확인 필요」 목록, 빌드·린트·타입 결과.
>
> **전제가 다르면 멈추고 보고하라** — 화면 목록과 `intent.md`·브리프가 서로 어긋나면 임의로 고르지 말고 무엇이 어긋나는지 적어 돌려보내라. 만들다가 화면 목록에 없는 화면이 꼭 필요해 보이면 만들지 말고 근거 한 줄과 함께 보고하라.

- **메뉴 형태는 지시에 적지 않는다** — `feature-list.md` 8절을 정본으로 가리키고 「그 절에 없는 메뉴는 새로 만들지 마라」는 금지만 둔다. 지시에 메뉴 형태를 직접 적으면 8절이 폭별로 다른 메뉴를 정해도 지시 쪽이 이겨 어긋난 화면이 나온다.
- **브리프 「12」와 공통 부품은 메인이 걸러 넣지 않아도 된다** — 「12」는 에이전트가 브리프 전문을 읽으며 보고, 공통 부품은 코드에 이미 있다. 다만 `visual-polish.md`의 항목 중 이번 화면에 닿는 것(예: 표가 있는 운영자 화면이면 R5 표 → 카드)은 부를 때만 들어오는 규칙 자료라 메인이 읽고 지시서에 걸러 넣는다 (`AGENTS.md` 위임 절).
- **프로젝트 얘기를 지시에 덧붙이지 않는다** — 무엇을 만들지는 세 파일과 이미 있는 코드가 다 말해 준다. 여기에 화면 설명이나 색·문구 지시를 덧대면 파일과 어긋난 지시가 섞인다. 특히 색·서체·문구는 `design-brief.md`가 정본이라 지시에 다시 적으면 브리프와 두 갈래가 된다.

#### 2.2.4 데이터 — 저장·조회 코드 완성

저장·조회 코드(`lib/storage.ts`)의 짓는 규칙 — 저장 구조 한 곳, `Promise` 반환, 저장소 객체를 인자로, 소유자 주석, 가짜 로그인 상태 — 은 `2-1-mockup.md` 「주요 화면 만들기」 절 그대로다. 이 단계는 남은 화면까지 그 규칙 안에서 **완성할 책임**을 진다:

- 저장·조회·수정·삭제가 실제로 돌아야 한다 — 새로고침해도 데이터가 남는 수준. 화면만 전환되는 껍데기는 이 단계 완료가 아니다.
- 새로 더한 데이터도 엔티티마다 소유자 주석 한 줄이 있다 (`// 소유자: 이 항목을 만든 사용자` 같은). 4단계에서 그대로 접근 규칙(RLS)의 기준이 된다.
- 화면(컴포넌트)에서 로컬스토리지 API를 직접 부르는 곳이 0건이다 — 반드시 저장·조회 코드를 거친다. 한 화면이라도 옆길로 새면 그 화면만 4단계에서 따로 찾아 고쳐야 하고, `?state=`로 상태 화면도 뜨지 않는다.

```bash
grep -rnE --exclude-dir=ui 'localStorage|sessionStorage' src/app src/components | grep -v 'src/app/(dev)/'
```

- 통과: 0건. 걸린 줄은 저장·조회 코드로 옮긴다.
- 비밀번호·개인정보를 로컬스토리지에 넣지 않는다 — 브라우저에 그대로 노출되는 공간이다.

#### 2.2.5 범위와 에스컬레이션

- **범위**: 화면 목록의 `MVP 포함 = O` 화면 전부 + 상태 표에 `O`로 적힌 상태 화면. `MVP 포함 = X`인 화면으로 가는 버튼은 만들지 않는다.
- **에스컬레이션**: 화면 코드와 `design-brief.md`가 서로 어긋날 때(→ 말투·고정 문구·규칙 결정은 브리프, 생김새·값은 코드가 기준. 어긋난 지점은 보고), 화면 목록에 있는데 코드에 없고 문서만으로는 모양을 정할 수 없는 화면을 발견했을 때, 외부 서비스 추가가 필요할 때는 멈추고 배치로 질문한다. 그 외 애매함은 합리적 가정 + `추후 결정:` 마킹 후 계속.
- **정지 조건**: 같은 산출물의 자율 재작업은 최대 2회 (SKILL.md §1.5).

### 2.3 빠진 화면 대조와 사람 확인

남은 화면을 다 만들면 모션으로 가기 전에 세 가지를 차례로 한다: ① 빠진 화면 대조 → ② `화면 대조 끝:` 표시와 비교안 정리 → ③ 사람이 목업 캔버스와 앱을 본다.

#### 2.3.1 빠진 화면 대조 — 화면 ID마다

메인이 화면 ID마다 확인한다. 눈대중으로 "대충 다 있네" 하고 넘어가지 않는다 — 여기가 빠진 화면을 잡는 마지막 자리다.

1. `MVP 포함 = O`인 모든 화면이 「주소」를 가졌고 목업 캔버스 목록 파일에 있는가 — 2단계 화면과 이번에 더한 화면 모두.
2. 상태 표 `O` 칸이 모두 `?state=` 값을 가졌는가.
3. **반대편 역할(공급자·운영자) 화면**이 빠지지 않았는가 — 플로우 표의 대표 일 쪽만 만들어지기 쉬운 자리다.
4. `MVP 포함 = X`인 화면으로 가는 **죽은 버튼**이 코드에 없는가 (9절 표 기준 — 표의 버튼 문구로 코드를 grep한다).
5. **홈 첫 화면**이 화면 목록 홈 행에 적힌 **유형·최상단 차례·로그인 전후 결정**과 맞는가. 유형별 관례(`common-patterns.md` §1)와 대조하는 게 아니라 **홈 행 기록**과 대조한다 — 사용자가 관례와 다르게 정해 둔 것을 관례로 되돌리지 않는다. 로그인 전후를 가르기로 했으면 두 화면이 다 있어야 한다.

1·2번은 기계로 맞댄다 — 화면 목록 6절의 ID와 목업 캔버스 목록 파일의 ID를 비교하고, 상태 표의 `O` 칸에 `?state=` 값이 있는지 본다. 프로젝트 루트에서 돌린다:

```bash
F=mvp/feature-list.md
R='src/app/(dev)/dev/canvas/screens.ts'
T=$(mktemp -d)
# 1-가. 「주소」 칸이 빈 MVP 화면
awk -F'|' '/^## 6\./{f=1;next} /^## /{f=0} f && $2 ~ /S-[0-9]/ && $9 ~ /^ *O *$/ && $11 ~ /^ *$/ {gsub(/ /,"",$2); print "주소 없음: " $2}' "$F"
# 1-나. 화면 목록(MVP 포함 = O)과 목업 캔버스 목록 파일의 ID 맞대기
awk -F'|' '/^## 6\./{f=1;next} /^## /{f=0} f && $2 ~ /S-[0-9]/ && $9 ~ /^ *O *$/ {gsub(/ /,"",$2); print $2}' "$F" | sort -u > "$T/list-ids.txt"
grep -oE '"S-[0-9]+[A-Za-z0-9-]*"' "$R" | tr -d '"' | sort -u > "$T/canvas-ids.txt"
comm -3 "$T/list-ids.txt" "$T/canvas-ids.txt"
# 2. 상태 표에서 O인데 ?state= 값이 없는 칸
awk -F'|' 'BEGIN{split("빈 상태|로딩|오류|권한없음",n,"|")} /^## 7\./{f=1;next} /^## /{f=0} f && $2 ~ /S-[0-9]/ {for(i=4;i<=7;i++) if($i ~ /^ *O/ && $i !~ /\?state=/) print "상태 값 없음:" $2 "— " n[i-3]}' "$F"
```

- 통과: 네 명령 모두 아무것도 출력하지 않는다. `comm -3`의 왼쪽 칸은 「화면 목록에는 있는데 목록 파일에 없는 화면」, 들여 쓴 오른쪽 칸은 「목록 파일에만 있는 화면」이다. 오른쪽 칸에 비교안만 나오면 §2.3.2에서 지우니 통과로 본다.
- 전제: 화면 목록 6절의 칸 순서가 `ID · 화면 이름 · 역할 · 목적 · 들어오는 길 · 나가는 길 · 주 행동 · MVP 포함 · 만드는 때 · 주소`이고(`2-1-mockup.md` §4.1 템플릿 — 줄 맨 앞 `|` 때문에 awk 칸 번호는 하나씩 밀려 ID가 `$2`, 주 행동 `$8`, MVP 포함 `$9`, 주소 `$11`), 목록 파일이 화면 ID를 `"S-01"`처럼 따옴표 안에 적는다. 칸 순서나 목록 파일 형식이 다르면 칸 번호(`$9`·`$11`)와 정규식만 맞춰 고친다 — 「주 행동」 칸이 없는 옛 화면 목록이면 `$8`·`$10`이다. 목록 파일 형식은 `.claude/templates/mockup-canvas/README.md`가 정본이다.
- 임시 파일은 `mktemp -d`로 만든 폴더에 쓴다 — 여러 프로젝트·세션이 같은 `/tmp` 파일 이름을 덮어쓰지 않게 하려는 것이다.

빠진 게 있으면 그 ID를 그대로 짚어 더 만들게 한다(§2.2 지시서 그대로). 다 채워야 다음으로 간다. 화면이 너무 많이 늘거나 흐름이 통째로 바뀌면 이 단계에서 더하지 말고 2-1로 돌아가 화면 목록을 다시 연다.

#### 2.3.2 화면 대조 끝 표시와 비교안 정리

대조가 끝나면 메인이 둘을 한다:

1. **`feature-list.md` 머리에 `화면 대조 끝: YYYY-MM-DD`를 적는다.** 이 표시는 진행 상황 표시일 뿐이다 — 문서를 고정한다는 뜻이 아니다. 다만 `feature-list.md`는 이 대조로 할 일 목록의 역할을 마쳤으므로, 그 뒤로는 화면이 늘거나 빠져도 갱신하지 않는 기록이 된다(코드에만 반영한다). 브리프와 코드는 그 뒤로도 계속 정본이다. `/idea-to-mvp`가 지금 몇 단계인지 알아낼 때 이 표시를 「3단계 앞부분이 끝났다」는 단서로 쓴다 (SKILL.md §1.2).
2. **고르지 않은 비교안을 비교안 폴더(`src/app/(dev)/dev/drafts/`)에서 지운다.** git에는 남는다. 2-2에서 고른 판은 이미 본 화면 자리로 옮겨졌으니 남은 것은 고르지 않은 판뿐이다. 지우기 전에 본 코드가 비교안 폴더를 불러오는 곳이 0건인지 확인하고, 지운 뒤 목업 캔버스 목록 파일에서도 그 항목을 빼고 **빌드를 먼저 다시 돌린 뒤 타입 검사(`tsc --noEmit`)를 돌린다** — 빌드가 만들어 두는 주소별 타입 파일(`.next/types`)이 지운 화면을 아직 가리키고 있어, 빌드 전에 타입 검사를 돌리면 지운 화면 때문에 실패한다:

```bash
grep -rn 'dev/drafts' src --include='*.ts' --include='*.tsx' | grep -v '^src/app/(dev)/'
```

- 통과: 0건. 걸리면 그 부품을 본 코드 쪽(`components/`)으로 옮긴 뒤 지운다.

#### 2.3.3 사람이 목업 캔버스와 앱을 본다

**여기서는 사람이 본다.** AI는 화면을 보지 않는다 — 브라우저 자동화로 대신 열어보고 "확인 완료"라고 결론 내지 않는다 (`AGENTS.md` 검증 원칙). 목업 캔버스는 사람이 보는 도구다.

1. 개발 서버가 이미 떠 있으면 그 서버를 쓰고, 없으면 띄운다. **목업 캔버스 주소**(`http://localhost:<포트>/dev/canvas`)를 사용자에게 알려주고, 대조 결과를 한 줄로 덧붙인다 — "화면 목록 O 화면 23개(2단계 14개 + 이번 9개) + 상태 화면 9개, 목록 파일과 전부 맞습니다". 모든 화면과 상태가 목업 캔버스에 처음 다 모이는 순간이라, 전체를 한 번에 볼 자리다. 다 만든 뒤에 보여준다 — 일부만 만든 상태로 확인받지 않는다.
2. 처음 내려 볼 때 느릴 수 있다고 한 번 알린다 — 개발 서버는 주소를 처음 열 때 그 화면을 컴파일(코드를 브라우저가 읽는 꼴로 바꾸는 일)한다. 사용자가 빠르게 훑고 싶어 하면 내 컴퓨터에서만 실서비스 빌드로 여는 방법(`.claude/templates/mockup-canvas/README.md` 「실서비스 빌드로 빠르게 보기」)을 쓴다.
3. 사용자가 **말로** 고칠 곳을 알리면 코드를 고치고 다시 보여준다. 문구 한 줄·색 하나 같은 작은 손질은 메인이 직접, 여러 화면은 §2.2 지시서대로 위임한다. 말투·고정 문구·규칙 결정이 바뀌면 브리프도 고친다. 괜찮다고 하면 모션으로 넘어간다.

### 2.4 모션·마이크로 인터랙션 다듬기

모션(motion)은 화면 속 움직임이고, 마이크로 인터랙션(micro-interaction)은 버튼을 눌렀을 때 살짝 들어가는 반응처럼 **동작 하나에 붙는 작은 움직임**이다. 이 절에서 둘을 함께 코드에 입힌다.

**왜 여기인가** — 2단계 화면은 움직임 없이 만들었다. `mvp/design-brief.md` 「8. 모션·인터랙션 방향」에 원칙만 있다. 그대로 두면 화면을 만드는 에이전트가 제멋대로 넣는다. 화면이 바뀌는 중에 움직임을 입히면 화면을 고칠 때마다 움직임도 다시 뜯게 되니, **남은 화면 대조와 사람 확인(§2.3) 직후가 자리다.** 4단계 전에 하는 건, 3단계 배포에서 사람이 화면과 움직임을 한 번에 보고 확정하려는 것이고, 4단계는 화면이 아니라 데이터·로그인을 얹는 자리라 움직임 작업이 섞이면 범위가 흐려진다. 순서는 §2.5 실행 순서 그림이 정한다.

**작업 모드** — 입구의 「참고 받기」만 인터뷰 모드다(사용자에게 한 번 묻는다). 분석·브리프 기록·코드 적용은 초안 모드로 AI가 완주한다.

**기본 세트 넷 — 바닥선, 항상 넣는다**

사용자에게 묻지 않고 넣는다. `mvp/design-brief.md` 「8. 모션·인터랙션 방향」의 「완전성」 행과 같은 목록이다.

| 자리 | 무엇을 | 예 |
|---|---|---|
| 눌렀을 때 반응 | 버튼·목록 행·탭처럼 누르는 요소 전부에 눌렸다는 표시 | 살짝 어두워지거나 작아짐 |
| 화면 진입·전환 | 화면이 열리거나 바뀔 때 갑자기 튀지 않게 | 짧은 페이드 |
| 목록 항목 추가·삭제 | 항목이 생기거나 사라질 때 | 새 항목이 스르르 나타남, 지운 항목이 접히며 사라짐 |
| 로딩·완료 피드백 | 기다리는 동안과 끝났을 때 | 로딩 뼈대(`Skeleton`)·알림 띠(`Sonner`) |

마우스로 쓰는 화면(웹 데스크톱 폭)이면 마우스를 올렸을 때 반응도 넣는다.

**장식 움직임(시그니처) — 선택, 사용자가 원할 때만**

시그니처 움직임(signature motion)은 서비스를 기억나게 하는 눈에 띄는 장식용 움직임이다 (예: 첫 화면이 스크롤에 따라 장면이 바뀜). **`mvp/design-brief.md` 「8. 모션·인터랙션 방향」의 「시그니처 움직임」 행에 `사용자 확정`으로 적혀 있을 때만 넣는다.** 그 행이 「없음」이면 넣지 않는다(지위 정의는 `1-intent.md` §4.3 — 이 행의 바닥선은 `기본값` 「없음」이다) — AI가 멋을 내려고 끼워 넣지 않는다. 장식도 같은 표의 「정서」·「금지」 행과 아래 접근성(동작 줄이기) 규칙을 그대로 따른다.

**참고 받기 — 이 절 입구에서 사용자에게 묻는다**

디자인 스타일을 참고 사이트로 정하듯(「토스처럼」), 움직임도 「이 사이트처럼」 식으로 받는다. `mvp/design-brief.md` 「8. 모션·인터랙션 방향」의 「참고 사이트」 행이 「없음」이 아니면 그걸로 시작하고, 더할 게 있는지만 묻는다.

안내 골자 — 말투는 `AGENTS.md` 응답 톤에 맞춰 풀어서 전달:

> 이제 화면에 움직임을 입힐 차례입니다. 아래 넷은 기본으로 넣겠습니다 — 버튼 눌렀을 때 반응, 화면 열리고 바뀔 때 부드럽게, 목록에 항목이 생기고 사라질 때, 로딩 중·완료 표시.
>
> 그 위에 「이런 느낌으로 움직였으면 좋겠다」 하는 참고가 있으면 알려 주세요. 받은 참고는 제가 「어디서·무엇이·얼마나 길게·어떤 속도 변화로·어떤 순서로」 움직이는지 나눠서 디자인 브리프에 적고, 그대로 앱 전체 움직임의 기준으로 쓰겠습니다. 아래 네 가지 중 편한 것으로 주세요.
>
> **1. 사이트 주소** — 「이 사이트처럼」 하고 주소만 주세요. 예: https://www.getstanley.ai/welcome
> - 제가 브라우저 도구로 직접 열어서 보겠습니다.
> - 다만 움직임은 화면 캡처에 잡히지 않을 때가 많습니다. 그래서 **어느 요소가 언제 어떻게 움직이는지** 한두 줄만 같이 적어 주세요. 예: 「스크롤을 내리면 가운데 그림이 커지면서 다음 장면으로 바뀜」.
>
> **2. 화면 녹화(영상·GIF)** — 마음에 드는 앱·사이트를 직접 찍어서 올려 주세요.
> - **맥**: Shift+Cmd+5를 누르면 화면 아래에 막대가 뜹니다. 거기서 화면 전체 기록이나 선택 부분 기록 단추를 고르고 「기록」을 누르세요. 끝낼 때는 화면 맨 위 메뉴 막대의 정지 단추(네모)를 누르면 됩니다. 파일은 보통 바탕화면에 저장됩니다.
> - **아이폰**: 화면 오른쪽 위에서 아래로 쓸어내려 제어 센터를 열고, 화면 기록 단추(동그라미 안에 점)를 누르세요. 3초 뒤 기록이 시작되고, 끝낼 때는 화면 위쪽의 빨간 표시를 눌러 멈추세요. 파일은 사진 앱에 저장됩니다. 제어 센터에 그 단추가 보이지 않으면 제어 센터 편집에서 「화면 기록」을 추가하시면 됩니다. 홈 버튼이 있는 기종은 화면 아래에서 위로 쓸어 올려 제어 센터를 여세요.
> - 제가 영상을 직접 못 볼 수도 있습니다. 그래서 **몇 초쯤에 무엇이 움직이는지** 말로 같이 적어 주세요. 예: 「2초쯤 카드 세 장이 아래에서 하나씩 올라옴」.
>
> **3. 말로 묘사** — 느낌을 그냥 말로 적어 주세요. 예:
> - 「버튼 누르면 살짝 눌리는 느낌」
> - 「카드가 아래에서 순서대로 올라옴」
> - 「화면이 바뀔 때 옆으로 밀리듯 넘어감」
>
> **4. 프리셋 중 고르기** — 미리 짜 둔 묶음 중 하나를 골라 주세요.
> - **절제** — 페이드(서서히 나타나고 사라지는 효과)만. 조용하고 믿음직한 인상(돈·건강·업무 도구)에 맞습니다.
> - **부드러움** — 페이드에 살짝 밀기를 더함. 친근하고 편안한 인상(생활 서비스·커뮤니티)에 맞습니다.
> - **생동감** — 끝에서 살짝 튀는 움직임에 하나씩 순서대로 등장. 발랄하고 재밌는 인상(놀이·소셜·젊은 사용자)에 맞습니다.
> - **스크롤 따라 드러남** — 내려갈수록 내용이 하나씩 나타남. 이야기를 풀어 주는 소개 화면(랜딩)에 맞습니다.
>
> 잘 모르겠으면 「모르겠어」라고 하셔도 됩니다. 브랜드 인상 한 줄을 보고 「절제」나 「부드러움」 중에 제가 골라서 진행하겠습니다. 「생동감」이나 「스크롤 따라 드러남」이 더 어울려 보이면, 그것은 눈에 띄는 장식이라 쓰기 전에 한 번 여쭙겠습니다. 배포한 화면을 보고 바꾸시면 됩니다.

받은 입력별로 AI가 하는 일:

- **사이트 주소** — 브라우저 도구로 열어 직접 본다. 우리 화면을 판정하는 게 아니라 참고를 읽는 일이라 「화면 검증은 사람 몫」 원칙과 부딪히지 않는다. 바깥 사이트를 여는 일이니 같은 실패 2회면 멈추고, 401·403·404는 다시 시도하지 않는다 — 그때는 사용자 묘사만으로 분석한다. 캡처로 움직임이 안 잡히면 사용자에게 묘사를 받는다.
- **화면 녹화** — 파일을 읽어 본다. 못 읽으면 사용자가 적은 「몇 초쯤 무엇이」 묘사를 근거로 삼는다.
- **말로 묘사·프리셋** — 그대로 아래 분석표로 옮긴다.
- **「모르겠어」** — `mvp/design-brief.md` 「1. 브랜드 인상과 관점」의 브랜드 인상 한 줄을 보고 프리셋 하나를 추천한다. AI가 추천해 바로 진행하는 프리셋은 「절제」·「부드러움」 둘뿐이고, 지위는 `가정`이다. 「생동감」·「스크롤 따라 드러남」은 장식·스크롤 연동이 들어 있어, 브랜드 인상에 맞아 보여도 그 자리에서 사용자 확인을 받아야 쓴다 — 받으면 「시그니처 움직임」 행에 `사용자 확정`으로 적는다.
- **「참고 없음」** — 기본 세트 넷만 넣고, 「정서」 행을 따라 길이·곡선을 정한다.

**분석 항목표 — 참고를 이 다섯 항목으로 나눈다**

| 항목 | 무엇을 적나 | 예 |
|---|---|---|
| 어디서 | 진입 · 스크롤 · 마우스 올렸을 때 · 화면 전환 · 피드백(누름·로딩·완료) 중 언제 | 첫 화면 진입 |
| 무엇이 | 페이드 · 밀기 · 확대 · 순서대로 등장 중 어떤 움직임으로 | 아래에서 밀며 페이드 |
| 길이 | 빠름 · 보통 · 느림 중 어느 단계 | 보통 |
| 가속 곡선 | 가속 곡선(easing — 움직임이 처음과 끝에서 빨라지고 느려지는 모양) | 끝에서 부드럽게 멈춤 / 끝에서 살짝 튀었다 멈춤 |
| 순서 | 여러 개가 같이 움직일 때 누가 먼저, 얼마 간격으로 | 제목 → 본문 → 버튼, 짧은 간격 |

분석 결과는 `mvp/design-brief.md` 「8. 모션·인터랙션 방향」 표에 **움직임 하나당 한 행**으로 적는다 — 항목 열에 「움직임: <어디서>」, 내용 열에 나머지 네 항목을 한 줄로, 지위는 `가정`. **적는 건 말로 된 방향(어디서·무엇이·길이 단계·곡선 느낌·순서)이지 ms 값이나 코드가 아니다** — 값은 1층 토큰에만 있다 (SKILL.md §2.1). 사용자가 배포 화면을 보고 괜찮다고 하면 `사용자 확정`과 확정일로 바꾼다 (§2.6 3번). 참고 사이트를 받았으면 같은 표의 「참고 사이트」 행에 주소와 닮을 움직임을 적고 지위를 `사용자 확정`으로 바꾼다 — 사용자가 직접 준 주소라서다. 사용자가 장식 움직임을 원하면 「시그니처 움직임」 행도 채운다 — 사용자가 원한다고 말한 것이라 바로 `사용자 확정`이다.

값이 전달되는 경로를 사용자에게 한 번 설명한다 — 말투는 `AGENTS.md` 응답 톤에 맞춰 풀어서 전달:

> 움직임 값은 이렇게 쓰입니다. 주신 참고를 제가 나눠서 디자인 브리프(`mvp/design-brief.md`의 「8. 모션·인터랙션 방향」)에 한 줄씩 적고 → 거기 적힌 길이와 속도 변화를 디자인 시스템 맨 아래층(1층)에 「빠름·보통·느림」 같은 값 몇 개로 넣고 → 화면 코드는 그 이름만 불러 씁니다. 그래서 나중에 「전체적으로 좀 느려」라고 하시면 화면을 하나하나 고치는 것이 아니라 1층 값 하나만 바꾸면 앱 전체가 같이 바뀝니다.

**값은 토큰으로**

- 길이 세 단계(빠름·보통·느림)와 가속 곡선 두세 개를 **1층(foundation)에 두고, 2층 이름으로만 참조한다.** 2층 이름은 `design-system` 스킬 naming-taxonomy.md 유형표 motion 행(`--duration-fast/base/slow`·`--ease-{느낌}`)을 따르고, 파일 자리와 모양은 bootstrap-project.md §1.4가 정한다.
- **3층·제품 코드에 ms 값이나 곡선(`cubic-bezier(…)`)을 직접 적지 않는다.** 검사 ① 11번이 잡는다.
- 이렇게 하는 이유: `mvp/design-brief.md` 「8. 모션·인터랙션 방향」의 「정서」(예: 조용한 브랜드면 절제된 페이드)가 **값 몇 개로 앱 전체에 먹게** 하려는 것이다. 화면마다 숫자를 적으면 화면마다 속도가 달라지고, 고칠 때도 전부 찾아다녀야 한다.

**구현 도구**

- **기본 세트는 tw-animate-css와 CSS 전환(transition)으로 한다.** tw-animate-css는 `npx shadcn init`이 진입 CSS에 넣는 등장·퇴장 효과 모음이다(`animate-in`·`fade-in` 같은 클래스). 새로 깔 것이 없다.
- **장식·스크롤 연동이 필요할 때만 `motion` 라이브러리(옛 이름 framer-motion)를 추가한다.** 버전은 직접 써 넣지 않는다 — 설치 시점의 최신 안정판을 확인해 쓰고 `mvp/adr.md`에 기록한다(`2-0-dev-setup.md` §2.2 「mandated core 밖은 필요할 때만」).
- 처음부터 라이브러리를 깔지 않는 이유: 기본 세트까지 그 라이브러리를 거치게 되어 첫 로딩에 실리는 코드가 무거워진다. CSS로 되는 움직임은 CSS로 둔다.
- `motion` 라이브러리는 값을 CSS 변수가 아니라 JS 숫자로 받는다. 그래서 값을 `lib/motion.ts` 한 파일에 1층과 같은 숫자로 모으고, 화면 코드는 그 이름만 부른다. 1층 값을 바꾸면 이 파일도 같이 바꾼다.

**접근성 — 동작 줄이기면 움직임을 끈다, 예외 없음**

운영체제 설정의 「동작 줄이기」(prefers-reduced-motion — 어지럼증 등으로 움직임을 줄여 달라고 켜 두는 설정)가 켜져 있으면 **움직임을 끈다. 장식 움직임도 예외가 아니다.** 화면마다 따로 분기하지 않고 **전역 규칙 한 번**으로 처리한다 — 규칙의 자리와 모양은 `design-system` 스킬 bootstrap-project.md §1.4. `motion` 라이브러리를 들였으면 그쪽에도 같은 설정을 따르게 하는 전역 설정을 앱 맨 바깥에 한 번 건다(설정 이름은 설치 시점 문서로 확인) — CSS 규칙은 JS로 돌리는 움직임까지 끄지 못한다.

**검증 — 보는 건 사람, AI 몫은 빌드와 grep까지**

움직임은 화면을 열어 봐야 판단된다. 그래서 **배포 뒤 사용자가 배포 주소에서 본다** (§2.6 3번). AI가 브라우저 자동화로 열어 보고 「움직임 확인 완료」라고 결론 내지 않는다 — §2.6 3번과 같은 원칙이다. AI 몫은 빌드 통과와 검사 ① 10·11번 grep까지다.

**이 절을 위임할 때 지시서에 넣을 것** — 이 절의 규칙은 자동으로 주입되지 않는 자료(이 문서·브리프·design-system 스킬)에만 있어 에이전트가 알 길이 없다. 메인이 걸러서 `<constraints>`에 넣는다: 기본 세트 넷, 「시그니처 움직임」 행의 지위(`사용자 확정`이 아니면 넣지 않음), 분석표 결과, 값은 2층 이름만 쓰기(ms·곡선 직접 금지), 도구 선택(기본은 tw-animate-css·CSS 전환), 동작 줄이기 전역 규칙, 그리고 「재위임 금지」 줄.

### 2.5 배포 전 검사 — 세 가지를 통과한다

남은 화면을 다 만들고 움직임까지 입혔다고(§2.4) 바로 배포하지 않는다. **배포 전 검사 세 가지**를 먼저 통과한다 — ① 디자인 규칙 검사 ② 코드 품질 검사 ③ 화면 문구 검사. 초안 모드로 중간 확인 없이 끝까지 달린 코드에는 화면을 눌러봐선 안 드러나는 위반이 쌓이기 마련이라, 배포 전에 기계로 한 번 훑는다. (프로젝트 `AGENTS.md` 디자인 시스템 연결 정보의 「디자인 규칙 검사 예외 줄」은 검사 ①의 예외를 적는 자리다. 일찍 시작한 프로젝트의 `AGENTS.md`에는 옛 이름 「관문 ① 예외 줄」로 남아 있을 수 있는데, 같은 항목이다.)

**실행 순서**:

```
화면 대조·사람 확인(§2.3) → 모션 다듬기(§2.4) → 검사 ① → 검사 ② → 검사 ③ → 수정 반영 → 코드 정리 → 배포(§2.6) → 사람 클릭 검증
```

**검사 ① — 디자인 규칙 검사**

`design-system` 스킬을 호출해 **그 스킬의 철칙과 안티패턴 표를 검사 기준으로 삼는다.** 기준 항목을 이 문서에 베껴 두지 않는 이유는, 스킬이 개정되면 검사 기준도 자동으로 따라가야 하기 때문이다 — 여기 복사해 두면 스킬만 바뀌고 검사는 옛 기준으로 남는다.

다만 **`grep`으로 기계 검증이 되는 항목은 아래 명령을 실제로 돌린다.** 눈대중으로 "괜찮아 보이네" 하고 넘어가는 걸 막는 장치다. 경로는 프로젝트마다 다르니 자리표시자를 자기 프로젝트 경로로 바꿔 쓴다 (`design-system` 도입 기본형은 `src/styles/1-foundation/`·`2-semantic.css`·`3-components.css`).

**`<제품 코드 경로>`는 화면·부품 코드가 있는 곳(기본형 `src/app`·`src/components`)이되 `components/ui/`(shadcn 복사본)는 뺀다** — 그래서 명령마다 `--exclude-dir=ui`가 붙어 있다. 복사본에는 `ring-[3px]`·`text-white`·`md:text-sm` 같은 값이 기본으로 들어 있고, 복사본은 2층 값과 adapter의 「고친 shadcn 부품 목록」으로 다룬다. 제품 코드 안에 `ui`라는 다른 폴더가 있으면 그 폴더도 빠지니 이름을 바꾸거나 따로 돌린다.

**개발용 묶음 `src/app/(dev)/`도 검사에 넣는다** — 기본형 `src/app` 안에 있으니 따로 더할 것은 없고, 빼지 않는다는 뜻이다.

- **비교안 폴더**(`(dev)/dev/drafts/`)는 반드시 넣는다. 비교안은 고르면 본 화면 자리로 옮겨지는 코드라, 비교안에서부터 토큰 규칙을 지켜야 옮길 때 고칠 것이 없다. §2.3.2에서 고르지 않은 판을 지웠으니 대개 비어 있다.
- **목업 캔버스·디자인 시스템 페이지·`(dev)` 레이아웃**(하네스 틀에서 복사해 온 코드)도 넣는다. 틀은 이 검사를 통과하게 만들어져 있다 — 창 폭은 `px` 문자열 없이 숫자 속성으로 주고, 디자인 시스템 페이지의 값 표시는 코드에 적지 않고 브라우저가 계산한 값을 읽어 보여 준다. 그래서 틀에서 걸리는 줄이 나오면 프로젝트가 틀을 고치다 규칙을 어긴 것이니 2층 이름·theme 단계로 고친다. 고친 적 없는 틀 줄이 걸리면 그 줄만 연결 정보의 예외로 적어 통과시키고, 하네스 틀을 고칠 문안을 사용자에게 준다 (`AGENTS.md` 「하네스 수정」).

1. **3층(component·제품 코드)에 색·크기 하드코딩 0건**

```bash
grep -rnE --exclude-dir=ui '#([0-9a-fA-F]{3}|[0-9a-fA-F]{4}|[0-9a-fA-F]{6}|[0-9a-fA-F]{8})|rgba?\(|hsla?\(|oklch\(|oklab\(' <3층 CSS 경로> <제품 코드 경로>
grep -rnE --exclude-dir=ui '[0-9]+px' <3층 CSS 경로> <제품 코드 경로>
```

- 잡는 예: `bg-[#333]`, `style={{ color: "#fff" }}`, `p-[13px]`, 문자열을 쪼갠 `"p-" + "[13px]"`, 3층 CSS의 `oklch(0.6 0.2 250)`.
- 못 잡는 예: 단위 없는 숫자(`style={{ padding: 13 }}`), `rem` 매직넘버(`p-[0.8rem]` — 7번이 잡는다).
- 오탐 예: 16진 글자로만 된 앵커(`href="#faded"`) — 눈으로 거른다.

걸린 줄은 전부 semantic 이름 클래스·theme 스케일 클래스로 바꾼다. `1px` 테두리처럼 남길 값이 있으면 그 줄을 프로젝트 `AGENTS.md`의 디자인 시스템 연결 정보(adapter)에 검사 ① 예외로 적어 둔다 — 적어두지 않으면 다음 라운드에 같은 걸 또 따진다.

2. **3층이 foundation 램프 변수를 직접 참조하는 곳 0건** — semantic 층을 건너뛰면 나중에 브랜드를 갈아끼울 때 3층까지 다 손대야 한다.

```bash
T=$(mktemp -d)
grep -rhoE '^[[:space:]]*--[A-Za-z0-9-]+' <1층 foundation 경로> \
  | sed -E 's/^[[:space:]]*//' | sort -u > "$T/foundation-vars.txt"
grep -rnwF --exclude-dir=ui -f "$T/foundation-vars.txt" <3층 CSS 경로> <제품 코드 경로>
```

- 이름을 `var(…)`로 감싸지 않고 이름 그대로 단어 단위(`-w`)로 찾는다 — 그래야 Tailwind 괄호 표기까지 잡힌다. `--brand-6`이 `--brand-600`에 잘못 걸리지도 않는다.
- 잡는 예: `var(--brand-600)`, `bg-(--brand-600)`, `text-[var(--brand-600)]`.
- 못 잡는 예: 이름을 문자열로 조립한 경우(`` `--brand-${n}` ``).

3. **뷰포트 분기는 화면 전환용만** — 뷰포트 미디어 쿼리와 Tailwind 뷰포트 접두어(`md:` 등)는 화면 전체가 통째로 바뀌는 전환(예: 좁은 화면에서 상단 내비게이션 → 하단 탭 막대)에만 쓴다. 그 경우 프로젝트 `AGENTS.md`의 디자인 시스템 연결 정보(adapter)에 기록하고 통과. 그 외 용도는 0건이어야 한다 — 부품 크기 대응은 컨테이너 쿼리(container query — Tailwind에선 부모에 `@container`, 자식에 `@md:` 같은 `@` 접두어)로 푼다 (`design-system` 스킬 layout-frames.md §5 반응형 계약). 브리프 「12. 화면 규칙」의 폰 배치 규칙(옆 칸 버튼 → 아래 고정 줄, 표 → 카드, 격자 열 수)도 부품 크기 대응이라 컨테이너 쿼리로 푼다. 분기 자체가 필요 없으면 flex 줄바꿈·`auto-fill`·`clamp()`로 푼다. 검사 기준은 스킬이 갖고, 여기서 보는 건 그 기준을 3층 제품 코드에 실제로 적용한 결과다.

```bash
grep -rnE --exclude-dir=ui '@media[^{]*(width|height|orientation|aspect-ratio)' <3층 CSS 경로> <제품 코드 경로>
grep -rnoE --exclude-dir=ui '(^|[^a-z0-9@-])(max-)?(sm|md|lg|xl|2xl):[a-z[!-]' <제품 코드 경로>
```

- 잡는 예: `@media (min-width: 768px)`, `@media (orientation: landscape)`, `md:flex`, `max-md:hidden`, `lg:px-4`. `@media (prefers-reduced-motion)`·`prefers-color-scheme`·`print`·`hover: hover` 같은 뷰포트 아닌 쿼리는 안 잡는다(의도대로 — 동작 줄이기 전역 규칙은 10번이 있어야 한다고 보는 줄이다). 컨테이너 쿼리 접두어 `@md:`는 앞이 `@`라 안 잡히고, cva의 `size: { sm: "h-8" }`처럼 콜론 뒤가 띄어진 객체 키도 안 잡힌다(의도대로).
- 못 잡는 예: 프로젝트가 만든 브레이크포인트 이름(`tablet:`) — 만들었으면 정규식에 더한다.

4. **새로 만든 부품·클래스가 컴포넌트 인벤토리에 전부 등록됐는지 대조** — 인벤토리 위치는 프로젝트마다 다르고, 그 프로젝트 `AGENTS.md`의 디자인 시스템 연결 정보(adapter)에 적혀 있다. 흔한 자리는 `docs/components.md`. 대조 대상은 부품 파일(`components/ui/` 포함 — 인벤토리는 두 곳 다 적는다)과 `3-components.css`의 클래스다.

```bash
T=$(mktemp -d)
sed -n '/^## 전체 부품 색인/,$p' <컴포넌트 인벤토리 문서 경로> > "$T/inventory-index.txt"
find <부품 폴더 경로> -name '*.tsx' | sort > "$T/parts.txt"
while read -r f; do grep -qxF -- "$f" "$T/inventory-index.txt" || echo "미등록 부품: $f"; done < "$T/parts.txt"
grep -rhoE '^\.[A-Za-z][A-Za-z0-9_-]*' <3층 CSS 경로> | sed 's/^\.//' | sort -u > "$T/classes.txt"
while read -r c; do grep -qxF -- "$c" "$T/inventory-index.txt" || echo "미등록 클래스: $c"; done < "$T/classes.txt"
```

(클래스 쪽은 줄 맨 앞에서 시작하는 클래스 선택자만 집는다. `@media` 안이나 한 줄에 선택자를 여러 개 늘어놓은 CSS면 놓치는 게 생기니, 결과가 수상하리만치 적으면 눈으로 한 번 더 훑는다.)

**인벤토리 표기와 grep 대조 방식이 어긋나면 오탐이 쏟아진다.** 인벤토리가 "button(변형 9 · 크기 4)"처럼 부품을 블록 단위로 뭉뚱그려 적어 두는 경우가 많은데, 클래스 이름을 문자 그대로 대조하면 `button--l` 같은 변형·하위 요소 클래스가 인벤토리 문구엔 없다는 이유로 줄줄이 미등록으로 잡힌다 — 실측으로 오탐 93건이 나온 사례가 있다. 그래서 대조는 인벤토리 본문이 아니라 **자동 생성한 색인**과 한다: 인벤토리 문서 **끝에 `## 전체 부품 색인` 구간을 따로 두고**, 부품 파일이나 `3-components.css` 클래스를 추가·삭제할 때마다 재생성한다. 색인은 위 명령과 같은 방식으로 뽑은 부품 파일 경로와 클래스 이름을 **한 줄에 하나씩 꾸밈 없이**(코드 블록 안에) 나열한 것이다 — 줄 전체 일치(`-x`)로 대조하니 앞에 `- ` 같은 꾸밈이 붙으면 전부 미등록으로 나온다. 부품 설명 자체는 블록 단위로 써도 되고, grep 대조만 이 색인을 대상으로 한다. 변형은 cva의 prop이라 클래스로 생기지 않는다 — 「`button--l`이 미등록」 같은 오탐이 생길 자리가 없다.

```bash
grep -rn --exclude-dir=ui 'key === "Enter"' <제품 코드 경로>
```

걸린 줄마다 같은 조건에 `isComposing` 확인이 있어야 한다.

6. **하단에 붙는 것이 안전 영역을 비웠는가**

```bash
grep -rn "viewportFit\|viewport-fit" <앱 설정 경로>
grep -rn "safe-area-inset" <2층 토큰 경로>
```

앞이 잡히는데 뒤가 0건이면 하단이 홈 막대에 깔린다.

7. **대괄호 임의 값 0건** — `p-[13px]`처럼 대괄호로 값을 직접 넣으면 theme 스케일·semantic 이름을 통째로 건너뛴다.

```bash
grep -rnoE --exclude-dir=ui '[a-z0-9]-\[[^]" ]+\]:?' <제품 코드 경로> | grep -vE '\]:$'
```

- 원리: 값 자리 대괄호(`p-[13px]`)만 잡고, 조건 자리 대괄호(`data-[state=open]:`·`has-[>svg]:`·`group-data-[…]:`·`supports-[…]:`)는 뒤에 `:`가 붙어서 빼낸다.
- 잡는 예: `p-[13px]`, `bg-[#333]`, `text-[15px]`, `w-[calc(100%-2rem)]`, `bg-[var(--x)]`, `p-[0.8rem]`.
- 못 잡는 예: 대괄호로 시작하는 임의 속성(`[mask-type:alpha]`), 문자열을 쪼개 이어 붙인 클래스(`"p-" + "[13px]"` — px면 1번이 잡는다), `style` 속성.

8. **Tailwind 기본 팔레트가 꺼져 있는가** — 2층 `@theme inline` 블록의 `--color-*: initial` 줄이 빠지면 `bg-blue-500` 같은 팔레트 클래스가 다시 살아나 2층을 건너뛰는 길이 열린다. 팔레트 이름을 하나씩 찾는 대신 이 줄이 있는지만 본다.

```bash
grep -cE -- '--color-\*:[[:space:]]*initial' <2층 토큰 경로>
```

- 통과: 1 이상. 0이면 그 줄부터 되살린다.
- 못 잡는 예: 제품 코드의 `text-white`·`bg-black` — 복사본이 깨지지 않게 2층에 남겨 둔 두 색이라 클래스가 살아 있다. 색은 semantic 이름만 쓴다는 철칙으로 눈으로 본다.

9. **괄호 변수로 이름 클래스 건너뛰기 0건**

```bash
grep -rnoE --exclude-dir=ui '[a-z]-\((--|[a-z-]+:--)[A-Za-z0-9-]*\)' <제품 코드 경로>
```

- 잡는 예: `bg-(--primary)`, `p-(--gap)`, `text-(length:--x)`. semantic 이름 클래스(`bg-primary`)가 있는데 변수를 직접 넣는 길이다. 클래스가 없는 이름이면 2층 `@theme inline` 블록에 올린다.
- 못 잡는 예: `bg-[var(--x)]`(7번이 잡는다), `style={{ color: "var(--x)" }}`(1층 이름이면 2번이 잡는다).

10. **동작 줄이기 전역 규칙이 있는가** — 운영체제의 「동작 줄이기」 설정이 켜져 있으면 움직임을 끄는 전역 규칙이 스타일 파일에 한 번 있어야 한다 (§2.4, 자리는 `design-system` bootstrap-project.md §1.4 — 기본형은 `3-components.css` 맨 위).

```bash
grep -rln 'prefers-reduced-motion' <진입 CSS 경로> <스타일 폴더 경로>
```

- 통과: 파일이 1개 이상 나온다. 0이면 규칙부터 넣는다.
- 못 잡는 예: 규칙은 있는데 `animation`만 끄고 `transition`은 남긴 경우, `motion` 라이브러리를 들였는데 그쪽 전역 설정을 안 건 경우 — 걸린 파일의 규칙 블록과 앱 맨 바깥 코드를 눈으로 한 번 본다.

11. **3층·제품 코드에 모션 값 하드코딩 0건** — 길이·곡선은 1층에 두고 2층 이름으로만 쓴다 (§2.4).

```bash
grep -rnoE --exclude-dir=ui '(duration|delay|ease)-\[[^]]+\]|(duration|delay)-[0-9]+|[0-9]+ms|cubic-bezier\(|(^|[^a-z-])ease-(linear|in-out|in|out)\b' <3층 CSS 경로> <제품 코드 경로>
```

- 잡는 예: `duration-[250ms]`, `ease-[cubic-bezier(0.2,0,0,1)]`, Tailwind 숫자 길이 `duration-300`·`delay-150`, Tailwind 기본 곡선 이름 `ease-out`·`ease-in-out`(끄지 않지만 제품 코드에선 `ease-standard` 같은 우리 이름만 쓴다 — bootstrap-project.md §1.4), `style={{ transitionDuration: "250ms" }}`, 3층 CSS의 `transition: opacity 200ms cubic-bezier(…)`.
- 못 잡는 예: 초 단위(`.3s`), `motion` 라이브러리에 넘기는 JS 숫자(`transition={{ duration: 0.3 }}`) — 마지막은 `lib/motion.ts` 밖에 숫자가 있는지 `grep -rnE 'duration:[[:space:]]*[0-9.]+|ease:[[:space:]]*\[' <제품 코드 경로>`로 따로 본다.
- 겹침: 대괄호 쪽은 7번도 잡는다. 같은 줄이 두 번 나와도 한 번 고치면 된다.

12. **화면마다 강조색 주 버튼이 하나인가** — 강조색(2층 `primary`)으로 꽉 찬 주 버튼은 화면마다 그 화면의 주 행동 하나에만 쓴다. 원칙의 정본은 `design-system` 스킬 SKILL.md 「강조색은 어디에 쓰나」다. 화면 목록 6절 「주 행동」 칸이 화면마다 그 행동을 적어 둔 자리라, 그 칸과 코드의 주 버튼 수를 맞대 본다. (2단계 2-1 끝에서도 이 12번을 미리 돌린다 — `2-1-mockup.md`가 가리킨다.)

```bash
# 12-가. 화면 목록의 「주 행동」 칸 (MVP 포함 = O)
awk -F'|' '/^## 6\./{f=1;next} /^## /{f=0} f && $2 ~ /S-[0-9]/ && $9 ~ /^ *O *$/ {gsub(/^ +| +$/,"",$8); gsub(/^ +| +$/,"",$11); gsub(/ /,"",$2); print $2 " · 주 행동: " $8 " · 주소: " $11}' mvp/feature-list.md
# 12-나. 화면 폴더마다 주 버튼 수 — 1개가 아닌 폴더만 나온다
BTN=Button; BTN_FN=buttonVariants; PRIMARY=default   # 연결 정보에서 읽은 버튼 부품 이름·클래스 함수 이름·주 버튼 variant
find src/app -name page.tsx -not -path '*/(dev)/*' | sort | while read -r f; do
  d=$(dirname "$f")
  n=$(find "$d" -maxdepth 1 -name '*.tsx' -exec cat {} + | BTN=$BTN BTN_FN=$BTN_FN PRIMARY=$PRIMARY perl -0777 -ne '
    my $b = qr/(\{(?:[^{}]++|(?-1))*\})/;
    my $v = qr/\bvariant\s*[=:]\s*\{?\s*["\x27]\Q$ENV{PRIMARY}\E["\x27]/;
    my $c = 0;
    while (/<\Q$ENV{BTN}\E\b((?:[^>{}]|$b)*)>/g) { my $a = $1; $c++ if $a !~ /\bvariant\s*=/ || $a =~ $v }
    while (/\b\Q$ENV{BTN_FN}\E\(((?:[^()]|\([^()]*\))*)\)/g) { my $a = $1; $c++ if $a !~ /\bvariant\s*:/ || $a =~ $v }
    print $c')
  [ "$n" = 1 ] || echo "주 버튼 ${n}개: $d"
done
```

- 버튼 부품 이름과 주 버튼 variant는 프로젝트마다 다르다 — 프로젝트 `AGENTS.md` 디자인 시스템 연결 정보(「고친 shadcn 부품 목록」의 버튼 줄)에서 읽어 첫 줄의 세 값을 바꾼다. variant를 안 적으면 기본 variant가 되므로, 기본 variant가 주 버튼이면 variant 없는 버튼도 주 버튼으로 센다.
- 원리: 화면 주소 폴더(`page.tsx`가 있는 폴더)마다 그 폴더 바로 안의 `.tsx` 파일을 모아, 버튼 부품 태그와 버튼 클래스 함수 호출 중 주 버튼인 것을 센다. 여러 줄에 걸친 태그와 `onClick={() => …}` 안의 `>`도 센다.
- 통과: 12-나가 아무것도 출력하지 않거나, 나온 폴더가 모두 아래 셋 중 하나로 설명된다. 설명은 12-가의 그 화면 줄과 맞대 본다.
  - **0개이고 「주 행동」이 「없음」** — 그 화면만의 주 행동이 없어 상단 메뉴의 대표 행동이 주 버튼이 되는 화면이다. 통과.
  - **0개인데 「주 행동」이 있음** — 주 버튼이 화면 폴더 밖 부품(`src/components/`)에 있으면 그 부품 파일을 열어 주 버튼이 하나인지 보고 통과. 주 버튼이 정말 없으면 「주 행동」의 행동을 주 버튼으로 바꾼다.
  - **2개 이상** — 같은 순간에 화면에 함께 뜨지 않는 경우(빈 상태일 때만 뜨는 버튼과 목록이 있을 때만 뜨는 버튼처럼 조건으로 갈리는 경우, 확인 창 안의 버튼)면 통과. 함께 뜨면 「주 행동」의 행동 하나만 주 버튼으로 남기고 나머지는 보조 버튼·글자 버튼 variant로 바꾼다.
- 못 잡는 예: 버튼 부품을 다른 이름으로 감싼 전용 부품(감싼 부품 이름도 `BTN`처럼 한 번 더 돌린다), 화면 폴더 밖 부품 안의 주 버튼(위 0개 갈래에서 눈으로 본다).

13. **간격이 허용 단계 안에 있는가** — 브리프 「12. 화면 규칙」이 정한 간격 단계 밖의 Tailwind 간격 클래스(안쪽 여백 `p`, 바깥 여백 `m`, 칸 사이 `gap`, 형제 사이 `space`)를 찾는다. 대괄호 값(`gap-[10px]`)은 7번이 잡고, 여기서는 Tailwind 숫자 단계(`gap-10`·`p-5`)를 잡는다.

```bash
ALLOWED="0 1 2 3 4 6 8 12 16"   # 연결 정보 「적용 규칙 요약」의 간격 단계(Tailwind 숫자). 0은 늘 허용
grep -rnoE --exclude-dir=ui '(^|[^a-z0-9-])-?([pm][xytrblse]?|gap(-[xy])?|space-[xy])-[0-9]+(\.[0-9]+)?' <제품 코드 경로> \
  | awk -v ok="$ALLOWED" 'BEGIN{n=split(ok,a," "); for(i=1;i<=n;i++) s[a[i]]=1} {m=$0; sub(/^[^:]*:[0-9]+:/,"",m); if (match(m,/-[0-9]+(\.[0-9]+)?$/)) {v=substr(m,RSTART+1,RLENGTH-1); if(!(v in s)) print}}'
```

- 허용 단계는 프로젝트마다 다르다 — 프로젝트 `AGENTS.md` 디자인 시스템 연결 정보의 「적용 규칙 요약」에 적힌 간격 단계(예: 「4·8·12·16·24·32·48·64 = `1`·`2`·`3`·`4`·`6`·`8`·`12`·`16`」의 Tailwind 쪽 숫자)를 `ALLOWED`에 옮긴다. 연결 정보에 없으면 브리프 「12」의 간격 단계를 Tailwind 숫자(px ÷ 4)로 바꿔 넣고, 연결 정보에도 적어 둔다.
- 잡는 예: `gap-10`, `p-5`, `pt-0.5`, `-mt-7`, `@2xl/list:gap-x-7`, `md:px-5`.
- 못 잡는 예: 대괄호 값(7번이 잡는다), 크기 클래스(`w-`·`h-`·`size-`)와 위치 클래스(`top-`·`inset-`) — 간격 단계가 아니라 이 검사에 넣지 않는다. 걸린 클래스가 정말 필요한 값이면(예: 아이콘 옆 반 칸) 연결 정보의 검사 ① 예외로 적는다.

위반이 나오면 **수정을 반영한 뒤 같은 검사를 다시 돌린다.** 고쳤다는 보고로 끝내지 않는다 — 재검사가 0건이어야 검사 통과다.

**검사 ② — 코드 품질 검사**

`/vercel:react-best-practices`를 호출해 앱 코드 전체를 리뷰하고, 나온 위반을 수정 반영한다. 스택이 React·Next 고정이라 이 스킬은 항상 적용된다. (스킬이 안 보이면 2단계 개발환경 준비에서 깐 Vercel 플러그인이 빠진 것이다 — `2-0-dev-setup.md` §2.4대로 먼저 깔고 온다.)

여기서 실제로 잡히는 결함은 이런 종류다 — 화면을 눌러보는 것만으로는 절대 안 보인다:

- 모달처럼 **조건부로만 쓰는 무거운 컴포넌트가 첫 번들**(bundle)**에 전부 실림.** 열어보지도 않은 화면 때문에 첫 로딩이 느려진다.
- **`localStorage` 접근에 예외 처리가 없음.** 사생활 보호 모드(private browsing)나 저장 공간이 꽉 찬 브라우저에서 앱 전체가 죽는다. 이 단계 데이터가 전부 로컬스토리지에 있으니 특히 치명적이다.
- **매 렌더마다 새로 만들어지는 함수를 이벤트 리스너**(event listener)**로 등록함.** 글자 하나 칠 때마다 리스너를 뗐다 다시 붙인다.

**검사 ③ — 화면 문구 검사**

`ux-writing-reviewer` 에이전트(opus — 정의에 정해져 있다)에 이번에 만들거나 고친 화면·컴포넌트 파일 목록을 넘겨, 사용자 노출 문구(라벨·버튼·안내·에러 등)를 감사·교정받는다. 기준은 에이전트 정의에 든 토스 글쓰기 8원칙과 브리프의 보이스 앤 톤·「문자 그대로」 고정 문구 표다 — 브리프는 에이전트가 스스로 읽으니, 위임 지시엔 파일 목록과 「재위임 금지」 한 줄만 있으면 된다. 초안 모드로 수십 개 화면의 문구를 한 번에 지은 직후가 이 검사가 제일 값어치 있는 자리다 — 사람이 배포 링크에서 화면을 눌러볼 땐 흐름을 보느라 문구 위반이 눈에 잘 안 들어온다.

**파일 목록은 메인이 뽑는다** — 이 에이전트에는 명령을 돌리는 도구(Bash)가 없어 바뀐 파일을 스스로 찾지 못한다. 메인이 프로젝트 루트에서 뽑아 지시서의 `<data>`에 붙인다:

```bash
{ git diff --name-only main...HEAD -- src; git ls-files --others --exclude-standard -- src; } \
  | grep -E '\.tsx$' | grep -v '^src/app/(dev)/' | sort -u
```

**파일이 많으면 나눠 맡긴다** — 한 번에 받은 파일이 20개 안팎을 넘으면 에이전트가 정해진 작업 횟수 안에 끝까지 가지 못한다. 그래서 20개 안팎씩 묶음으로 나눠 여러 번 맡긴다. 묶음은 폴더(화면 흐름)대로 자르면 한 화면의 문구가 한 묶음에 모인다. 묶음끼리 파일이 겹치지 않으니 한꺼번에 띄워도 된다. 메인은 묶음 보고를 합칠 때 같은 문구(버튼 이름 등)를 묶음마다 다르게 고쳤는지 본다. 에이전트가 「못 한 파일」을 보고하면 그 파일만 다음 묶음으로 다시 맡긴다.

- 남은 화면을 다 만든 직후 1차는 반드시 돌린다.
- 이후 라운드는 **사용자 노출 문구가 바뀐 라운드에만** 다시 돌린다 — 검사 ①처럼 반복이 싸지 않아서다.
- 에이전트가 `판단 필요:`로 돌려준 항목(고정 문구·톤 미확정·의미가 바뀔 수 있는 문구)은 임의로 정하지 말고 사용자에게 물어 정리한다.

**검사 뒤 — 코드 정리**

검사 ①②③의 수정을 반영했으면, 배포하기 전에 **지난 정리 뒤 바뀐 코드만** 정리한다 — 재사용(같은 일을 하는 코드가 두 곳에 있는가)·단순화·효율·깊이(한 부품이 너무 많은 일을 하는가)를 보는 일이다. 절차와 「지난 정리」를 찾는 법은 코드 정리 스킬 `code-cleanup`이 정한다 — 메인이 Skill 도구로 부른다. 이 문서에 절차를 다시 적지 않는다. 3단계는 남은 화면을 여러 묶음이 동시에 만들어 같은 일을 하는 코드가 생기기 쉬운 자리라, 배포 전에 한 번 거른다. 정리 반영은 opus가 한다(`code-cleanup`이 정해 둔 대로) — 어느 코드를 합칠지 판단이 섞인 일이라서다. 정리로 코드가 바뀌었으면 검사 ①을 다시 돌린다.

**배포 전 검사는 1회성이 아니다 — 검사 ①②는 코드가 바뀔 때마다, ③은 사용자 노출 문구가 바뀐 라운드마다 배포 전에 다시 돌린다**

남은 화면을 다 만든 직후의 1차 실행으로 기준선을 잡고, 그 뒤로도 **ui/ux/bx(디자인 콘셉트) 변경 라운드나 피드백 반영(§2.7)으로 코드가 바뀔 때마다 배포 전에 다시 돌린다.**

검사 없이 변경만 쌓으면 위반과 잔재(아무도 안 쓰는 고아 토큰, 죽은 스타일)가 라운드마다 누적돼서, 나중엔 어느 라운드에서 들어온 건지 추적하는 비용이 고치는 비용보다 커진다. 검사 ①은 grep 기반이라 **반복 비용이 싸다** — 한 번 통과했다고 아끼지 않는다.

**합치기 전 코드 정리와는 축이 다르다**

하네스에는 이미 합치기 전 코드 정리(`code-cleanup` — 재사용·단순화·효율·깊이 검토, 관문은 `ship-task` §1.5)가 있다. 배포 전 검사와 겹치는 검사가 아니다 — **검사 ①은 디자인 규칙 준수, 검사 ②는 프레임워크 모범 사례(성능·정확성 관례), 검사 ③은 사용자 노출 문구, 코드 정리는 코드 구조·중복**을 본다. 넷이 서로 다른 곳을 보는 상호 보완이라, 코드 정리를 했다고 배포 전 검사를 건너뛰지 않고 그 반대도 마찬가지다. 위 「검사 뒤 — 코드 정리」가 그 코드 구조·중복을 배포 전에 미리 보는 자리다 — 합칠 때(`/done-task`)의 정리는 지난 정리 뒤 바뀐 것만 보므로, 여기서 정리해 두면 합치기가 작아진다.

### 2.6 배포

**지금 배포하는 건 백엔드 없는 프런트엔드 워킹 프로토타입이다.** Supabase는 2단계 개발환경 준비에서 붙일 자리만 잡아뒀고(`2-0-dev-setup.md` §2.3), 데이터는 서버가 아니라 브라우저 로컬스토리지에 있다. **그래도 배포에는 아무 문제가 없다** — 서버가 할 일이 없을 뿐이라 그냥 올라간다. "백엔드부터 붙여야 배포할 수 있다"는 건 오해다.

**그래서 얻는 게 공개 URL 하나다.** 링크를 보내면 상대는 아무것도 설치하지 않고 브라우저로 바로 열어본다 — 이 단계에서 굳이 배포까지 하는 이유가 이거다. 쓰임은 두 가지다. (가) 지인·팀 동료 앞에 띄워 직접 만져보게 하기(§2.7), (나) **멀리 있는 사람에게 링크만 보내 반응 받기.** 만나지 않고도 반응을 모을 수 있다는 게 실질 이점이다.

**보여주기 전에 상대에게 한계를 한 줄 미리 알린다**: 아직 로그인도 서버 저장도 없어서 기기나 브라우저를 옮기면 넣어둔 데이터가 이어지지 않는다. 미리 말해두지 않으면 상대가 이걸 버그로 읽고, 정작 받아야 할 화면·플로우 반응이 그 얘기에 묻힌다.

1. **Vercel에 배포한다** — 연결하기 전에 로그인된 Vercel 계정·팀이 `AGENTS.md` 「소유와 계정」 표와 일치하는지 대조한다 (절차·함정은 `docs/account-check.md`를 그때 읽는다). 첫 배포가 호스팅 프로젝트가 계정에 묶이는 순간이라, 다르면 만들지 않고 멈춰 보고한다 — 어긋난 채 만들면 프로젝트가 다른 소유의 팀에 조용히 생긴다. 그다음 저장소를 Vercel 프로젝트에 연결한다. main 직접 push 금지 — PR 워크플로로 간다 (repo 훅이 막는다).

   > **배포의 정본 경로는 git 연동이다** — main 머지 = 자동 프로덕션, PR = 자동 프리뷰. CLI 수동 배포(`npx vercel deploy --prod`)는 연동 전·비상시 예비 수단이다. CLI 배포는 로컬 작업 트리를 그대로 올려서(머지 안 된 브랜치·커밋 안 된 변경 포함) "실서비스 코드 = main" 보장이 깨진다 — 연동이 걸린 뒤에는 수동 배포를 쓰지 않는다. 3단계 안에 git 연동까지 마치는 게 기본이고, 못 마쳤으면 그 사실을 4-0 준비 목록에 넘긴다.

   **Vercel CLI 인증 — 이 첫 배포가 CLI를 처음 쓰는 때다.** CLI는 2단계 개발환경 준비에서 개발용 패키지로 깔아 두었으니(`2-0-dev-setup.md` §2.1 도구 점검표) 프로젝트 안의 것을 `npx vercel`로 부른다. 인증은 전역 `vercel login` 세션 대신 소유자 계정의 발급 토큰으로 한다 — 로그인 세션은 컴퓨터 전체에 하나라, 소유가 다른 프로젝트를 조용히 다른 계정으로 돌린다 (`docs/account-check.md` 원칙 ②). 토큰은 프로젝트 폴더가 아니라 이 컴퓨터의 **계정 장부**(`~/.config/harness/<소유>.env` — 소유마다 파일 하나, git 저장소 밖)에 `VERCEL_TOKEN` 한 줄로 둔다. 발급 절차는 `4-0-backend-prep.md` §3이다. 장부에 아직 없으면 그 절차대로 사용자가 발급해 넣게 안내하고 멈춘다 — 토큰 값을 대화에 붙여 받지 않는다.

   부를 때는 **실행기**(`.claude/scripts/with-owner.sh`)를 앞에 붙인다. 실행기는 `.claude/owner`에 적힌 이 프로젝트의 소유를 읽어, 그 소유의 장부를 환경변수로 넣고 명령을 실행한다. Vercel CLI는 환경변수 `VERCEL_TOKEN`을 받으므로(Vercel 공식 문서 「Global Options」) 토큰을 명령줄에 적을 일이 없다 — 명령줄 인자는 프로세스 목록·기록에 보일 수 있다.

   ```bash
   .claude/scripts/with-owner.sh --check
   .claude/scripts/with-owner.sh npx vercel whoami
   ```

   `--check`는 키 값을 찍지 않고 소유·장부 파일 자리·있는 키 이름만 보여 준다 — `VERCEL_TOKEN`이 목록에 있는지 먼저 본다. 아래 `npx vercel` 명령도 전부 이 모양(앞에 `.claude/scripts/with-owner.sh`)으로 부른다. `whoami`가 답하는 계정과 장부의 `VERCEL_TEAM`(팀 이름)을 위 계정 대조에 쓴다.

   첫 배포 체크리스트:

   - [ ] Vercel 프로젝트 이름은 소문자만 허용 — 저장소 폴더명에 대문자가 있으면 `npx vercel link --project <소문자이름>`을 먼저 한다 (실측: 대문자 폴더명 deploy가 400으로 거부됨)
   - [ ] `npx vercel git connect` → "Connected" 확인
   - [ ] `npx vercel link`가 `.gitignore` 끝에 `.env*` 한 줄을 덧붙일 수 있다 — 그러면 올려야 할 `.env.example`까지 git에서 빠진다. `git check-ignore .env.example`이 아무것도 안 내야 정상이고, 걸리면 그 줄을 지운다(`.env*.local`은 남긴다). (실측 2026-10-17)
   - [ ] 남에게 보낼 공개 링크는 **`<프로젝트이름>.vercel.app`** 이다 — 팀 이름이 붙은 다른 주소(`<프로젝트>-<팀>.vercel.app`·`-git-<브랜치>-` 주소)는 팀 계정의 배포 보호 때문에 Vercel 로그인으로 튕길 수 있다. `curl -s -o /dev/null -w "%{http_code}" https://<프로젝트이름>.vercel.app`이 200인지 확인한다. (실측 2026-10-17)
   - [ ] 공개 주소에서 목업 캔버스가 막혀 있다 — `curl -s -o /dev/null -w "%{http_code}" https://<프로젝트이름>.vercel.app/dev/canvas`가 404인지 확인한다. 개발용 묶음 레이아웃(`src/app/(dev)/layout.tsx`)이 실서비스 빌드에서 404를 내야 하고, 200이면 배포를 멈추고 그 레이아웃부터 고친다. Vercel 환경변수에 `MOCKUP_CANVAS`가 없는지도 `npx vercel env ls`로 본다 — 이 변수는 내 컴퓨터에서 목업 캔버스를 실서비스 빌드로 빠르게 볼 때만 명령 앞에 붙이는 것이라, Vercel에 들어가면 공개 주소에서 열린다
   - [ ] Vercel 빌드 기록(배포 화면의 Build Logs)의 Node 버전이 `package.json`의 `engines.node`·`.nvmrc`와 같은 주 버전이다 — 기록에 버전이 안 보이면 Vercel 공식 문서(「Supported Node.js versions」)가 권하는 대로 빌드 명령 앞에 `node -v`를 붙여 한 번 배포해 보고 되돌린다. 다르면 Vercel 프로젝트 설정(Settings → Build and Deployment → Node.js Version)이나 `engines.node`를 2단계 개발환경 준비에서 정한 주 버전으로 맞춘다 (`2-0-dev-setup.md` §2.2). Vercel은 `engines.node`를 프로젝트 설정보다 먼저 따른다
   - [ ] 연동 실패("you have access to the repository" 류) 시 원인은 대부분 앱 미설치가 아니라 **설치된 Vercel GitHub 앱의 저장소 접근 목록(Only select repositories)에 이 저장소가 빠진 것** — GitHub 계정 Settings → Applications → Vercel → Repository access에 이 저장소만 추가한다(All repositories 전환 금지). 세부 함정은 `docs/account-check.md` Vercel 항목 참조
2. **사이트 전체에 색인 제외(noindex)를 건다.** 지금 올리는 건 로컬스토리지로 도는 워킹 프로토타입이라 빈 상태 화면과 예시 데이터뿐인데, 이 링크는 4단계까지 몇 주를 떠 있는다. 그동안 검색에 잡히면 서비스가 그 얇은 화면으로 알려진다. 막는 건 검색 색인뿐이고 링크를 보내 여는 건 그대로 되니 남에게 보여주는 데는 아무 지장이 없다. Vercel의 preview 배포는 기본으로 막혀 있지만 **여기서 만드는 공개 URL은 production이라 안 막힌다** — 그래서 직접 걸어야 한다. 4단계에서 검색 노출을 켤 때 푼다 (`4-3-backend-deploy.md` §2.2).
3. **사용자가 배포 URL을 브라우저로 직접 클릭해 확인한다** (사람 몫 — SKILL.md §1.5, AI가 자동 도구로 사인오프하지 않는다):
   - 화면 목록의 핵심 플로우가 끝까지 돌아가는지.
   - 데이터를 넣고 **새로고침해도 남아 있는지** (로컬스토리지 동작 확인).
   - 웹 모드면 브라우저 창을 모바일 폭으로 줄여도 안 깨지는지 — 폰으로 열어볼 수 있어야 한다.
   - 움직임(§2.4)이 어색하지 않고 브랜드 인상에 맞는지. 괜찮다고 하면 AI가 `mvp/design-brief.md` 「8. 모션·인터랙션 방향」의 `가정` 행을 `사용자 확정`과 확정일로 바꾼다.
4. 발견된 문제는 초안 모드로 수정 → 재배포 → 재확인.

(Expo를 택했으면 이 절은 Expo 공유 링크·QR로 대체된다 — 보여줄 상대가 Expo Go를 설치해야 한다는 점을 미리 알린다.)

**같은 성질을 *준비* 쪽에서도 한 번 짚어둔다** (위 한 줄은 *상대에게 알릴 것*이고, 이건 *미리 마련해 둘 것*이다): 데이터가 브라우저마다 따로 산다. 다른 사람 기기로 열면 빈 상태부터 시작하고, 내가 넣어둔 예시 데이터는 안 보인다. 보여줄 때 예시 데이터가 필요하면 앱 안에 **초기 예시 데이터를 심는 방법**(첫 방문 시 자동 채움 등)을 마련해 둔다. 이때 심는 시드(seed)는 적게 만든다. 빈 상태·몇 개·많은 개수처럼 화면이 보여줘야 할 상태만 확인되면 충분하다 — 수십 명·수백 건을 지어내 봐야 4단계에서 DB용으로 다시 만들며 그만큼 버려진다.

### 2.7 피드백 반영 (지인·팀 동료와 본 뒤)

**이 절은 건너뛰어도 된다.** 워킹 프로토타입이 완성됐으면 주변 지인이나 팀 동료와 함께 한 번 보는 걸 권한다 — 보고 나온 수정거리를 반영하고, 수정할 게 없으면 그냥 다음 단계로 넘어간다. **관문이 아니고 산출물도 없다** — 사람을 새로 구하러 다닐 필요도 없다. 마땅한 사람이 없으면 이 절을 통째로 건너뛴다.

**지인에게 보내는 링크는 실서비스 주소(§2.6의 공개 URL)로 보낸다** — Vercel Pro 팀 계정이면 프리뷰 배포에 로그인 보호가 기본이라, 프리뷰 링크는 상대가 열면 Vercel 로그인으로 튕긴다 (`4-0-backend-prep.md` §3.3 — 보호를 끄는 길도 거기).

**화면 목록은 갱신하지 않는다** — `화면 대조 끝:`을 적은 시점에 할 일 목록의 역할이 끝났다 (§2.3.2). 화면이 늘거나 빠져도 코드에만 반영한다. 화면 구조가 통째로 뒤집히는 대규모 개편(화면 절반을 새로 짜는 수준)이라면 이건 피드백 반영이 아니라 **피봇**이다 — 2-1로 되돌아가 화면 목록을 다시 여는 재실행으로 다룬다(SKILL.md §2.2).

절차:

1. **코드를 고친다** (초안 모드). 무엇을 왜 바꾸는지 **화면 ID로** 정리해서 시작한다 (예: "S-04(카드 정보 입력)를 온보딩에서 빼고 S-03 다음에 바로 S-05로 — 이유: 본 사람 대부분이 그 화면에서 멈췄다"). 화면을 새로 만들 땐 `design-system` 스킬의 semantic 토큰·기존 컴포넌트를 그대로 쓰고, 목업 캔버스 목록 파일에도 올린다. 움직임 피드백(「전체적으로 느려」·「너무 튀어」)은 화면마다 고치지 않고 1층 모션 값을 고쳐 앱 전체에 먹인다 — 이 코드 수정은 위임해도 된다. `mvp/design-brief.md` 「8. 모션·인터랙션 방향」의 해당 행은 메인 클로드가 직접 고친다(SKILL.md §3) — 행에는 값(ms)이 아니라 바뀐 방향만 적는다 (§2.4).
2. **화면을 추가·수정할 땐 상태 화면도 같이 만들었는지 코드에서 확인한다** — 빈 상태·오류·로딩 같은 변형이 `?state=`로 뜨는지. 화면 목록의 상태 표는 `화면 대조 끝:` 뒤 갱신하지 않는 기록이라, 이 점검은 코드 수정 절차가 맡는다.
3. **코드를 고쳤으면 배포 전에 §2.5 배포 전 검사를 다시 돌린다** (재실행 기준은 거기).
4. **재배포 + 사용자 클릭 확인** (§2.6).

더 고칠 게 없으면 이 단계는 끝이다. 코드는 그대로 4단계로 넘어가 백엔드가 얹힌다 — 파일을 확정해 고정하는 게 아니라, 지금 화면으로 다음으로 간다는 뜻이다.

- [ ] **화면 문구 검사 통과** (§2.5 검사 ③) — 메인이 뽑은 파일 목록을 20개 안팎씩 나눠 `ux-writing-reviewer`에 맡겼고, 못 한 파일 0개. 교정 반영, `판단 필요` 항목은 사용자 확인으로 정리.
- [ ] **코드 정리** (§2.5 「검사 뒤 — 코드 정리」) — 배포 전 검사 뒤 코드 정리 스킬 `code-cleanup`으로 지난 정리 뒤 바뀐 코드를 정리했고, 바뀌었으면 검사 ①을 다시 돌림.
- [ ] (해당 시) **코드를 고칠 때마다 배포 전 검사 재실행함** (§2.5·§2.7) — 첫 1차만 돌리고 끝내지 않았다.
- [ ] **배포 완료 + 공개 링크 확보** (§2.6) — 남에게 보여주고 4단계에서 이어 쓸 링크.
- [ ] **배포 주소의 `/dev` 404** (§2.6) — `curl`로 공개 주소의 `/dev/canvas`가 404임을 확인. Vercel 환경변수에 `MOCKUP_CANVAS` 없음.
- [ ] **Vercel의 Node 주 버전이 `engines.node`와 같음** (§2.6) — 빌드 기록으로 확인.
- [ ] **색인 제외 적용 확인** (§2.6) — 배포 URL이 검색엔진에 안 잡히게 막혀 있음. 4단계에서 푼다.
- [ ] (사용자 검증) **사람이 브라우저로 클릭 확인 완료** (§2.6) — 핵심 플로우 끝까지 + 새로고침 후 데이터 유지 + 모바일 폭에서 안 깨짐 + 움직임 확인(§2.6 3번). AI 자동 사인오프 아님.

## 4. 산출물 스펙

이 단계의 산출물은 둘이다.

**① 앱 코드 (본 산출물)**

- **위치**: 프로젝트 루트 (`package.json`·`src/` 등)
- **스택**: 2단계에서 고정한 core — Next.js(App Router)·React·TypeScript·Tailwind·shadcn·Supabase·Vercel (`2-0-dev-setup.md` §2.2). 해소된 버전 조합은 `package.json`에 핀 + `mvp/adr.md`에 기록돼 있다.
- **범위**: 화면 목록 `MVP 포함 = O` 화면 전부 + 상태 화면(`?state=`로 뜸). **데이터는 브라우저 로컬스토리지** — Supabase는 `.env.example`에 환경변수 자리만 잡아둔 상태이고, 프로젝트 생성은 4단계 준비(4-0)에서 계정을 확정한 뒤에 한다.
- **성격**: 2단계에서 화면을 만든 순간부터 **화면 생김새·흐름·상태·화면 문구·디자인 값의 정본**. 피드백을 반영할 때도 4단계에서도 이 코드를 고친다. **버리는 시제품이 아니라 실서비스가 될 본체다** — 지금은 백엔드가 없을 뿐이다.

**② 배포 링크**

- Vercel 공개 URL (Expo면 공유 링크·QR). 남에게 보여줄 때 쓰는 도구다.
- 코드를 고칠 때마다 재배포해 항상 최신 코드가 그 링크에 있게 한다.

**산출물이 아닌 것 — 목업 캔버스.** 목업 캔버스(`/dev/canvas`)와 디자인 시스템 페이지(`/dev/design-system`)는 사람이 화면을 보는 개발용 도구다. 앱 코드 안(`src/app/(dev)/`)에 있지만 개발 서버에서만 열리고, 실서비스 빌드에서는 404로 막힌다(§2.6 첫 배포 체크리스트). 4단계에도 남겨 둔다 — 백엔드를 붙인 뒤에도 전 화면을 훑는 데 쓴다.

## 5. 사용자 응대 톤

- **톤**: SKILL.md §1.3 따름 — `AGENTS.md` 응답 톤(~입니다 체)·친근·짧게.
- **진입 안내**: "화면 목록과 화면 규칙이 다 나왔으니 이제 진짜 돌아가는 앱을 마저 채울 차례입니다 — 남은 화면을 지금 코드에 더하고, 화면 목록과 하나하나 맞춰 본 뒤 모든 화면을 모아 보는 목업 캔버스 주소를 드리겠습니다. 보시고 괜찮다고 하시면 움직임을 입히고 배포까지 하겠습니다. 중간에 어떤 움직임을 닮고 싶은지 한 번 여쭙겠습니다. 데이터는 아직 브라우저에 저장되는 수준이고, 진짜 DB는 나중에 붙입니다."
- **목업 캔버스를 보는 건 사용자 몫이라고 분명히 말한다** — "제가 열어서 확인해 봤습니다"라고 하지 않는다. 주소를 주고 본 결과를 기다린다 (§2.3.3). 대신 화면 목록 ID 대조 결과는 AI가 세어서 같이 보고한다 (§2.3.1).
- **화면 품질 불만**: "화면이 별로다", "이상하게 나왔다" 하면 다시 만들어달라고만 던지지 말고, §2.2.3 지시를 더 구체화(빠진 화면 ID·상태 화면 짚기, 어느 화면 어디가 이상한지)해서 보완하자고 안내한다. 전체 생김새가 문제면 화면을 하나하나 다시 만들지 않고 토큰·공통 부품을 고쳐 앱 전체에 먹인다.
- **화면이 너무 많다고 할 때**: **`화면 대조 끝:` 전이면** 화면 목록에서 임의로 화면을 빼지 말고, 2-1로 돌아가 `MVP 포함` 열을 다시 정하자고 안내한다 — 목록에서 지우는 게 아니라 이번엔 안 만든다고 표시하는 거다. 기능 목록의 범위 결정도 같이 고친다. **대조 뒤라면** 코드에서 그 화면을 바로 빼면 된다. 화면 목록은 그 시점엔 이미 갱신하지 않는 기록이라 고치지 않는다 (§2.3.2).
- **3단계에서 DB까지 붙이자고 할 때**: 화면이 도는지 보는 데는 백엔드가 필요 없고, 화면 구조가 뒤집히면 미리 만든 테이블·RLS가 통째로 버려진다고 짚어준다 (`2-0-dev-setup.md` §2.3). 지금은 붙일 자리(환경변수 이름·클라이언트 초기화 코드)만 잡아두고, 화면이 굳은 뒤 4단계에서 로컬스토리지를 Supabase로 갈아끼운다.
- **빌드 중**: 잘게 확인 요청 금지 (초안 모드). 에스컬레이션 기준 해당 시에만 멈추고 배치로 질문.
- **배포·클릭 검증 안내**: "배포까지는 제가 하지만, 실제로 눌러 보고 확인하는 것은 사용자 몫입니다 — 자동 검증 도구로 대신 사인오프하지 않습니다" (SKILL.md §1.5 사람 몫). 새로고침해도 데이터가 남는지 같이 봐 달라고 짚는다.
