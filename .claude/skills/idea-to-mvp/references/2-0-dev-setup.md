이 문서는 2단계의 맨 앞 하위 단계다. 2단계는 **`2-0-dev-setup.md`(개발환경 준비) → `2-1-mockup.md`(기능·화면 목록과 주요 화면) → `2-2-mockup-design-upgrade.md`(전문가 수준 디자인 개선)** 순서로 간다. 단계 번호는 하나라 대화가 끊기지 않고 이어진다.

**왜 맨 앞인가** — 2단계는 화면을 그림이 아니라 실제 앱과 같은 코드(리액트)로 바로 만든다. 리액트로 화면을 만들려면 그 바닥 — 앱 뼈대, 고정한 버전, 디자인 토큰, 셸, 목업 캔버스 — 이 먼저 있어야 한다. 여기서 만든 코드는 버리는 물건이 아니다 — 2-1이 그 위에 주요 화면을 짓고, 3단계가 남은 화면을 더하고, 4단계가 백엔드를 얹는다. 처음부터 끝까지 앱은 하나다.

**들어오는 때** — 1단계가 끝나 `mvp/intent.md`와 `mvp/design-brief.md`가 있고, 루트에 앱 코드(`package.json`)가 아직 없을 때다 (SKILL.md §1.2). 2단계에 처음 들어오면 이 문서와 `2-1-mockup.md`를 함께 읽는다 — 2단계 시작 안내(`2-1-mockup.md` §2.1)에 이 문서의 스택 질문(§2.1)을 얹어 한 메시지로 낸다.

**이 문서는 2-1과 나란히 돈다** — 스택 답이 오면 §2.2~§2.6은 서브 에이전트 하나가 끝까지 하고, 그동안 메인은 2-1의 기능 목록·화면 목록(`2-1-mockup.md` §2.3~§2.5)을 쓴다. 둘은 서로 기다리지 않는다. 셸의 메뉴만 화면 목록 8절(메뉴 구조)이 나온 뒤 한 번 맞춘다(§2.5). 2-1의 주요 화면 만들기(`2-1-mockup.md` §2.6)는 이 문서가 끝난 뒤에 시작한다.

## 1. 단계 목표

이 문서의 목표는 **2-1이 주요 화면을 리액트로 바로 만들 수 있는 바닥을 까는 것**이다. 끝나면 아래가 있다.

- **루트 앱 코드 뼈대** — 고정 스택으로 만든 Next.js 앱. 정확한 버전을 `package.json`에 고정했고(Vercel CLI·Supabase CLI는 개발용 패키지로 함께), Node.js 주 버전을 이 컴퓨터(fnm으로 받은 이 프로젝트의 판)·`engines.node`·`.nvmrc`(CI가 읽는다)에 같게 맞췄다. 이 컴퓨터에 없던 도구는 AI가 깔았다.
- **기술 결정 기록** — `mvp/adr.md`(ADR — 왜 그 기술을 골랐는지 적어 두는 문서)에 스택 선택과 버전 조합.
- **디자인 시스템 첫 세팅** — `src/styles/`의 토큰 세 층, 모든 화면에 씌우는 셸, 부품 목록 문서(`docs/components.md`), `AGENTS.md`의 「디자인 시스템 연결 정보」 절.
- **목업 캔버스 뼈대** — 개발 서버에서만 열리는 목업 캔버스(`/dev/canvas`)와 「[서비스 이름] 디자인 시스템」 페이지(`/dev/design-system`), 목업 캔버스 목록 파일, 상태 표시 도우미.

**여기서 안 하는 것 (의도적)**:

- ❌ **화면** — 주요 화면은 2-1 §2.6이 만든다. 이 문서는 셸까지다.
- ❌ **Vercel 연결·배포** — 2단계는 사용자의 개발 서버 주소로 본다. 배포는 3단계 배포 절(`3-frontend-build.md`)이 한다.
- ❌ **Supabase 프로젝트 생성·테이블** — 4단계 준비(`4-0-backend-prep.md`)에서 계정을 확정한 뒤에 한다 (§2.3).
- ❌ **프로젝트 전용 variant**(부품의 모양 종류 — 버튼의 주 버튼·보조 버튼 같은 것)와 브리프 「12. 화면 규칙」의 코드 반영 — 2-2가 규칙을 정한 뒤에 한다 (`2-2-mockup-design-upgrade.md`). 지금 1층에 들어가는 값은 대부분 브리프 「4」의 출발값(`가정`)이라, 2-2가 바꿀 것을 미리 굳히지 않는다.

**외부 리소스가 생기지 않는다** — GitHub 저장소는 이미 있고, Vercel·Supabase는 아직 만들지 않는다. 그래서 이 문서에서는 계정 대조(`AGENTS.md` 「소유와 계정」)가 필요 없다.

**붙여 넣을 문안 — 디자인 시스템 첫 세팅** (`<constraints>` 안에 그대로):

<content id="design-system-constraints">
- 세 층 자리 — 진입 CSS `src/app/globals.css`는 import 줄만. 1층 `src/styles/1-foundation/`은 `:root`에 둔다(`@theme`에 두면 `bg-brand-600` 같은 램프 클래스가 생겨 2층을 건너뛴다). 2층 `src/styles/2-semantic.css`는 `:root`·`.dark`·`@theme inline`이고 값은 전부 1층 변수만 가리킨다. 3층 보조 `src/styles/3-components.css`는 body 기본 스타일·동작 줄이기 전역 규칙·셸 클래스.
- 차례 — ① `npx shadcn init`(CSS 경로는 진입 CSS. init이 진입 CSS에 넣은 `:root`·`.dark`·`@theme inline` 블록은 2층으로 옮기고, import 줄은 지우지 않는다) → ② 1층 → ③ 2층 → ④ 진입 CSS import 순서 고정 → ⑤ 셸 → ⑥ 부품 받기 → ⑦ 부품 목록 → ⑧ 연결 정보.
- import 순서 — `tailwindcss` → init이 넣은 줄(예: `tw-animate-css`·`shadcn/tailwind.css` — 빼면 부품의 열림·닫힘 모양이 조용히 사라진다) → npm 폰트 CSS → 1층 → 2층 → 3층 → `@custom-variant dark`.
- 1층 값은 브리프 「4」 「우리가 쓰는 값」 표에서 — 색은 hex를 oklch로 바꾼다. 강조색은 H를 고정하고 L만 바꿔 50~950 램프를 만들고, 원래 색을 600 근처에 둔다(양 끝은 C를 줄인다). 성공·위험도 램프로. 둥글기는 `--radius-base` = 카드 값. 서체는 무료 서체(유료면 대체 서체)로 로딩 방식까지 정한다. 모션은 길이 셋·곡선 둘의 자리만 잡는다(값은 3단계).
- 2층 — shadcn 이름 세트(`--background`…`--sidebar-*`와 `-foreground` 짝)를 지우지 말고 전부 1층 변수로 다시 잇는다. `--success`·`--success-foreground`를 더한다. `--primary` 위 글자, `--background` 위 `--foreground`·`--muted-foreground`는 4.5:1 이상 — 모자라면 잇는 단계를 진한 쪽으로 고르고, 어느 색을 어느 단계로 이었는지 보고한다.
- `@theme inline` — 맨 앞에 `--color-*: initial;`(Tailwind 기본 팔레트 끄기 — 빼지 않는다)과 `--color-white`·`--color-black` 둘만 남긴다. 글자 이름 `--text-h1`~`--text-b2`를 두고, `--text-sm`·`--text-xs`는 b2 값으로 다시 정의한다(글자 바닥선 14px). 둥글기 `--radius-card`·`--radius-control`(`calc()`로 파생). 길이 클래스는 `--transition-duration-fast|base|slow`, 곡선은 `--ease-standard`·`--ease-emphasis`, 기본값 `--default-transition-duration`·`--default-transition-timing-function`.
- 2층 맨 끝에 「비교안」 주석 한 줄 자리만 둔다(2-2가 쓴다). 3층 맨 위에 `prefers-reduced-motion: reduce` 전역 규칙(애니메이션·전환 길이 0s)을 둔다.
- 클래스 합치기 — `src/lib/utils.ts`의 `cn`에 2층 `@theme inline`에 더한 이름 전부(글자 크기·둥글기·컨테이너 폭·움직임)를 알려 준다(`tailwind-merge`면 `extendTailwindMerge`, `cn` 패키지면 `createCn` — 설치된 쪽 문서로 모양을 확인한다). 부품을 받을 때마다 `grep -rlE "from ['\"](cn|tailwind-merge)['\"]" src/components/ui`가 0건이 되게 import를 `@/lib/utils`로 바꾼다.
- 부품을 받은 직후 — 누르는 요소(버튼·입력칸·고르기 칸·탭·체크 상자·라디오·스위치)의 누르는 영역을 부품 파일에서 44px 이상으로 고친다(`size="sm"` 포함. 보이는 네모는 두고 누르는 영역만 넓혀도 된다). 화면에서 `className`으로 덮어쓰지 않는다. 색·모양은 2층 값으로 먼저 풀고, 그래도 부품 파일을 고쳤으면 연결 정보의 「고친 shadcn 부품 목록」에 적는다.
- 셸 — 헤더/본문/하단 세 영역으로 시작한다(하단 고정 요소가 아직 없어도). 폰 폭에서 숨기는 건 상단 메뉴뿐이고 헤더(로고·알림·프로필)는 두 폭 모두 남긴다. 쌓이는 화면은 폰 폭 앱바가 「뒤로 · 화면 제목 · 동작 하나」로 바뀐다 — 화면 제목 줄 부품이 셸에 등록하는 방식(셸 컨텍스트)으로, 뒤로 가기 줄을 앱바 아래 따로 두지 않는다.
- 연결 정보(`AGENTS.md` 「디자인 시스템 연결 정보」)에 적을 것 — 진입 CSS·세 층 경로와 import 순서 · `components.json` 위치와 별칭 · 부품 목록 위치 · 프레임·화면 패턴 목록 위치 · 고친 shadcn 부품 목록(import 바꾸기·44px 포함. 다시 받을 땐 `--diff`로 비교하고 `--overwrite` 금지) · 디자인 규칙 검사 예외 줄 · 철칙 요약 · 적용 규칙 요약(① 글자 크기 바닥선과 예외 자리 ② 역할 한정 토큰 목록) · 링크 버튼 쓰는 법.
</content>

**보고에 담을 것** — 고른 Node 주 버전과 이 컴퓨터의 Node 버전, 이 컴퓨터에 깐 것(도구·판·까는 데 쓴 방법 — fnm을 Homebrew로 깔았는지 공식 실행 파일로 받았는지 포함)과 원래 있던 Node를 그대로 뒀는지, 고정한 버전 조합(Vercel CLI·Supabase CLI 포함), 끈 Next.js 설정, ADR에 적은 것, `가정` 값으로 채운 1층 항목, 받은 shadcn 부품과 고친 부품, 셸의 메뉴(어느 근거로 정했는지), 목업 캔버스 뼈대를 넣은 자리, 빌드·린트·타입 결과, `추후 결정:` 목록.

## 2. 진행 절차

### 2.1 시작 — 도구 점검과 스택 확인

**도구 점검표 — 2-0을 시작할 때 한 번에 본다.** 이 하네스가 쓰는 도구를 두 갈래로 나눠 둔 표다. 메인이 스택 질문을 내기 전에 아래 확인 명령(`--version`)을 실제로 돌리고, 결과를 한 표로 스택 질문과 같은 메시지에 붙인다. 빠진 도구를 처음에 한 번에 알려야 단계 중간에 하나씩 멈추지 않는다.

**2단계에서 쓰는 도구는 AI가 묻지 않고 깐다.** 목업 캔버스와 화면 코드를 만들려면 모두 있어야 하는 도구라, 설치해도 되는지 묻고 기다리는 왕복 없이 개발환경 준비의 맨 앞에서 깐다. 사용자에게는 무엇을 깔았는지 결과만 표로 알린다(아래 「깐 것을 알리는 문안」). **Docker Desktop만 다르다** — 4단계에야 필요하고 용량이 커서, 깔지 말지는 사용자가 정한다. 지금은 「4단계에서 필요합니다」라고만 알리고, 4단계 준비(`4-0-backend-prep.md` §3.6)에서 크기와 용도를 알려 묻는다.

**컴퓨터 전체에 까는 도구**

| 도구 | 하는 일 | 확인 명령 | 언제 필요한가 | 없으면 |
|---|---|---|---|---|
| git | 코드 변경 이력을 저장한다 | `git --version` | 이미 쓰고 있다 — 프로젝트를 처음 만들 때 `github-connect` ①이 확인했다 | `github-connect` ① |
| gh | GitHub을 터미널에서 다루는 공식 도구(GitHub CLI). 작업 보내기(`done-task`)가 이 도구로 PR을 만든다 | `command gh --version` | 이미 쓰고 있다 — `github-connect` ②가 확인했다 | `github-connect` ② |
| jq | JSON(프로그램끼리 주고받는 데이터 형식)을 읽는 작은 도구. 하네스 자동 장치인 훅(hook — 클로드 코드가 명령 전후에 저절로 돌리는 검사 스크립트)이 쓴다 | `jq --version` | 이미 쓰고 있다 — 하네스를 처음 적용할 때 `github-connect` ③이 확인했다. 없으면 main 브랜치로 바로 올리기를 막는 훅이 안전을 위해 `git push`를 전부 막아 작업 보내기가 안 되고, 응답마다 하는 자동 중간 저장(wip 커밋)도 쉰다 | 메인이 점검 때 `github-connect` ③대로 바로 깐다 |
| Node.js·npm | 자바스크립트 실행기와 그 패키지 설치 도구 | `node -v`·`npm -v` | 지금(2-0) | 있든 없든 개발환경 준비 서브 에이전트가 맨 먼저 §2.2 「Node.js 버전부터 정한다」대로 fnm으로 이 프로젝트의 판을 받는다. 원래 있던 Node는 그대로 둔다. 판단은 `node -v`로 한다 — `npm -v`는 Node 없이 남은 옛 npm 파일 때문에 있는 것처럼 보일 수 있다 |
| Aside(견본 이미지 검색용 브라우저) | 화면을 채울 견본 이미지를 무료 사진 사이트(Pexels·Unsplash·Pixabay)에서 검색하는 데 쓴다. 이 세 사이트는 명령(curl)으로는 검색이 막히고 Aside 브라우저로는 열린다 | `command -v aside` | 지금(2-0) — 화면에 견본 이미지가 들어가기 전 | **있으면 아무것도 깔지 않는다.** 없을 때만 설치한다: 명령줄 도구는 공식 설치 명령(`curl -fsSL https://releases.aside.com/install.sh \| bash`)으로 AI가 깔고, 브라우저 앱 설치·첫 설정처럼 사람 손이 필요한 곳은 「aside.com/download에서 받아 설치해 주세요」처럼 한 단계씩 안내한다. 맥·윈도우만 지원한다. 사용자가 미루거나 설치가 실패하면 멈추지 않는다 — 견본 이미지는 Burst로 채운다 |
| Docker Desktop | 내 컴퓨터 안에 작은 서버 묶음(컨테이너)을 띄우는 프로그램. 4단계의 로컬 DB가 그 위에서 돈다 | `docker --version` | 4단계 | 지금 깔지 않는다 — 「4단계에서 필요합니다」라고만 알린다. 깔지는 4단계 준비(`4-0-backend-prep.md` §3.6)에서 사용자가 정한다 |

**프로젝트 안에 까는 도구** — §2.2의 패키지 설치 때 한 번에 깔고 `package.json`에 정확한 버전으로 고정한다. 전역이 아니라 프로젝트 안에 두는 까닭은 사람·컴퓨터마다 버전이 달라지지 않게 하려는 것이다. 부를 때는 `npx`(프로젝트 안에 깐 명령을 찾아 실행해 주는 npm 도구)를 붙인다.

| 도구 | 하는 일 | 까는 법 | 로그인·키 설정 |
|---|---|---|---|
| Next.js 등 앱 패키지 | 앱 자체 | §2.2 고정 스택 | 없음 |
| shadcn | 범용 부품 파일을 프로젝트에 복사해 주는 명령 | 깔지 않고 쓸 때 `npx shadcn`으로 실행 | 없음 |
| Vercel CLI(`vercel` 패키지) | 배포·환경변수를 터미널에서 다룬다 | 개발용 패키지 `npm install --save-dev vercel` | 3단계 첫 배포 때 (`3-frontend-build.md` §2.6) |
| Supabase CLI(`supabase` 패키지) | 로컬 DB를 올리고 마이그레이션을 다룬다 | 개발용 패키지 `npm install --save-dev supabase` | 4단계 (`4-0-backend-prep.md` §3.2) |
| React Grab(`react-grab` 패키지) | 목업 캔버스·개발 서버 화면에서 요소에 마우스를 올리고 ⌘+C(윈도우는 Ctrl+C)를 누르면 그 요소의 코드 자리를 복사해 준다(요소 복사) | 개발용 패키지 — §2.6에서 목업 캔버스 뼈대와 함께 | 없음 |
| Playwright(`playwright` 패키지) | 브라우저를 코드로 여는 도구. 목업 캔버스가 멀리서 보여 줄 미리보기 그림을 찍는 데 쓴다 | 개발용 패키지 — §2.6에서 목업 캔버스 뼈대와 함께. 그림을 찍을 브라우저는 처음 찍을 때 내려받는다. 이 크롬은 컴퓨터에 하나만 깔리고 프로젝트끼리 같이 쓴다 | 없음 |

**키는 프로젝트 폴더에 두지 않는다** — 두 CLI와 gh가 쓰는 토큰(로그인 대신 쓰는 열쇠 문자열)은 그 단계에서 이 컴퓨터의 계정 장부(`~/.config/harness/<소유>.env` — 소유마다 계정 이름과 토큰을 모아 둔 파일, git 저장소 밖)에 들어간다. AI는 명령 앞에 실행기(`.claude/scripts/with-owner.sh` — 이 프로젝트의 소유를 읽어 그 장부의 토큰을 넣고 명령을 돌리는 스크립트)를 붙여 부른다. 예: `.claude/scripts/with-owner.sh npx vercel deploy`. 2-0에서는 깔기만 하니 장부를 만들지 않는다.

두 CLI도 §2.2의 버전 조합 확인 대상이다. 4단계에서 Supabase CLI를 Docker와 맞춰 판을 다시 고를 수 있다 (`4-0-backend-prep.md` §3.6).

**점검표를 보여 주는 문안** — 판 숫자는 그때 확인한 값을 넣는다. 묻지 않고, 무엇을 했고 무엇을 할지만 적는다. 골자:

> 시작하기 전에 이 컴퓨터에 필요한 도구가 있는지 봤습니다.
>
> | 도구 | 상태 | 이어서 하는 일 |
> |---|---|---|
> | git·gh | 있음 | 없음 |
> | jq | 없어서 제가 깔았습니다 | 없음 |
> | Node.js | 있음([판]판) | 이 프로젝트에 맞는 판을 정해, 필요하면 개발환경을 준비하며 제가 깔겠습니다 |
> | Aside(견본 이미지 검색용 브라우저) | [있음 / 없어서 제가 깔겠습니다] | [없음 / 앱 설치가 필요하면 한 단계씩 안내하겠습니다. 미루셔도 견본 이미지는 다른 사이트로 채웁니다] |
> | Docker Desktop | 없음 | 4단계에서 필요합니다. 그때 깔지 여쭙겠습니다 |
>
> 앱 안에 들어가는 도구(배포 도구 Vercel CLI, DB 도구 Supabase CLI 등)도 제가 개발환경을 준비하며 함께 깔겠습니다.

다 있으면 표 대신 「필요한 도구는 다 있습니다(Docker Desktop은 4단계에서 필요합니다)」 한 줄로 줄인다.

**jq가 없으면** 점검표를 보여 주기 전에 `github-connect` ③대로 바로 깔고, 표에는 「없어서 제가 깔았습니다」로 적는다. 깔다가 같은 실패가 2번 나면 그 사실을 표의 「이어서 하는 일」 칸에 적어 사용자에게 알린다 — 2-0은 멈추지 않지만, 3단계 끝 작업 보내기(`done-task`) 전에는 깔려 있어야 한다.

**깐 것을 알리는 문안** — 개발환경 준비 서브 에이전트의 보고가 오면, 메인이 그다음 응답에 이 컴퓨터에 깐 것을 결과 표로 붙인다. 깐 것이 없으면 이 표는 내지 않는다. 골자(판 숫자와 방법은 보고 그대로):

> 개발환경을 준비하며 이 컴퓨터에 깐 것입니다.
>
> | 도구 | 한 일 |
> |---|---|
> | fnm(Node 판 관리 도구 — 여러 판을 깔아 두고 골라 쓰게 해 주는 프로그램) | 이 프로젝트의 Node 판을 맞추려고 깔았습니다([Homebrew(맥용 프로그램 설치 도구)로 / fnm 공식 실행 파일을 받아]) |
> | Node.js [판]판 | fnm으로 이 프로젝트용으로 받았습니다. 원래 있던 Node [지금 판]판은 그대로 두었습니다 |
> | Vercel CLI·Supabase CLI 등 앱 패키지 | 이 프로젝트 폴더 안에 깔았습니다 |
> | Aside(견본 이미지 검색용 브라우저) | 없어서 명령줄 도구를 깔았습니다. [앱 설치는 aside.com/download에서 받아 해 주셔야 합니다 / 설치가 안 돼 견본 이미지는 다른 사이트로 채웁니다] |
> | Docker Desktop | 깔지 않았습니다 — 4단계에서 필요할 때 여쭙겠습니다 |

표 행은 실제로 한 일만 남긴다. 사용자가 할 일이 남았으면(설치 중에 운영체제가 띄운 허락 창에서 「예」를 누르는 일 같은 것) 표 아래 한 줄로 적고, 그 일이 꼭 지금 필요한지도 함께 적는다.

**스택 선택은 인터뷰 모드다** (SKILL.md §1.5 에스컬레이션 기준 (c) "결과를 되돌리기 비싼 갈림길") — AI가 임의로 정하지 않고 사용자에게 확인받는다. 다만 고를 게 하나뿐이라 길지 않다: **React 웹이냐 Expo냐.**

**때** — 2단계 시작 안내(`2-1-mockup.md` §2.1)의 끝에 붙여 한 메시지로 묻는다. 답이 오면 바로 §2.2부터 위임한다. 이미 루트에 `package.json`이 있으면(스킬 중간 재실행 등) 묻지 않고 §3 체크리스트로 검증해 빠진 것만 보완한다 — 처음부터 다시 만들지 않는다.

질문 골자 — 말투는 `AGENTS.md` 응답 톤에 맞춰 풀어서 전달:

> 화면을 만들기 전에 개발환경부터 깔겠습니다. 하나만 정해 주세요 — **웹으로 만들까요, 폰 앱(Expo)으로 만들까요?** 기본은 웹입니다. 링크 하나로 남에게 보여 줄 수 있고, 휴대폰 브라우저에서도 열립니다. 폰 앱은 브라우저로는 안 되는 것 — 앱이 꺼져 있을 때 오는 알림을 모든 폰에서 확실히 받기, 뒤에서 계속 위치를 재기 — 이 검증할 가설의 핵심일 때만 권합니다. 사진·짧은 영상 올리기, 위치 한 번 읽기, 오프라인에서 보기는 웹으로도 됩니다.
>
> 예시 답변: 「웹으로 해 주세요」 / 「앱이 꺼져 있어도 알림이 꼭 와야 해요」 / 「아직 모르겠어요 — 웹으로 시작하고 나중에 다시 정할래요」

**기본: React 웹.** 아래 §2.2 고정 스택과 그대로 맞물리고, 배포하면 링크 하나로 공유돼 남에게 보여줄 때 마찰이 가장 적다. 별다른 이유가 없으면 이걸로 간다.

**웹 우선 — 먼저 이 스택으로 웹 제품을 하나 완성하는 게 기본이다.** 처음부터 여러 플랫폼을 동시에 노리면 어느 쪽도 완성되지 않은 채 단계만 길어진다. 그래서 기본을 이 스택으로 둔다.

**장기 그림 — 지금 할 일은 없고, 방향만 알아두는 것이다.** **웹은 계속 웹으로 돌린다.** 이 스택 그대로 유지하고, 앱이 필요해지면 **그 웹 코드를 옮겨서 앱을 만든다.** 웹을 앱으로 이사시키는 게 아니다 — 웹은 그 자리에서 계속 돌고, 웹 코드가 앱의 출발점이 되는 것이다. 결과는 웹·모바일 앱·데스크톱 앱을 함께 운영하는 그림이고, **Supabase가 그 셋 전부의 공유 등뼈**다 (같은 DB·같은 로그인을 셋이 같이 본다).

**언제 — 6단계(MvpLaunch) 판정을 통과한 *다음*이다.** 사용자가 늘어 사업화 단계로 가거나, 앱이어야만 되는 기능이 필요해질 때. 그 전에 앱을 논하는 건 이르다 — 대부분의 아이디어는 6단계에서 걸러진다. 이건 어디까지나 나중 얘기고, **지금 당장 앱으로 시작해야 하는 경우는 바로 아래 Expo 문단**을 본다.

**무엇으로 — 기본은 React Native다.** 앱이 필요해지면 React Native로 옮긴다 — 화면 층만 다시 쓰면 되고 TypeScript·Supabase 호출·도메인 규칙·타입은 그대로 간다. 데스크톱 네이티브 성능이 제품의 핵심일 때만 Flutter를 검토한다.

**지금 대비 작업은 하지 않는다.** 나중을 위한 추상화 층이나 플랫폼 분기 코드를 MVP에 미리 깔지 않는다.

**Expo/React Native로 갈아타는 경우** — 다음처럼 **브라우저로는 안 되는 것이 검증 가설 자체의 핵심**일 때만:

- 앱이 꺼져 있을 때 오는 알림을 모든 폰에서 확실히 받아야 할 때
- 앱을 보고 있지 않을 때도 위치를 계속 재야 할 때(뒤에서 도는 위치)
- **웹으로 되는 것은 이유가 아니다** — 사진·짧은 영상 올리기(파일 고르기 칸이 휴대폰 카메라·보관함을 연다), 위치 한 번 읽기, 화면 안 알림, 오프라인에서 저장한 것 보기는 웹으로 된다. 2·3단계 검증은 이것으로 충분하다.

"나중에 앱으로 낼 거니까"는 이유가 안 된다 — 지금 검증할 가설이 네이티브 기능 없이는 확인이 안 될 때만이다. 이 경우 다음을 사용자에게 명시적으로 짚는다:

- **앱스토어 심사 마찰** — 심사 기간·정책 리스크가 있어 배포가 웹보다 느리다.
- **공유 비용** — 보여줄 상대가 Expo Go 앱을 설치해야 접근 가능하다(링크 하나로 끝나는 웹보다 마찰이 크다). 3단계 배포도 Vercel 링크가 아니라 Expo 공유로 대체된다.
- **고정 스택과의 괴리** — Supabase·Vercel 등 아래 §2.2 조합과 §2.6 목업 캔버스 틀은 웹 기준으로 짜여 있어, Expo를 택하면 그 조사·적용 절차와 화면을 보는 방법 상당 부분을 스스로 다시 판단해야 한다.

**애매하면 웹으로 시작한다** — 알림이 핵심인지 확실하지 않으면 웹으로 시작하고, 4단계 준비(`4-0-backend-prep.md`)에서 웹 푸시(홈 화면에 추가한 웹 앱이 받는 알림)로 갈지 React Native로 갈지 다시 정한다. 그 결정은 ADR에 적는다. 본보기: 「ADR-NNNN: 스택 — React 웹으로 시작. 알림은 2·3단계에서 화면 안 안내로 흉내 내고, 4단계 준비에서 웹 푸시·React Native 중 정한다.」

**선택 결과는 ADR로 기록한다** (`mvp/adr.md` — SKILL.md §3.1 "스택 주요 컴포넌트 추가·제거" 트리거). **스택 자체는 이후 에스컬레이션·재논의 대상이 아니다.** **고정 범위는 2단계에서 끝나지 않는다.** React·Next.js·Supabase 스택과 Vercel 배포는 **4단계(BackendBuild)까지 그대로 이어지는 고정**이다. 3·4단계는 스택을 새로 고르는 자리가 아니라 여기서 만든 같은 코드에 남은 화면·백엔드·계측을 얹는 자리다 (SKILL.md §2.1). 그래서 이 절의 선택은 한 번 쓰고 버리는 결정이 아니라, 남은 단계 전부가 올라탈 바닥이다.

**웹을 고르면 검색 노출(SEO)도 따라온다** — 웹 제품에서 빼고 갈 수 있는 항목이 아니라 4단계에 반드시 온다. **그렇다고 지금 서버 렌더를 만들라는 뜻은 아니다** — §2.3이 Supabase를 "붙일 자리만" 잡아두는 것과 같은 결로, **데이터 층을 나중에 서버에서도 불릴 수 있는 모양으로 짜두기만** 한다(`2-1-mockup.md` §2.6.2 「저장·조회 코드」). 2·3단계는 로컬스토리지 워킹 프로토타입 그대로 끝난다.

### 2.2 고정 core — 최신 호환 버전 조합 조사·적용

**React 웹을 택했으면 스택 자체는 고정이다 — 후보 제시·사용자 선택 없음.** idea-to-mvp 웹앱은 무조건 이 조합으로 빌드한다:

| 영역 | 고정 (mandated core) |
|---|---|
| 프레임워크 | Next.js (App Router) |
| 언어 | TypeScript |
| UI | React |
| 스타일링·부품 | Tailwind CSS + shadcn/ui |
| DB·Auth | Supabase (`@supabase/ssr` + `@supabase/supabase-js`) |
| 호스팅 | Vercel |
| lint | eslint-config-next |
| 패키지 매니저 | npm |

**왜 고정** (매 프로젝트 재결정 안 함): 2단계에서 만든 화면 코드가 그대로 실서비스 화면이 되려면 처음부터 실서비스와 같은 바닥 위에서 지어야 한다. Tailwind + shadcn은 범용 부품(버튼·입력·대화 창 등)을 프로젝트마다 새로 짓지 않고 받아 쓰게 해 준다. Supabase는 DB+Auth+소셜 로그인이 붙으면 바로 되는 최단 경로, Vercel은 main 머지→자동 배포+프리뷰. 빌드가 싼 시대엔 *뭘 쓸지*를 매번 고르는 일을 없애고 *뭘 만들지*에 집중한다.

**mandated core 밖**은 프로젝트별 추가 (지도=leaflet, 아이콘=lucide 등) — 검증 가설에 필요할 때만. core에서 빼거나 다른 것으로 갈아타는 건 하지 않는다. (결제 PG는 4단계 — 2·3단계엔 결제가 없다.)

**Node.js 버전부터 정한다** — Node.js(자바스크립트를 컴퓨터에서 돌리는 실행기 — 개발 서버와 빌드가 이 위에서 돈다)의 주 버전(맨 앞 숫자)이 이 컴퓨터·CI·Vercel에서 서로 다르면, 내 컴퓨터에서는 되던 빌드가 배포에서 깨진다. 그래서 패키지보다 먼저 정하고, 이 컴퓨터의 Node부터 맞춘다.

1. **고를 주 버전** — 아래 셋을 모두 만족하는 것 중 가장 새 것이다. 이 컴퓨터에 Node가 없어도 고를 수 있게, 확인은 `curl`과 `jq`로 한다.
   - ① 고를 Next.js의 `engines.node`를 만족한다 — `curl -s https://registry.npmjs.org/next/<버전> | jq -r .engines.node`(최신 stable이면 `<버전>` 자리에 `latest`). Node가 있으면 `npm view next@<버전> engines`도 같다.
   - ② Vercel이 지원한다 — Vercel 공식 문서 「Supported Node.js versions」(<https://vercel.com/docs/functions/runtimes/node-js/node-js-versions>)의 지원 목록과 기본값으로 확인한다.
   - ③ LTS(장기 지원판 — 오래 보안 수정을 받는 판)다. 막 나온 Current판(LTS가 되기 전 판)은 Vercel이 아직 지원하지 않을 수 있어 고르지 않는다.

   지금 LTS인 판은 Node.js 공식 릴리스 일정(nodejs/Release 저장소의 `schedule.json`)으로 확인한다. 명령 예:

   ```bash
   curl -s https://raw.githubusercontent.com/nodejs/Release/main/schedule.json \
     | jq -r --arg t "$(date +%F)" 'to_entries[] | select(.value.lts != null and .value.lts <= $t and .value."end" > $t) | "\(.key) LTS 시작 \(.value.lts) 지원 끝 \(.value."end")"'
   ```

2. **이 컴퓨터의 Node를 맞춘다 — 언제나 fnm으로, AI가 묻지 않고 한다.** fnm(Node 버전 관리 도구 — 여러 판을 깔아 두고 명령마다 골라 쓰게 해 주는 프로그램)으로 이 프로젝트의 판만 받아 둔다. 이 컴퓨터에 Node가 없든, 낮든, 다른 판이든, 이미 맞든 갈래가 하나다. 이 컴퓨터에 원래 있던 Node·Homebrew(맥용 프로그램 설치 도구)는 지우지도 바꾸지도 않고 그대로 둔다 — 사용자의 다른 프로젝트가 그 판을 쓸 수 있어서다.
   - **fnm 깔기** — `fnm --version`(또는 `~/.local/share/fnm/fnm --version`)이 되면 건너뛴다. 없으면 묻지 않고 깐다.
     - **맥, Homebrew 있음** (`brew --version` 성공) — `brew install fnm`. 이 명령이 실패하면 같은 명령을 다시 돌리지 않고 바로 아래 「Homebrew 없음」 방법으로 바꾼다 — Homebrew 자체의 상태 때문에 막히는 일은 다시 돌려도 풀리지 않는다.
     - **맥, Homebrew 없음** — Homebrew를 새로 들이지 않는다. fnm 공식 GitHub 릴리스의 `fnm-macos.zip`을 받아 사용자 폴더에 푼다(fnm 공식 설치 스크립트는 맥에서 Homebrew를 쓰라고 안내하므로 스크립트 대신 실행 파일을 직접 받는다). 관리자 암호 창이 뜨지 않는다.

       ```bash
       tmp="$(mktemp -d)" && mkdir -p ~/.local/share/fnm \
         && curl -fsSL -o "$tmp/fnm-macos.zip" https://github.com/Schniz/fnm/releases/latest/download/fnm-macos.zip \
         && unzip -o "$tmp/fnm-macos.zip" -d ~/.local/share/fnm && chmod +x ~/.local/share/fnm/fnm && rm -rf "$tmp"
       ```

       이렇게 받은 fnm은 명령 경로에 없으니 `~/.local/share/fnm/fnm`처럼 전체 경로로 부른다.
     - **윈도우** — `winget install -e --id Schniz.fnm`(winget — 윈도우에 들어 있는 공식 프로그램 설치 도구). 깔았는데 명령을 못 찾으면 「fnm을 깔았습니다. 새 명령이 잡히도록 클로드 코드를 껐다 켜 주세요」 한 줄만 알린다.
   - **판 받기** — `fnm install <주 버전>`. fnm이 Node 공식 배포판(nodejs.org)에서 받아 사용자 폴더에 둔다. 이미 받아 둔 판이 있으면 건너뛴다.
   - **부르는 법** — 이 프로젝트의 node·npm·npx 명령은 전부 `fnm exec --using=.nvmrc -- <명령>`으로 부른다. 예: `fnm exec --using=.nvmrc -- npm install`, `fnm exec --using=.nvmrc -- npx supabase start`. `--using`은 판 숫자나 판이 적힌 파일 이름을 받는다(fnm 공식 명령 설명) — `.nvmrc`를 만들기 전에는 `--using=<주 버전>`으로 부른다. 받은 뒤 `fnm exec --using=<주 버전> -- node -v`로 주 버전을 확인한다.
   - **하지 않는 것** — 셸 설정 파일(`~/.zshrc`·`~/.zprofile` 등 터미널이 열릴 때 읽는 파일)에 fnm을 넣지 않는다(`fnm env`·`fnm use`·`fnm default`는 셸 설정이 있어야 듣는 명령이라 쓰지 않는다). 이 컴퓨터의 기본 Node를 바꾸거나 명령을 찾는 경로 순서를 고치지 않는다. 위 세 설치 방법은 셸 설정 파일을 고치지 않는다.
   - **이후 단계에도 이어진다** — 프로젝트 `AGENTS.md` 「이 프로젝트가 쓰는 도구」의 Node.js 줄이 이 규칙을 담는다: AI는 이 프로젝트의 node·npm·npx 명령(`npm run`·`npx supabase`·`npx vercel` 포함) 앞에 `fnm exec --using=.nvmrc --`를 붙여 저장소 최상위 폴더에서 부른다. 그래서 다른 단계 문서의 명령은 붙이지 않은 모양 그대로 적혀 있다.

   **왜 언제나 fnm인가** — 경우마다 기본 Node를 깔거나 바꾸는 방법도 있다. 고르지 않는 까닭은 셋이다. 첫째, 이 컴퓨터의 기본 Node는 사용자의 다른 프로젝트도 함께 쓰는 것이라 바꾸면 그쪽이 깨질 수 있다. 둘째, 기본 Node를 까는 길은 운영체제마다 다르고(Homebrew의 Node 묶음, 관리자 암호가 필요한 공식 설치 파일 등) 실패하는 갈래도 제각각이라, 갈래를 하나로 두는 편이 틀릴 곳이 적다. 셋째, 아무것도 깔지 않고 CI와 Vercel만 `.nvmrc`·`engines.node`로 고정하면 2~4단계 내내 개발 서버·빌드·테스트가 배포와 다른 판에서 돈다 — npm은 `engines.node`가 안 맞아도 경고만 내고 설치를 이어 가서(npm 설정 `engine-strict`의 기본값이 꺼짐 — npm 공식 문서) 판이 다르다는 걸 알아채기 어렵다. 여러 버전 관리 도구 중 fnm을 고르는 까닭은, 실행 파일 하나라 묻는 창 없이 깔리고, Node 공식 배포판을 받고, `.nvmrc`를 읽고, 셸 설정 없이 `fnm exec`로 명령마다 판을 고를 수 있어서다. AI의 명령은 부를 때마다 새 셸에서 돌아 앞 명령의 상태가 이어지지 않으니, 명령마다 판을 붙이는 방식이 맞다. nvm은 셸 설정 파일에 넣어야 동작하는 도구라 고르지 않는다. 사용자가 이미 다른 버전 관리 도구를 써도 fnm을 따로 깐다 — 서로 다른 폴더를 써서 부딪히지 않는다.

   **실패하면** — fnm 깔기·판 받기·확인 중 같은 실패가 2번 나면 멈추고, 어느 명령이 무엇으로 실패했는지 사용자에게 알린다(맥에서 Homebrew로 fnm을 깔다 실패한 것은 이 2번에 세지 않는다 — 공식 실행 파일로 바꾸는 것이 정해진 다음 길이다). 사람에게 넘기는 건 그때뿐이다. Node 없이는 이 절의 나머지를 할 수 없으니 2-0은 거기서 멈춘다(메인의 2-1 기능·화면 목록 작업은 이어 간다).

3. **다섯 자리를 같은 주 버전으로 맞춘다.**

   | 자리 | 맞추는 법 |
   |---|---|
   | 이 컴퓨터 | 위 2번. 확인은 `fnm exec --using=.nvmrc -- node -v`의 맨 앞 숫자 |
   | `package.json`의 `engines.node` | 「주 버전.x」 모양으로 적는다 — 예: `"engines": { "node": "24.x" }` (숫자는 모양을 보이려는 예시다) |
   | `.nvmrc` | 루트에 주 버전 숫자 한 줄. Node 버전 관리 도구(fnm 등)가 이 파일을 읽어 이 프로젝트에 맞는 판을 고른다 |
   | CI | 하네스가 넣은 `.github/workflows/ci.yml`이 `setup-node`의 `node-version-file: .nvmrc`로 읽는다 — 따로 고칠 것이 없다 |
   | Vercel 프로젝트 설정 | Settings → Build and Deployment → Node.js Version. 프로젝트는 3단계 첫 배포 때 생기니 그때 맞춘다. Vercel은 `package.json`의 `engines.node`를 프로젝트 설정보다 먼저 따른다(공식 문서) — `engines.node`를 적어 두면 설정이 달라도 그 주 버전으로 빌드되고, 3단계 첫 배포 체크리스트가 빌드 기록으로 다시 확인한다 (`3-frontend-build.md` §2.6) |

4. **ADR에 한 줄** — 고른 주 버전과 그 근거(①②③ 각각 무엇으로 확인했는지). 이 컴퓨터에 무엇을 깔았는지는 컴퓨터마다 다른 일이라 ADR이 아니라 보고와 「깐 것을 알리는 문안」에 적는다.

**이 절에서 실제로 하는 일 = 고정 스택의 최신 호환 버전 조합을 상호 의존성 고려해 조사·적용** (초안 모드 — AI가 조사·적용·보고, 사용자 선택 없음). **버전 숫자는 휘발성이라 이 references에 적지 않는다.** 조합은 빌드 시점에 조사해 `mvp/adr.md`에 기록한다:

1. Next.js 최신 stable 확인 → 그것이 받는 React 범위와 Node 범위 파악(`npm view next@<버전> peerDependencies engines`). Node 주 버전은 위 「Node.js 버전부터 정한다」에서 정한다.
2. TypeScript·ESLint·eslint-config-next를 그 Next와 맞는 것 중, 서로 받는 범위 안에서 가장 새 것으로 (아래 「서로 받는 범위를 먼저 본다」).
3. Supabase(`@supabase/ssr`·`@supabase/supabase-js`) 최신. 그리고 개발용 패키지(`--save-dev`)로 깔 Vercel CLI(`vercel`)·Supabase CLI(`supabase`) 최신 — 둘 다 `npm view <패키지>@<버전> engines`로 고른 Node 주 버전을 받는지 본다. 깔기만 하고 로그인·키 설정은 하지 않는다(§2.1 도구 점검표).
4. Tailwind CSS 최신 stable. Next.js와 잇는 방식(PostCSS 플러그인이든 Turbopack 로더 — `next.config.ts`의 `turbopack.rules` — 든)은 그때의 create-next-app이 넣는 기본값을 그대로 따르고, 어느 방식인지 ADR에 적는다. 다른 방식으로 바꾸지 않는다. shadcn은 npm 패키지가 아니라 CLI가 부품 파일을 프로젝트에 복사해 주는 방식이라 버전을 고정하지 않는다 — 대신 고른 style 이름과 `components.json` 내용을 ADR에 적는다. 이 값이 같아야 나중에 부품을 다시 받아도 같은 모양이 나온다.
5. **조합 설치 검증** — `npm install`이 peer-dep 충돌(`ERESOLVE`) 없이 통과하는지. 충돌 시 마지막 호환 조합으로 한 단계 물러선다 (`--force`·`--legacy-peer-deps`로 덮지 말 것).
6. 해소된 정확한 버전을 `package.json`에 고정 + ADR에 조합 기록. `package-lock.json`(설치된 정확한 버전을 적어 두는 파일)도 커밋한다 — CI의 `npm ci`와 Vercel이 이 파일 그대로 설치한다. 3·4단계는 이 기록을 참조만 하고 다시 고르지 않는다.

**서로 받는 범위를 먼저 본다** — 핵심 패키지마다 `npm view <패키지>@<버전> peerDependencies engines`(다른 패키지를 끌어오는 패키지면 `dependencies`도)로 다른 패키지를 어느 범위까지 받는지 본다. 한 패키지의 최신이 다른 패키지가 받는 범위 밖이면, 범위 안에서 가장 새 것으로 내린다. 설치를 돌리기 전에 고를 버전을 정하는 데 쓴다 — 설치가 막힌 뒤 거꾸로 되짚는 것보다 빠르다. 흔한 예:

- **TypeScript** — eslint-config-next가 끌어오는 typescript-eslint가 받는 범위 안에서만. `npm view eslint-config-next@<버전> dependencies`로 typescript-eslint 범위를 보고, `npm view typescript-eslint@<그 범위의 최신> peerDependencies`로 TypeScript 범위를 본다.
- **ESLint** — eslint-config-next가 끌어오는 eslint-plugin-react·eslint-plugin-import·eslint-plugin-jsx-a11y가 받는 주 버전 안에서만.
- **React·react-dom** — Next가 받는 범위 안에서만.

최신을 못 쓴 패키지는 ADR에 「누가 어떤 범위만 받아서」를 한 줄씩 적는다 — 예: 「TypeScript는 최신 대신 `<고른 버전>` — typescript-eslint `<버전>`이 `<범위>`만 받아서」. 다음에 올릴 때 그 패키지가 범위를 넓혔는지만 보면 된다.

`shadcn` 패키지는 진입 CSS의 `@import "shadcn/tailwind.css"` 때문에 앱 의존성(개발 의존성이 아님)에 남아, `npm audit --omit=dev`에 그 CLI 쪽 의존성의 high가 걸린다. 번들에 안 실리니 ADR에 한 줄로 남긴다 — 「`npm audit --omit=dev`의 shadcn 쪽 high {N}건은 `shadcn` 패키지의 CLI·MCP 서버 의존성이라 브라우저 번들에 실리지 않는다 — 진입 CSS의 `@import "shadcn/tailwind.css"` 때문에 앱 의존성에 둔다. 4단계 준비에서 판 올림으로 풀렸는지 확인한다.」

- **조사 소스**: 공식 docs·npm registry·context7 (최신 버전·peer 요구). LLM 학습 시점 이후 버전은 반드시 조사로 확인 — 기억으로 적지 말 것.
- **graceful degradation**: 조사가 불확실하면 마지막 known-good 조합으로 진행하고 `추후 결정: [무엇을 재확인]` 마킹.
- **에스컬레이션**: 고정 스택 자체를 못 쓰는 근본 비호환일 때만 멈추고 사용자에게. 그 외엔 조사·적용 완주.

**루트에 이미 있는 파일을 덮지 않는다** — 프로젝트 루트에는 `AGENTS.md`·`CLAUDE.md`·`mvp/`·`.claude/`·`.gitignore`가 이미 있다. 스캐폴딩(scaffolding — 앱의 기본 폴더·파일을 한 번에 만들어 주는 명령) 도구가 빈 폴더를 요구하면 임시 폴더에 만든 뒤 루트로 옮기고, `.gitignore`는 두 쪽 줄을 합친다. 겹치는 파일을 덮어야 할 것 같으면 멈추고 보고한다.

스캐폴딩·첫 `next dev` 뒤 AGENTS.md에 Next 구역(`<!-- BEGIN:nextjs-agent-rules -->`)이 붙어도 지우지 않는다 — 우리 규칙은 `<!-- BEGIN:project-rules -->` 구역에 있으니 서로의 구역을 건드리지 않는다. Next.js는 버전마다 바뀌는 것이 많으니, 이후 코드를 쓸 때는 그 구역이 가리키는 `node_modules/next/dist/docs/`를 먼저 본다.

**새 앱의 Next.js 설정 둘을 끈다** — create-next-app이 `next.config.ts`에 `cacheComponents`·`partialPrefetching`을 켜 두면 둘 다 `false`로 적는다(줄을 지우지 않는다 — `partialPrefetching`은 적지 않으면 경고가 난다, Next.js 공식 문서). 켜 두면 주소에 따라 달라지는 화면(주소의 검색 조건을 읽는 화면, 목업 캔버스의 `?state=` 흉내를 받는 화면)마다 Suspense(불러오는 동안 대신 보일 자리를 정하는 리액트 감싸개)로 감싸야 해서 2·3단계 화면 코드가 는다. ADR에 끈 설정과 이 이유를 한 줄 적는다. 두 설정은 Next.js가 주 버전을 올리며 기본으로 바꿀 예정이라(공식 문서), 판을 올릴 때 `node_modules/next/dist/docs/`를 다시 본다.

**CI가 이때부터 돈다** — CI(저장소에 올릴 때마다 자동으로 도는 검사)는 `package.json`이 생기면 린트·빌드를 돌리기 시작한다. 그래서 이 문서 끝(§3)에 `lint`·`build`가 통과하는지 확인한다.

### 2.3 Supabase·Vercel — 붙일 자리만

Supabase는 **환경변수 자리만 비워서 잡아둔다** — 프로젝트는 아직 만들지 않는다:

- `.env.example`에 Supabase URL·공개 키(Publishable key, 옛 anon) 자리를 이름만 채워 둔다 — `NEXT_PUBLIC_SUPABASE_URL`·`NEXT_PUBLIC_SUPABASE_PUBLISHABLE_KEY`. CI 빌드(`.github/workflows/ci.yml`)가 같은 이름에 자리표시자를 넣으니 이름을 바꾸지 않는다(실제 값은 없음 — 이 앱은 2·3단계에서 백엔드 없이 로컬스토리지로 돈다).
- 클라이언트 초기화 코드(`@supabase/ssr`)까지만 두고 **테이블은 만들지 않는다.**
- **Supabase 프로젝트 생성은 4단계 준비(4-0)에서 계정을 확정한 뒤에 한다** — 실제 테이블·RLS·로그인·데이터 이전도 전부 4단계 몫이다. 계정이 안 정해진 채 프로젝트부터 만들면, 나중에 다른 계정으로 옮길 때 프로젝트 재생성·키·시크릿·콜백 주소를 전부 다시 잇게 된다.

**왜 여기서 끊나.** 두 가지다. (1) 화면이 제대로 돌아가는지 확인하는 데는 백엔드가 필요 없다 — 로컬스토리지로도 "데이터가 쌓이고 다시 보이는" 경험은 똑같이 난다. (2) 화면을 만들다 보면 구조가 뒤집히는 일이 흔한데, 그때 미리 짜둔 DB 스키마 작업이 통째로 버려진다. 화면이 굳은 다음에 테이블을 뜨는 게 싸다. 로컬스토리지로 데이터를 다루는 규칙은 화면을 만드는 2-1에 있다 (`2-1-mockup.md` §2.6.2 「저장·조회 코드」).

**Vercel은 아무것도 연결하지 않는다** — Vercel CLI는 §2.2에서 개발용 패키지로 깔기만 하고 로그인하지 않는다. 2단계는 사용자의 개발 서버 주소로 화면을 본다. 프로젝트 연결·환경변수·첫 배포는 3단계 배포 절(`3-frontend-build.md`)에서 계정 대조와 함께 한다. 그래서 2단계는 main에 따로 합치지 않고 같은 브랜치로 3단계까지 간다(SKILL.md 「2·3단계는 한 브랜치로 간다」).

### 2.4 Vercel 플러그인 설치

**Vercel 플러그인**이 깔려 있는지 확인하고, 없으면 사용자에게 설치를 안내한다 — 스택 질문(§2.1)과 같은 메시지에 한 줄로 붙인다.

**플러그인은 CLI가 아니다** — Claude Code의 Vercel 플러그인은 클로드 코드 안에서 부르는 스킬 묶음이다. 터미널에서 치는 명령인 Vercel CLI(§2.1 도구 점검표 — 프로젝트 안에 깐다)와 이름만 같고 하는 일이 다르다.

**이 하네스에서 쓰는 곳** — 쓰임이 없는 도구는 받게 하지 않는다. 그래서 무엇에 쓰는지 적어 둔다.

| 스킬 | 쓰는 곳 | 꼭 필요한가 |
|---|---|---|
| `/vercel:react-best-practices` | 3단계 배포 전 검사 중 코드 품질 리뷰 (`3-frontend-build.md` §2.5) | 필요 — 이 검사가 이 스킬로 돈다 |
| `/vercel:nextjs`·`/vercel:deploy` 등 | Next.js 사용법을 확인하거나 배포를 도울 때 | 선택 — 없어도 절차가 막히지 않는다 |

- **대화 중 설치**: `/plugin install vercel@claude-plugins-official`
- **터미널에서 설치**: `claude plugin install vercel@claude-plugins-official`
- **마켓플레이스를 따로 추가할 필요 없다** — `claude-plugins-official`은 공식 마켓플레이스라 자동으로 등록돼 있다.
- **설치 범위는 사용자 전역(User)을 권한다** — 프로젝트마다 다시 깔지 않아도 된다. 전역으로 깔면 `~/.claude/settings.json`의 `enabledPlugins`에 기록된다.
- **설치 확인**: 대화에서 `/plugin` → Installed 탭, 또는 터미널에서 `claude plugin list`
- **스킬 호출 형식**: `/vercel:nextjs`처럼 `플러그인이름:스킬이름`

설치는 사용자 설정을 바꾸는 일이라 AI가 대신 하지 않는다. 사용자가 아직 안 깔았어도 §2.2부터 진행한다 — 플러그인이 꼭 필요한 건 3단계 배포 전 검사의 코드 품질 리뷰부터다.

### 2.5 디자인 시스템 첫 세팅

같은 하네스의 `design-system` 스킬 방법론대로, 그 스킬의 `bootstrap-project.md` §1~§4 순서로 간다. 메인은 그 절차를 걸러 둔 문안(§1 「붙여 넣을 문안 — 디자인 시스템 첫 세팅」)을 지시서에 그대로 넣는다 — 그 문서를 따로 읽지 않는다.

1. **`npx shadcn init`** — shadcn(버튼·창 같은 기본 부품 모음을 프로젝트에 까는 명령)을 설치한다. `components.json`·`lib/utils.ts`·진입 CSS가 생긴다. 이어서 **클래스 합치기 설정**을 한다 — shadcn 부품은 클래스 이름을 합치는 도구로 겹치는 클래스를 지우는데, 그대로 두면 우리 글자 이름(`text-b2` 등)을 글자색 클래스로 잘못 알고 지운다. 그래서 `lib/utils.ts`의 합치기 함수에 우리 2층 이름을 알려 두고, 부품 파일이 그 함수를 불러 쓰게 import를 바꾼다. 부품을 새로 받을 때마다(5번과 이후 단계 모두) 같은 import를 바꾼다. 방법은 design-system `bootstrap-project.md`가 정본이다.
2. **1층**(기본 값 — 색 단계·글자 크기 같은 원래 값) — 브리프 「4. 확정 브랜드 자산」의 「우리가 쓰는 값」 표로 채운다. 옮기는 법은 design-system `reference-analysis.md` §5다. 색은 hex를 oklch로 바꿔 램프에 넣는다. 흰 바탕 대비 때문에 브리프 「4」의 값보다 한 단계 진한 단계에 이었으면(예: 위험색·성공색) 어느 색을 어느 단계로 이었는지 보고에 적고, 메인이 브리프 「4」 그 색 행에 「코드는 한 단계 진하게 — 대비」를 붙인다. 서체는 표에 적힌 무료 서체(유료면 대체 서체)로 로딩 방식까지 정한다. 모션 기본 값도 이때 1층에 자리만 잡는다 — 값은 3단계 모션 다듬기 절이 브리프 「8」로 정한다.
3. **2층**(역할 이름 — `primary`처럼 쓰임새로 붙인 이름) — shadcn 이름 세트를 지우지 않고 전부 1층 변수로 다시 잇는다. 진입 CSS의 import 순서를 고정한다.
4. **셸**(shell — 모든 화면에 공통으로 씌우는 상단 메뉴·바탕 틀) — `feature-list.md` 8절 「메뉴 구조」대로 만든다. 아직 없으면 브리프 「6. 주 사용 맥락」에 맞는 기본 메뉴로 만들고, 메인이 8절을 쓴 뒤 한 번 맞춘다(메인이 직접 고치거나 같은 에이전트에 이어 맡긴다). 폰 폭에서 숨기는 건 상단 메뉴뿐이다 — 헤더(로고·알림·프로필)는 두 폭 모두 남긴다. 쌓이는 화면(메뉴 → 상세처럼 들어간 화면)은 폰 폭 앱바가 「뒤로 · 화면 제목 · 동작 하나」로 바뀐다 — 모바일 앱 관례다. 뒤로 가기 줄을 앱바 아래 따로 두지 않고, 화면 제목 줄 부품이 셸에 「뒤로·제목·동작」을 등록하는 방식으로 만든다(화면마다 고치지 않게). 넓은 화면은 탭 화면과 같은 헤더에 본문 맨 위 뒤로 가기 줄. 화면 폭으로 갈리는 자리는 상단 메뉴 ↔ 햄버거 메뉴(또는 하단 탭) 전환 하나뿐이고, 나머지 영역 크기 대응은 컨테이너 쿼리(부품이 놓인 자리의 폭에 맞춰 바뀌는 CSS)로 만든다 — 3단계 배포 전 검사의 디자인 규칙 검사가 이 규칙을 잡는다. 셸의 메뉴 주소는 아직 화면 목록이 없으니 임시 글자(자리 표시)로 두고, 2-1 첫 화면 에이전트가 주소 모음 파일을 만들 때 셸이 그 파일을 쓰게 바꾼다(`2-1-mockup.md` §2.6.3 3번). 2-0이 주소를 지어 정하지 않는다.
5. **부품** — 2-1의 주요 화면에 꼭 필요한 shadcn 부품만 `npx shadcn add`로 받는다. 받은 부품은 2층 값만으로 브랜드 색·모양이 적용되는 것이 정상이다. **처음 받을 때 브리프 「9. 접근성 바닥선」의 누르는 요소 크기(최소 44px)를 부품 파일에 바로 넣는다** — 입력칸·선택 상자·탭·체크박스처럼 shadcn 기본 높이가 모자란 부품이다. 화면 코드에서 `className`으로 덮어써 맞추지 않는다. 브리프 「4」의 「부품 모양」 행이 44px보다 작은 크기를 적었으면 「9」가 이기고, 그 어긋남을 보고에 적는다. 브리프 「우리가 쓰는 값」의 「부품 모양」 행(버튼·카드·입력칸·상단 메뉴의 생김새)은 2층 값으로 먼저 풀고, 그래도 부품 파일을 고쳐야 하면 고친 파일과 이유를 연결 정보의 「고친 shadcn 부품 목록」에 적는다. 새 variant는 만들지 않는다(§1).
6. **부품 목록 문서**(`docs/components.md`) — 받은 범용 부품과 셸 부품을 등록한다. 형식은 design-system `component-taxonomy.md` §6. 문서 끝의 「## 전체 부품 색인」(부품 파일 경로 한 줄씩)까지 만든다 — 3단계 배포 전 검사가 이 색인과 실제 부품 파일을 대조한다(`3-frontend-build.md` §2.5 검사 ①). 색인은 손으로 쓰지 않고 아래 명령으로 만든다 — 한 줄에 하나, 꾸밈 없이, 코드 블록 안이어야 3단계 검사가 줄 전체 일치로 대조할 수 있다. 이미 색인 구간이 있으면 그 구간을 지우고 다시 붙인다. 아래 명령은 색인 구간 머리 설명 줄에 목록을 뽑는 명령도 함께 적는다 — 뒤에 부품을 더하는 에이전트가 이 문서를 읽지 않고도 `docs/components.md`에서 명령을 읽어 다시 만든다. 형식의 정본은 design-system `component-taxonomy.md` §6.1이다.

   ```bash
   { echo '## 전체 부품 색인'; echo; echo "_부품 파일이나 \`3-components.css\` 클래스를 더하거나 지울 때 이 구간을 지우고 다시 만든다. 목록은 \`find src/components -name '*.tsx' | sort\`와 \`grep -hoE '^\\.[A-Za-z][A-Za-z0-9_-]*' src/styles/3-components.css | sed 's/^\\.//' | sort -u\`의 출력이다._"; echo; echo '```'; find src/components -name '*.tsx' | sort; grep -hoE '^\.[A-Za-z][A-Za-z0-9_-]*' src/styles/3-components.css | sed 's/^\.//' | sort -u; echo '```'; } >> docs/components.md
   ```

7. **연결 정보**(adapter — `AGENTS.md`의 「디자인 시스템 연결 정보」 절) — 진입 CSS와 세 층 경로, `components.json` 위치와 별칭, 부품 목록 위치, 고친 shadcn 부품 목록(1번의 import 바꾸기와 5번의 44px 반영 포함), 철칙 요약, 적용 규칙 요약(글자 크기 바닥선 · 역할 한정 토큰), 링크 버튼 쓰는 법(받은 `Button` 부품 파일을 보고, 버튼 안에 `Link`를 넣어 링크로 쓸 때 어떤 속성을 쓰는지 한 줄로 적는다. 화면 에이전트는 이 줄대로 쓴다). 버튼처럼 생긴 링크는 `Button` 안에 `Link`를 넣는다. 링크로 바꾸는 속성은 받은 `Button` 부품 파일이 정한다 — 2-0이 부품을 받을 때 그 파일을 보고 연결 정보(`AGENTS.md` 「디자인 시스템 연결 정보」)에 「링크 버튼 쓰는 법」 한 줄로 적어 두고, 화면 에이전트는 그 줄대로 쓴다. 「12」가 아직 `추후 결정`이라 글자 이름 대응표·간격 허용 단계는 비워 두고 2-2가 채운다.

**이후 모든 화면·부품 코드는 2층 이름 클래스(`bg-primary`)와 theme 단계 클래스(`p-4`·`text-b1`)만 쓴다** (hex·px·대괄호 임의 값 금지 — 스킬 철칙). 그래야 2-2가 1·2층 값을 바꿀 때 화면이 다시 만들지 않고도 따라온다.

**값은 대부분 `가정`이다** — 브리프 「4」의 값 중 지위가 `가정`인 것은 그대로 1층에 넣되, 보고에 「`가정` 값으로 채운 1층 항목」으로 적는다. 2-1이 화면을 보여 줄 때 사용자가 확인하고(`2-1-mockup.md` §2.6.5 「보며 특히 확인할 것」), 2-2가 다듬는다. 사용자가 2-1 도중에 값을 바꾸면 1층과 브리프 「우리가 쓰는 값」 표를 함께 고친다 (`2-1-mockup.md` §2.7).

### 2.6 목업 캔버스 뼈대 넣기

**목업 캔버스**는 리액트로 만든 개발용 페이지다. 만든 화면들을 무한 캔버스(끌고 확대해 보는 넓은 판) 위에 흐름 순서로 펼치고, 화면마다 데스크톱 폭과 폰 폭(390) 창을 한 쌍으로 둔다. 멀리서는 미리 찍어 둔 그림을, 확대하면 그 화면만 실제 주소의 창(iframe — 페이지 안에 다른 페이지를 띄우는 창)을 보여 준다. 화면 위에서 요소의 코드 자리를 복사하거나(요소 복사) 고칠 곳에 메모를 꽂을(코멘트 핀) 수도 있다. 옆에는 실제 토큰·부품으로 글자 단계·색 역할·간격·둥글기·부품 상태를 보여 주는 「[서비스 이름] 디자인 시스템」 페이지가 있다. 사람이 2단계 내내 모든 화면을 한눈에 보는 자리다.

**하네스가 틀을 준다** — 뼈대 코드는 `.claude/templates/mockup-canvas/`에 있다. 틀의 파일 이름, 각 파일을 프로젝트 어디에 놓는지, 채울 자리는 그 폴더의 `README.md`가 정본이다 — 여기 다시 적지 않는다. 틀 파일의 끝 이름은 `.tsx.template`·`.ts.template`이다(프로젝트의 타입 검사·린트가 `.claude/` 안까지 훑어 오류를 내지 않게).

**차례**:

1. **복사** — `README.md`대로 틀 파일을 프로젝트 자리로 복사하며 끝 이름의 `.template`을 뗀다. 들어가는 자리는 목업 캔버스(`src/app/(dev)/dev/canvas/`, 주소 `/dev/canvas`)와 그 아래 개발용 라우트 핸들러(그림·코멘트·창 목록), 디자인 시스템 페이지(주소 `/dev/design-system`), 개발용 묶음 레이아웃(`src/app/(dev)/layout.tsx`), 상태 표시 도우미(`src/lib/dev-state.ts`), 그림 찍기 스크립트(`scripts/canvas-shots.mjs`) 등이다. `(dev)`는 Next.js 라우트 묶음(route group — 주소에는 안 나타나고 폴더만 묶는 이름)이다.
   - **새 개발 의존성을 같이 깐다** — 요소 복사 도구(`react-grab`)와 그림 찍기에 쓰는 브라우저 자동화 도구(`playwright`)를 개발 의존성으로, 판을 고정해 깐다. 묻지 않고 깐다(2단계에서 쓰는 도구라서 — §2.1 「2단계에서 쓰는 도구는 AI가 묻지 않고 깐다」). 그림 찍기에 쓸 브라우저는 처음 그림을 찍을 때 내려받는다.
   - **`README.md`가 정한 나머지 연결도 한다** — `package.json`의 목록 만들기·그림 찍기 명령(`canvas:list`·`canvas:shots`), `.gitignore`의 그림 폴더 줄, 루트 레이아웃에 요소 복사 스크립트 한 줄(개발 서버에서만 실림).
2. **서비스 이름 채우기** — 디자인 시스템 페이지 제목을 「[서비스 이름] 디자인 시스템」으로(예: 서비스 이름이 「책갈피」면 「책갈피 디자인 시스템」), 그 밖에 `README.md`가 가리키는 채울 자리를 채운다. 「규칙 페이지」라고 부르지 않는다. **페이지의 설명 글에는 px 숫자와 hex 색 값을 쓰지 않는다** — 값은 글로 적지 말고 브라우저가 계산한 값(토큰이 실제로 돌려주는 값)으로 보여 준다. 글에 적은 숫자는 토큰이 바뀌어도 따라오지 못하고, 디자인 규칙 검사(`design-check.sh` 1번)에도 걸린다.
3. **목업 캔버스 목록 파일** — 목업 캔버스에 띄울 화면 목록이고, 두 파일로 나뉜다. 자동 부분 `src/app/(dev)/dev/canvas/screens.generated.ts`는 `npm run canvas:list`(그림 찍기처럼 `package.json`에 더하는 명령 — 틀 `README.md`)가 화면 목록(`feature-list.md` 6절)과 상태 표(7절)에서 만든다. 손 부분 `screens.ts`에는 비교안처럼 사람이 더하는 것만 적는다. 지금은 화면이 없으니 자동 부분은 빈 목록이다 — 2-1이 화면을 만들고 화면 목록 「주소」 칸을 채운 뒤 스크립트를 돌린다 (`2-1-mockup.md` §2.6.2 「목업 캔버스 목록 파일」).
4. **상태 표시 도우미를 저장·조회 코드에 잇기** — 도우미는 개발 서버에서만 주소 끝 `?state=empty|loading|error|forbidden`과 `?as=guest`를 읽어 돌려준다. 저장·조회 코드(`src/lib/storage.ts`)의 뼈대를 만들고, 그 안에서 도우미를 불러 빈 결과·느린 응답·오류를 돌려주게 잇는다(권한없음은 가짜 로그인 상태를 바꿔서 낸다). 아직 데이터 종류가 없으면 공통 읽기·쓰기 함수 자리만 둔다. 화면 코드는 상태 표시를 읽지 않는다 — 화면은 저장·조회 코드가 돌려준 결과대로 실제 처리 경로를 탄다. 저장·조회 코드의 규칙은 `2-1-mockup.md` §2.6.2 「저장·조회 코드」다. 가짜 로그인 함수의 뼈대도 이때 만들어 둔다. 목업 캔버스의 창들은 같은 주소라 브라우저 저장소(가짜 로그인 상태 포함)를 같이 쓴다. 그래서 「로그인 전」 모습은 저장소를 바꾸지 않고 주소로 흉내 낸다 — 상태 표시 도우미(`src/lib/dev-state.ts`)의 `readDevGuest()`가 개발 서버에서만 주소 끝 `?as=guest`를 읽어 돌려주고, 저장·조회 코드에서 지금 로그인한 사람을 읽는 함수가 이 값을 먼저 봐서 참이면 「로그인 전」으로 답한다. 목록 만들기 스크립트는 화면 목록 「역할」 칸이 「비로그인 방문자」인 화면 주소 끝에 `?as=guest`를 저절로 붙인다.
5. **검사** — 빌드·린트·타입 검사를 돌려 통과시킨다. 실서비스 빌드에서 `/dev` 주소가 막히는지(개발용 묶음 레이아웃과 라우트 핸들러의 문지기가 404를 내는지)도 화면을 열지 않고 확인한다 — 예: 실서비스 빌드를 띄워 `curl -s -o /dev/null -w "%{http_code}" http://localhost:<포트>/dev/canvas`와 `…/dev/canvas/comments`가 둘 다 `404`인지. 확인용으로 띄운 서버는 끝나면 자기가 띄운 것만 끈다. 내 컴퓨터에서 실서비스 빌드로 빠르게 볼 때 쓰는 `MOCKUP_CANVAS=1`(틀 `README.md` 「실서비스 빌드로 빠르게 보기」)은 명령 앞에만 붙인다 — `.env` 파일과 Vercel 환경변수에는 절대 넣지 않는다(넣으면 공개 주소에서 열린다).

**원칙**:

- **틀을 다시 짓지 않는다** — 복사하고 이름만 채운다. 매번 새로 지으면 토큰이 들고 프로젝트마다 목업 캔버스가 달라진다.
- **Next.js 버전 차이는 문서로 확인한다** — 라우트 묶음 레이아웃이 실서비스에서 막히는 방식처럼 버전마다 다를 수 있는 곳은 `node_modules/next/dist/docs/`로 확인하고, 틀이 그 버전과 안 맞으면 프로젝트에 복사한 파일만 고치고 무엇을 고쳤는지 보고한다. `.claude/templates/` 안의 원본은 고치지 않는다 — 하네스 사본이라 다음 동기화 때 사라진다. 원본을 고칠 문안은 메인이 사용자에게 준다 (`AGENTS.md` 「하네스 수정」).
- **실서비스에서는 늘 막힌다** — 개발용 묶음 레이아웃은 실서비스 빌드에서 404를 내고, 상태 표시 도우미도 같은 조건에서만 켜진다. Vercel 미리보기 배포도 실서비스 빌드라 같이 막힌다. 3단계 첫 배포 때 공개 주소로 한 번 더 확인한다.
- **목업 캔버스는 사람이 보는 도구다** — AI는 브라우저로 열어 보고 판정하지 않는다 (`AGENTS.md` 검증 원칙). 디자인 시스템 페이지가 무엇을 보여 주고 토큰·부품이 바뀔 때 어떻게 따라오는지는 design-system `bootstrap-project.md`의 디자인 시스템 페이지 절이 정한다.
- **4단계에도 남겨 둔다** — 개발 서버에서만 열리니 해가 없고, 백엔드를 붙인 뒤에도 전 화면을 훑는 데 쓴다.

이 문서가 끝나도 사용자에게 화면을 따로 보여 주지 않는다 — 볼 화면이 아직 없다. 2-1이 주요 화면을 만든 뒤 목업 캔버스 주소와 함께 한 번에 보여 준다 (`2-1-mockup.md` §2.6.5). 대화창에는 「개발환경 준비가 끝났습니다」 한 줄과 사용자가 정할 것(있으면)만 알린다.

### 2.7 아티팩트 캔버스로 진행한 프로젝트 — 옮겨 오기

이 절은 **2단계를 아티팩트 캔버스(Artifact 도구의 Design 캔버스 — claude.ai에 게시하는 그림판)로 진행하다가 하네스를 동기화한 프로젝트**만 쓴다. `feature-list.md` 머리에 `캔버스:` 줄이 있고 루트 앱 코드가 아직 없으면 여기다 (SKILL.md §1.2). 앱 코드가 이미 있는 프로젝트(캔버스를 리액트로 다 옮긴 프로젝트)는 이 절을 쓰지 않는다.

남은 일은 새 방식으로 이어 간다. 아티팩트 캔버스는 **한 번만 읽어 옮기는 참고**로 쓰고, 캔버스에 더 그리지 않는다.

| 멈춘 자리 | 이어 가는 길 |
|---|---|
| 2-1 도중(`확정:` 없음) | ① 이 문서 §2.1~§2.6 → ② 아티팩트 캔버스를 한 번 읽어 이미 그린 주요 화면을 리액트로 옮김 → ③ 화면 목록 칸 바꾸기 → ④ `2-1-mockup.md` §2.6.5 보고와 §2.7 목업 캔버스 보며 다듬기부터 |
| 2-2 도중(`확정:` 있음, 브리프 「12」가 `추후 결정` — 비교안이 아티팩트 캔버스에 있음) | ① 사용자가 아티팩트 캔버스에서 판을 고르고(캔버스 링크는 그대로 열린다) 메인이 브리프 「12」·「4」·「7」에 기록 → ② 이 문서 §2.1~§2.6(1층은 고른 판이 바꾼 브리프 「4」 값으로) → ③ 고른 판을 기준으로 주요 화면을 리액트로 옮김 → ④ 「12」를 토큰·연결 정보에 옮겨 전체 화면에 적용(`2-2-mockup-design-upgrade.md`의 전체 화면 적용 절과 같은 일) → ⑤ 화면 목록 칸 바꾸기. 사용자가 원하면 2-2를 리액트 비교안으로 다시 해도 된다 |

**옮기는 절차**:

1. **최신본을 한 번 받는다** — Artifact 도구 `read`로 `feature-list.md` 머리 `캔버스:` 줄의 주소를 읽고, 이어서 `paths`로 옮길 아트보드(`.dc.html`)와 공통 스타일·부품 파일을 묶어 받는다. 받은 파일이 원본이다 — 로컬 `mvp/mockup/` 사본은 사람이 브라우저에서 고친 것보다 낡았을 수 있어 쓰지 않는다.
2. **옮길 것만 고른다** — 화면 목록 「아트보드 이름」 칸과 상태 표 칸 괄호에 적힌 아트보드뿐이다. 규칙표·「고르지 않음 —」·「이전 판 —」 아트보드는 옮기지 않는다(2-2 도중이면 사용자가 고른 판만).
3. **리액트로 옮긴다** — 아트보드는 화면 구조·흐름의 원본이고, 문구는 브리프 「문자 그대로」 표에서 그대로 가져온다(둘이 어긋나면 브리프가 이긴다). 요소마다 `2-1-mockup.md` §2.6.2 「화면 요소 → 부품」 표로 부품을 정한다. 아트보드의 hex·px 값은 화면 코드에 옮기지 않는다 — 색은 1층 램프의 가장 가까운 단계로, 간격·크기는 가장 가까운 theme 단계로 맞추고 단계를 새로 만들지 않는다(「12」가 정한 값은 반올림하지 않고 그대로). 피해야 할 모양(목록 항목마다 카드 등)도 그대로 베끼지 않는다. 아트보드에 든 그림 자산은 `public/`으로 옮긴다. 옮긴 화면은 화면 목록 「주소」 칸을 채우고 `npm run canvas:list`로 목업 캔버스 목록 파일에 올린다.
4. **화면 목록 칸을 바꾼다** — 6절의 「그리는 때」 칸 이름을 「만드는 때」로, 「아트보드 이름」 칸을 「주소」로 바꾸고 옮긴 화면의 주소를 적는다. 7절 칸 끝 괄호의 아트보드 이름은 `?state=` 값으로 바꾼다. 옮기지 않은 화면의 칸은 비워 둔다. 맨 끝에 「흐름 묶음」 칸을 더해 채우고(`2-1-mockup.md` §2.5.2), `npm run canvas:list`로 목업 캔버스 목록 파일을 만든다.
5. **머리 표시를 덧붙인다** — `feature-list.md` 머리 `캔버스:` 줄은 지우지 않고, 줄 끝에 ` (리액트로 옮김 YYYY-MM-DD)`를 덧붙인다. 이 덧붙임이 있어야 SKILL.md §1.2가 이 프로젝트를 새 방식 순서로 판별한다. `README.md`의 `캔버스:` 한 줄과 `.gitignore`의 `mvp/mockup/`은 그대로 둔다.
6. **검사** — 빌드·린트·타입 검사와 §2.6 5번의 `/dev` 막힘 확인.

**아티팩트 캔버스 전용 규칙은 이 절에만 있다** — 이 절은 캔버스를 읽기만 하고 게시하지 않으니 게시 한도·강제 덮어쓰기는 일어나지 않는다. 그래도 지킬 것:

- **Skill 도구로 `/design`을 부르지 않는다** — 사용자만 칠 수 있는 Claude Code 내장 명령이라, AI가 부르면 막히고 에이전트가 Artifact 도구까지 접고 멈춘다. 캔버스는 Artifact 도구로만 읽는다.
- **게시하지 않는다** — 고칠 것이 보여도 캔버스가 아니라 옮긴 코드에서 고친다. 캔버스를 고쳐 다시 게시하지 않는다.
- **캔버스 소유 계정으로 연다** — 아티팩트 캔버스는 게시한 claude.ai 계정으로만 열린다. 프로젝트 `AGENTS.md` 「소유와 계정」 표의 「캔버스(claude.ai 아티팩트) 소유 계정」 행과 지금 계정을 대조하고, 다르면 멈추고 사용자에게 알린다.
- **같은 읽기 실패 2회면 멈추고 보고한다** — 401·403·404는 재시도하지 않는다.

**위임** — 옮기기는 서브 에이전트(opus — 아트보드를 읽어 부품을 정하는 판단이 많다)에 맡긴다. 지시서에 위 절차와 「아티팩트 캔버스 전용 규칙」 네 줄, `2-1-mockup.md` §2.6.3 「화면 작업 지시서에 꼭 넣을 문장」을 넣는다. 받은 캔버스 파일은 옮기는 입력(대상)이라 에이전트가 직접 읽는다. 화면 목록 칸 바꾸기(4번)와 머리 표시(5번)는 메인이 에이전트 보고의 「화면 ID ↔ 주소」 표로 직접 한다.

## 3. 완료 체크리스트

2단계 전체의 완료 체크리스트는 `2-2-mockup-design-upgrade.md` §3이다. 아래는 이 문서 몫이다.

- [ ] **도구 점검표** (§2.1) — 컴퓨터 전체에 까는 도구의 확인 결과를 한 표로 사용자에게 보여 줬다. jq·Node.js가 있다(없거나 맞지 않았으면 AI가 묻지 않고 깔았고, 깐 것을 결과 표로 알렸다). Aside는 있으면 그대로 뒀고, 없을 때만 설치를 시도했다(미루거나 실패해도 멈추지 않았다). Docker Desktop은 「4단계에서 필요합니다」로만 알렸다.
- [ ] **스택 선택 확정** (§2.1) — 사용자에게 React 웹 / Expo를 확인받았고 `mvp/adr.md`에 기록. Expo면 짚을 것 셋을 사용자에게 말했다.
- [ ] **Node.js 주 버전** (§2.2) — Next.js `engines.node`·Vercel 지원 목록·LTS를 모두 만족하는 가장 새 판으로 골랐고, fnm으로 받은 이 프로젝트의 Node(`fnm exec --using=.nvmrc -- node -v`)·`package.json` `engines.node`·`.nvmrc`가 같은 주 버전. 원래 있던 Node·Homebrew는 그대로 뒀고, 셸 설정 파일은 고치지 않았다. 고른 근거가 ADR에 있음.
- [ ] **고정 core 버전 조합 조사·적용** (§2.2) — 정확한 버전이 `package.json`에 고정됐고, `npm install`이 `ERESOLVE` 없이 통과(`--force`·`--legacy-peer-deps` 0건). 조합과 shadcn style·`components.json` 내용이 ADR에 있고, 최신을 못 쓴 패키지마다 「누가 어떤 범위만 받아서」 한 줄. `package-lock.json` 커밋됨. `next.config.ts`의 `cacheComponents`·`partialPrefetching`이 `false`이고 그 이유가 ADR에 있음. Tailwind 연결은 create-next-app 기본값 그대로. Vercel CLI·Supabase CLI가 `devDependencies`에 정확한 버전으로 있고 로그인·키 설정은 안 했음. 루트에 원래 있던 파일을 덮지 않았음.
- [ ] **Supabase 환경변수 자리** (§2.3) — `.env.example`에 이름만, 초기화 코드까지만. Supabase·Vercel 프로젝트 0개(외부 리소스 안 만듦).
- [ ] **Vercel 플러그인** (§2.4) — 깔려 있거나, 사용자에게 설치를 안내했음.
- [ ] **디자인 시스템 첫 세팅** (§2.5) — shadcn 설치, 1층이 브리프 「4」 「우리가 쓰는 값」으로 채워짐(`가정` 항목은 보고에 있음), 2층이 shadcn 이름 세트를 1층으로 다시 이음, 셸이 `feature-list.md` 8절 메뉴 구조와 맞음(8절이 나온 뒤 맞췄음), 클래스 합치기 설정을 했고 받은 부품 파일의 import가 그쪽을 부름, 누르는 부품이 44px 이상, `docs/components.md`에 받은 부품 등록과 끝의 「## 전체 부품 색인」, `AGENTS.md` 연결 정보 절이 있음. 새 variant 0개.
- [ ] **목업 캔버스 뼈대** (§2.6) — `/dev/canvas`·`/dev/design-system`(제목 「[서비스 이름] 디자인 시스템」)이 있고, 목업 캔버스 목록 파일이 있고, 상태 표시 도우미가 저장·조회 코드에 이어졌음. 요소 복사·그림 찍기 개발 의존성과 `canvas:list`·`canvas:shots` 명령·`.gitignore` 줄·루트 레이아웃 스크립트 줄이 있음. 실서비스 빌드에서 `/dev/canvas`와 `/dev/canvas/comments`가 404.
- [ ] **화면 밖 검사 통과** — `lint`·`build`·타입 검사 통과(CI가 같은 검사를 돈다).
- [ ] **옮겨 오기** (§2.7, 해당할 때만) — 옮길 아트보드가 전부 리액트로 옮겨져 목업 캔버스 목록 파일과 「주소」 칸에 있음. 6절 칸 이름이 「만드는 때」·「주소」로 바뀌고 「흐름 묶음」 칸이 더해짐. `캔버스:` 줄 끝에 ` (리액트로 옮김 YYYY-MM-DD)`.

## 4. 사용자 응대 톤

- **톤**: SKILL.md §1.3 따름 — `AGENTS.md` 응답 톤(~입니다 체)·친근·짧게.
- **설치는 묻지 않고 결과로 알린다** — 2단계에서 쓰는 도구는 「깔아도 될까요?」라고 묻지 않는다. 무엇을 어떤 방법으로 깔았는지 결과 표로 알린다(§2.1 「깐 것을 알리는 문안」). 원래 있던 Node를 그대로 뒀으면 왜 그랬는지 한 줄(다른 프로젝트가 그 판을 쓸 수 있다)을 붙인다. 같은 실패가 두 번 났을 때만 무엇이 실패했는지 알리고 도움을 청한다.
- **도구 점검표는 표 하나로 끝낸다** — 확인한 결과와 이어서 할 일만 적는다. 다 있으면 한 줄로 줄인다. Docker Desktop은 「4단계에서 필요합니다」만 말하고 지금 깔지 묻지 않는다 — 깔지는 4단계 준비에서 사용자가 정한다.
- **스택 질문은 짧게 한 번** — 고를 게 하나뿐이다. 「잘 모르겠어요」면 웹으로 간다고 알리고 진행한다. 버전 숫자·패키지 이름 같은 조사 내용은 묻지 않는다 — AI가 조사해 정하고 ADR에 남긴다.
- **기다리게 하지 않는다** — 개발환경 준비는 뒤에서 돌고, 그동안 기능 목록과 화면 목록을 함께 본다고 알린다. "설치가 끝날 때까지 기다려 주세요"라고 하지 않는다.
- **"빨리 화면부터 보고 싶다"** — 화면은 이 바닥 위에 바로 지어져 그대로 진짜 앱이 된다고 짚는다. 그림을 먼저 그리고 나중에 다시 만드는 방식이 아니라서, 바닥을 까는 시간이 뒤에서 다시 만드는 시간을 없앤다.
- **개발 용어는 처음 나올 때 풀이한다** — 셸·토큰·목업 캔버스·개발 서버 같은 말. 「1층」「2층」은 사용자에게 꼭 필요할 때만 쓰고, 쓸 때는 「앱 전체의 색·글꼴 원래 값을 모아 두는 곳」처럼 풀어 쓴다.
- **값이 임시라고 분명히 말한다** — 지금 색·글꼴은 1단계 참고에서 뽑은 출발값이고, 화면을 보고 바꾸거나 2-2에서 다듬는다고 알린다.
- **플러그인 설치는 사용자 몫이라고 말한다** — 명령 한 줄과 어디에 치는지만 알려 준다. AI가 사용자 설정을 대신 바꾸지 않는다.
- **목업 캔버스는 사용자가 보는 것** — "제가 열어서 확인해 봤습니다"라고 하지 않는다. 주소를 주고 본 결과를 기다린다.
