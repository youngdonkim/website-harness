# 하네스 시험하는 법

## 1. 왜 시험하나

하네스 문서는 AI가 읽고 그대로 움직이는 절차입니다. 그래서 문서를 고치면 AI의 행동이 바뀝니다. 그런데 문서만 읽어서는 아래 같은 문제가 보이지 않습니다.

- 문서가 시킨 명령이 이 컴퓨터에서 실제로 안 되는 곳 (도구의 새 판이 기본값을 바꾼 경우 등)
- 앞 단계가 만들어 두지 않은 것을 뒤 단계가 「있다」고 여기는 곳
- 위임받은 에이전트가 알 길이 없는 규칙 (스킬에만 있고 지시서에는 없는 규칙)
- 시간·토큰이 생각보다 많이 드는 곳

그래서 고친 하네스를 빈 프로젝트에 적용해, 사람이 끼는 자리까지 끝까지 한 번 돌려 봅니다. 돌리며 막힌 곳과 문서와 실제가 달랐던 곳을 모으면 그게 다음에 고칠 목록이 됩니다. `docs/eval-scenarios.md`(실사고 색인)는 「고친 문제가 다시 생기지 않나」를 머리로 되짚는 목록이고, 이 문서는 실제로 돌려 보는 방법입니다.

## 2. 시험 폴더 만들기

1. **하네스 저장소 밖에 새 폴더를 만든다** — 하네스 저장소의 시작 스크립트로 만듭니다: `~/dev/website-harness/new-project.sh ~/dev/harness-test-<날짜>`. 하네스 저장소 안이나 이미 쓰는 프로젝트 안에 만들지 않습니다. 이 스크립트가 빈 `.claude/skills/`·`.claude/agents/`·`.claude/hooks/`를 먼저 만들어 두어야, 하네스를 깐 뒤 스킬·에이전트가 같은 세션에서 잡힙니다.
2. **1단계 문서 두 개만 넣고 시작한다** — `mvp/intent.md`와 `mvp/design-brief.md`. 1단계(인터뷰)는 사람의 생각이 재료라 AI끼리 돌리면 시험이 되지 않습니다. 그래서 1단계 결과만 미리 만들어 두고 2단계부터 시험합니다. 1단계 자체를 시험할 때는 사람이 직접 인터뷰에 답합니다.
   - 1단계까지 AI가 답하게 돌렸으면 보고서의 1단계 항목에는 「근거 약함 — AI가 답함」을 붙입니다. 사람의 답 모양은 다를 수 있습니다.
3. **시험 폴더도 `new-project.sh`로 만들고, 그 폴더에서 새 세션을 열어 `/project-init`부터 시킨다** — 하네스 적용 → GitHub 연결 → `/idea-to-mvp` 순서입니다. GitHub 저장소는 비공개로, 시험용 이름(`<아이디어>-harness-test`)으로 만듭니다.
4. **소유는 개인으로 한다** — 시험 저장소가 회사 계정에 생기지 않게, 시험 폴더의 소유를 개인으로 두고 개인 계정 장부(`~/.config/harness/personal.env`)를 씁니다.

**지시서에 다른 프로젝트의 경로를 넣지 않는다.** 시험 세션에 「`~/dev/<다른 프로젝트>`를 참고해라」처럼 다른 프로젝트 경로를 주면, AI가 그 프로젝트의 코드와 결정을 베껴 와 하네스 문서만으로 됐는지 알 수 없게 됩니다. 시험 세션이 읽어도 되는 것은 시험 폴더와 하네스 원본(`project-init`이 복사해 오는 자리)뿐입니다. 시험 보고서를 쓸 폴더 하나만 따로 알려 줍니다.

## 3. 다른 아이디어로 시험한다

**시험할 때마다, 하네스 문서의 예시와 겹치지 않는 아이디어를 쓴다.** 하네스 문서에는 「이런 화면이면 이렇게」 같은 예시가 들어 있습니다. 예시를 만든 서비스로 시험하면 그 예시가 정답지처럼 작동해서, 문서가 일반적인 원칙으로도 통하는지가 아니라 「예시를 베꼈는지」만 보게 됩니다.

- 예: 지난번에 창작물 공유 서비스로 시험했으면, 이번엔 동네 가게 예약·독서 모임 관리처럼 분야가 다른 아이디어로 1단계 문서를 만듭니다.
- 시험하다 「예시가 답안처럼 쓰였다」 싶은 곳이 보이면 보고서의 고칠 목록에 넣습니다 — 그 예시는 특정 서비스 결정이 아니라 일반 원칙으로 고쳐야 합니다.

## 4. 이 컴퓨터를 「처음 상태」로 만들기

하네스는 「도구가 없으면 AI가 깐다」를 시험해야 합니다. 그래서 시험 전에 그 도구를 이 컴퓨터에서 지워 둡니다. 다만 지울 수 없는 것과, 지워도 흔적이 남는 것이 있습니다.

**맥에서 지울 수 없는 도구** — `/usr/bin/git`·`/usr/bin/jq`는 맥 운영체제가 보호하는 파일(시스템 무결성 보호)이라 지울 수 없습니다. 그래서 「git·jq가 아예 없을 때」 갈래는 이 맥에서 시험할 수 없습니다. Homebrew로 깐 판을 지우면 「운영체제 기본 판만 있을 때」까지만 시험됩니다. 보고서에 「시험하지 못한 갈래」로 적습니다.

**Node는 흔적까지 지워야 깨끗하다** — Node를 지웠다고 생각해도 아래가 남으면 하네스가 「받을 것이 없다」며 건너뜁니다.

| 남는 흔적 | 자리 |
|---|---|
| fnm이 받아 둔 Node 판들 | `~/.local/share/fnm/node-versions` |
| fnm 실행 파일 | `~/.local/share/fnm/fnm` 또는 Homebrew의 fnm |
| Node 없이 남은 npm·npx 파일 | `~/.npm-global/bin` 등 — `npm -v`가 있는 것처럼 보이게 만든다 |

**셸 함수가 「있음」으로 보이게 만든다** — 셸 설정 파일(`~/.zshrc`)에 `gh()` 같은 함수가 있으면, 실행 파일이 없어도 `which gh`가 함수를 보여 줍니다. 시험 전에 `whence -p gh`(zsh)로 실행 파일이 정말 없는지 확인합니다.

**지우기 전에 사용자에게 묻는다** — 이 컴퓨터의 다른 프로젝트가 그 도구를 쓸 수 있습니다. 무엇을 지울지는 사람이 정합니다.

## 5. 사람 몫 자리를 AI에게 맡기는 지시

하네스에는 사람이 화면을 보고 정하는 자리가 있습니다(목업 캔버스 보며 다듬기, 디자인 비교안 중 고르기, 배포 전 화면 확인 등). 사람 없이 끝까지 돌려 보려면, 시험 세션을 시작할 때 이 자리를 AI가 정하게 하는 문장을 넣습니다. 이 문장이 없으면 AI는 규칙대로 그 자리에서 멈추고 기다립니다.

시작 지시에 넣을 문장 — 그대로 붙여 넣어 씁니다:

> 이번 작업은 하네스 시험입니다. 하네스 문서가 「사람 몫」이라고 정한 자리(사용자에게 묻는 질문, 화면을 보고 고르는 자리, 「보내도 되겠습니까?」 확인)는 멈추지 말고 네가 정해서 진행해라. 정할 때마다 무엇을 골랐고 왜 골랐는지 한 줄씩 기록해 두었다가 보고서 「사람 몫 자리에서 AI가 고른 것」에 모아라. 단 관리자 암호·로그인·결제·실서비스 배포처럼 사람만 할 수 있는 일은 하지 말고 그 자리에서 멈춰 보고해라. 3단계 배포(Vercel)는 하지 말고, 이 컴퓨터에서 실서비스 방식으로 빌드해 띄우는 데까지 해라. 백그라운드로 띄운 에이전트를 기다릴 때 턴을 끝내지 마라 — 알림이 올 때까지 기다린 뒤 이어라. 단계 끝 `/clear` 권장이 나오면 그 사실만 기록하고 `/clear` 없이 계속해라.

- `/clear`를 하지 않고 돌리면 메인 문맥이 실제 사용보다 크게 쌓입니다 — 보고서의 문맥 크기 해석에 적습니다.
- AI가 고른 값은 시험용입니다. 그 프로젝트를 진짜로 이어 간다면, 사람이 화면을 보고 브리프의 `가정` 행을 다시 정해야 합니다.
- 화면이 잘 나왔는지는 AI가 판정하지 않습니다. 시험 끝에 사람이 6절대로 직접 봅니다.

## 6. 결과 보기

시험이 끝나면 사람이 화면을 직접 봅니다. 개발 서버는 처음 여는 화면마다 새로 만들어 느리니, 실서비스 방식으로 빌드해 띄웁니다. 시험 폴더에서:

```bash
MOCKUP_CANVAS=1 npm run build && MOCKUP_CANVAS=1 npm run start -- -p 3300
```

- `MOCKUP_CANVAS=1`을 붙여야 실서비스 빌드에서도 목업 캔버스가 열리고 `?state=`(빈 상태·오류 같은 상태 화면 보기)가 켜집니다. 시험 폴더에서만 이렇게 쓰고 Vercel에는 넣지 않습니다(`payload/.claude/templates/mockup-canvas/README.md` 「실서비스 빌드로 빠르게 보기」).
- 포트는 3000을 피해 3300처럼 비어 있는 번호를 씁니다 — 3000에는 다른 프로젝트의 개발 서버가 떠 있을 수 있습니다.
- Node 판이 이 컴퓨터의 기본 판과 다르면 명령 앞에 `fnm exec --using=.nvmrc --`를 붙입니다.

볼 주소:

| 주소 | 무엇 |
|---|---|
| `http://localhost:3300` | 앱 |
| `http://localhost:3300/dev/canvas` | 목업 캔버스 — 모든 화면을 데스크톱 폭·폰 폭으로 나란히 |
| `http://localhost:3300/dev/design-system` | 디자인 시스템 페이지 — 토큰과 부품 |

## 7. 시간·토큰 재기

**시작할 때도 잰다.** 끝에만 재면 시험이 얼마나 썼는지 알 수 없습니다. 시험을 시작하기 직전에 아래 넷을 먼저 적어 둡니다.

| 무엇 | 어디서 보나 | 언제 |
|---|---|---|
| 걸린 시간 | 커밋 시각(`git log --reverse --format='%ci %s'`)과 GitHub PR의 생성·머지 시각. 메인 세션이 단계 경계마다 시각을 적어 두면 더 정확하다 | 단계 경계마다 |
| 서브 에이전트 토큰 | 알림에 적힌 토큰 수는 그 에이전트가 끝날 때의 **문맥 크기**다 — 누적 처리량이 아니다. 누적 입력·출력은 대화 기록 폴더의 `subagents/*.jsonl`에서 `usage` 값을 더해 뽑는다. 에이전트마다 단계·모델과 함께 표로 모은다 | 에이전트가 끝날 때마다 |
| 메인 세션 문맥 크기 | Claude Code의 `/context` — 지금 대화에 쌓인 양 | 시작·단계 경계·끝 |
| 요금제 사용량 % | claude.ai 설정의 사용량 화면 — 「5시간 한도」와 「주간」 % 그리고 다음 초기화 시각 | 시작·끝(가능하면 단계 경계마다) |

재며 알아 둘 것:

- 스킬이 fork로 부르는 git 작업(`new-task`·`ship-task`)은 알림에 토큰 수가 나오지 않습니다. 보고서에 「빠진 것」으로 적습니다.
- 같은 에이전트를 이어서 일하게 하면 알림 값(문맥 크기)에 앞 회차의 내용이 이미 들어 있습니다. 그 행에 이어 일한 회차임을 표시해 두고, 회차끼리 더하지 않습니다. 누적량은 위 `usage` 합계로 봅니다.
- `usage` 합계를 뽑는 명령 예(필드 이름이 다르면 그 자리에서 맞춥니다): `jq -s '[.[] | .message.usage? // empty | .input_tokens + (.cache_read_input_tokens // 0) + (.cache_creation_input_tokens // 0)] | add' <subagents/ 아래 jsonl 파일>`
- 메인 세션 문맥 크기는 그 시점에 쌓인 양이지 누적 처리량이 아닙니다.
- 요금제 사용량 %는 계정 전체 값이라, 같은 시간에 돌던 다른 대화도 들어 있습니다. 시험 중에는 다른 무거운 작업을 돌리지 않습니다.
- 지어낸 값은 쓰지 않습니다. 못 잰 값은 「못 잼」으로 적습니다.

## 8. 보고서 목차

시험 보고서는 아래 목차로 씁니다. 보고서는 시험 폴더가 아니라 시험을 시킨 쪽이 알려 준 폴더에 둡니다.

1. **결과 한눈에** — 어디까지 끝났나, 띄워 둔 주소, 화면 수, 검사 결과, 막힌 곳
2. **단계별로 한 일과 걸린 시간** — 단계마다 시작·끝 시각과 한 일
3. **자동으로 깐 도구와 판** — 무엇을 어떤 방법으로 깔았나, 원래 있던 것을 그대로 뒀나
4. **사람 몫 자리에서 AI가 고른 것과 이유**
5. **하네스를 고칠 목록** — ① 막혔거나 엉뚱한 진단을 낸 곳 ② 문서와 실제가 달랐던 곳. 항목마다 「일어난 일」·「고칠 자리(파일·절)」·「고칠 것」
6. **시간·토큰·요금제** — 7절의 표와, 시작·끝 사용량 %
7. **시험하지 못한 갈래와 남은 문제** — 4절의 지울 수 없는 도구, 사람 눈 확인이 아직 없는 자리 등
