## 1. 왜 바꾸나

먼저 지금 방식을 설명하고, 그 방식의 문제, 새 방식 순서로 적습니다.

**지금 방식** — 2단계에서 화면을 Artifact 도구의 Design 캔버스(claude.ai 아티팩트 — 웹에 게시되는 그림판)에 그립니다. 이 문서는 이것을 **아티팩트 캔버스**라고 부릅니다. 3단계에서는 그 캔버스를 읽어 리액트(React — 화면을 만드는 자바스크립트 도구) 코드로 다시 씁니다. 이 「그리기 → 다시 읽기 → 다시 쓰기」에서 비용과 어긋남이 함께 생깁니다.

- **아티팩트 캔버스 파일은 앱에 다시 쓸 수 없습니다.** 캔버스 파일(`.dc.html`)은 px·hex 값을 직접 적는 캔버스 전용 형식입니다. 앱은 디자인 토큰(디자인 값에 이름을 붙여 한곳에 모아 둔 것) 이름만 씁니다. 그래서 3단계가 캔버스를 처음부터 다시 읽어 리액트로 새로 씁니다.
- **다시 쓰기에서 어긋남이 났습니다.** aikung 3단계에서 실제로 겪은 일입니다. 창 폭, 탭 높이, 확인 창 연결, 부품 출처를 잘못 읽은 곳이 나왔습니다. 바로잡는 데 에이전트를 한 번 더 썼습니다.
- **남은 화면을 캔버스에 더하는 비용이 컸습니다.** aikung에서 남은 화면 122장을 캔버스에 더하는 데만 약 37만 토큰이 들었습니다. 그 대부분은 상태 화면(빈 상태·로딩·오류)과 확인 창이었습니다. 이런 화면은 상태 표의 한 줄 문구로 충분히 만들 수 있었습니다.
- **「그림 먼저」는 사람이 코드를 짜기 비싸던 때의 관행입니다.** AI에게는 HTML도 리액트도 똑같이 코드입니다. 그림을 먼저 그릴 이유가 「싸게 틀려 보기」라면, 리액트 화면도 이제 그만큼 쌉니다.
- **캔버스의 장점 중 이 하네스에 필요 없는 것이 있습니다.** 이 하네스의 주 사용자는 1인 개발자입니다. 사용자는 「화면에서 직접 고치기」를 쓰지 않는다고 확인했습니다 — 음성 입력이 안 돼 타이핑이 불편하고, 말로 AI에게 고칠 곳을 알리는 쪽이 낫습니다. 「링크 하나로 공유」도 필요 없다고 확인했습니다.
- **캔버스 전용 규칙이 하네스를 무겁게 합니다.** `payload/` 안에 캔버스를 전제로 한 문장이 337줄입니다(§11 부록). 게시 한도(하루 게시 횟수 제한, 429 오류), 최신본 먼저 읽기, 강제 덮어쓰기 금지, `/design` 호출 금지, 진행 기록 파일, 캔버스 소유 계정 대조가 모두 캔버스 때문에 생긴 규칙입니다.

**새 방식** — 2단계부터 화면을 실제 앱과 같은 고정 스택(Next.js·React·TypeScript·Tailwind·shadcn)으로 바로 만듭니다. 사람은 **목업 캔버스**에서 모든 화면을 한눈에 봅니다. 목업 캔버스는 리액트로 만든 개발용 페이지입니다. 만든 화면들을 한 페이지에 데스크톱 폭·폰 폭으로 나란히 띄워 보는 곳입니다.

**3단계는 새로 짓지 않고 이어서 짓습니다.** 「3단계에서 세 문서를 보고 앱을 리액트로 처음부터 새로 만든다」가 아닙니다.

1. 2단계에서 만든 리액트 코드가 곧 앱의 화면입니다.
2. 3단계는 그 코드에 남은 화면과 상태 화면을 더합니다. 무엇을 더할지는 문서를 보고 정합니다.
3. 이어서 모션(움직임)을 입히고, 배포 전 검사를 돌리고, 배포합니다.

다시 쓰는 일이 없으니 토큰이 줄어듭니다.

**무엇이 정본인지(진실의 원천)도 2단계부터 정해집니다.** 하네스에는 이미 「코드가 정본이 된 뒤 문서에는 코드에 실을 수 없는 것만 남긴다」는 원칙이 있습니다(SKILL.md §2.2). 지금은 이 원칙이 3단계부터 적용되는데, 새 방식에서는 2단계에서 화면을 만든 순간부터 적용됩니다. 문서를 「고정하는 순간」은 따로 두지 않습니다.

| 무엇 | 무엇의 정본인가 | 언제까지 |
|---|---|---|
| ① 리액트 코드(= 목업 캔버스에 보이는 화면) | 화면 생김새·흐름·상태·화면 문구·디자인 값(토큰) | 2단계에서 화면을 만든 순간부터 끝까지 |
| ② 디자인 브리프(`design-brief.md`) | 코드에 실을 수 없는 다섯 가지 — 말투(보이스·톤), 「문자 그대로」 고정 문구, 「11. 이 서비스만의 사실」, 왜 그렇게 정했는지(결정 대장), 모션 방향(말로). 색·글자 크기 같은 값은 코드(1층 토큰)가 정본이고, 브리프의 값 표는 「처음에 무엇으로 정했고 왜」의 기록입니다. 문구 검토 에이전트와 6단계가 브리프를 기준으로 씁니다 | 끝까지 |
| ③ 기능·화면 목록(`feature-list.md`) | 「어떤 화면을 만들어야 하나」 할 일 목록 | 3단계에서 목록의 화면이 코드에 다 있는지 대조를 마칠 때까지. 그 뒤로는 갱신하지 않는 기록입니다 |
| ④ `intent.md` | 1단계 인터뷰 기록. 5·6단계가 참고합니다 | — |

**2단계 동안 화면이 바뀌면** 아래 순서로 고칩니다.

1. 코드를 고칩니다.
2. 그 변경이 「만들어야 할 화면」에 영향을 주면 기능·화면 목록도 고칩니다.
3. 말투·고정 문구·규칙 결정이 바뀌면 브리프를 고칩니다.

| 8 | **2-2 전문가 수준 디자인 개선 — 유지.** ① 점검 항목 고르기(사용자) → ② 「[서비스 이름] 디자인 시스템」 페이지 → ③ 첫 화면 A판·B판을 리액트 두 벌로, 목업 캔버스에 나란히 → ④ 판 고르기(사용자), 브리프 「12. 화면 규칙」에 기록 → ⑤ 전체 화면에 적용은 토큰 값·공통 부품 수정으로(화면을 다시 만들지 않음). 비교안은 앱 본 화면과 섞이지 않게 따로 떼어 둔 비교안 폴더에 둔다. 개선 기준(`visual-polish.md`)은 그대로 쓰되 캔버스 전제 문장은 고친다 | 사용자가 꼭 필요하다고 했다 |
| 9 | 고르지 않은 비교안은 **3단계에서 `화면 대조 끝:` 표시를 적을 때 지운다**(git에는 남는다) | 그 전까지는 「무엇과 비교해 골랐는지」를 목업 캔버스에서 다시 볼 수 있다. 끝까지 남기면 토큰이 바뀔 때마다 깨진 비교안이 쌓인다 |
| 10 | **3단계는 이어서 짓는다** — 2단계 코드에 남은 화면(`만드는 때 = 3단계`)과 상태 표 `O` 칸을 문서(`feature-list.md`·`design-brief.md`·`intent.md`)를 보고 더한다. 캔버스를 거치지 않는다. 여러 에이전트에 묶음으로 나누면 나누기 전에 공통 부품부터 만든다(`3-frontend-build.md` §2.5.3에 이미 있는 문단). 빠진 화면 대조는 「화면 ID마다 주소와 상태 화면이 코드에 있는가」로 한다. 대조를 마치면 `feature-list.md` 머리에 `화면 대조 끝: YYYY-MM-DD`를 적는다 — 문서를 고정한다는 뜻이 아니라 진행 상황 표시일 뿐이다. 그 뒤 사람이 목업 캔버스와 앱을 본다(AI는 화면을 보지 않는다). 이어서 모션 → 배포 전 검사 → 배포(§2.6) → 피드백(§2.7)은 그대로 | 다시 쓰는 단계가 없어진다 |
| 11 | **진실의 원천은 문서마다 정하고, 문서를 고정하는 순간은 두지 않는다** — ① 리액트 코드: 2단계에서 화면을 만든 순간부터 끝까지 화면 생김새·흐름·상태·화면 문구·디자인 값의 정본 ② 디자인 브리프: 코드에 실을 수 없는 다섯 가지(말투, 고정 문구, 「11」, 결정 이유, 모션 방향)의 정본으로 끝까지. 값 표는 처음 정한 값과 이유의 기록 ③ `feature-list.md`: 만들어야 할 화면 목록, 3단계 대조를 마치면 기록 ④ `intent.md`: 1단계 인터뷰 기록(§1) | SKILL.md §2.2에 이미 있는 원칙(「코드가 정본이 된 뒤 문서에는 코드에 실을 수 없는 것만 남긴다」)이 3단계가 아니라 2단계부터 적용된다 |
| 12 | **아티팩트 캔버스는 이 하네스에서 빠진다. 예외도 남기지 않는다** — 여러 안을 나란히 놓고 고르는 일도 목업 캔버스에서 한다. 그래서 캔버스 전용 규칙(게시 한도·최신본 읽기·강제 덮어쓰기 금지·`/design` 금지·캔버스 소유 계정 행)은 새 방식 본문에서 모두 빠지고, 아티팩트 캔버스로 진행한 프로젝트를 위한 호환 절(§7)에만 남는다 | 비교안 하나를 리액트로 더 만드는 비용이 캔버스 한 판과 비슷해, 캔버스가 따로 줄 이점이 거의 없다 |
| 13 | **상태 표시(`?state=`)는 데이터를 저장·조회하는 코드가 개발 서버에서만 읽는다.** 화면 코드는 그대로 둔다 | 화면이 실제 빈 결과·오류 처리 경로를 그대로 타므로, 상태 화면이 진짜로 동작하는지까지 보인다. 막는 자리가 한 곳이다 |
| 14 | 목업 캔버스 페이지 뼈대 코드를 하네스 `payload/.claude/templates/`에 둘 때 **파일 끝 이름은 `.tsx.template`** 로 한다 | `.tsx` 그대로면 프로젝트의 타입 검사가 `.claude/` 안까지 훑어 오류를 낼 수 있다 |
| 15 | **아티팩트 캔버스로 진행한 프로젝트 호환** — 이미 캔버스로 진행한 프로젝트가 동기화 뒤에도 깨지지 않아야 한다. just-do-it(aikung)은 동기화 뒤 `/idea-to-mvp`가 2단계로 되돌아가지 않고 「3단계 마무리 확인 → 4단계」로 가야 한다. 2단계 도중에 캔버스로 진행 중인 프로젝트를 이어 가는 길도 적는다 | §7 |
| 16 | **보류**: 「제품 총괄 에이전트」 신설은 이번 범위가 아니다 | — |

## 4. 2단계 — 목업

### 4.1 개발환경 준비

**들어오는 때** — 1단계가 끝나 `intent.md`와 브리프가 있고, 루트에 앱 코드(`package.json`)가 아직 없을 때입니다. 2단계 시작 안내(2-1 §2.1)와 같은 메시지에서 스택 선택(React 웹 / Expo)을 묻고, 답이 오면 바로 시작합니다.

**하는 일** — 지금 `3-frontend-build.md` §2.4·§2.4.1·§2.4.2·§2.5.1과 §2.5.3 첫 문단이 하는 일을 그대로 가져옵니다. 문서는 새 파일 `2-0-dev-setup.md`입니다(결정 5).

   - ② 1층(기본 값 — 색 단계·글자 크기 같은 원래 값)을 브리프 「4. 확정 브랜드 자산」의 「우리가 쓰는 값」으로 채움. 옮기는 법은 `reference-analysis.md` §5
   - ③ 2층(역할 이름 — `primary`처럼 쓰임새로 붙인 이름)
   - ④ 셸(shell — 모든 화면에 공통으로 씌우는 상단 메뉴·바탕 틀). `feature-list.md` 8절 메뉴 구조가 아직 없으면 브리프 「6. 주 사용 맥락」의 기본 메뉴로 만들고, 화면 목록이 나온 뒤 맞춤
   - ⑤ 부품 목록 문서(`docs/components.md`)
   - ⑥ 연결 정보(adapter — `AGENTS.md`의 「디자인 시스템 연결 정보」 절)
6. 목업 캔버스·디자인 시스템 페이지 틀을 복사해 넣기(§6.6).

**작업 모드** — 1번만 인터뷰 모드입니다. 나머지는 서브 에이전트 하나(opus — 토큰 값 정하기와 부품 모양 판단이 많이 섞임, 결정 6)가 초안 모드로 끝까지 합니다. 메인은 그동안 기능 목록과 화면 목록(2-1 §2.3~§2.5)을 씁니다. 둘은 서로 기다리지 않습니다 — 셸의 메뉴만 화면 목록 8절이 나온 뒤 한 번 맞춥니다.

**값은 대부분 `가정`입니다** — 1층에 들어가는 값은 브리프 「4」의 출발값이고, 상당수가 아직 `가정`입니다. 2-2가 이 값을 바꿉니다. 그래서 개발환경 준비에서는 토큰과 셸, 화면에 꼭 필요한 shadcn 부품만 받습니다. 프로젝트 전용 variant(부품의 모양 종류 — 버튼의 주 버튼·보조 버튼 같은 것)는 2-2 전에는 만들지 않습니다.

**외부 리소스가 생기지 않습니다** — GitHub 저장소는 이미 있고, Vercel·Supabase는 아직 만들지 않습니다. 그래서 이 자리에서는 계정 대조가 필요 없습니다.

### 4.2 2-1 기능·화면 목록과 주요 화면

**그대로 가는 것** — §2.1 단계 시작, §2.2 참고 디자인 확인·이미지 계획, §2.3 기능 목록, §2.4 라이트 기술 확인, §2.5 화면 목록(일곱 종류·홈 결정·상태 표·메뉴 구조·미룬 화면 버튼·빠짐 점검), §2.8 확정. 문장 안의 「캔버스」만 바꿉니다.

**화면 목록의 칸이 바뀝니다** (`feature-list.md` 6절).

| 지금 | 바꾼 뒤 | 채우는 때 |
|---|---|---|
| 그리는 때(2단계 / 3단계 / 해당없음) | **만드는 때**(2단계 / 3단계 / 해당없음). 나누는 기준은 지금 「그리는 때」 규칙 그대로 | 화면 목록을 쓸 때 |
| 아트보드 이름 | **주소** — 그 화면을 여는 실제 주소. 주소에 ID가 들어가는 화면이면 예시 값을 넣은 주소(예: `/challenges/c-01`) | 화면을 만든 뒤 |

상태 표(7절) 칸 끝의 괄호도 아트보드 이름 대신 상태 표시 값을 적습니다 — 예: `O "아직 모임이 없어요" + 만들기 버튼 (?state=empty)`.

머리의 `캔버스:` 표시는 없앱니다. 대신 3단계에서 `화면 대조 끝:` 표시가 붙습니다(§5.2).

**주요 화면 만들기 (지금 §2.6을 다시 씀)**

1. **범위** — `만드는 때 = 2단계` 행만. 지금 「그리는 범위」 규칙 그대로입니다.
2. **폭** — 따로 정하지 않습니다. 코드는 처음부터 반응형이고, 목업 캔버스가 늘 데스크톱 폭과 폰 폭을 나란히 보여 줍니다. 지금 「웹이면 핵심 화면은 폰 판도」 규칙은 「모든 화면이 두 폭에서 보인다」로 저절로 채워집니다. 화면 폭으로 갈리는 자리는 상단 메뉴 ↔ 햄버거 메뉴 전환 하나뿐입니다. 나머지 부품 크기 대응은 컨테이너 쿼리(부품이 놓인 자리의 폭에 맞춰 바뀌는 CSS)로 만듭니다 — 지금 디자인 규칙 검사 3번 규칙을 2단계부터 지킵니다.
3. **데이터** — 화면은 처음부터 데이터를 저장·조회하는 코드(`lib/storage.ts` — 이하 「저장·조회 코드」)를 거쳐 예시 데이터를 읽습니다. 지금 `3-frontend-build.md` §2.5.4의 규칙(저장 구조 한 곳, `Promise` 반환, 저장소 객체를 인자로, 소유자 주석, 가짜 로그인 상태)을 여기로 옮깁니다. 안 그러면 3단계가 화면에 박아 둔 가짜 데이터를 저장·조회 코드로 다시 쓰게 됩니다 — 이번 개편이 없애려는 다시 쓰기입니다.
4. **화면 요소 → 부품 대응** — 지금 §2.5.3 「캔버스 → shadcn 이식 규칙」 표를 「화면 요소 → 부품」 표로 바꿔 여기로 옮깁니다. 버튼은 `Button` + variant, 확인 창은 `AlertDialog`/`Dialog` 같은 대응입니다. 피해야 할 모양(목록 항목마다 카드, 상태색 장식, 14px 아래 글자, 안내 문구가 이름 노릇)을 피하는 규칙도 같이 옮깁니다.
5. **이미지 자리** — 브리프 「이미지·영상 계획」의 장면은 회색 상자에 장면 설명을 적은 자리 표시로 둡니다. 지금 규칙 그대로입니다.
6. **목록 파일에 올리기** — 만든 화면마다 목업 캔버스 목록 파일(§6.4)에 ID·이름·주소·상태를 올리고, 메인이 화면 목록 「주소」 칸을 채웁니다.
7. **위임** — 서브 에이전트(opus — 처음으로 화면의 생김새를 정하는 일이라 디자인 판단이 많음)에 맡깁니다. 화면이 많으면 공통 부품을 먼저 만든 뒤 묶음으로 나눕니다(지금 3단계 §2.5.3 문단과 같은 원칙). 입력 파일 셋(`intent.md`·`feature-list.md`·`design-brief.md`)은 에이전트가 전문으로 읽습니다. 홈 첫 화면 제약과 브리프 읽는 법 다섯 문장은 메인이 지시서에 넣습니다 — 지금 §2.6.3 규칙 그대로입니다.

**화면 작업 지시서에 꼭 넣을 문장** — 지금 「캔버스 작업 지시서에 꼭 넣을 문장」(게시·최신본·429·`/design`)을 아래로 바꿉니다. 2-1·2-2·3단계의 화면 위임 지시서에 모두 넣습니다.

- 「화면 코드는 2층 이름 클래스와 theme 단계 클래스만 쓴다 — hex·px·대괄호 임의 값 금지.」
- 「만든 화면은 목업 캔버스 목록 파일에 올리고, 상태 표의 `O` 칸은 `?state=` 값으로 띄울 수 있게 한다.」
- 「브라우저 자동화로 화면을 열어 보고 '확인 완료'라고 결론 내지 마라 — 빌드·린트·타입 검사까지만 하고 결과를 보고하라.」
- 「개발 서버가 필요하면 이미 떠 있는 서버를 쓰고, 네가 띄운 프로세스만 끈다.」
- 「재위임 금지: 다른 에이전트를 띄우지 말고, 필요해 보이면 멈추고 보고하라.」
- 2-1 몫 한 문장: 「화면 목록에서 `만드는 때 = 2단계`인 화면만 만들어라. 이미 있는 화면은 다시 만들지 말고 고칠 곳만 고쳐라.」

**보고와 사람이 보는 자리 (지금 §2.6.5·§2.7을 다시 씀)**

- 메인은 에이전트 보고의 「화면 ID ↔ 주소」 표로 「주소」 칸을 채우고, `만드는 때 = 2단계` 행이 다 찼는지 대조합니다.
- 화면 밖 검사(빌드·린트·타입)를 돌리고 결과와 함께 **개발 서버의 목업 캔버스 주소**를 알립니다. 보고할 내용(화면 수·새로 넣은 화면·빠짐 점검·목록 전문·「보며 특히 확인할 것」)은 지금 §2.6.5 그대로입니다.
- 사용자는 목업 캔버스를 보며 **말로** 고칠 곳을 알립니다. 지금 「캔버스 댓글 처리 차례」(최신본 읽기 → 고치기 → 게시 → 스레드 답 → 해결 표시)는 없앱니다.
- 나온 것은 §1 「2단계 동안 화면이 바뀌면」 순서로 고칩니다 — ① 코드 ② 만들어야 할 화면에 영향이 있으면 `feature-list.md` ③ 말투·고정 문구·규칙 결정이 바뀌면 브리프. 지금 나누는 표의 「플로우·의도 → `intent.md`」 행은 `intent.md`가 1단계 인터뷰 기록이 되므로 남길지 문안 쓸 때 정합니다(확인 필요).
- 「고치는 손」 — 문구 한 줄·색 하나 같은 작은 손질은 메인이 직접, 여러 화면은 위임합니다. 「통째로 다시 그리기」 규칙과 「사람이 캔버스에서 직접 고친 것을 물어보기」는 없앱니다 — 코드는 고치는 것이 기본이고, 사람이 코드를 직접 고쳤어도 git이 남깁니다.

- 2-2 몫 한 문장(②③): 「비교안 폴더에만 만들어라. 1·2층 토큰 파일과 본 부품, 본 화면은 고치지 마라 — 비교안은 범위 클래스와 비교안 전용 부품으로만 바꾼다. 보고에 건드린 본 파일 수(0이어야 한다)를 적어라.」
- 2-2 몫 한 문장(⑤): 「고른 판의 비교안 값을 1·2층 토큰과 본 부품에 넣고 고른 판 화면을 본 화면 자리로 옮겨라. 다른 화면은 어긋난 곳만 고치고 다시 만들지 마라. 보고에 바꾼 토큰·부품 목록, 손질한 화면 목록, 구조를 바꿔야 해서 손대지 않은 화면 목록을 담아라.」

**지시 파일 자리** — 지금 지시 파일(`design-prompt.md`·`polish-prompt.md`·`add-screens-prompt.md`)은 git에서 빠진 `mvp/mockup/`에 있습니다. 바꾼 뒤에는 지시 파일을 따로 두지 않고 지시서 본문으로 넘깁니다. 지시서를 파일로 남길 필요가 있으면 `mvp/prompts/`에 두고 커밋(commit — git에 변경을 기록하는 일)합니다(확인 필요 — 남길 값어치가 있는지는 검토 때 판단).

## 5. 3단계 — 프런트엔드

### 5.1 남은 화면 만들기

지금 §2.2(남은 화면 그리기)와 §2.5(리액트로 옮기기)를 「남은 화면 만들기」 한 절로 합칩니다. 2단계 코드에 이어서 더하는 일이고, 새로 짓는 일이 아닙니다.

- **입력** — `feature-list.md` 6~10절(무엇을 만들지), `design-brief.md`(문구·미감·「12」), `intent.md`(순서·원하는 것), 그리고 **이미 있는 코드**(2단계 화면과 공통 부품이 생김새의 본보기). 「2단계 캔버스」 입력은 없어집니다.
- **범위** — `만드는 때 = 3단계` 화면과, 상태 표 `O` 칸 중 아직 `?state=`로 뜨지 않는 상태 화면. 상태 화면은 상태 표의 `O` 옆 한 줄 문구를 그대로 지시로 씁니다.
- **공통 부품부터** — 지금 §2.5.3의 「나누기 전에 공통 부품부터」 문단을 3단계 첫 순서로 올립니다. 2-2가 만든 빈 상태·로딩 비교안이 상태 화면의 본보기입니다.
- **지시서** — §4.2 「화면 작업 지시서에 꼭 넣을 문장」 + 3단계 몫 한 문장: 「화면 목록의 `만드는 때 = 3단계` 행과 상태 표의 `O` 칸 중 아직 없는 것만 만들어라. 이미 있는 화면은 고치지 마라. 공통 부품은 `components/common/`의 것을 쓰고, 공통으로 쓸 만한 부품을 새로 만들지 말고 보고하라.」 지금 「캔버스 요소 → 부품 표를 보고에 남겨라」는 「화면 요소 → 부품 표」로 남깁니다 — 메인이 바뀐 코드를 검수할 때 같은 요소가 화면마다 다른 부품으로 만들어졌는지 이 표로 잡습니다.
- **빠진 화면 대조 (지금 §2.2.4를 다시 씀)** — 메인이 화면 ID마다 확인합니다.
  - ① `MVP 포함 = O`인 모든 화면이 「주소」를 가졌고 목업 캔버스 목록 파일에 있는가
  - ② 상태 표 `O` 칸이 모두 `?state=` 값을 가졌는가
  - ③ 반대편 역할 화면이 있는가
  - ④ 죽은 버튼(9절)이 없는가
  - ⑤ 홈 첫 화면이 홈 행 기록과 맞는가
  - 목록 파일과 화면 목록의 ID를 기계로 맞대 보는 명령을 하나 둡니다(예: 화면 목록 6절의 ID 목록과 목록 파일의 ID 목록을 비교해 차이를 출력 — 명령 모양은 문안 쓸 때 정함).
- **없어지는 것** — 폭 정하기(§2.2.1), 캔버스 새로 그리기(§2.2.5), 아트보드에서 읽는 것(§2.5.2), 캔버스 값 → 토큰 반올림(§2.5.3 끝 문단), 캔버스 링크를 README에 적기(§2.3 3번), 「캔버스는 여기서 역할이 끝난다」(§2.5.6).

### 5.2 화면 대조 끝 표시와 사람 확인

**시점** — 3단계에서 남은 화면과 상태 화면을 다 만들고 빠진 화면 대조(§5.1)를 마친 직후, 모션 전입니다.

**하는 일**

1. 메인이 `feature-list.md` 머리에 `화면 대조 끝: YYYY-MM-DD`를 적습니다.
2. 고르지 않은 비교안을 비교안 폴더에서 지웁니다(결정 9). git에는 남습니다.
3. 사람이 목업 캔버스와 앱을 봅니다. 모든 화면과 상태가 목업 캔버스에 처음 다 모이는 순간이라, 전체를 한 번에 볼 자리입니다. 고칠 곳이 나오면 고치고 모션으로 넘어갑니다.

**이 표시는 진행 상황 표시일 뿐입니다** — 문서를 고정한다는 뜻이 아닙니다. 문서마다 정본으로 남는 범위는 §1 표대로입니다. 다만 `feature-list.md`는 이 대조로 할 일 목록의 역할을 마쳤으므로, 그 뒤로는 갱신하지 않는 기록이 됩니다. 브리프와 코드는 그 뒤로도 계속 정본입니다.

**지금 몇 단계인지 알아내는 단서가 됩니다** — 이 표시가 3단계 앞부분이 끝났다는 단서입니다(§7.1). 지금은 「루트에 앱 코드가 있다」가 그 단서였는데, 앱 코드가 2단계부터 생기므로 쓸 수 없습니다.

**AI는 화면을 보지 않습니다** — 목업 캔버스는 사람이 보는 도구입니다. AI는 빌드·린트·타입 결과와 대조 결과를 보고하는 데까지입니다.

**SKILL.md의 「화면 SoT의 진화」를 다시 씁니다** — SoT(Source of Truth, 진실의 원천 — 그 내용의 정본이 어디 있나)를 지금 SKILL.md §2.2는 「화면 목록 → 캔버스 → 앱 코드」 세 자리로 옮겨 가는 것으로 적습니다. 바꾼 뒤에는 §1 표의 네 자리 — 2단계부터 코드가 화면의 정본, 브리프는 코드에 실을 수 없는 다섯 가지의 정본, 화면 목록은 3단계 대조까지의 할 일 목록, `intent.md`는 인터뷰 기록 — 로 적습니다. 「코드가 정본이 된 뒤 문서에는 코드에 실을 수 없는 것만 남긴다」는 원칙이 적용되는 때를 「3단계부터」에서 「2단계에서 화면을 만든 순간부터」로 바꿉니다.

### 5.3 그대로 가는 것

§2.5.7 모션, §2.5.8 배포 전 검사, §2.6 배포, §2.7 피드백, §3 완료 체크리스트의 뒷부분, §4 산출물(앱 코드 + 배포 주소)은 그대로입니다. 바뀌는 문장은 아래뿐입니다.

- §2.5.7 「캔버스는 정지 화면이라 움직임은 앞 단계 어디서도 다뤄지지 않았다」 → 「2단계 화면은 움직임 없이 만들었다」.
- §2.5.8 디자인 규칙 검사 — 검사 경로에 비교안 폴더와 목업 캔버스가 들어가는지 정합니다(§9 위험 표). 숫자 폭(1440·390)은 `px` 문자열 없이 숫자 속성으로 써서 1번 검사에 걸리지 않게 합니다.
- §2.6 첫 배포 체크리스트에 한 항목을 더합니다: 「공개 주소의 `/dev/screens`가 404인지 `curl`로 확인」.
- §2.7의 「캔버스를 다시 만들지 않는다」 문단은 없앱니다.

## 6. 목업 캔버스와 디자인 시스템 페이지

### 6.1 목업 캔버스

- **주소** — `/dev/screens`(제안). 개발 서버에서만 열립니다(§6.5).
- **맨 앞** — 「[서비스 이름] 디자인 시스템」 페이지로 가는 칸(§6.2).
- **화면 배치** — 화면 ID 순서(흐름 순서)로 위에서 아래로 한 화면씩 놓습니다. 화면마다 데스크톱 폭 창과 폰 폭(390) 창을 가로로 나란히 둡니다. 데스크톱 창은 실제 폭(1440 — 지금 2-1의 데스크톱 폭)으로 띄우고 화면에 맞게 줄여 보여 줍니다. 그래야 창 안의 컨테이너 쿼리가 실제 폭 기준으로 돕니다.
- **상태 화면** — 같은 화면 아래에 상태(빈·로딩·오류·권한없음) 창을 이어 붙입니다. 주소는 `/challenges?state=empty`처럼 목록 파일의 상태 목록에서 만듭니다.
- **흐름 묶음** — 지금 캔버스의 「줄 제목 메모」(예: 「소비자 — 찾아보기에서 참가 신청까지」)를 묶음 제목으로 둡니다. 맨 위에 묶음으로 바로 가는 목차를 둡니다.
- **비교안 묶음** — 2-2 동안은 대상 화면 자리에 원래 화면 · A판 · B판을 나란히 둡니다(§6.3).
- **보이는 창만 불러오기** — 창(iframe)에 `loading="lazy"`를 걸어 화면에 들어온 창만 불러옵니다. 개발 서버는 주소를 처음 열 때 그 화면을 컴파일(코드를 브라우저가 읽는 꼴로 바꾸는 일)하므로, 처음 내려 볼 때는 느릴 수 있다고 사용자에게 한 번 알립니다.
- **아티팩트 캔버스와 다른 점** — 끌어서 확대·이동하는 그림판이 아니라 위아래로 내려 보는 페이지입니다. 화면에서 직접 고치는 기능은 없습니다.

### 6.2 디자인 시스템 페이지

- **주소와 이름** — `/dev/design-system`(제안). 페이지 제목은 「[서비스 이름] 디자인 시스템」(예: 「aikung 디자인 시스템」). 「규칙 페이지」라고 부르지 않습니다.
- **보여 주는 것** — 실제 토큰과 실제 부품으로 그립니다.
  - 글자 단계 — 우리 글자 이름(`text-h1`~`text-b2`)마다 견본 문장, 크기·굵기·줄 간격, 쓰는 자리.
  - 색 역할 — 2층 이름(`primary`·`highlight`·`emphasis` 등)마다 견본과 쓰는 자리. 값은 코드에 적지 않고 브라우저가 계산한 값을 읽어 보여 줍니다(디자인 규칙 검사의 hex 검사에 안 걸리게).
  - 간격 단계, 둥글기, 격자.
  - 부품 다섯 상태 — 버튼(variant별)·칩·입력칸·탭. 평소와 비활성은 그대로 그립니다. 마우스 올림·누름은 사람이 직접 올리고 눌러 보는 칸으로 둡니다. 포커스를 고정해 보여 주는 방법은 확인 필요입니다(브라우저가 포커스 표시를 강제로 그리게 하려면 부품에 개발용 속성을 더해야 할 수 있음 — §9).
  - 폰 배치 규칙 메모 — 어느 폭에서 무엇이 접히는지.
- **2-2 동안** — 「지금 값」 칸과 「비교안 값」 칸을 나란히 둡니다. 비교안 값은 범위 클래스(§6.3) 안에서 그려, 같은 부품이 비교안 값으로 어떻게 보이는지 보여 줍니다. 고른 뒤에는 「지금 값」 하나로 돌아갑니다.
- **정본이 아닙니다** — 이 페이지는 토큰의 정본(1·2층 CSS)을 비춰 보여 주는 거울입니다. 결정의 정본은 브리프 「12」, 값의 정본은 1층입니다.

### 6.3 비교안 폴더

- **자리** — `src/app/(dev)/dev/drafts/` 아래(제안). `(dev)`는 Next.js 라우트 묶음(route group — 주소에는 안 나타나고 폴더만 묶는 이름)입니다. 비교안 화면은 `/dev/drafts/home-a`·`/dev/drafts/home-b` 같은 주소가 됩니다.
- **비교안 전용 부품** — 비교안 폴더 안에 둡니다. 본 코드(`src/app` 본 화면·`src/components`)가 비교안 폴더를 불러오는 일은 금지하고, grep(파일 안의 글자를 찾는 명령)으로 0건을 확인합니다.
- **비교안 안에서만 디자인 값을 바꿔 보는 장치(범위 클래스)** — B판의 한 줄 높이처럼 비교안이 토큰 값을 바꿔 봐야 할 때 씁니다. 비교안을 감싼 CSS 클래스 안에서만 2층 변수를 덮어씁니다. 1·2층 파일은 그대로 둡니다. design-system 스킬에는 2층 파일 안에 이런 범위 클래스를 두는 앞선 예가 있습니다(`naming-taxonomy.md` 114줄 근처). 범위 클래스를 비교안 폴더에 둘지 2층 파일에 둘지는 문안 쓸 때 스킬 규칙과 맞춰 정합니다(확인 필요).
- **고른 뒤** — 고른 판의 코드는 본 화면 자리로 옮기고, 비교안 값은 1·2층으로 옮깁니다. 고르지 않은 판은 3단계 `화면 대조 끝:` 때 지웁니다(결정 9).

### 6.4 목업 캔버스 목록 파일과 상태 띄우기

- **목업 캔버스 목록 파일** — 목업 캔버스에 띄울 화면을 적어 둔 코드 파일 하나입니다(예: `src/app/(dev)/dev/screens/registry.ts`). 기획 문서 `feature-list.md`의 「화면 목록」과는 다른 것입니다 — 화면 목록은 「어떤 화면이 있어야 하나」를 적은 문서이고, 목록 파일은 「목업 캔버스가 어떤 주소를 띄울까」를 적은 코드입니다. 화면마다 ID · 이름 · 흐름 묶음 · 주소 · 띄울 상태 목록을 적습니다. 화면을 만드는 에이전트가 화면을 만들 때 함께 올립니다.
- **왜 `feature-list.md`를 직접 읽지 않나** — 화면 목록은 3단계 대조를 마치면 갱신하지 않는 기록이 되는데, 목업 캔버스는 그 뒤로도 코드를 따라가야 합니다. 그래서 목업 캔버스는 코드 쪽 목록 파일을 읽고, 대조를 마치기 전에는 메인이 목록 파일과 화면 목록 「주소」 칸을 맞춰 둡니다.
- **상태 띄우기** — 주소 끝에 `?state=empty|loading|error|forbidden` 표시를 붙이면 그 상태가 뜹니다. 이 표시는 **저장·조회 코드가 개발 서버에서만 읽습니다**(결정 13). 화면 코드는 고치지 않습니다. 저장·조회 코드가 빈 결과·오류·느린 응답을 돌려주면, 화면이 실제 처리 경로대로 상태 화면을 그립니다. 권한없음은 가짜 로그인 상태를 바꿔서 냅니다. 4단계에서 저장·조회 코드를 Supabase로 바꿀 때 이 처리도 함께 옮깁니다.
- **창끼리 섞이지 않게** — 모든 창이 같은 출처(origin — 주소의 앞부분, 예: `http://localhost:3000`)라 브라우저 저장소(로컬스토리지)를 같이 씁니다. 상태 표시는 저장소에 쓰지 않고 주소로만 정해, 한 창이 다른 창의 상태를 바꾸지 않게 합니다.

### 6.5 실서비스에서 막기

- `src/app/(dev)/layout.tsx`가 실서비스 빌드(`NODE_ENV=production`)에서 `notFound()`를 부릅니다(제안 — 쓰는 Next.js 버전의 `node_modules/next/dist/docs/`로 레이아웃에서 `notFound()`가 이렇게 동작하는지 확인 필요). Vercel 미리보기 배포도 실서비스 빌드라 같이 막힙니다.
- `?state=`를 읽는 저장·조회 코드도 같은 조건에서만 켭니다.
- 3단계 §2.6 첫 배포 체크리스트에서 `curl -s -o /dev/null -w "%{http_code}" https://<프로젝트이름>.vercel.app/dev/screens`가 404인지 봅니다.
- 4단계 SEO(검색 노출) 작업의 sitemap(검색 엔진에 알리는 주소 목록)에 `/dev`가 들어가지 않는지도 같은 자리에서 봅니다.
- 목업 캔버스는 4단계에도 남겨 둡니다 — 개발 서버에서만 열리니 해가 없고, 백엔드를 붙인 뒤에도 전 화면을 훑는 데 쓸 수 있습니다.

### 6.6 틀을 어디에 두나

**제안** — 코드 틀은 `payload/.claude/templates/screen-board/`에, 쓰는 절차는 문서 두 곳에 둡니다. 틀 코드 파일의 끝 이름은 `.tsx.template`입니다(결정 14).

| 무엇 | 자리 | 이유 |
|---|---|---|
| 목업 캔버스 페이지·디자인 시스템 페이지 뼈대·목록 파일 형식·`(dev)` 레이아웃 | `payload/.claude/templates/screen-board/` | `project-init`이 `templates`를 프로젝트 `.claude/templates/`로 동기화한다(`project-init` SKILL.md 동기화 절). 개발환경 준비 에이전트가 이 폴더를 `src/app/(dev)/`로 복사하면서 끝 이름의 `.template`을 떼고 이름만 채운다 — 매번 새로 짓는 토큰이 거의 없다 |
| 디자인 시스템 페이지가 무엇을 보여 주나·언제 고치나 | design-system `bootstrap-project.md`의 새 절(예: §6) | 디자인 시스템 페이지는 idea-to-mvp 밖에서도 쓸모 있는 design-system 스킬의 일이다 |
| 목업 캔버스를 언제 쓰고 누가 보나 | `2-0-dev-setup.md`와 2-1 | idea-to-mvp 흐름의 일이다 |

검토한 다른 방법과 득실입니다.

- design-system `references/`에 코드 블록으로만 싣기 — 동기화할 코드 파일이 없어 단순합니다. 하지만 프로젝트마다 에이전트가 코드를 새로 쓰므로 토큰이 들고, 프로젝트마다 목업 캔버스가 조금씩 달라집니다.
- `payload/` 밖 별도 저장소나 npm 패키지 — 하네스 동기화 체계 밖이라 버전이 따로 놉니다. 이번 범위에 맞지 않습니다.

## 7. 아티팩트 캔버스로 진행한 프로젝트

### 7.1 지금 몇 단계인지 알아내는 순서

`/idea-to-mvp`는 부를 때마다 산출물을 보고 지금 몇 단계인지 알아냅니다(SKILL.md §1.2). 지금 규칙은 「루트에 앱 코드가 있으면 3단계 리액트 옮기기가 끝났다」를 단서로 씁니다. 새 방식에서는 앱 코드가 2단계 개발환경 준비에서 생깁니다. 이 단서가 그대로면 **새 방식 프로젝트가 개발환경 준비 직후 3단계 이후로 잘못 읽힙니다.** 그래서 순서를 아래로 바꾸고, 옛 단서는 `캔버스:` 표시가 있는 프로젝트에만 씁니다.

**0. 아티팩트 캔버스로 진행한 프로젝트부터 가려낸다** — `feature-list.md` 머리에 `캔버스:` 표시가 있으면 아티팩트 캔버스로 진행한 프로젝트입니다. 아래 표로 단계를 정하고 1~7은 보지 않습니다.

| `캔버스:` 표시가 있을 때 | 지금 단계 |
|---|---|
| 루트 앱 코드 있음 | 캔버스 확인과 리액트 옮기기까지 끝남. `backend-build.md`가 없으면 「3단계가 끝났는지 사용자에게 확인 → 4단계」(지금 §1.2 마지막 항목 그대로) |
| 앱 코드 없음, `확정:` 없음 | 2-1 도중 → §7.3 |
| 앱 코드 없음, `확정:` 있음, 「12」가 `추후 결정` | 2-2 도중 → §7.3 |
| 앱 코드 없음, 「12」 채워짐 또는 `건너뜀` | 3단계 앞부분(캔버스에 남은 화면을 그리던 중) → §7.3 |

**새 방식** (`캔버스:` 표시가 없을 때)

1. `intent.md` + `design-brief.md`가 없으면 → 1단계.
2. 루트 앱 코드(`package.json`)가 없으면 → 2단계 개발환경 준비.
3. `feature-list.md`가 없거나 `확정:`이 없으면 → 2-1(기능 목록은 있는데 6~10절이 없으면 화면 목록부터).
4. 브리프 「12」가 `추후 결정`이면 → 2-2.
5. `feature-list.md` 머리에 `화면 대조 끝:`이 없으면 → 3단계 앞부분(남은 화면 만들기·대조·사람 확인).
6. `화면 대조 끝:`이 있고 `backend-build.md`가 없으면 → 3단계 뒷부분(모션·배포 전 검사·배포·피드백). 배포가 됐으면 「더 고칠 곳이 없으면 다음으로」를 묻고 4단계로. 배포했는지 알아낼 단서는 지금 규칙에 따로 없습니다 — `.vercel/project.json` 유무를 쓸지, 사용자에게 묻기만 할지는 문안 쓸 때 정합니다(확인 필요).
7. `backend-build.md` → 4단계 이후, `market-research.md` → 5, `launch-*` → 6 — 지금 그대로.

**지워야 하는 지금 규칙** — 「뒤 단계 산출물이 있으면 앞 단계는 지난 것으로 본다 — 예: 앱 코드가 있는데 브리프 「12」가 비어 있으면 2-2로 되돌리지 않고 3단계 이후로」. 이 예는 새 방식에서 정확히 틀린 답을 냅니다. 그래서 0번 표 안으로만 옮깁니다. 「앱 코드는 4단계 구분자가 못 된다」는 「3단계 구분자도 못 된다」로 넓힙니다.

| 단서 | 상태 |

### 7.3 2단계 도중에 아티팩트 캔버스로 진행 중인 프로젝트

동기화하면 캔버스 절차 문서가 없어지므로, 남은 일은 새 방식으로 이어 갑니다. 아티팩트 캔버스는 **한 번만 읽어 옮기는 참고**로 씁니다.

| 멈춘 자리 | 이어 가는 길 |
|---|---|
| 2-1 도중 | ① 2단계 개발환경 준비 → ② 아티팩트 캔버스를 한 번 읽어 이미 그린 주요 화면을 리액트로 옮김 → ③ 화면 목록의 「그리는 때」·「아트보드 이름」 칸을 「만드는 때」·「주소」로 바꿈 → ④ 새 2-1의 목업 캔버스 보며 다듬기부터 |
| 2-2 도중(비교안이 아티팩트 캔버스에 있음) | ① 사용자가 아티팩트 캔버스에서 판을 고르고(캔버스 링크는 그대로 열림) 「12」에 기록 → ② 개발환경 준비 → ③ 고른 판을 기준으로 주요 화면을 리액트로 옮김 → ④ 2-2 ⑤ 전체 화면에 적용은 토큰·공통 부품으로. 사용자가 원하면 2-2를 리액트로 다시 해도 됩니다 |
| 3단계 앞부분(남은 화면을 아티팩트 캔버스에 그리던 중) | ① 개발환경 준비 → ② 「아트보드 이름」 칸에 적힌 아트보드만 리액트로 옮김 → ③ 나머지는 새 3단계대로 문서를 보고 만듭니다. 캔버스에 남은 화면을 더 그리지 않습니다 |

- **옮기는 절차** — 지금 `3-frontend-build.md` §2.5.2(클라우드 최신본을 `paths`로 묶어 받기, 「아트보드 이름」 열에 적힌 것만)를 줄여 `2-0-dev-setup.md` 끝에 「아티팩트 캔버스에서 옮겨 오기」 한 절로 남깁니다. 하네스 문서에 옛 절차를 남기지 않는 원칙과 부딪히는 자리라, 호환 절로만 두고 본문 흐름에는 섞지 않습니다.
- **캔버스 전용 규칙은 이 절에만** — 게시 한도·최신본 읽기·강제 덮어쓰기 금지·`/design` 금지는 이 호환 절에만 남깁니다(결정 12).
- **캔버스 소유 계정 행** — 아티팩트 캔버스는 게시한 claude.ai 계정으로만 열립니다. 그래서 이런 프로젝트의 `AGENTS.md`에는 「캔버스 소유 계정」 행을 남겨 둡니다.
- **`캔버스:` 표시** — 옮긴 뒤에도 `feature-list.md` 머리의 `캔버스:` 표시는 **지우지 않습니다** — 0번 단서이고 옛 흔적입니다. 그런데 0번 표의 「앱 코드 있음 = 리액트 옮기기 끝」 행이 이런 프로젝트를 3단계 뒷부분으로 보내 버립니다. 그래서 옮겨 온 프로젝트는 옮기는 순간 `캔버스:` 옆에 `(리액트로 옮김 YYYY-MM-DD — 이후 새 방식)`을 붙이고, 0번은 이 덧붙임이 있으면 새 방식 순서로 넘깁니다(표시 모양은 문안 쓸 때 확정).
