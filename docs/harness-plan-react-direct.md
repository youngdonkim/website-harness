## 1. 왜 바꾸나

지금 하네스는 2단계에서 화면을 Artifact 도구의 Design 캔버스(claude.ai 아티팩트 — 웹에 게시되는 그림판)에 그리고, 3단계에서 그 캔버스를 읽어 리액트 코드로 다시 씁니다. 이 「그리기 → 다시 읽기 → 다시 쓰기」에서 비용과 어긋남이 함께 생깁니다.

- **캔버스 파일은 앱에 다시 쓸 수 없습니다.** 캔버스 파일(`.dc.html`)은 px·hex 값을 직접 적는 캔버스 전용 형식입니다. 앱은 디자인 토큰(디자인 값에 이름을 붙여 한곳에 모아 둔 것) 이름만 씁니다. 그래서 3단계가 캔버스를 처음부터 다시 읽어 리액트로 새로 씁니다.
- **다시 쓰기에서 어긋남이 났습니다.** aikung 3단계 실측입니다. 창 폭, 탭 높이, 확인 창 연결, 부품 출처를 잘못 읽은 곳이 나왔습니다. 바로잡는 데 에이전트를 한 번 더 썼습니다.
- **남은 화면을 캔버스에 더하는 비용이 컸습니다.** aikung에서 남은 화면 122장을 캔버스에 더하는 데만 약 37만 토큰이 들었습니다. 그 대부분은 상태 화면(빈 상태·로딩·오류)과 확인 창이었습니다. 이런 화면은 상태 표의 한 줄 문구로 충분히 만들 수 있었습니다.
- **「시안 먼저」는 사람이 코드를 짜기 비싸던 때의 관행입니다.** AI에게는 HTML도 리액트도 똑같이 코드입니다. 그림을 먼저 그릴 이유가 「싸게 틀려 보기」라면, 리액트 화면도 이제 그만큼 쌉니다.
- **캔버스의 장점 중 이 하네스에 필요 없는 것이 있습니다.** 이 하네스의 주 사용자는 1인 개발자입니다. 사용자는 「화면에서 직접 고치기」를 쓰지 않는다고 확인했습니다 — 음성 입력이 안 돼 타이핑이 불편하고, 말로 AI에게 고칠 곳을 알리는 쪽이 낫습니다. 「링크 하나로 공유」도 필요 없다고 확인했습니다.
- **캔버스 전용 규칙이 하네스를 무겁게 합니다.** `payload/` 안에 캔버스 전제가 담긴 줄이 337줄입니다(§12 부록). 게시 한도(하루 게시 횟수 제한, 429 오류), 최신본 먼저 읽기, 강제 덮어쓰기 금지, `/design` 호출 금지, 진행 기록 파일, 캔버스 소유 계정 대조가 모두 캔버스 때문에 생긴 규칙입니다.

그래서 2단계부터 화면을 실제 앱과 같은 고정 스택(Next.js·React·TypeScript·Tailwind·shadcn)으로 바로 만듭니다. 사람은 개발용 페이지 하나(화면 모음 판)에서 모든 화면을 한눈에 봅니다.

## 3. 새 단계 구성

### 3.1 단계 표

| 단계 | 하위 문서 | 하는 일 | 지금과 달라지는 것 |
|---|---|---|---|
| 1 인터뷰 | `1-intent.md` | 그대로 | 「2단계 캔버스에서 확인한다」 같은 문장만 화면 모음 판으로 |
| 2 목업 | `2-0-dev-setup.md`(새 문서 — 자리는 §9 질문 4) → `2-1-mockup.md` → `2-2-mockup-design-upgrade.md` | 개발환경·디자인 시스템 기초 공사 → 기능·화면 목록 + 주요 화면을 리액트로 → 전문가 수준 디자인 개선 | 기초 공사가 3단계에서 넘어온다. 그림 대신 코드, 캔버스 대신 화면 모음 판 |
| 3 프런트엔드 | `3-frontend-build.md` | 남은 화면을 리액트로 → 사람 확인(확정) → 모션 → 관문 ①②③ → 배포 → 피드백 | 「남은 화면 그리기」와 「리액트 마이그레이션」이 「남은 화면 만들기」 하나가 된다 |
| 4~6 | 그대로 | 그대로 | 「3단계에서 고정된 스택」 같은 가리킴만 2단계로 |

2단계의 이름은 「목업(Mockup)」 그대로 둡니다. 목업은 「아직 백엔드 없이 생김새와 흐름을 보는 화면」이라는 뜻으로 여전히 맞고, 파일 이름(`2-1-mockup.md`)을 바꾸면 번호 바꾸기 작업이 하나 더 붙습니다.

### 3.2 2단계 흐름

| 순서 | 하는 일 | 누가 | 산출물 |

## 4. 2단계 — 목업

### 4.1 개발환경과 디자인 시스템 기초 공사

**들어오는 때** — 1단계가 끝나 `intent.md`와 브리프가 있고, 루트에 앱 코드(`package.json`)가 아직 없을 때입니다. 2단계 시작 안내(2-1 §2.1)와 같은 메시지에서 스택 선택(React 웹 / Expo)을 묻고, 답이 오면 바로 시작합니다.

**하는 일** — 지금 `3-frontend-build.md` §2.4·§2.4.1·§2.4.2·§2.5.1과 §2.5.3 첫 문단이 하는 일을 그대로 가져옵니다.

1. 스택 선택 확인 — 기본은 React 웹, Expo는 네이티브 기능이 가설의 핵심일 때만. ADR에 기록.
2. 고정 core 최신 호환 버전 조합 조사·적용 — 지금 §2.4.1의 6단계 절차 그대로.
3. Supabase는 `.env.example`의 환경변수 이름과 클라이언트 초기화 코드까지만. 프로젝트 생성은 4-0.
4. Vercel 플러그인 설치 안내 — 2단계 코딩부터 `vercel:nextjs` 같은 스킬이 쓸모 있어 여기로 당깁니다. 관문 ②(3단계)도 같은 플러그인을 씁니다.
5. design-system 기초 공사 — `bootstrap-project.md` §1~§4 순서: `npx shadcn init` → 1층 램프(브리프 「4. 확정 브랜드 자산」의 「우리가 쓰는 값」, 옮기는 법은 `reference-analysis.md` §5) → 2층 → 셸(`feature-list.md` 8절 메뉴 구조가 아직 없으면 브리프 「6. 주 사용 맥락」의 기본 메뉴로 만들고 화면 목록이 나온 뒤 맞춤) → 컴포넌트 인벤토리 → adapter.
6. 화면 모음 판·디자인 시스템 페이지 틀을 복사해 넣기(§6.6).

**작업 모드** — 1번만 인터뷰 모드이고, 나머지는 서브 에이전트(sonnet — 명세가 분명함) 하나가 초안 모드로 완주합니다. 메인은 그동안 기능 목록과 화면 목록(2-1 §2.3~§2.5)을 씁니다. 둘은 서로 기다리지 않습니다 — 셸의 메뉴만 화면 목록 8절이 나온 뒤 한 번 맞춥니다.

**값은 대부분 `가정`입니다** — 1층에 들어가는 값은 브리프 「4」의 출발값이고, 상당수가 아직 `가정`입니다. 2-2가 이 값을 바꿉니다. 그래서 기초 공사에서는 토큰과 셸, 화면에 꼭 필요한 shadcn 부품만 받습니다. 프로젝트 전용 variant(부품의 모양 갈래)는 2-2 전에는 만들지 않습니다.

**외부 리소스가 생기지 않습니다** — GitHub 저장소는 이미 있고, Vercel·Supabase는 아직 만들지 않습니다. 그래서 이 자리에서는 계정 대조가 필요 없습니다.

### 4.2 2-1 기능·화면 목록과 주요 화면

**그대로 가는 것** — §2.1 단계 시작, §2.2 참고 디자인 확인·이미지 계획, §2.3 기능 목록, §2.4 라이트 기술 확인, §2.5 화면 목록(일곱 갈래·홈 결정·상태 표·메뉴 구조·미룬 화면 버튼·빠짐 점검), §2.8 확정. 문장 안의 「캔버스」만 바꿉니다.

**화면 목록의 칸이 바뀝니다** (`feature-list.md` 6절).

| 지금 | 바꾼 뒤 | 채우는 때 |
|---|---|---|
| 그리는 때(2단계 / 3단계 / 해당없음) | **만드는 때**(2단계 / 3단계 / 해당없음). 나누는 기준은 지금 「그리는 때」 규칙 그대로 | 화면 목록을 쓸 때 |
| 아트보드 이름 | **주소** — 그 화면을 여는 실제 주소. 동적 주소면 예시 값을 넣은 주소(예: `/challenges/c-01`) | 화면을 만든 뒤 |

상태 표(7절) 칸 끝의 괄호도 아트보드 이름 대신 `?state=` 값을 적습니다 — 예: `O "아직 모임이 없어요" + 만들기 버튼 (?state=empty)`.

머리의 `캔버스:` 표시는 없앱니다. 대신 3단계 확정 때 `화면 확정:` 표시가 붙습니다(§5.2).

**주요 화면 만들기 (지금 §2.6을 다시 씀)**

1. **범위** — `만드는 때 = 2단계` 행만. 지금 「그리는 범위」 규칙 그대로입니다.
2. **폭** — 따로 정하지 않습니다. 코드는 처음부터 반응형이고, 화면 모음 판이 늘 데스크톱 폭과 폰 폭을 나란히 보여 줍니다. 지금 「웹이면 핵심 화면은 폰 판도」 규칙은 「모든 화면이 두 폭에서 보인다」로 저절로 채워집니다. 다만 화면 폭으로 갈리는 자리는 상단 메뉴 ↔ 햄버거 메뉴 전환 하나뿐이고, 나머지 부품 크기 대응은 컨테이너 쿼리(부품이 놓인 자리의 폭에 맞춰 바뀌는 CSS)로 만듭니다 — 지금 관문 ① 3번 규칙을 2단계부터 지킵니다.
3. **데이터** — 화면은 처음부터 데이터 층(`lib/storage.ts`)을 거쳐 예시 데이터를 읽습니다. 지금 `3-frontend-build.md` §2.5.4의 규칙(저장 구조 한 곳, `Promise` 반환, 저장소 객체를 인자로, 소유자 주석, 가짜 세션)을 여기로 옮깁니다. 안 그러면 3단계가 화면에 박아 둔 가짜 데이터를 데이터 층으로 다시 쓰게 됩니다 — 이번 개편이 없애려는 다시 쓰기입니다.
4. **화면 요소 → 부품 대응** — 지금 §2.5.3 「캔버스 → shadcn 이식 규칙」 표를 「화면 요소 → 부품」 표로 바꿔 여기로 옮깁니다. 버튼은 `Button` + variant, 확인 창은 `AlertDialog`/`Dialog` 같은 대응입니다. 안티패턴(목록 항목마다 카드, 상태색 장식, 14px 아래 글자, 안내 문구가 이름 노릇)을 피하는 규칙도 같이 옮깁니다.
5. **이미지 자리** — 브리프 「이미지·영상 계획」의 장면은 회색 상자에 장면 설명을 적은 자리 표시로 둡니다. 지금 규칙 그대로입니다.
6. **등록** — 만든 화면마다 화면 등록부(§6.4)에 ID·이름·주소·상태를 올리고, 메인이 화면 목록 「주소」 칸을 채웁니다.
7. **위임** — 서브 에이전트(opus — 처음으로 화면의 생김새를 정하는 일이라 디자인 판단이 많음)에 맡깁니다. 화면이 많으면 공통 부품을 먼저 만든 뒤 묶음으로 나눕니다(지금 3단계 §2.5.3 문단과 같은 원칙). 입력 파일 셋(`intent.md`·`feature-list.md`·`design-brief.md`)은 에이전트가 전문으로 읽습니다. 홈 첫 화면 제약과 브리프 읽는 법 다섯 문장은 메인이 지시서에 넣습니다 — 지금 §2.6.3 규칙 그대로입니다.

**코드 작업 지시서에 꼭 넣을 문장** — 지금 「캔버스 작업 지시서에 꼭 넣을 문장」(게시·최신본·429·`/design`)을 아래로 바꿉니다. 2-1·2-2·3단계의 화면 위임 지시서에 모두 넣습니다.

- 「화면 코드는 2층 이름 클래스와 theme 단계 클래스만 쓴다 — hex·px·대괄호 임의 값 금지.」
- 「만든 화면은 화면 등록부에 올리고, 상태 표의 `O` 칸은 `?state=` 값으로 띄울 수 있게 한다.」
- 「브라우저 자동화로 화면을 열어 보고 '확인 완료'라고 결론 내지 마라 — 빌드·린트·타입 검사까지만 하고 결과를 보고하라.」
- 「개발 서버가 필요하면 이미 떠 있는 서버를 쓰고, 네가 띄운 프로세스만 끈다.」
- 「재위임 금지: 다른 에이전트를 띄우지 말고, 필요해 보이면 멈추고 보고하라.」
- 2-1 몫 한 문장: 「화면 목록에서 `만드는 때 = 2단계`인 화면만 만들어라. 이미 있는 화면은 다시 만들지 말고 고칠 곳만 고쳐라.」

**보고와 사람이 보는 자리 (지금 §2.6.5·§2.7을 다시 씀)**

- 메인은 에이전트 보고의 「화면 ID ↔ 주소」 표로 「주소」 칸을 채우고, `만드는 때 = 2단계` 행이 다 찼는지 대조합니다.
- 화면 밖 검사(빌드·린트·타입)를 돌리고 결과와 함께 **개발 서버의 화면 모음 판 주소**를 알립니다. 보고할 내용(화면 수·새로 넣은 화면·빠짐 점검·목록 전문·「보며 특히 확인할 것」)은 지금 §2.6.5 그대로입니다.
- 사용자는 화면 모음 판을 보며 **말로** 고칠 곳을 알립니다. 지금 「캔버스 댓글 처리 차례」(최신본 읽기 → 고치기 → 게시 → 스레드 답 → 해결 표시)는 없앱니다.
- 나온 것을 세 곳으로 나누는 표(기능·화면·범위 → `feature-list.md`, 플로우·의도 → `intent.md`, 문구·미감 → 브리프)는 그대로입니다.
- 「고치는 손」 — 문구 한 줄·색 하나 같은 작은 손질은 메인이 직접, 여러 화면은 위임. 「통째로 다시 그리기」 규칙과 「사람이 캔버스에서 직접 고친 것을 물어보기」는 없앱니다 — 코드는 고치는 것이 기본이고, 사람이 코드를 직접 고쳤어도 git이 남깁니다.

**위임** — ②③은 서브 에이전트 하나(opus — 디자인 판단이 많음), ⑤는 서브 에이전트 하나(sonnet — 규칙이 정해졌고 사람이 결과를 봄). 지금 §4.2 지시서 템플릿은 「새로 만들 아트보드」 표를 「새로 만들 시안」 표(주소·내용)로, 캔버스 전용 제약(게시·최신본·`-v2`·`_progress.md`)을 §4.2의 「코드 작업 지시서에 꼭 넣을 문장」과 2-2 몫 한 문장으로 바꿉니다.

- 2-2 몫 한 문장(②③): 「시안 자리에만 만들어라. 1·2층 토큰 파일과 본 부품, 본 화면은 고치지 마라 — 시안은 시안 범위 클래스와 시안 전용 부품으로만 바꾼다. 보고에 건드린 본 파일 수(0이어야 한다)를 적어라.」
- 2-2 몫 한 문장(⑤): 「고른 판의 시안 값을 1·2층 토큰과 본 부품에 넣고 고른 판 화면을 본 화면 자리로 옮겨라. 다른 화면은 어긋난 곳만 고치고 다시 만들지 마라. 보고에 바꾼 토큰·부품 목록, 손질한 화면 목록, 구조를 바꿔야 해서 손대지 않은 화면 목록을 담아라.」

**지시 파일 자리** — 지금 지시 파일(`design-prompt.md`·`polish-prompt.md`·`add-screens-prompt.md`)은 git에서 빠진 `mvp/mockup/`에 있습니다. 바꾼 뒤에는 지시 파일을 따로 두지 않고 지시서 본문으로 넘깁니다. 지시서를 파일로 남길 필요가 있으면 `mvp/prompts/`에 두고 커밋합니다(확인 필요 — 남길 값어치가 있는지는 검토 때 판단).

## 5. 3단계 — 프런트엔드

### 5.1 남은 화면 만들기

지금 §2.2(남은 화면 그리기)와 §2.5(리액트 마이그레이션)를 「남은 화면 만들기」 한 절로 합칩니다.

- **입력** — `feature-list.md` 6~10절(무엇을 만들지), `design-brief.md`(문구·미감·「12」), `intent.md`(순서·원하는 것), 그리고 **이미 있는 코드**(2단계 화면과 공통 부품이 생김새의 본보기). 「2단계 캔버스」 입력은 없어집니다.
- **범위** — `만드는 때 = 3단계` 화면과, 상태 표 `O` 칸 중 아직 `?state=`로 뜨지 않는 상태 화면. 상태 화면은 상태 표의 `O` 옆 한 줄을 그대로 지시로 씁니다.
- **공통 부품부터** — 지금 §2.5.3의 「나누기 전에 공통 부품부터」 문단을 3단계 첫 순서로 올립니다. 2-2가 만든 빈 상태·로딩 시안이 상태 화면의 본보기입니다.
- **지시서** — §4.2 「코드 작업 지시서에 꼭 넣을 문장」 + 3단계 몫 한 문장: 「화면 목록의 `만드는 때 = 3단계` 행과 상태 표의 `O` 칸 중 아직 없는 것만 만들어라. 이미 있는 화면은 고치지 마라. 공통 부품은 `components/common/`의 것을 쓰고, 공통으로 쓸 만한 부품을 새로 만들지 말고 보고하라.」 지금 「캔버스 요소 → 부품 표를 보고에 남겨라」는 「화면 요소 → 부품 표」로 남깁니다 — diff 검수 때 같은 요소가 화면마다 다른 부품으로 만들어졌는지 메인이 이 표로 잡습니다.
- **빠진 화면 대조 (지금 §2.2.4를 다시 씀)** — 메인이 화면 ID마다 확인합니다: ① `MVP 포함 = O`인 모든 화면이 「주소」를 가졌고 등록부에 있는가 ② 상태 표 `O` 칸이 모두 `?state=` 값을 가졌는가 ③ 반대편 역할 화면 ④ 죽은 버튼(9절) ⑤ 홈 첫 화면이 홈 행 기록과 맞는가. 등록부와 화면 목록의 ID를 기계로 맞대 보는 명령을 하나 둡니다(예: 화면 목록 6절의 ID 목록과 등록부 ID 목록을 비교해 차이를 출력 — 명령 모양은 문안 쓸 때 정함).
- **없어지는 것** — 폭 정하기(§2.2.1), 캔버스 새로 그리기(§2.2.5), 아트보드에서 읽는 것(§2.5.2), 캔버스 값 → 토큰 반올림(§2.5.3 끝 문단), 캔버스 링크를 README에 적기(§2.3 3번), 「캔버스는 여기서 역할이 끝난다」(§2.5.6).

### 5.2 사람이 확인하는 자리와 확정 시점

지금 확정은 「다 그린 캔버스를 보고 이대로 가자」(§2.3)입니다. 모든 화면이 처음으로 한 판에 모이고, 아직 코드가 없어 고치기 가장 싼 순간이라 그 자리에 있었습니다.

바꾼 뒤에는 코드가 2단계부터 있으니, 「고치기 가장 싼 순간」이라는 이유는 약해집니다. 남는 이유는 「모든 화면이 처음으로 한 판에 모이는 순간」입니다. 그래서 설계안은 **3단계 남은 화면을 다 만들고 빠진 화면 대조를 마친 직후, 모션 전**을 확정 시점으로 제안합니다(§9 질문 1에 다른 선택지와 함께).

- 사람이 화면 모음 판과 앱을 보고 「이대로 가자」고 하면, 메인이 `feature-list.md` 머리에 `화면 확정: YYYY-MM-DD`를 적습니다. 이 순간 `intent.md`·`feature-list.md`·`design-brief.md`가 기록이 됩니다. 브리프 「8. 모션·인터랙션 방향」 행만 배포 확인까지 열려 있습니다 — 지금과 같습니다.
- 이 표시가 3단계 앞부분이 끝났다는 판별 단서가 됩니다(§7.1). 지금은 「루트에 앱 코드가 있다」가 그 단서였는데, 앱 코드가 2단계부터 생기므로 쓸 수 없습니다.
- AI는 화면을 보지 않습니다. 화면 모음 판은 사람이 보는 도구이고, AI는 빌드·린트·타입 결과와 대조 결과를 보고하는 데까지입니다.

**화면 SoT(진실의 원천 — 그 내용의 정본이 어디 있나)는 두 자리로 줄어듭니다** — 지금 SKILL.md §2.2는 「화면 목록 → 캔버스 → 앱 코드」 세 자리입니다. 바꾼 뒤에는 「화면 목록(어떤 화면이 있어야 하나) + 앱 코드(생김새, 2단계부터)」 → 「앱 코드(확정 뒤 끝까지)」입니다. 확정 전에는 코드와 브리프가 어긋나면 브리프가 이깁니다. 확정 뒤에는 코드만 고칩니다.

### 5.3 그대로 가는 것

§2.5.7 모션, §2.5.8 관문 ①②③, §2.6 배포, §2.7 피드백, §3 완료 체크리스트의 뒷부분, §4 산출물(앱 코드 + 배포 주소)은 그대로입니다. 바뀌는 문장은 아래뿐입니다.

- §2.5.7 「캔버스는 정지 화면이라 움직임은 앞 단계 어디서도 다뤄지지 않았다」 → 「2단계 화면은 움직임 없이 만들었다」.
- §2.5.8 관문 ① — 검사 경로에 시안 자리와 화면 모음 판이 들어가는지 정합니다(§10 위험 표). 숫자 폭(1440·390)은 `px` 문자열 없이 숫자 속성으로 써서 1번 검사에 걸리지 않게 합니다.
- §2.6 첫 배포 체크리스트에 한 항목을 더합니다: 「공개 주소의 `/dev/screens`가 404인지 `curl`로 확인」.
- §2.7의 「캔버스를 다시 만들지 않는다」 문단은 없앱니다.

## 6. 화면 모음 판과 디자인 시스템 페이지

### 6.1 화면 모음 판

- **주소** — `/dev/screens`(제안). 개발 서버에서만 열립니다(§6.5).
- **맨 앞** — 「[서비스 이름] 디자인 시스템」 페이지로 가는 칸(§6.2).
- **줄 구성** — 화면 ID 순서(흐름 순서)로 한 줄에 한 화면. 한 줄 안에 데스크톱 폭 창과 폰 폭(390) 창을 나란히 둡니다. 데스크톱 창은 실제 폭(1440 — 지금 2-1의 데스크톱 폭)으로 띄우고 화면에 맞게 줄여 보여 줍니다. 그래야 창 안의 컨테이너 쿼리가 실제 폭 기준으로 돕니다.
- **상태 화면** — 같은 화면 줄 아래에 상태(빈·로딩·오류·권한없음) 창을 이어 붙입니다. 주소는 `/challenges?state=empty`처럼 등록부의 상태 목록에서 만듭니다.
- **흐름 묶음** — 지금 캔버스의 「줄 제목 메모」(예: 「소비자 — 찾아보기에서 참가 신청까지」)를 묶음 제목으로 둡니다. 맨 위에 묶음으로 바로 가는 목차를 둡니다.
- **시안 묶음** — 2-2 동안은 대상 화면 줄에 원래 화면 · A판 · B판을 나란히 둡니다(§6.3).
- **보이는 칸만 불러오기** — 창(iframe)에 `loading="lazy"`를 걸어 화면에 들어온 칸만 불러옵니다. 개발 서버는 주소를 처음 열 때 그 화면을 컴파일하므로 처음 내려 볼 때는 느릴 수 있다고 사용자에게 한 번 알립니다.
- **캔버스와 다른 점** — 끌어서 확대·이동하는 판이 아니라 위아래로 내려 보는 판입니다. 화면에서 직접 고치는 기능은 없습니다.

### 6.2 디자인 시스템 페이지

- **주소와 이름** — `/dev/design-system`(제안). 페이지 제목은 「[서비스 이름] 디자인 시스템」(예: 「aikung 디자인 시스템」). 「규칙 페이지」라고 부르지 않습니다.
- **보여 주는 것** — 실제 토큰과 실제 부품으로 그립니다.
  - 글자 단계 — 우리 글자 이름(`text-h1`~`text-b2`)마다 견본 문장, 크기·굵기·줄 간격, 쓰는 자리.
  - 색 역할 — 2층 이름(`primary`·`highlight`·`emphasis` 등)마다 견본과 쓰는 자리. 값은 코드에 적지 않고 브라우저가 계산한 값을 읽어 보여 줍니다(관문 ① hex 검사에 안 걸리게).
  - 간격 단계, 둥글기, 격자.
  - 부품 다섯 상태 — 버튼(variant별)·칩·입력칸·탭. 평소와 비활성은 그대로 그리고, 마우스 올림·누름은 사람이 직접 올리고 눌러 보는 칸으로 둡니다. 포커스를 고정해 보여 주는 방법은 확인 필요입니다(브라우저가 포커스 표시를 강제로 그리게 하려면 부품에 개발용 속성을 더해야 할 수 있음 — §10).
  - 폰 배치 규칙 메모 — 어느 폭에서 무엇이 접히는지.
- **2-2 동안** — 「지금 값」 칸과 「시안 값」 칸을 나란히 둡니다. 시안 값은 시안 범위 클래스(§6.3) 안에서 그려 같은 부품이 시안 값으로 어떻게 보이는지 보여 줍니다. 고른 뒤에는 「지금 값」 하나로 돌아갑니다.
- **자리와 정본** — 이 페이지는 토큰의 정본이 아니라 정본(1·2층 CSS)을 보여 주는 거울입니다. 결정의 정본은 브리프 「12」, 값의 정본은 1층입니다.

### 6.3 시안 자리

- **자리** — `src/app/(dev)/dev/drafts/` 아래(제안). `(dev)`는 Next.js 라우트 묶음(route group — 주소에는 안 나타나고 폴더만 묶는 이름)입니다. 시안 화면은 `/dev/drafts/home-a`·`/dev/drafts/home-b` 같은 주소가 됩니다.
- **시안 전용 부품** — 시안 폴더 안에 둡니다. 본 코드(`src/app` 본 화면·`src/components`)가 시안 폴더를 불러오는 일은 금지하고, grep으로 0건을 확인합니다.
- **시안 범위 클래스** — 시안이 토큰 값을 바꿔 봐야 할 때(B판의 한 줄 높이 등), 시안을 감싼 클래스 안에서만 2층 변수를 덮어씁니다. 1·2층 파일은 그대로 둡니다. design-system 스킬에는 2층 파일 안에 범위 클래스를 두는 앞선 예가 있습니다(`naming-taxonomy.md` 114줄 근처). 범위 클래스를 시안 폴더에 둘지 2층 파일에 둘지는 문안 쓸 때 스킬 규칙과 맞춰 정합니다(확인 필요).
- **고른 뒤** — 고른 판의 코드는 본 화면 자리로 옮기고, 시안 값은 1·2층으로 옮깁니다. 고르지 않은 판을 언제 지울지는 §9 질문 5.

### 6.4 화면 등록부와 상태 띄우기

- **화면 등록부** — 화면 모음 판이 읽는 목록 파일 하나(예: `src/app/(dev)/dev/screens/registry.ts`). 화면마다 ID · 이름 · 흐름 묶음 · 주소 · 띄울 상태 목록을 적습니다. 화면을 만드는 에이전트가 화면을 만들 때 함께 올립니다.
- **왜 `feature-list.md`를 직접 읽지 않나** — 화면 목록은 확정 뒤 갱신하지 않는 기록이 되는데, 화면 모음 판은 그 뒤로도 코드를 따라가야 합니다. 그래서 판은 코드 쪽 등록부를 읽고, 확정 전에는 메인이 등록부와 화면 목록 「주소」 칸을 맞춰 둡니다.
- **`?state=` 띄우기** — 결정 2대로 주소 끝 `?state=empty|loading|error|forbidden` 표시로 상태가 뜹니다. 그 표시를 누가 읽을지는 §9 질문 3입니다. 설계안의 추천은 **데이터 층이 개발 모드에서만 읽는 것**입니다 — 화면 코드는 고치지 않고, 데이터 층이 빈 결과·오류·느린 응답을 돌려주면 화면이 실제 분기대로 상태 화면을 그립니다. 권한없음은 가짜 세션 갈래로 냅니다.
- **창끼리 섞이지 않게** — 모든 창이 같은 주소(origin)라 로컬스토리지를 같이 씁니다. 상태 표시는 저장소에 쓰지 않고 주소로만 정해, 한 창이 다른 창의 상태를 바꾸지 않게 합니다.

### 6.5 실서비스에서 막기

- `src/app/(dev)/layout.tsx`가 실서비스 빌드(`NODE_ENV=production`)에서 `notFound()`를 부릅니다(제안 — 쓰는 Next.js 버전의 `node_modules/next/dist/docs/`로 레이아웃에서 `notFound()`가 이렇게 동작하는지 확인 필요). Vercel 프리뷰 배포도 실서비스 빌드라 같이 막힙니다.
- `?state=`를 읽는 데이터 층 갈래도 같은 조건으로만 켭니다.
- 3단계 §2.6 첫 배포 체크리스트에서 `curl -s -o /dev/null -w "%{http_code}" https://<프로젝트이름>.vercel.app/dev/screens`가 404인지 봅니다.
- 4단계 SEO(검색 노출) 작업의 sitemap에 `/dev`가 들어가지 않는지도 같은 자리에서 봅니다.
- 판은 4단계에도 남겨 둡니다 — 개발 서버에서만 열리니 해가 없고, 백엔드를 붙인 뒤에도 전 화면을 훑는 데 쓸 수 있습니다.

### 6.6 틀을 어디에 두나

**제안** — 코드 틀은 `payload/.claude/templates/screen-board/`에, 쓰는 절차는 문서 두 곳에 둡니다.

| 무엇 | 자리 | 이유 |
|---|---|---|
| 판 페이지·디자인 시스템 페이지 뼈대·등록부 형식·`(dev)` 레이아웃 | `payload/.claude/templates/screen-board/` | `project-init`이 `templates`를 프로젝트 `.claude/templates/`로 동기화한다(`project-init` SKILL.md 동기화 절). 기초 공사 에이전트가 이 폴더를 `src/app/(dev)/`로 복사하고 이름만 채운다 — 매번 새로 짓는 토큰이 거의 없다 |
| 디자인 시스템 페이지가 무엇을 보여 주나·언제 고치나 | design-system `bootstrap-project.md`의 새 절(예: §6) | 디자인 시스템 페이지는 idea-to-mvp 밖에서도 쓸모 있는 design-system 스킬의 일이다 |
| 화면 모음 판을 언제 쓰고 누가 보나 | 2단계 기초 공사 문서와 2-1 | idea-to-mvp 흐름의 일이다 |

다른 선택지와 득실입니다.

- design-system `references/`에 코드 블록으로만 싣기 — 동기화할 코드 파일이 없어 단순하지만, 프로젝트마다 에이전트가 코드를 새로 쓰므로 토큰이 들고 프로젝트마다 판이 조금씩 달라집니다.
- `payload/` 밖 별도 저장소나 npm 패키지 — 하네스 동기화 체계 밖이라 버전이 따로 놉니다. 이번 범위에 맞지 않습니다.

틀 파일의 확장자는 `.tsx` 그대로 두면 프로젝트의 타입 검사·린트가 `.claude/templates/` 안까지 훑을 수 있습니다. `.tsx.template`처럼 확장자를 바꾸거나 `tsconfig.json`·eslint 설정에서 뺍니다(확인 필요 — §10).

## 7. 옛 순서 호환

### 7.1 새 판별 순서

지금 판별(SKILL.md §1.2)은 「루트에 앱 코드가 있으면 3단계 마이그레이션이 끝났다」를 씁니다. 바꾼 뒤에는 앱 코드가 2단계 기초 공사에서 생기므로 이 단서가 그대로면 **새 순서 프로젝트가 기초 공사 직후 3단계 이후로 잘못 판별됩니다.** 그래서 판별을 아래로 바꾸고, 옛 단서는 `캔버스:` 표시가 있는 프로젝트에만 씁니다.

**0. 옛 순서 먼저 가른다** — `feature-list.md` 머리에 `캔버스:` 표시가 있으면 옛 순서(캔버스) 프로젝트입니다. 아래 표로 판별하고 1~7은 보지 않습니다.

| `캔버스:` 표시가 있을 때 | 판별 |
|---|---|
| 루트 앱 코드 있음 | 옛 순서로 캔버스 확인과 마이그레이션까지 끝남 = 세 문서 확정이 지남. `backend-build.md`가 없으면 「3단계가 끝났는지 사용자에게 확인 → 4단계」(지금 §1.2 마지막 항목 그대로) |
| 앱 코드 없음, `확정:` 없음 | 2-1 도중 → §7.3 |
| 앱 코드 없음, `확정:` 있음, 「12」가 `추후 결정` | 2-2 도중 → §7.3 |
| 앱 코드 없음, 「12」 채워짐 또는 `건너뜀` | 3단계 앞부분(캔버스에 남은 화면을 그리던 중) → §7.3 |

**새 순서** (`캔버스:` 표시가 없을 때)

1. `intent.md` + `design-brief.md` → 1단계.
2. 루트 앱 코드(`package.json`)가 없으면 → 2단계 기초 공사.
3. `feature-list.md`가 없거나 `확정:`이 없으면 → 2-1(기능 목록은 있는데 6~10절이 없으면 화면 목록부터).
4. 브리프 「12」가 `추후 결정`이면 → 2-2.
5. `feature-list.md` 머리에 `화면 확정:`이 없으면 → 3단계 앞부분(남은 화면 만들기·대조·사람 확인).
6. `화면 확정:`이 있고 `backend-build.md`가 없으면 → 3단계 뒷부분(모션·관문·배포·피드백). 배포가 됐으면 「더 고칠 곳이 없으면 다음으로」를 묻고 4단계로. 배포 여부의 단서는 지금 판별 규칙에 따로 없습니다 — `.vercel/project.json` 유무를 쓸지 사용자에게 묻기만 할지는 문안 쓸 때 정합니다(확인 필요).
7. `backend-build.md` → 4단계 이후, `market-research.md` → 5, `launch-*` → 6 — 지금 그대로.

**지워야 하는 지금 규칙** — 「뒤 단계 산출물이 있으면 앞 단계는 지난 것으로 본다 — 예: 앱 코드가 있는데 브리프 「12」가 비어 있으면 2-2로 되돌리지 않고 3단계 이후로」. 이 예는 새 순서에서 정확히 틀린 판별을 냅니다. 이 예는 0번(옛 순서) 표 안으로만 옮깁니다. 「앱 코드는 4단계 구분자가 못 된다」는 「3단계 구분자도 못 된다」로 넓힙니다.

- 옮긴 뒤 `feature-list.md` 머리의 `캔버스:` 표시는 **지우지 않습니다** — 0번 판별 단서이고 옛 흔적입니다. 다만 0번 표의 「앱 코드 있음 = 마이그레이션 끝」 행이 이런 프로젝트를 3단계 뒷부분으로 보내 버립니다. 그래서 옮겨 온 프로젝트는 옮기는 순간 `캔버스:` 옆에 `(리액트로 옮김 YYYY-MM-DD — 이후 새 순서)`를 붙이고, 0번은 이 덧붙임이 있으면 새 순서 판별로 넘깁니다(문안 쓸 때 표시 모양 확정).
